# goVLESS pro 1.4.1 — взгляд «наивного пользователя» (критик)

Дата: 2026-09-22. Ветка `test` (6dcf4f5), версия 1.4.1. Роль: человек без Linux-опыта, купил VPS, поставил goVLESS через goinstall, дальше живёт в `govless`, Telegram-боте и Mini App. Всё ниже проверено по коду (файл:строка, цитата), а не по документации. Пункты карт `docs/qa/BUG-MAP-1.4.1.md` (BM-xx) не повторяются, кроме случаев, где они углубляются.

Приоритеты: **P1** — теряются данные/доступ или установка ломается без внятного сообщения; **P2** — тупик или обман, обход есть; **P3** — неудобство/текст.

## P1

### U-01 [P1] «Установить / Обновить» на уже установленном сервере даёт поставить ДРУГОЙ режим поверх — сайт-маскировка затирается заглушкой, nginx-конфиг Pro переписывается, config врёт про режим

**Где.**
- `govless.sh:1019` — `1) select_and_install ;;` (пункт «Установить / Обновить» в меню VPN).
- `govless.sh:1318-1326` — `read -r mode_choice … ""|1) GOVLESS_LAZY=1 install_pro ;; 2) install_pro ;; 3) install_lite ;;` — текущий режим из config не проверяется вовсе.
- `govless.sh:183-187` (install_lite): `setup_lite_nginx || …` → `config_set "mode" "lite"` — безусловно.
- `lib/website.sh:532-533` (`setup_lite_nginx`): `deploy_stub_site` + `generate_nginx_lite_config`; `deploy_stub_site` (`:322`) делает `cat > "$WEBSITE_ROOT/index.html"` без бэкапа; `generate_nginx_lite_config` (`:140`) пишет `cat > "$NGINX_SITE_CONF"` — тот же файл `/etc/nginx/sites-available/govless`, что и у Pro, но уже без `location /.well-known/acme-challenge/` и без include Mini App.

**Что увидит пользователь.** Pro-сервер с сайтом из каталога. Хочет «обновиться»: `govless → 1 → 1`. Видит меню «Выберите режим маскировки» (по умолчанию 1 — Pro-авто, спросит домен заново) — жмёт 3 «Lite, быстро, без домена». Проходит выбор сайта-маскировки, транспорт, отпечаток, «Установить VPN? 1». Дальше: «Переиспользую существующее подключение…» / «Автонастройка не удалась. Панель установлена — настройте VPN вручную», «Заглушка nginx работает на порту 80», «goVLESS v1.4.1 установлен! (Lite-режим)». Результат: на https://домен вместо сайта — «Server is running» (файлы шаблона частично остались, index.html затёрт, бэкапа нет: `deploy_stub_site` его не делает), в дашборде «Режим: lite», пункт 1 → 5 отвечает «Управление сайтом доступно только в pro-режиме», продление сертификата через 60 дней не пройдёт (ACME-location из vhost исчез), а VLESS-inbound на 443 при этом остался Pro/TLS. Обратное направление (Lite-сервер, Enter = Pro-авто) аналогично: сертификат, vhost, `mode=pro` в config, а inbound остаётся Reality («Автонастройка не удалась»).

**Почему плохо.** Пункт назван «Обновить», но обновления кода он не делает (BM-14), зато молча позволяет разрушить рабочую конфигурацию; потеря сайта-маскировки без бэкапа и рассинхрон config ↔ реальный inbound.

**Как исправить.** Если `config.mode` уже задан: (а) переименовать пункт в «Обновить goVLESS» и объяснить, что обновление — через `goinstall`; (б) в `select_and_install` при выборе режима, отличного от текущего, отказывать: «Сейчас установлен режим Pro. Для смены режима используйте 1 → 4 «Сменить режим (Lite ↔ Pro)» — ключи и подписки сохранятся»; (в) `setup_lite_nginx`/`deploy_stub_site` никогда не запускать поверх Pro-vhost без бэкапа сайта (`deploy_template_to_nginx` его умеет — использовать тот же путь).

### U-02 [P1] Mini App: «Создать бэкап», «Восстановить», «Восстановление (repair)» на goinstall-установках не могут сработать — демон ищет `lib/` не там; ошибка «backup failed: rc!=0»

**Где.**
- `phase-a/govlessctl/methods.py:1179-1181` (`backup_create`): `"set -e; cd /root/goVLESS 2>/dev/null || cd /opt/govless 2>/dev/null || true; source lib/common.sh 2>/dev/null || true; … source lib/xui.sh 2>/dev/null && backup_govless"`; то же в `:1218-1220` (`backup_restore`) и `:1232-1234` (`repair_run`).
- Код на сервере лежит в `/opt/govless-installer` (сам демон это знает: `methods.py:382` `"/opt/govless-installer/govless.sh"`), а `/opt/govless` — только данные (`install_phase_a.sh:84-87` копирует туда лишь `govlessctl/bot/webapp`; `grep '/opt/govless/lib'` по репозиторию — пусто). Каталога `/root/goVLESS` у goinstall-установки нет.
- `methods.py:1184`: `raise MethodError(500, "backup failed: " + (res.stderr[-200:] or res.stdout[-200:] or "rc!=0"))` — stderr подавлен `2>/dev/null`, остаётся «rc!=0».
- `app.jsx:1412-1415`: `const r = await rpc("repair.run", {}); … if (r.ok) toast(L.restore_done) else toast(L.repair_warn, "warn")` — при провале показывается `repair_warn` = «Запускаю восстановление…» (`app.jsx:77`+, ключ `repair_warn`).

**Что увидит пользователь.** Открывает Mini App → «Резервные копии» → «+ Создать бэкап» → тост «Ошибка: backup failed: rc!=0». В «Восстановление» жмёт «Запустить» → тост «Запускаю восстановление…» — и ничего; `ok:false`. Решает, что бэкап у него есть (тайлы обещают), а его нет.

**Почему плохо.** Обещанная резервная копия не создаётся; текст ошибки для человека бессмысленный; сообщение о провале repair выглядит как прогресс. Восстановление из Mini App после типового подтверждения `RESTORE <имя>` тоже упадёт («restore failed: rc!=0»).

**Как исправить.** В трёх методах искать код по тому же списку, что в `:382-383` (`/opt/govless-installer`, затем `/root/goVLESS`), `source lib/i18n.sh` тоже (иначе `t`/`tf` не определены); при провале возвращать понятный текст («не найден код goVLESS: …»), а в Mini App на `ok:false` показывать «Восстановление не выполнено» + stderr, а не «Запускаю…». Прогнать на живом стенде (сценарий №1 ниже).

### U-03 [P2] Первая установка: опечатка в домене, пустой Enter или «Вернуться обратно» — установщик просто завершается, без подсказки «запустите govless»

**Где.**
- `govless.sh:240-248`: `read -e -r domain … if ! valid_domain "$domain"; then log_error "$(tf pro_bad_domain "$domain")"; return 1; fi` — без повторного запроса.
- `govless.sh:1322`: `""|1) GOVLESS_LAZY=1 install_pro ;;` — по умолчанию (Enter) выбирается режим, которому нужен домен.
- `govless.sh:354`: `confirm "$(t config_confirm)" "$(t confirm_install)" "$(t confirm_back)" || return 0` — «Вернуться обратно» = `return 0`.
- `govless.sh:1529`: `select_and_install` вызывается под `set -euo pipefail` (`set +e` включается только в ветке «уже установлено», `:1498`) — `return 1` из `install_pro` завершает весь скрипт.

**Что увидит пользователь.** Сразу после дисклеймера нажимает Enter (или вводит `мойсайт.рф` кириллицей, или `example,com`) → «✗ Некорректный домен: …» → приглашение shell. Или доходит до сводки, жмёт 2 «Вернуться обратно» → вообще ничего не печатается, процесс завершён. Подсказка «Команда для управления: govless» выводится только в конце успешной установки, так что человек не знает, чем продолжить; повторный goinstall заново скачает код и повторит все вопросы. Если goInstaller судит об успехе по ветке/версии клона, он ещё и отчитается «установлено».

**Почему плохо.** Тупик на первом же вопросе; «Вернуться обратно» некуда, текст врёт.

**Как исправить.** Домен запрашивать в цикле с подсказкой «0 — назад к выбору режима»; кириллические/URL-подобные значения объяснять («введите латиницей, без https://»). «Вернуться обратно» при первой установке → возврат к `select_and_install`, а не выход. При любом раннем выходе печатать «Чтобы продолжить установку, выполните: govless».

### U-04 [P2] Неверный email → certbot падает, а подсказка винит DNS и порт 80; сама причина скрыта (`2>/dev/null`)

**Где.**
- `govless.sh:264-266`: `read -r email; email=$(echo "$email" | tr -d '[:space:]')` — никакой проверки формата.
- `lib/website.sh:241-242`: `certbot_args+=(--email "$email")`; `:253`: `if certbot "${certbot_args[@]}" 2>/dev/null; then`; `:265-267`: `log_error "$(t site_ssl_fail)"; log_dim "$(tf site_ssl_fail_dns "$domain")"; log_dim "$(t site_ssl_fail_port)"` — «Не удалось получить SSL-сертификат / Проверьте, что домен указывает на IP этого сервера / и что порт 80 открыт в файрволе».
- `govless.sh:376`: `setup_pro_website … || return 1` → при первой установке скрипт завершается (см. U-03).

**Что увидит пользователь.** Вводит `vasya` или `vasya@mail` (LE отвергает контакт), видит две попытки certbot, затем «Проверьте, что домен указывает на IP…» — а DNS он только что подтвердил. Идёт править DNS/файрвол, переустанавливает, качает шаблон заново, снова падает.

**Почему плохо.** Диагноз ложный, настоящая причина спрятана; каждая попытка тратит время и квоты LE (BM-06).

**Как исправить.** Проверять email регэкспом (`^[^@[:space:]]+@[^@[:space:]]+\.[a-z]{2,}$`) и переспрашивать; писать вывод certbot в `/tmp/govless_certbot.log` и при ошибке показывать последние 3–5 строк; в подсказку добавить «или email указан неверно (Enter = без email)».

### U-05 [P2] Мастер бота на RU-сервере — бесконечный цикл «Telegram не подтвердил токен»: проверка идёт напрямую, минуя «Прокси для API Telegram», и ни слова о причине

**Где.**
- `govless.sh:887-900`: `while true; do … if uname="$(_bot_getme "$tok")" …; then …; break; fi; log_warning "$(t bot_token_verify_fail)"; done` — выход только пустым вводом («Настройка отменена»).

- Для сравнения `bot_set_token` (`:733-736`) умеет «Сохранить всё равно?», мастер — нет.

**Что увидит пользователь.** Российский VPS. Настройте «Прокси для API Telegram» (govless → 4 → 6) и повторите мастер, либо 2 — сохранить токен без проверки». Не зацикливать: максимум 2 попытки, затем меню.

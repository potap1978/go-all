# goWARP 2.4: исправления и приёмка, 5 сентября 2026

Код подготовлен в ветке `v2.4-menu`. Финальная версия установлена на тестовом VPS `62.60.228.179` в `/usr/local/bin/gowarp` и `/usr/local/bin/warp.sh`. Исходящий WARP настроен по IPv4. Старый тег `v2.3` не изменён.

## Исправленные проблемы нашего кода

- Меню сокращено до главного экрана и одного экрана настроек. Убраны обязательные стартовые промо, старое меню ключей и неиспользуемые экраны/обработчики. Старые кнопки Telegram направляют на актуальный экран.
- Применение WARP+ объединяет выбор/ввод ключа, применение и проверку; имя ключа создаётся автоматически. Принятый ключ, платный тип аккаунта и подтверждённый трафик больше не смешиваются.
- Парсер принимает вывод wgcf `Account type : unlimited` с пробелом перед двоеточием. Раньше такой формат мог не распознаться.
- При миграции старого конфига новый default Free больше не удаляет `license_key` из существующего wgcf-аккаунта. Ключ сохраняется и импортируется в список; платный режим восстанавливается при подтверждении метаданных Cloudflare.
- Общий HTTP 400 больше не объявляется доказательством неверного ключа. Лимит устройств определяется по явному сообщению/коду 1056; сетевой отказ и неподтверждённый статус имеют отдельные сообщения.
- Каждый AWG-контейнер получает свою регистрацию и WireGuard-идентичность. Для исходящего WARP установлены отдельные стандартные WG-инструменты: `wg -> awg` во входящем VPN не подменяется.
- Перевыпуск AWG транзакционный для каждого контейнера: подготовка новой регистрации, сохранение старой, проверка нового трафика, затем удаление старого устройства. При отказе восстанавливаются профиль и учётные данные. Частичный успех возвращает ошибку; глобальные настройки не изображают полный успех.
- Сохраняются endpoint и фактический локальный UDP-порт, включая старые конфиги с `ListenPort = 0`. Исправлено определение входящего интерфейса по имени реально найденного конфига.
- Выбор клиентов применяется без перезапуска контейнера. Ошибки установки правил передаются вызывающему коду. IPv4-адреса проверяются до записи правил и автозапуска.
- Конфиг WARP, установленная команда и блок автозапуска заменяются атомарно. Автозапуск проверяется `sh -n` до замены; неудачная запись сохраняет прежний файл. Фоновый восстановитель учитывает сохранённое выключение WARP.
- Telegram использует общий путь применения и одноразовые подтверждения с проверкой пользователя и срока действия. Неактивный бот при обновлении не запускается.

## Автоматические проверки

На Linux прошли:

- `bash -n` и статические проверки;
- 86 проверок состояния, включая миграцию, форматы аккаунта, классификацию ошибок и хранение ключей;
- три сценария транзакций: успех, частичный отказ, полный отказ;
- проверки бота: JSON клавиатуры, применение после подтверждения, другой пользователь, повтор и истечение подтверждения, Free, совместимость старых кнопок, запрет приёма ключа в группе;
- проверки автозапуска: вставка перед блокирующим `tail`, резервная копия, синтаксис, повторное применение, сохранение оригинала при ошибках записи/синтаксиса, отклонение некорректных адресов до изменения файлов.

Локально прошли ShellCheck уровня error и `git diff --check`. Тесты используют временные каталоги и имитацию внешних команд; настоящие Telegram-сообщения не отправлялись.

## Живой стенд

Ubuntu 24.04, Docker 29.1.3. На чистом VPS подняты три сервера и три соответствующих клиента AmneziaWG:

| Контейнер | Входящий протокол | Базовый образ |
|---|---|---|
| `amnezia-awg` | AWG 1 | `amneziavpn/amnezia-wg`, digest `ea050861bd20…` |
| `amnezia-awg2` | AWG 2 | `amneziavpn/amneziawg-go:0.2.19`, digest `acef5ae84808…` |
| `amnezia-awg3` | AWG 3.1 | `amneziavpn/amneziawg-go:3.1.20260828`, digest `cbafc02b8373…` |

Клиенты — отдельные Docker-контейнеры с соответствующими версиями AWG. Они устанавливают настоящее зашифрованное VPN-соединение с серверными контейнерами через Docker bridge; затем выбранный клиент выходит через WARP. Это проверка клиентской пересылки, но не испытание внешнего телефона или маршрута от домашнего провайдера до VPS.

Первичная установка Free и применение Plus к трём отдельным регистрациям прошли с проверкой trace. Перед Plus владелец освободил слоты в аккаунте. Повторная регистрация старого VPS не выполнялась, чтобы не занимать освобождённые места.

Проверка сохранения состояния:

1. WARP выключен на всех трёх контейнерах; после их перезапуска интерфейс WARP не появляется, входящий VPN поднимается.
2. После переподключения тестовых клиентов все три выходят напрямую: `ip=62.60.228.179`, `warp=off`.
3. WARP включён; после повторного перезапуска восстановлены интерфейс, IPv4-маршрут таблицы 100, самопроверка `oif warp` и правило выбранного клиента. Дубликатов правил нет.
4. Хэши конфигов входящего VPN и файлов выбора клиентов до/после совпали.
5. Реальный запуск установленного `gowarp`: главное меню → WARP+ → главное меню → выход, код завершения 0. Фоновый восстановитель активен, Telegram-бот не запущен.

В первой проверке сразу после перезапуска сервера клиент дал таймаут, затем прямой выход восстановился у всех трёх без изменения правил. Повторный сценарий использовал явное переподключение клиентов; мгновенное восстановление уже открытой VPN-сессии не заявляется.

Последняя проверка после перезапусков, обычный IPv4 HTTPS-запрос из каждого VPN-клиента:

| Клиент | Результат | Время запроса |
|---|---|---:|
| AWG 1 | `warp=plus` | 9,61 с |
| AWG 2 | `warp=plus` | 3,89 с |
| AWG 3.1 | `warp=plus` | 9,26 с |

Таким образом, применение ключа и прохождение трафика WARP+ подтверждены для всех трёх протоколов; стабильная скорость не подтверждена.

## Что осталось на внешнем сетевом пути

В ходе тестирования IPv4 WARP давал как быстрые ответы порядка 0,04–0,15 с, так и задержки 3–9 с и таймауты. DNS и загрузка файла также работали непостоянно. Смена MTU, UDP-порта и IPv4 endpoint не дала устойчивого улучшения. Финально оставлены `162.159.192.1:2408` и MTU 1280.

Контрольный запуск сетевых функций v2.2 с тем же WARP-профилем также показал задержки 3,4–9,35 с. Проба WARP вне Docker воспроизвела задержки. В синхронном захвате TCP SYN прошёл от тестового клиента через входящий VPN до интерфейса WARP примерно за 0,3 мс; SYN-ACK появился на WARP примерно через 3,84 с и сразу вернулся клиенту. Это локализует задержку за интерфейсом WARP в той пробе, но не доказывает конкретный сбой Cloudflare или провайдера.

В v2.3 обнаружены реальные ошибки обработки ключа и миграции, перечисленные выше. Они исправлены. Приписывать всю текущую сетевую задержку регрессии v2.3 оснований нет; объявлять сбой Cloudflare доказанным тоже нельзя.

По указанию владельца временные IPv6-проверки удалены: тестовый интерфейс, маршруты и дополнительная Docker-сеть убраны. Все три итоговых WARP-профиля используют IPv4. Исходная конфигурация IPv6 ОС не менялась.

## Артефакты и восстановление

На тестовом VPS результаты находятся в `/root/gowarp-v24-test/`: `lifecycle.log`, хэши до/после, `cli-smoke.log`, `final-client*.trace`, `results.csv`, скрипты подготовки стенда. Резервная копия текущих настроек и отдельных аккаунтов перед заключительной приёмкой — `before-final-cleanup-complete-*.tar.gz` в том же каталоге. Аккаунты, удалённые при более ранних успешных перевыпусках, нельзя восстановить простым возвратом старых файлов.

Секреты в отчёт и репозиторий не включены. Для запуска установленной версии на новом VPS: `gowarp`. Команда скачивания, указывающая на тег `v2.3`, продолжит получать старую версию; новый код находится в ветке `v2.4-menu`.

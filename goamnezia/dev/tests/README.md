# Проверки goAmnezia pro

Все проверки здесь, кроме `tests/live/`, **не требуют сервера**: ни Docker, ни root, ни сети. Живая
приёмка на настоящем сервере — [live/README.md](live/README.md). Прежние план приёмки и ручной обход интерфейсов
(0.1.x) — в архиве: [STAND.md](../docs/archive/STAND.md), [MENU_REVIEW.md](../docs/archive/MENU_REVIEW.md).

## Как запускать

```bash
BASH5=/opt/homebrew/bin/bash bash tests/run_static.sh
```

`BASH5` обязателен на macOS: `/bin/bash` там версии 3.2, а продукт использует
ассоциативные массивы и `printf -v` из bash 4+. На сервере достаточно
`bash tests/run_static.sh`. Переменная экспортируется внутрь — сквозные прогоны
запускают `install.sh` тем же интерпретатором.

### Параллельный прогон: `GA_TEST_JOBS` и журналы

По умолчанию одновременно идёт половина ядер + 1 задание: на всех ядрах сразу тесты со временем изредка мигали (TAIL-25).

Тяжёлые части идут одновременно: shellcheck, юнит-тесты по модулю на задание (pty-мастер
`test_wizard_pty` — восемью частями через `tests/unit_shard.py`), пять сверок `check_*.py`,
`lib/selftest.sh` и двенадцать сквозных наборов. Долгие запускаются первыми. На Mac с 18
ядрами полный прогон — около четырёх минут вместо 26 последовательных.

```bash
bash tests/run_static.sh                   # заданий сразу — по числу ядер (sysctl -n hw.ncpu / nproc)
GA_TEST_JOBS=4 bash tests/run_static.sh    # не больше четырёх заданий одновременно
GA_TEST_JOBS=1 bash tests/run_static.sh    # по-старому: по одному, юнит-тесты одним discover
bash tests/run_static.sh --job e2e:tests/test_core_dryrun.sh   # одно задание, вывод — в терминал
```

- **Отчёт тот же**: те же разделы в том же порядке, те же строки ✓/✗/SKIP, «ИТОГ» наборов,
  итоговая строка и код выхода (число непройденных проверок). Разделы печатаются по мере
  готовности. В заголовке раздела — длительность, у юнит-тестов — ещё число тестов и время
  каждого задания, в конце — общее время и пять самых долгих заданий.
- **Юнит-тесты — одна проверка**, сколько бы заданий их ни гоняло: пропуски и их причины
  складываются по журналам всех частей. Части одного модуля сверяются с его полным списком
  тестов (строка `unit_shard: …` в журнале) — потерянный класс валит раздел, а не пропадает.
- **Журналы** — в каталоге прогона `${TMPDIR:-/tmp}/goamnezia-static.XXXXXX/`, по файлу
  `<задание>.log` на задание. Журнал прошедшего задания удаляется, проваленного — остаётся, и
  отчёт называет его строкой «полный журнал: …». Всё прошло — каталог удаляется целиком.
- **Изоляция.** Каждое задание — отдельный процесс в своей сессии (без управляющего терминала,
  stdin — `/dev/null`) со своим `TMPDIR` внутри каталога прогона; `HOME` общий — наборы в него не
  пишут (проверено сравнением до и после прогона). Сигналы задание получает в исходном виде:
  фоновой команде оболочка ставит SIGINT в «игнорировать», и pty-тест Ctrl-C в окне привязки
  бота без этого краснел. Ctrl-C по самому `run_static.sh` останавливает все задания.
- **Новый тест параллельности не ломает**, если держится правил, которых держатся нынешние:
  временные файлы — только через `mktemp`/`tempfile` (то есть в `TMPDIR`), порты — свободные
  (`bind` на порт 0), ничего не писать в дерево репозитория (кроме `__pycache__`) и в `HOME`.
  Новый `tests/test_*.py` попадает в прогон сам — отдельным заданием.

Набор гоняется и на Linux-сервере (GNU coreutils), и на macOS (BSD-утилиты). Где ключи
утилит расходятся (`stat -c` против `stat -f`), проверка обязана работать на обеих.

### Linux и macOS: что держит набор одинаковым

- **Права файла** — `stat -c %a … || stat -f %Lp …`, именно в этом порядке: у GNU `-f` значит
  «файловая система», он печатает её сведения и только потом падает. **Сумма** — `sha256sum`, иначе
  `shasum -a 256` (shasum идёт с perl, на минимальном Linux его нет).
- **Машина стенда не должна решать исход.** На macOS нет `ip`, `flock`, `timeout`, `systemctl`, на Linux
  они есть, а `dig`, наоборот, на Mac есть, а в контейнере CI обычно нет, — и сухой прогон может пойти
  другой веткой. Поэтому DNS на стенде — только `GOAMNEZIA_DNS_STUB`, а тест, которому нужен сам факт
  «dig установлен», кладёт свой `dig` первым в PATH и проверяет, что его ни разу не позвали; проверкам
  без сети — подставной `curl`; адреса машины там, где от них зависит проверка, — свой `ip` в PATH
  (EDGEBIN, ADDRBIN) или `GOAMNEZIA_EDGE_IPS_STUB`. Настоящий `ip` Linux-машины с одним и двумя внешними
  адресами наборы не ломает (проверено подменой 27.09): лишние пункты меню встают в хвост, номера прежние.
- **От root** права на файл ничего не запрещают: проверки на «недоступно для записи» от root
  пропускаются с причиной, а не краснеют.
- **Очередь приёма у macOS короче на деле:** соединения сверх очереди сервера (у `ThreadingHTTPServer` —
  пять) macOS сбрасывает сразу, Linux придерживает. Тест, который шлёт пачку разом, повторяет только
  запрос, не ушедший на сервер (`unsent_retries` в `tests/test_admin_http.py`), — ответ не повторяется.
- **Нужны** `bash` 4+, `python3`, `jq` (без него продукт не пишет `config.json`; pty-тесты тогда
  пропускаются с причиной), `curl`, `openssl`. Остальное (`node`, `qrencode`, `shellcheck`, `lsof`,
  `python-telegram-bot`) — по возможности: без них свои проверки пропускаются с причиной.
- **Совместимость jq:** продукт поддерживает штатный `jq 1.6` Ubuntu 22.04. При изменении фильтров
  запустите набор с настоящим jq 1.6 первым в `PATH`: jq 1.7+ принимает ключевые слова как имена
  переменных и иначе обрабатывает пустой результат `-e`, скрывая ошибки старого пакета.
  [Требования и подготовка зависимостей](../docs/DEPENDENCIES.md).
- **pty-стенд** делает терминал управляющим (TIOCSCTTY), как настоящий SSH-вход: на Linux одного `setsid`
  мало, и `/dev/tty` у мастера давал бы ENXIO. Временные файлы с ключами — в каталоге стенда, а не в
  `/dev/shm` машины; локаль у bash, чей stderr должен быть пуст, — `C.UTF-8` на Linux, без `LC_*` машины.
- **Не запускайте набор от root на сервере с установленным продуктом.** Тесты подменяют что могут, но
  восстановление из бэкапа и бюджет логов в продукте пока не знают сухого прогона (находки L1-20, L3-07,
  L3-08 — у исполнителя ядра): от root они тронули бы службы и журналы машины.

Выход `run_static.sh` — число непройденных проверок. Отсутствие **инструмента**
(`shellcheck`, `node`, `python3`) даёт SKIP с громкой строкой, а не провал:
иначе набор был бы красным на любой машине без полного окружения.

### Живые прогоны на сервере (`tests/live/`, вручную)

`run_static.sh` их не запускает: нужен сервер с установленным продуктом, Docker и root. Запуск с
машины разработчика — `ssh root@<сервер> 'bash -s' < tests/live/<файл>`. Пользователей владельца,
режим и сайт они не трогают. Тестового пользователя заводят заранее

## Чем подменяется система

Ключ к тому, что всё это работает на macOS без Docker и без интернета.

| переменная | что подменяет |
|---|---|
| `GOAMNEZIA_DRY_RUN=1` | **главный выключатель**: любая docker-команда печатается в stderr как `DRY: …` и возвращает 0. Все обращения к docker идут через `lib/docker.sh`, поэтому одного флага хватает на весь продукт. Исключения по контракту: `docker_container_state` → `missing`, `docker_read_file` → пусто, диагностика `quality` смотрит на docker по-настоящему (`docker_api_pin --probe`). То же для `systemctl`, `ufw`, `iptables`, `apt`, `certbot`, `nginx` |
| `GOAMNEZIA_DOCKER_VERSION_JSON` | файл с ответом демона на `GET /version` — подменяет обращение к сокету при определении версии API (`docker_api_pin`, `docker_diag_json`) |
| `GOAMNEZIA_DOCKER_SOCK` | путь к сокету демона (по умолчанию `/var/run/docker.sock`): в прогонах указывают несуществующий, чтобы тест не зависел от настоящего Docker на машине разработчика |
| `FAKE_DOCKER_MODE`, `FAKE_DOCKER_AWG_DUMP` | режим подставного `docker` (`tests/fixtures/fake_docker.sh`): `mismatch` — версии CLI и демона разошлись, как на стенде 10.09.2026; `down` — демон не отвечает; `ok` — норма. Второй — файл с сохранённым `awg show … dump` |
| `GOAMNEZIA_NOTIFY_MAX` | предел очереди уведомлений (по умолчанию 200) |
| `GOAMNEZIA_DIR` | корень продукта — тесты кладут его во временный каталог; все производные пути едут за ним |
| `GOAMNEZIA_SERVER_IP` | адрес сервера без обращения к сети (иначе каждый `status` ждал бы три таймаута `curl`) |
| `GOAMNEZIA_ACTION_BIN` | путь к `install.sh` или к заглушке — для бота, панели и MCP |
| `GOAMNEZIA_CONTAINER_FS_DIR` | «файловая система контейнеров»: `<каталог>/<контейнер>/<путь>`; файлы `.state`, `.iface_down`, `.image` изображают остановку, молчащий интерфейс и образ |
| `GOAMNEZIA_DOCKER_PS_FIXTURE` | сохранённый вывод `docker ps` |
| `GOAMNEZIA_SS_FIXTURE` | сохранённый вывод `ss` (`tests/fixtures/preflight/ss_*.txt`); в сухом прогоне без него занятость порта не спрашивается у машины (и у доступов агентов без `lib/docker.sh`, TAIL-9) |
| `GOAMNEZIA_DF_FIXTURE` | сохранённый вывод `df -Pm` — место на диске для всех порогов (`ga_df_mb`: образ, копия, зеркало, журналы, «Диагностика») вместо диска машины. `run_static.sh` задаёт фикстуру с запасом (TAIL-12: на маленьком `/tmp` CI сухие прогоны отказывали «мало места»); проверки «диск полон» подменяют `df` сами и снимают фикстуру на свой вызов (`GOAMNEZIA_DF_FIXTURE=''`) |
| `GOAMNEZIA_UPSTREAM_FIXTURE_DIR` | сохранённые ответы GitHub и Docker Hub. **Без него dry-run отвечает `unreachable`** — а не идёт в сеть |
| `GOAMNEZIA_AWG_SHOW_FIXTURE` | вывод `awg show awg0 dump` вместо живого |
| `GOAMNEZIA_DNS_STUB`, `_DNS_STUB_AAAA` | ответ DNS в сухом прогоне (адреса через пробел, пусто — записей нет). **Без него — «не знаем»**, а не поход в сеть |
| `GOAMNEZIA_EDGE_IPS_STUB`, `GOAMNEZIA_OWN_IPS6_STUB` | внешние IPv4 и IPv6 машины в сухом прогоне (пусто — адресов нет). Без первого продукт спрашивает настоящий `ip` (на macOS его нет) |
| `GOAMNEZIA_SYSTEMD_DIR` | куда писать юниты вместо `/etc/systemd/system` |
| `GOAMNEZIA_NGINX_DIR`, `_SITE_ROOT`, `_LE_DIR`, `_ACME_ROOT`, `_TLS_DIR` | куда писать вместо `/etc/nginx`, `/var/www`, `/etc/letsencrypt` |
| `GOAMNEZIA_TEMPLATE_LOCAL_DIR` | шаблон сайта из локального каталога без клона |
| `GOAMNEZIA_LE_STAGING=1` | staging-сертификат Let's Encrypt (браузер и `website_check` его не примут — это ожидаемо) |
| `GOAMNEZIA_TFA_SINK` | **только тесты**: код 2FA дописывается в файл вместо отправки в Telegram. В юните не задавать никогда |
| `GOAMNEZIA_AGENTS_JSON`, `_LOCK_DIR`, `_NOTIFY_DIR`, `_AUDIT_LOG`, `_LOG_FILE` | пути состояния |

## Чего эти проверки не ловят

Честно, чтобы не создавать ложного ощущения полноты.

**Всё, что требует настоящего Docker:**

- соберётся ли образ из вендоренного `Dockerfile` на текущем Docker Hub;
- поднимется ли контейнер, ответит ли `awg show awg0`, встанет ли порт;
- правила iptables внутри контейнера и на хосте;
- переживает ли `state/` реальный `docker rm` и восстановление;
- совместимость образа 3.1 с конфигами линеек 2.0 и 1.x.

**Всё, что требует сети и внешних сервисов:**

- `certbot` и настоящий Let's Encrypt (сертификат, `renew`, хуки);
- настоящие ответы GitHub и Docker Hub (мы гоняем сохранённые);
- доступность сервера снаружи и файрвол хостинга;
- настоящий Telegram: разметка сообщений, медиагруппы, WebApp, мини-апп.

**Всё, что требует устройства:**

- читается ли наш чанковый QR **настоящим приложением Amnezia** (сверено только
  с собственным декодером);
- открывается ли `.conf` в AmneziaWG-клиенте и на роутере Keenetic/MikroTik;
- подключается ли клиент на самом деле — то есть работает ли VPN.

**Всё, что требует времени и параллелизма:**

- одновременная работа двух администраторов из разных интерфейсов;
- поведение при обрыве сети или процесса посреди пересоздания контейнера;
- накопление трафика за сутки и месяц на живых счётчиках;
- реальное срабатывание таймеров и переживание перезагрузки хоста.

**Прочее:** восстановление из бэкапа на чистом сервере, переезд между VPS,
сожительство с goTelegram / goVLESS / goWARP на одной машине.

Всё это — работа живой приёмки: [live/README.md](live/README.md); прежний план — [STAND.md](../docs/archive/STAND.md).

## Тёмные тесты: экраны бота

`tests/test_bot_features.py` (экраны, кнопки, потоки мастеров, что уходит в
мост — больше сотни проверок) требует библиотеку `python-telegram-bot`. Без неё
весь класс **молча пропускается**, и `run_static.sh` до 11.09.2026 показывал
«юнит-тесты пройдены» — то есть зелёную строку на месте трети непроверенного
продукта. Именно там отстали три ожидания: команда подключения, два новых шага
мастера доступов и диапазон предлагаемого порта. Выглядело бы как дефекты
продукта, а на деле продукт был прав.

Счётчик пропусков тоже врал: он считал строки со словом «skipped», а в них
попадали итоговая строка отчёта и ПРОШЕДШИЙ тест, у которого это слово в
названии. Теперь число берётся из итоговой строки самого `unittest`, и это
проверяет сам набор — шаг «самопроверка отчёта» в начале прогона.

Теперь число пропусков печатается всегда. Чтобы их не было:

```
python3 -m venv .venv && .venv/bin/pip install 'python-telegram-bot>=21,<22'
.venv/bin/python -m unittest discover -s tests -p 'test_*.py'
```

Ставить библиотеку в системный python не нужно и не стоит.
Исторические цепочки в `test_update_dryrun.sh` дополнительно запускайте с jq >= 1.7:
старые выпуски сами используют несовместимый с 1.6 `$label` и в матрице 1.6
эти цепочки пропускаются с явной причиной. Остальные сценарии текущего кода идут с jq 1.6.

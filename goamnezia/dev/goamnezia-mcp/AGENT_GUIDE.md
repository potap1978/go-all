# goAmnezia pro — гайд для агента (ресурс `goamnezia://guide`)

Для кого: модель, подключённая к MCP-серверу `goamnezia`. Для человека — `goamnezia-mcp/README.md`.
Версия гайда: 3 (2026-10-05), под контракт `docs/CONTRACT.md` v1, `lib/actions.json` schema 1 и goAmnezia pro 1.0.10.
Читай целиком один раз в начале сессии; дальше — по разделам.

## 0. Девять правил

1. Сначала картина, потом действие: `server_status` → `profiles_list` → по задаче `users_list` / `user_show`. Не меняй то, чего не видел.
2. Перед каждым изменяющим вызовом скажи человеку, что именно будет сделано и что изменится для пользователей.
3. Разрушительный инструмент — только после явного согласия человека на это конкретное действие и с `confirm`, равным значению первого параметра (§5).
4. Ключи и конфиги выдаёт только `user_get_key`. Приватные ключи, `.conf`, `vpn://` и QR отдавай только человеку, который их попросил, и никуда больше. Адрес страницы подключения (`page_create`, `page_url`) — секрет того же порядка: по нему выдаются те же ключи. Адресов подписок (постоянных ссылок для Clash, incy, роутеров и приложений) и их коротких ссылок (кодов из 8 знаков вида `XXXX-XXXX`) у тебя нет вовсе — только `sub_list` без адресов.
5. Линейки AmneziaWG несовместимы: ключ профиля `awg2` не подойдёт к `awg3`. Выдавай ключ профиля, подходящего клиенту (§8.1), и называй `min_client`.
6. Серверные параметры профиля (`S1–S4`, `H1–H4`, `HeaderProtectionKey`, `RandomTrailers`, `DisableCookies`), `profile_regen` и `profile_set_subnet` обесценивают ключи всех пользователей профиля — предупреди до вызова, перевыпусти ключи после.
7. UDP/443 может держать ровно один профиль. Перед портом 443 посмотри `profiles_list`.
8. `status=error` — читай `code` и действуй по §7. Не повторяй изменяющий вызов «на всякий случай»: сначала проверь состояние.
9. Долгие действия (`profile_install`, `upstream_update`, `backup_restore`) идут минуты. После `timeout` проверь состояние (`profiles_list`, `backup_list`), а не вызывай заново.

## 1. Что это и что под капотом

goAmnezia pro — установщик и панель управления серверной частью AmneziaVPN. Поднимает официальные Docker-контейнеры Amnezia, держит три линейки AmneziaWG (1.x, 2.0, 3.1) как отдельные профили на своих UDP-портах, выдаёт ключи в форматах приложения Amnezia (`vpn://`, QR приложения), AmneziaWG-клиентов (`.conf`, QR) и роутеров.

Четыре интерфейса к одному ядру:

| Интерфейс | Для кого | Как ходит к ядру |
|---|---|---|
| SSH-меню `goamnezia` | администратор в терминале | напрямую (bash-ядро `install.sh` + `lib/*.sh`) |
| Telegram-бот | администратор с телефона | мост `install.sh --action=<имя> --json` |
| Веб-панель | администратор в браузере | тот же мост |
| MCP-сервер `goamnezia-mcp` | ты | тот же мост: `ssh root@HOST goamnezia-mcp` (stdio) или HTTP-доступ (§10) |

Что из этого следует:

- Инструмент = одно действие моста. Сервер ничего не делает сам: проверяет параметры по схеме, запускает `install.sh --action=… --json --k=v`, последняя JSON-строка stdout моста становится результатом.
- Один замок `/run/goamnezia/config.lock` на все интерфейсы: пока бот, панель или человек в SSH-меню что-то пишут, твой изменяющий вызов ждёт до 30 с, потом `lock_timeout`. Читающие инструменты замок не берут.
- Единый источник правды — `/opt/goamnezia/config.json` (профили, порты, параметры) и `/opt/goamnezia/users.json` (пользователи, пиры, ключи). Напрямую ты их не читаешь — только через инструменты.
- Каждый вызов пишется в `/var/log/goamnezia-audit.log` с пометкой `mcp`: инструмент, параметры без секретов, статус. Ответы моста в аудит не попадают.

Форма ответа любого инструмента:

```json
{
  "content": [
    {"type": "text", "text": "{ …JSON моста, поля *_png_b64 заменены заглушками… }"},
    {"type": "image", "mimeType": "image/png", "data": "<base64>"}
  ],
  "structuredContent": {"status": "success", "message": "ok", "…": "…"},
  "isError": false
}
```

- `structuredContent` — ответ моста как есть: `status` (`success` | `error`), `message` (текст на языке сервера), `code` (машинный код при ошибке, §7), поля данных.
- `content[0].text` — тот же JSON, но вместо `*_png_b64` стоит заглушка `<PNG N байт: см. изображение №k>`; сами PNG приходят `image`-блоками (QR у `user_get_key`).
- `isError: true` при любом `status ≠ success`, включая `code: transport` (мост не запустился или не вернул JSON) и `code: timeout`.

Профили — что за чем стоит:

| Профиль | Линейка | Контейнер | Подсеть | Порт по умолчанию | Мин. приложение Amnezia | Кому подходит |
|---|---|---|---|---|---|---|
| `awg2` | AmneziaWG 2.0 | `amnezia-awg2` | `10.8.2.0/24` | `pro`: UDP/443; `lite` и `lite_site`: случайный 30000–49999 | 4.8.12.9 | приложения Amnezia 4.8.12+; единственный контейнер, который видит официальное приложение Amnezia; ставится всегда |
| `awg3` | AmneziaWG 3.1 | `amnezia-awg3` | `10.8.3.0/24` | случайный 30000–49999 | 5.0.1.5 | приложения Amnezia 5.0.1.5+; сильнейшая маскировка (защита заголовков, сигнатурные пакеты) |
| `awg1` | AmneziaWG 1.0/1.5 | `amnezia-awg1` | `10.8.1.0/24` | случайный 30000–49999 | 4.0.0 (1.0), 4.8.8.3 (1.5) | роутеры Keenetic/MikroTik/OpenWrt, ядерный модуль, старые приложения; пресет `router` |

Порты по умолчанию — из плана. Реальные значения смотри в `profiles_list` (`port`), не предполагай.

Три режима — чем на самом деле отличаются:

| Режим | Сайт, домен, сертификат, панель | Где AmneziaWG |
|---|---|---|
| `lite` | сайта нет, nginx не ставится | на своём UDP-порту (случайный 30000–49999) |
| `lite_site` | домен, сайт-заглушка и панель на TCP/443 с сертификатом Let's Encrypt | на своём UDP-порту |
| `pro` | **то же самое**, ничем не отличается | на UDP/443 рядом с сайтом (TCP/443 у сайта — другой сокет) |

Два режима с сайтом различаются **только местом AmneziaWG**. Сайт, домен, сертификат и панель у
них общие, и переход `lite_site ↔ pro` не трогает ни nginx, ни сертификат.

**Самоподписанный сертификат — не признак режима, а запасной путь.** На него сервер сворачивает
временно и в любом из двух режимов с сайтом: домена ещё нет или его A-запись пока не указывает сюда.
Тогда сайт отдаётся по IP (`https://<IP>/`), `site.cert = selfsigned`, в ответе есть
`cert_fingerprint_sha256`, а панель на домене не включается. Как только домен готов, человек
выпускает настоящий сертификат, и режим при этом не меняется. Поэтому вопрос «что сейчас можно» —
это вопрос про `cert` и `domain`, а не про название режима: смотри `server_status.site` и
`panel_status`, а не `mode`.

## 2. Начало сессии — обязательный порядок

| Шаг | Вызов | Что взять из ответа |
|---|---|---|
| 1 | `resources/read goamnezia://guide` | этот гайд (ты здесь) |
| 2 | `server_status` | `installed` (`false` → сервер не установлен, менять нечего), `mode` (`lite` — только AmneziaWG, сайта нет; `lite_site` — плюс сайт и панель на домене с Let's Encrypt, AmneziaWG на своём порту; `pro` — тот же сайт, AmneziaWG на UDP/443 рядом с ним), `domain`, `server_ip`, `version`, `users`, `profiles[]`; в обоих режимах с сайтом — блок `site` (по нему и суди, что сейчас можно: `cert`, `domain`, `panel`); тревоги — `disk` (`level` `low`/`critical` — место кончается), `docker_stale` (служба Docker старше пакета), `update_rollback` (обновление не встало и откатано), `kmod.warn` (на сервере модуль ядра AmneziaWG без исправлений, а есть профиль 3.1 — только сказать человеку, ничего не менять), `profiles[].packet_risk` (не `null` — у профиля слишком большие пакеты: при стандартном MTU 1280 пакет данных 1280 + 80 + S4 больше 1400, на мобильном интернете, PPPoE и у части хостеров скачивание не идёт; сказать человеку словами и предложить кнопку «Исправить S4» в SSH-меню, панели или боте — у агента такого инструмента нет; `keyless` — сколько людей с ключами из приложения Amnezia потеряют связь); `lines_check` (`no_20` — на сервере нет AmneziaWG 2.0: старые версии приложений и роутеры Keenetic не подключатся; `reline` — свой профиль можно переставить на недостающую линию, это делает человек кнопкой «Переставить на 2.0» в SSH, панели или боте — у агента инструмента нет; `install` — недостающая встанет на свободное место по `profile_install` без `line`; `text` — словами), `free_lines` (какая линия встанет на свободное место), `dupline_fix` (не `null` — ошибка прошлых версий: вместо 2.0 встала вторая 3.1; сказать человеку и указать на «Исправить»), `profiles[].title` — так профиль называют людям («AmneziaWG 3.1 · порт 6714»; имена awg2/awg3 людям не показывать) |
| 3 | `profiles_list` | по каждому профилю: `state` (`running`/`exited`/`missing`/`docker_unreachable` — демон Docker не отвечает, состояние контейнеров неизвестно; это НЕ пропажа контейнера), `port`, `line`, `peers`, `image_tag`, `enabled`, `port_published` (`false` — контейнер работает, а порт Docker не опубликовал: связи нет, лечит `profile_repair`), `packet_risk` (`{packet, budget, s4, safe_s4, mtu, keyless}` или `null` — см. шаг 2) |
| 4 | по задаче: `users_list` или `user_show` | `enabled`, `profiles[]`, `quota_bytes`, `expires`, `peers.<профиль>.active`, `last_handshake` |
| 5 | при симптомах: `diagnose`, `traffic_report` | §4.2 |

Те же данные доступны как ресурсы (`goamnezia://status`, `goamnezia://profiles`, `goamnezia://users`, `goamnezia://traffic`, `goamnezia://diagnose`) — клиент может подключить их к контексту без вызова инструмента.

Чего не делать в начале: не вызывать изменяющие инструменты «посмотреть, что будет»; не читать ключи (`user_get_key`) без запроса человека; не ставить профили и не менять порты «для порядка».

## 3. Каталог инструментов по задачам

Обозначения: R — только чтение (замок не берётся, безопасно); W — изменяющий; D — разрушительный (нужен `confirm`, §5). Параметры со `*` обязательны.

### 3.1 Обзор и диагностика

| Инструмент | Параметры | Когда применять | Когда нельзя / осторожно |
|---|---|---|---|
| `server_status` R | `brief` (`on` \| `off`; `on` — сводка для частых опросов: без `ports`, `mode_port_mismatch`, `site`, `key_hosts`, `endpoint_effective` и `endpoint_auto`) | первым в сессии (полная, без `brief`); после любого изменения режима или профилей; тревоги — `disk` (раздел продукта: `free_mb`, `used_pct`, `level` `ok` / `low` / `critical`), `docker_stale` (пакет Docker обновлён, а служба старая: `reason`, версии, `since`, что сделал сторож — `last_attempt`, `retry_after`; `null` — служба свежая; лечение — `docker_restart`), `update_rollback` (обновление не встало и откатано: версии, этап; `null` — не было); в обоих режимах с сайтом (`pro`, `lite_site`) несёт блок `site` — `url` сайта, `domain` (заполнен, пока сайт стоит на домене с Let's Encrypt; на запасном самоподписанном пуст, а сохранённый домен виден в корневом `domain`), `template_id`, `cert` (`letsencrypt` / `selfsigned`), срок, для самоподписанного — `cert_fingerprint_sha256` (по нему человек и клиент MCP доверяют серверу), `panel` (работает ли панель на домене), `alt_svc`, `listen`; в любом режиме — `key_hosts`: хосты, которые примет `endpoint` у `user_get_key` (сначала домены, затем IPv4 машины; без похода в сеть, §4.9) | секретного пути панели в `site` нет — только факт `panel: true`; в `lite` `site: null`; `cert: selfsigned` — не признак режима, а запасной путь (домена нет или A-запись не указывает на сервер), и он один решает, что доступно: панель, ссылки мини-аппа, адрес доступа агента |
| `profiles_list` R | — | перед любой операцией с профилем или портом; после установки и обновления | `port_published: false` — контейнер работает, а порт Docker не опубликовал: связи нет, лечит `profile_repair` |
| `kmod_status` R | — | «быстрее ли на модуле ядра», «почему профили работают программой», тревога `server_status` → `kmod.warn`: `state` (`off` — модуля нет, профили на программе `amneziawg-go`, так по умолчанию; `ready` — модуль есть, профили на программе; `on` — профили на модуле; `fallback` — выбран модуль, а работает программа: обычно после обновления ядра модуля под новое ядро нет, в `reason` — словами и с ядром; `failed` — последняя установка на этом ядре не удалась, `failed.reason`; `unpatched` — в памяти чужой модуль без исправлений; `busy` — идёт установка или перевод, ход — `progress.text`), `want` (выбор человека), `profiles.<профиль>.engine` (`kernel` / `program`) | только смотрит. Ставить модуль, переводить профили на него и обратно агенту нечем и нельзя: это выбор человека с согласием на пакеты сборки и короткий обрыв у людей (переподключатся сами за 15–25 секунд). Скажи, что увидел, и что включается это в SSH: «Обслуживание → Ускорение AmneziaWG (модуль ядра)» |
| `diagnose` R | — | «не подключается», «не ставится», перед `profile_install`: `docker`, `docker_info` (версии клиента, демона и бинаря на диске; `mismatch` — рассогласование API, `stale` — пакет обновлён, а служба старая), `ip_forward`, сеть `amnezia-dns-net` (`network`), `disk_free_mb`, `ports[]` профилей (занятость и публикация), ключи сервера, таймеры, порты 80/443 | `ports[].free=true` у установленного профиля означает, что порт никто не слушает — контейнер не поднят |
| `traffic_report` R | — | кто онлайн (рукопожатие < 3 мин), трафик по пирам и пользователям; до и после обновления ядра | — |
| `edge_status` R | — | «у части людей не работает» на сервере с несколькими внешними адресами: по каждому адресу `packets_15m` / `packets_1h` / `packets_day`, `users`, `verdict` (`dark` — адрес замолчал, хотя в это время обычно занят, а у других трафик идёт: похоже на блокировку адреса) и `silent_since`; `domain_endpoint: true` — в ключах домен, адрес выбирает DNS; `dns` — A-записи этого домена (`state`, `a`, `foreign`), `in_dns` у адреса — есть ли он в них: доменные пользователи считаются только на адресах из A-записей, а если DNS не ответил — на каждом; пользователи со своим адресом считаются на нём. Для ключа на другой адрес (§4.9): `keys_host` — общий адрес в ключах как обычно (без закреплённых адресов людей) и `key_choices[]{host, kind (`ip` \| `domain`), default, verdict, users, in_dns}` — ровно те хосты, что примет `endpoint` у `user_get_key`, по порядку: `default: true` (это `keys_host`) первым, затем домены, затем адреса, замолчавшие (`dark`) — в конце; `verdict` и `users` — только при двух и более адресах, иначе `null`; `in_dns` — из записи адреса, у домена `null` | `count` < 2 — адрес один, сторожить нечего; при `dark` предложи человеку снять A-запись адреса из DNS домена, пересадить пользователей `user_set_address` или выдать тому, кто не подключается, тот же ключ на живой адрес (`user_get_key` с `endpoint`, §4.9); `dns.foreign` не пуст — в A-записях домена чужой адрес, часть клиентов уходит на другую машину: скажи об этом человеку; сам адреса и DNS не меняй без просьбы |
| `logs_tail` R | `component`* (`awg1`, `awg2`, `awg3`, `bot`, `admin`, `mcp`, `nginx`, `system`), `lines` (10–2000, по умолчанию 100) | ошибки рукопожатий (`component=<профиль>`), падения бота или панели; `mcp` — аудит **твоих же** вызовов: сервер отбирает строки по метке твоего доступа и кладёт в ответ `lines_total`, `lines_shown`, `narrowed_to_agent`. Чужие действия (человек, бот, панель, другие агенты) не показываются. В журнале действий — имена действий, их аргументы и адреса, с которых звали: это личные данные, не пересказывай их без нужды | `component=system` — это весь журнал машины от root, и по HTTP он доступен только уровню `admin`: остальным `-32003 forbidden`, журнал даже не читается. Не проси 2000 строк без нужды — они уйдут в контекст. Пустой `log` значит ровно «записей нет»: когда читать нечего или нечем, приходит отказ с кодом — `logs_no_container`, `logs_driver_unreadable` (профили запускаются с `--log-driver none`, как в самом приложении AmneziaVPN: `docker logs` им не отдаст ничего и не отдаст никогда — смотри `profiles_list` и `traffic_report`), `logs_docker_down`, `logs_no_unit`, `logs_no_journal`, `logs_absent`, `logs_read_failed` |
| `logs_status` R | — | «мало места», перед бэкапом: размеры логов по участкам диска и бюджет — `areas[]{area, used_mb, budget_mb, percent}`, где `area` это `journal`, `nginx`, `goamnezia`, `docker`; свободное место на диске — отдельным полем `free_mb` | это НЕ имена компонентов `logs_tail`: там читают строки, здесь считают место. Подставлять `area` в `component` бессмысленно — совпадает только `nginx`, и то случайно |
| `logs_enforce` W | — | «место кончается прямо сейчас» (`server_status.disk.level` — `low` или `critical`): применить бюджет логов немедленно, не дожидаясь суточного таймера. В ответе `trimmed` — строка о том, что подрезали | подрезает журналы и docker-логи по пределу из настроек; данные продукта, ключи и пользователей не трогает |
| `panel_status` R | — | вопросы про панель и мини-апп. Ответ различает три разных вещи, не смешивай их: `enabled` — панель на домене **работает**; `configured` — секретный путь записан в конфиге; `available` — включить её здесь вообще возможно (есть сайт, домен и доверенный сертификат). Теги `I1–I5` — только понятные всем клиентам (`b`, `t`, `r`, `rc`, `rd`): отрицательный размер, незнакомый тег, `<c>` (не поймёт AmneziaVPN на телефонах) и `<d>`/`<ds>`/`<dz>` (не поймут роутеры с модулем ядра) → отказ `params_invalid` со словами. С 1.0.13 каждый из `I1–I5` ещё и начинается с `<b 0x…>`: пакет, который начинается иначе (например `<r 2><b …>`), KeeneticOS 5.1 не примет → тот же отказ с советом. `import_adopt` с `<c>`, `<d>` или пакетом не с `<b` в конфиге подхватывает, а в ответе `ipacket_warnings` — что заменить: передай человеку. I1 по умолчанию у новых профилей — универсальный `<b 0x…>`; прежнее умолчание обновление и подхват меняют сами, без перевыпуска (ключ для Keenetic человек скачивает заново). `S4` — не больше 40 (иначе при стандартном MTU 1280 пакет данных больше 1400 и на мобильных сетях скачивание встанет) → отказ `params_invalid` со словами «Задайте S4 до 40». Новые профили 2.0 и «Исправить S4» сами берут S4 12–24 (с 1.0.13, запас 16 байт). С 1.0.13 — пределы (§8.2), иначе `params_invalid` со словами и допустимым диапазоном: тайминги 3.1 и `ContentPaddingAddition` в коридоре вокруг значений приложения, `Jc × Jmax` до 16384, `Jc` + число заданных `I1–I5` до 127, при `RandomTrailers` — без широких `H` у `S`, отличных от `S4`; не перебирай значения — возьми диапазон из `message`. Не применилось (контейнер не поднялся) — прежнее значение уже вернулось: `param_rolled_back` (профиль работает) или `param_apply_failed` (профиль лежит — `profile_repair`). В ответе `clients_update=true` — выданные ключи несут прежнее значение; `result.steps` — кому что делать по именам (подписки обновятся сами, ключи `vpn://` и `.conf` — выдать заново `user_get_key`, ключ из приложения Amnezia — поделиться заново или перевыпустить); `message` — то же одной фразой |
| `profile_regen` D | `profile`*, `preset`, `confirm`* | полностью новые параметры маскировки (профиль «засветился») | все ключи профиля перестают работать; после — перевыпуск каждому (§4.3) |
| `profile_set_subnet` D | `profile`*, `subnet`* (частная сеть `/20`–`/24`, например `10.8.5.0/24`), `confirm`*, `adopted_confirm` (имя того же профиля — согласие человека, как у `profile_set_port`) | подсеть конфликтует с локальной сетью клиента; `server_status.subnet_overlaps` — подсети профилей пересекаются (так приложение Amnezia ставит свои контейнеры, подхват их берёт как есть): выход — `move` {profile, subnet} оттуда | пиры перенумеровываются по порядку, контейнер пересоздаётся; все пользователи профиля импортируют ключ заново. Пересечение с занятым — `subnet_overlap`, в `message` свободная подсеть. Подхваченному старому контейнеру (`wg0`) подсеть не сменить — `subnet_legacy`, в `message` — какой профиль перенести вместо него. У профиля с людьми приложения без ключа на сервере — `adopted_keyless` (их ключи с прежним адресом перестанут проходить); повтор с `adopted_confirm` — только после прямого согласия человека |
| `profile_remove` D | `profile`*, `confirm`* | убрать линейку целиком | ключи всех пользователей этого профиля умирают; их пиры в других профилях остаются |

|---|---|---|---|
| `endpoint_set` W | `host`* (домен или IPv4; пустая строка — по умолчанию: в режиме Pro домен сервера, иначе IP) | домен вместо IP в `Endpoint` ключей — переезд на другой сервер без перевыпуска; `host: ""` — вернуть значение по умолчанию | только новые выдачи; домен должен указывать на сервер; вписанный домен годится в любом режиме, а в `pro` домен сервера стоит в ключах и без этого. Параметр обязателен и пустым передаётся явно: вызов без `host` отвергает схема (раньше он молча стирал `Endpoint`) |

| `mode_set` W | `mode`* (`lite`, `lite_site`, `pro`), `domain` | переключить режим, переход из любого в любой (§1). `lite → lite_site` или `lite → pro`: nginx, сертификат Let's Encrypt на домен (из `domain`, а без него — из конфига), случайный шаблон сайта из библиотеки, если сайта ещё нет; домена нет вообще — запасной путь, самоподписанный сертификат на IP (EC P-256, 10 лет, `/opt/goamnezia/tls`, сайт и по 80, и по 443): это законное состояние режима, а не отказ. `lite_site ↔ pro` **без `domain`**: сайт, домен, сертификат, шаблон и панель не трогаются вовсе — certbot не зовётся, vhost остаётся прежним, меняется только запись режима. `domain`, переданный из режима с сайтом, — это уже переезд на другой домен: сайт поднимается заново и выпускается новый сертификат, поэтому передавай `domain` только когда человек прямо просит сменить домен. `* → lite`: сайт снят (vhost убран; сертификаты, домен и файлы сайта остаются на диске). Повтор того же режима — ремонт vhost. Ответ — `mode`, `previous_mode`, `domain`, `template`, `site` (с `cert` и `cert_fingerprint_sha256`), `dns_fallback` (`true` — A-запись ещё не сюда или DNS не ответил: сайт на запасном самоподписанном, домен сохранён; когда DNS дойдёт, повтори `mode_set` с тем же `domain` — выпустится настоящий), `keys_host_before` / `keys_host` — адрес в новых ключах до и после (домен в ключах только в `pro`; разные — скажи человеку, что уже выданные ключи со старым адресом работают, пока порт не менялся). Смена домена у живого сайта на Let's Encrypt при неготовом DNS не уводит его на запасной: certbot откажет (`cert_failed`), и сайт останется на прежнем домене | **порт AmneziaWG мост не двигает**: `mode_set pro` сам по себе не переносит профиль на UDP/443, а `mode_set lite_site` не уводит его оттуда — это отдельный `profile_set_port`, и рвать связь всем без просьбы человека действие не имеет права. Обоим режимам с сайтом нужны свободные и открытые снаружи TCP/80 и 443 (`preflight_modes` скажет заранее): занятый чужим процессом → `port_busy`, закрытый локальным файрволом → `closed_local`, в обоих ответах `port`, `proto`, `process`, `pid`, `unit`, `container`, `product`, `hint` и полный список `reasons` (§7). Выпуск сертификата идёт до минуты (certbot) — не повторяй по таймауту, проверь `server_status`; сертификат выпускается один раз (лимиты Let's Encrypt), повторный вызов его не трогает. На запасном самоподписанном браузер покажет предупреждение — это ожидаемо, сайт не для людей; отпечаток меняется только при смене IP сервера или явном перевыпуске из SSH — сообщи человеку, если он изменился. Контейнеры и ключи не пересоздаются |
| `preflight_modes` R | — | перед `mode_set` в `lite_site` или `pro`: кто занимает TCP/80 и 443 (и UDP/443), какой юнит, контейнер или продукт-сосед, локальный файрвол; какие режимы доступны на этом сервере. Ответ: `modes{lite, lite_site, pro}` с `available` и `reasons[]{port, proto, state (busy \| closed_local), process, pid, unit, container, product, message}`, `modes.warnings[]` (UDP/443 занят — профиль по умолчанию получит случайный порт, не блокирует), `modes.ports{tcp80, tcp443, udp443}`, `modes.hints{free_cmd, open_cmd}`; в корне — `lite_site_available`, `pro_available`, `hint` (команда освобождения или открытия порта) | только чтение; занятый порт — не повод останавливать чужую службу без человека: покажи `message` и `hint`, решение — за ним; свой nginx или контейнер goAmnezia (`ours: true`) режим не блокирует |
| `site_set_template` W | `template`* (идентификатор из каталога или `__random__`) | сменить сайт-маскировку в обоих режимах с сайтом (вид сертификата тут не важен); ответ — `template{template_id, name, category, license, preview_url, deployed}` | в `lite` → `needs_site`; отказ по самому шаблону приходит кодом модуля: `unknown_template`, `download_failed`, `no_index`, `app_shell`, `broken_assets` — предложи другой шаблон, не перебирай каталог циклом; клон идёт до минуты |
| `site_alt_svc` W | `state`* (`on`, `off`) | заголовок `Alt-Svc: h3=":443"` — объявление HTTP/3 ради правдоподобия; ответ `alt_svc` (булево) и `applied` (дошло ли до nginx: в `lite` настройка только сохраняется до включения сайта) | предупреди человека: браузеры попробуют QUIC на UDP/443, упрутся в AmneziaWG и откатятся на TCP с задержкой в секунду-две; по умолчанию выключено |
| `panel_domain_enable` W | — | открыть панель на домене по секретному пути `app-<86 знаков, 512 бит>`; ответ — `path`, `url` (`https://<домен>/<path>/`), `changed`, `hint` | нужен **домен с доверенным сертификатом**, а не название режима: работает в обоих режимах с сайтом, как только сайт стоит на домене с Let's Encrypt. В `lite` и на запасном самоподписанном — `not_pro` с полями `mode`, `cert`, `domain` и `reason`; спроси `panel_status` заранее, `available: false` — включать нечего. Повторный вызов путь не меняет (`changed: false`); **`url` — секрет**: покажи только человеку, который попросил, и не упоминай в других ответах; вход в панель — по одноразовому коду из Telegram-бота |
| `panel_domain_rotate` W | — | сменить секретный путь панели; ответ как у `panel_domain_enable` | те же условия, что у `panel_domain_enable` (домен с доверенным сертификатом), иначе `not_pro`; у выключенной панели → `panel_disabled` (сначала `panel_domain_enable`); старый адрес перестаёт открываться сразу — предупреди |
| `panel_domain_disable` W | — | снять панель с домена (вход остаётся через SSH-туннель) | работает в любом режиме и при любом сертификате — это единственное действие панели без условий |

### 3.8 Страница подключения, каталог приложений, зеркало сборок

Страница подключения — адрес `https://<домен>/p-<секрет>/`, по которому человек сам скачивает свои ключи (`.conf`, QR, `vpn://`, ссылка в приложение), видит приложения под своё устройство и может попросить копию сборки на наш сервер. | Инструмент | Параметры | Когда применять | Когда нельзя / осторожно |
|---|---|---|---|
| `clients_list` R | `platform` (`ios`, `tvos`, `android`, `android_tv`, `windows`, `macos`, `linux`, `router`), `line` (`1.0`, `1.5`, `2.0`, `3.1`) | «какое приложение поставить на iPhone под ключ 3.1»: `apps[]{id, name, developer, official, license, platforms{<p>{links[], support{<линейка>: yes \| no \| unknown \| версия}, note}}, import{conf, qr-conf, vpn, qr-vpn, deeplink, hint}, mirror}` — сначала официальные, потом с пометкой «неофициальное» | сведения проверены на дату `checked`; `unknown` — не подтверждено источником, так и скажи человеку; ничего не меняет |
| `page_create` W | `name`*, `ttl`* (`1h…720h`, `1d…365d`, `forever`), `profiles` (`awg2,awg3`; не передан — все, в которых есть ключ), `mirror` (`on`/`off`, по умолчанию `on`) | человек просит «дай ссылку/страницу для подключения»: ответ `id`, `url`, `expires`, `forever`, `profiles`, `mirror` | нужен домен с доверенным сертификатом (`server_status.site.cert = letsencrypt`), иначе `pages_need_domain` — предложи `mode_set` с доменом или временную ссылку из SSH-меню; **`url` — секрет**: покажи только человеку, который попросил, не повторяй в других ответах; `forever` — только по явной просьбе, с предупреждением, что отозвать можно лишь `page_revoke`; выключенный пользователь — `user_disabled` (сначала `user_enable`); больше 200 страниц — `page_limit` |
| `page_list` R | `name` | список страниц с `id`, сроком, `visits`, `last_visit` — без адресов | адреса здесь нет намеренно; нужен снова — `page_url` |
| `page_url` W | `id`* | отправить адрес ещё раз | **тот же секрет**, что у `page_create`; каждая выдача пишется в аудит |
| `page_revoke` W | `id`* | ссылка утекла, человек ушёл, срок пора закрыть | адрес умирает сразу; последняя страница останавливает службу и снимает маршрут |
| `page_revoke_all` D | `name`, `confirm`* | отозвать все страницы (или все страницы одного человека) разом | `confirm` = `name`, если он передан, иначе `page_revoke_all`; необратимо — новые адреса будут другими |
| `sub_list` R | `name` | есть ли у человека подписка — постоянная ссылка на все его ключи: профиль `all.yaml` для Clash Verge Rev, FlClash, Mihomo Party (обновляется сам), `all.txt` для incy и AWG Manager, `.conf` и `vpn://` по линиям 1.0–3.1 для роутеров и приложений. Ответ: `subs[]{name, label, created, rotated, generation, fetches, last_fetch, last_suffix, last_client, lines[]{line, profile, has_key}, disabled, prev_fetches, prev_last_fetch}` (`prev_*` — сколько раз и когда последний раз забирали адрес до последнего перевыпуска), `count`, `domain_ready` (нет домена с доверенным сертификатом — подписки на паузе), `update_interval` (через сколько часов приложения забирают профиль сами) | **адресов здесь нет и у тебя их не будет**: адрес подписки — постоянный ключ ко всем ключам человека без срока, поэтому создать, показать, перевыпустить и отозвать её может только человек — SSH-меню (карточка → «Подписка»), бот («📡 Подписка»), панель или мини-апп; утёк адрес — скажи человеку перевыпустить подписку там же. Короткие ссылки подписки (`https://<домен>/<код из 8 знаков>`, вход с нового адреса подтверждает администратор числом в Telegram-боте) — тоже только у человека: ни кода, ни запросов подтверждения, ни банов у тебя нет |
| `mirror_list` R | — | что уже лежит на нашем сервере: `items[]{app, platform, state (queued \| downloading \| ready \| failed), version, size, sha256, fetched, error}`, `used_mb`, пределы | `failed` с `error` — причина (`mirror_unverified` — источник не дал контрольную сумму или она не сошлась, `mirror_too_big`, `mirror_no_space`, `mirror_fetch_failed`) |
| `mirror_fetch` W | `app`*, `platform`* (`android`, `android_tv`, `windows`, `macos`, `linux`) | положить официальную сборку на наш сервер заранее, до просьб с страниц | только открытые приложения с полем `mirror` в `clients_list` (`unknown_app`, `not_mirrorable`); iOS — никогда (App Store); ответ `state: queued` — загрузка в фоне, итог в `mirror_list`; повтор во время загрузки — `mirror_busy`; тянет сотни мегабайт из GitHub — не зови «на всякий случай» |
| `mirror_remove` D | `app`*, `platform`*, `confirm`* | освободить место | `confirm` = `app`; страницы перестанут предлагать «скачать с нашего сервера» |

## 4. Обязательные порядки операций

Общее: перед изменяющим шагом — фраза человеку «сейчас сделаю X, изменится Y»; перед D-шагом — явное согласие и `confirm`.

### 4.1 Подключить нового пользователя и выдать ключ нужной линейки

Подсказка `onboard_user` (аргументы `name`, `profiles`) даёт тот же порядок.

1. `profiles_list` — какие профили установлены и `running`. Нужной линейки нет → не ставь профиль молча, спроси человека (§4.7).
2. Выбери профиль под клиента (§8.1): приложение Amnezia ≥ 5.0.1.5 → `awg3` (или `awg2`); 4.8.12.9+ → `awg2`; роутер или старое приложение → `awg1`. Клиент неизвестен — спроси; если спросить нельзя, выдай `awg2` (его видит приложение) и назови `min_client`.
3. `users_list` — имя свободно. Занято → предложи другое, чужую запись не переиспользуй. Имени нет или человек просит придумать — `name_suggest` (подпись на его языке: `lang`), его `id` и `label` — в `user_add`.
4. `user_add` `{"name": …, "profiles": "<нужные через запятую>"}`; `label`, `quota_gb`, `days` — только если названы.
5. `user_get_key` `{"name": …, "profile": <профиль>, "format": "all"}` по каждому нужному профилю. Передай человеку `.conf` (текст), ссылку `vpn://`, QR (приходят картинками), `line` и `min_client`.
6. `user_show` — `enabled=true`, пиры в нужных профилях `active=true`.

Нельзя: выдавать ключ профиля, который клиент не поддерживает; отправлять ключ куда-либо, кроме ответа человеку.

### 4.2 Пользователь не подключается

Подсказка `diagnose_user` (аргумент `name`). Собери факты по порядку, выводы — после.

| Шаг | Вызов | На что смотреть |
|---|---|---|
| 1 | `user_show` | `enabled=false` → `user_enable`; `quota_bytes` исчерпан или `expires` в прошлом → `user_set_quota` / `user_set_expiry`; в `peers` нет нужного профиля → `user_add_profile` |
| 2 | `traffic_report` | `latest_handshake_ts` пира: никогда → ключ или путь до сервера; давно → клиент отвалился |
| 3 | `profiles_list` | профиль `running`; `port` совпадает с `Endpoint` в ключе (после `profile_set_port` старый ключ содержит старый порт) |
| 4 | `diagnose` | `docker=true`, `ip_forward="1"`, `network=true`, `disk_free_mb` > 0, `ports[]` |
| 5 | `logs_tail` `{"component": "<профиль>", "lines": 200}` | отказы рукопожатий, отклонённые ключи |

Типовые причины и что делать: приложение старее `min_client` → обновить приложение (ключ не виноват); ключ выдан до `profile_regen`, серверного `profile_set_param` или `profile_set_subnet` → перевыпустить `user_get_key`; ключ не той линейки → выдать ключ подходящего профиля; провайдер режет порт → `profile_set_port` (443 у одного профиля) и переслать `.conf`; крайняя мера — перевыпуск ключа: `user_reissue_key` (D, `confirm`) + `user_get_key`.

### 4.3 Сменить порт, подсеть или параметр — с предупреждением о перевыпуске

Сначала определи, что изменится для ключей:

| Изменение | Инструмент | Ключи | Что сказать человеку до вызова |
|---|---|---|---|
| порт | `profile_set_port` W | не меняются; меняется `Endpoint` | «старые `.conf`/`vpn://` содержат старый порт — их надо переслать; 443 может держать один профиль»; у профиля, подхваченного у приложения Amnezia, людям без ключа на сервере переслать нечего — отказ `adopted_keyless`, согласие — `adopted_confirm` (§3.3) |
| MTU, DNS, хост Endpoint, клиентские параметры (`Jc`, `Jmin`, `Jmax`, `I1–I5`, `PersistentKeepalive`, тайминги) | `profile_set_mtu`, `client_dns_set`, `endpoint_set`, `profile_set_param` | действуют на новые выдачи; старые ключи продолжают работать со старым значением | «старые ключи работают как раньше; новое значение получат с новым конфигом: подписки — сами, ключам `vpn://` и `.conf` — выдать заново» (у `profile_set_param` — `clients_update` и `result.steps` по именам) |
| серверные параметры `S1–S4`, `H1–H4`, `HeaderProtectionKey`, `RandomTrailers`, `DisableCookies` | `profile_set_param` D | все ключи профиля перестают работать | «каждому пользователю профиля нужен новый ключ» — их число: `profiles_list` → `peers` |
| пресет целиком | `profile_regen` D | все ключи профиля | то же |
| подсеть | `profile_set_subnet` D | пиры перенумерованы; все ключи профиля надо импортировать заново | то же + «контейнер пересоздаётся, сессии рвутся» |

Порядок для D-варианта:

1. `profile_params` — текущее значение (чтобы человек мог откатить руками).
2. `backup_create`.
3. Предупреждение по таблице, явное согласие человека.
4. Вызов с `confirm` = имя профиля.
5. Если в ответе `reissue_required=true` — или это `profile_regen` / `profile_set_subnet`: сервер уже переписал конфиги, твоя часть — `users_list` → каждому пользователю с пиром в профиле `user_get_key` → передать. Скажи человеку, что старые ключи больше не работают. У `profile_set_param` (с 1.0.13) `result.steps` уже называет людей по тому, что им делать: подписка (`subscription`) обновится сама — ей ключ не нужен; `page` и `key` — `user_get_key` и передать; `app` — ключ выдало приложение Amnezia, его приватной части на сервере нет: поделиться конфигом из приложения заново или `user_reissue_key` по согласию. `clients_update=true` при `reissue_required=false` (клиентский параметр) — старые ключи работают со старым значением, новое — с новым конфигом теми же путями.
6. `profiles_list` — контейнер `running`; через несколько минут `traffic_report` — рукопожатия возобновились.

### 4.4 Безопасно обновить ядро

Подсказка `safe_core_update` (аргумент `profile`). Автообновления нет намеренно: обновление ядра — всегда по решению человека.

1. `upstream_check` — есть ли обновление: `profiles[]` с `current_tag → available_tag` и `update`; `unsupported[]` — новые параметры протокола, которых goAmnezia ещё не знает (обновление их не подставит — предупреди человека). Код `unreachable` — источники недоступны с сервера: предложи повторить позже, откат при этом всё равно возможен.
2. `profiles_list`, `traffic_report` — состояние и активные рукопожатия «до».
3. `backup_create` — обязательно (действие делает свой бэкап, но твой — независимая страховка).
4. Согласие человека → `upstream_update` `{"profile": …, "tag": …(необязательно), "confirm": <профиль>}`. Действие само делает бэкап, ставит скрипты релиза, тянет образ по дайджесту, пересоздаёт контейнер из копии состояния, проверяет `awg show` и порт и при неудаче пытается откатиться. Провал приходит двумя разными кодами, и путаница тут дорогая: `update_failed` — откат сделан, состояние прежнее, дальше шаг 6 не нужен; `update_failed_no_rollback` — откат **не** сделан, контейнер снесён и не поднят, профиль лежит: останови сценарий, скажи человеку, что нужен он сам (SSH), и предложи `backup_restore` из бэкапа, который сделало обновление. `already_current` — обновлять нечего.
5. `profiles_list` — `running`, новый `image_tag`; через несколько минут `traffic_report` — рукопожатия есть.
6. Рукопожатий нет или клиенты не подключаются → `upstream_rollback` `{"profile": …, "confirm": <профиль>}` (`no_previous` — откатывать не на что). Контейнер сломан, а образ менять не нужно → `core_update` (пересоздание на закреплённом образе).

Ключи пользователей и линейка профиля при обновлении не меняются. Если на сервере стоит goWARP PRO, после обновления ядра ему нужно «восстановление» — скажи об этом человеку.

### 4.5 Бэкап и восстановление

- Бэкап: `backup_create` → в ответе `file`; проверь `backup_list`. Внутри: `config.json`, `users.json`, состояние контейнеров, `.env` бота, nginx и сертификаты.
- Восстановление: `backup_list` → выбери файл вместе с человеком → `backup_create` (снимок текущего состояния, чтобы было куда вернуться) → согласие → `backup_restore` `{"file": "<имя>", "confirm": "<то же имя>"}` → `profiles_list` (`running`) → `users_list`.
- Переезд на другой сервер — тот же `backup_restore` на чистой установке: контейнеры поднимаются из сохранённого состояния, ключи пользователей не меняются. IP при этом меняется: `endpoint_set` с доменом до переезда избавляет от пересылки ключей. `backup_restore` сам сверяет адрес: `server_ip_changed: true` — у ключей с прежним IP адрес устарел, скажи человеку.

### 4.6 Импорт существующей установки (сервер уже ставили приложением Amnezia)

1. `import_scan` — что нашлось: `containers[]` с `line`, `peers`, `clients[]`, `managed` (`true` = уже наш профиль), `adoptable` и `reason`, `suggested_profile`; список `adoptable[]`.
2. Покажи человеку таблицу; объясни, что подхват не пересоздаёт контейнер и не меняет ключи; `profile_exists` означает, что сначала надо убрать наш профиль того же имени.
3. Согласие → `import_adopt` `{"container": "amnezia-awg"}` — ответ с `users_added` и `users[]`.
4. `profiles_list`, `users_list` — что появилось (у подхваченных `imported: true`).
4а. Позже, если человек продолжает пользоваться приложением Amnezia: `import_reconcile` `{"profile": "awg2"}` показывает новых и исчезнувших пиров; с `apply: "on"` — подхватывает изменения. При старте SSH-меню сервер делает ту же сверку сам.
5. У подхваченных пользователей нет приватных ключей на сервере: приложение Amnezia их не хранит (и в его бэкапе их нет), ключ есть только у человека и в ссылке `vpn://` или `.conf`, которые ему когда-то отправили. `user_get_key` для них невозможен (`no_private_key`); такие пиры видно по `has_key: false` в `user_show`. Сначала спроси человека, сохранились ли эти ссылки или файлы: если да — `user_attach_key` (ключ станет выдаваемым, у человека ничего не изменится). Если нет — `user_reissue_key` (D, `confirm`) + `user_get_key`, предупредив, что старый ключ в приложении перестанет работать сразу.

### 4.7 Установить или убрать профиль

- Установка: `diagnose` (Docker, место) → `profiles_list` (профиль не стоит, порт свободен, 443 не занят) → согласие → `profile_install` `{"profile": "awg1", "preset": "router"}` (порт — только если человек назвал) → `profiles_list` (`running`) → существующим пользователям пиры в новом профиле по желанию: `user_add_profile` для тех, кого назовёт человек.
- Удаление: `profiles_list` (`peers` — сколько пользователей потеряют доступ) → `backup_create` → предупреждение и согласие → `profile_remove` `{"profile": …, "confirm": <профиль>}`.

### 4.8 Ограничить или отключить пользователя

«Временно отключить» → `user_disable`; «включить обратно» → `user_enable`; «дать N ГБ» → `user_set_quota`; «до такой-то даты» → посчитай дни от сегодня → `user_set_expiry`; «удалить» → сначала уточни, не имелось ли в виду отключение; затем `user_delete` с `confirm`. «Удалить сразу несколько» («всех выключенных», «с истёкшим сроком», «office-…», «этих десятерых») → `users_del_bulk_preview` с тем же выбором → покажи человеку `selected` и `count` → явное согласие на это число → `users_del_bulk` с `confirm` = `count`; `confirm_mismatch` — список изменился: новый предпросмотр и новое согласие.

### 4.9 Ключ на другой адрес сервера: адрес `dark` → `edge_status` → `user_get_key` с `endpoint`

Задача: «адрес замолчал (`dark`) — дай человеку ключ на живой адрес» или «у человека не открывается домен». `user_get_key` с `endpoint` выдаёт **тот же ключ** — та же пара ключей и тот же порт профиля, меняется только адрес сервера внутри. За пользователем ничего не сохраняется, прежний ключ продолжает смотреть на прежний адрес. Замысел — docs/EDGEIPS.md §3.4 «Разовый ключ на адрес».

1. `edge_status` — вердикты по адресам (`ips[]`), `keys_host` и `key_choices`. Значение для `endpoint` бери только отсюда (или из `server_status.key_hosts`): других хостов сервер не примет.
2. `user_show` `{"name": …}` — `key_host`: куда смотрят обычные ключи человека сейчас. `key_host_gone: true` — его закреплённого адреса на машине больше нет: обычная выдача ответит `address_gone`, и разовая — выход прямо сейчас.
3. Выбери в `key_choices` запись с `verdict: ok` или домен (`kind: domain` — адрес выберет DNS; проверь по `edge_status.dns` и `in_dns` у адресов, что A-записи домена не ведут на замолчавший адрес). Адрес `dark` не предлагай. `in_dns: false` — адреса нет в A-записях домена; ключу по IP это не мешает. `verdict: null` — у машины один адрес, сравнивать не с чем. Кроме нынешнего `key_host` выбрать не из чего — скажи человеку, что другого адреса у сервера нет.
4. Скажи человеку, что будет: «выдам тот же ключ на адрес X; запись со старым адресом в приложении останется».
5. `user_get_key` `{"name": …, "profile": …, "format": "all", "endpoint": "<адрес>"}`. Проверь в ответе `key_host_override: true` и `key_host` — выбранный адрес (`key_endpoint` — он же с портом профиля). Отдай `.conf`, `vpn://` и QR по правилам секрета (§0 п. 4, §8.4): только человеку, который попросил, и никуда больше. Запись `vpn://` в приложении Amnezia называется «<подпись> · AmneziaWG <линейка> · <адрес>» — две записи одного человека различаются.
6. Человек должен остаться на этом адресе — предложи закрепить его: `user_set_address` `{"name": …, "ip": "<адрес>"}` (закрепляется только IPv4 машины, домен — нет). Без закрепления сторож человека на новом адресе не видит: людей он считает по закреплённому адресу (без него — по общему, доменных — по A-записям), разовых ключей не знает, тревога `dark` нового адреса о человеке не скажет, а следующая обычная выдача снова пойдёт на старый адрес. После закрепления — как всегда у `user_set_address`: `resend_required: true` → обычный ключ (`user_get_key` без `endpoint`) и переслать; `domain_endpoint: true` — в ключах вписанный вручную домен, закрепление ничего не меняет, а разовая выдача работает и так.

Предупреди человека: **одна пара ключей — один пир.** Тот же ключ одновременно с двух адресов сервера или с двух устройств «прыгает» (у пира на сервере один адрес клиента), поэтому старую запись в приложении выключают или удаляют, а одновременным устройствам заводят отдельных пользователей (`user_add`). Не выдавай один ключ сразу на несколько адресов «про запас».

Человек может сделать то же сам: SSH-меню — карточка пользователя → «Ключ: QR, файл, ссылка» → «Ключ на другой адрес сервера (разово)»; бот — «🌐 Ключ на другой адрес» в карточке; панель — «Адрес сервера в ключе» в блоке ключа профиля. Ссылка на скачивание файлом с разовым адресом есть только там — агенту она не публикуется.

## 5. Правило `confirm`

Разрушительные инструменты: `profile_remove`, `profile_regen`, `profile_set_param`, `profile_set_subnet`, `profile_restart`, `profiles_restart`, `docker_restart`, `user_delete`, `users_del_bulk`, `user_remove_profile`, `user_reissue_key`, `backup_restore`, `upstream_update`, `upstream_rollback`, `core_update`, `page_revoke_all`, `mirror_remove`.

**Разрушительное — не то же, что опасное.** Пометка `destructive` включает вопрос `confirm`, но
несколько инструментов БЕЗ неё меняют сервер целиком, и подтверждения у них нет: `mode_set`
`{"mode": "lite"}` снимает сайт-маскировку, панель на домене и весь HTTP-транспорт агентов —
включая тот, по которому пришёл ты сам (дальше связи не будет вовсе); `site_set_template`
заменяет сайт-маскировку целиком; `panel_domain_disable` закрывает панель; `backup_schedule off`
оставляет сервер без ночных копий. Спрашивай человека перед каждым из них так же, как перед
разрушительным, и не зови их «чтобы посмотреть, что будет».

- У каждого есть обязательный строковый параметр `confirm`; он должен точно (с учётом регистра) повторять значение первого параметра инструмента: `user_delete`, `user_remove_profile`, `user_reissue_key` → `confirm` = `name`; `profile_*`, `upstream_*`, `core_update` → `confirm` = `profile`; `backup_restore` → `confirm` = `file`; `mirror_remove` → `confirm` = `app`; `page_revoke_all` → `confirm` = `name`, а без `name` (все страницы всех людей) — имя инструмента `page_revoke_all`; `profiles_restart` (параметров нет) → `confirm` = `profiles_restart`; `docker_restart` (параметров нет) → `confirm` = `docker_restart`. Перезапуск профилей — разрушительный с 0.5.0: он рвёт связь всем подключённым, и на уровне `write` его больше нет (только `admin`); перезапуск Docker — так же.
- Несовпадение или отсутствие → JSON-RPC ошибка `-32602`, мост не запускается, попытка пишется в аудит со статусом `rejected`.
- `confirm` — не формальность «повтори имя ради протокола»: подставляй его только когда человек явно согласился на это конкретное действие с этой конкретной целью. Подтверждение клиента (диалог «разрешить вызов?») защищает от вызова вообще; `confirm` — от вызова не с той целью. Нужны обе линии.
- Мосту `confirm` не передаётся — кроме `users_del_bulk`: у него `confirm` свой — **число людей**, которое человек увидел в `users_del_bulk_preview` и на которое согласился (строкой, `"12"`). Его сверяет сам сервер в момент удаления, под замком: выбор задевает сейчас другое число — отказ `confirm_mismatch` до изменений (в ответе `matched`). Отсутствие или не число 1–100 — `-32602`, как у остальных.
- Согласие бывает и у не разрушительного инструмента — отдельным параметром, который сверяет сам сервер: `profile_set_port` у профиля, подхваченного у приложения Amnezia, где у людей нет ключей на сервере, отказывает `adopted_keyless`, пока не передан `adopted_confirm` = имя профиля (§3.3). Правило то же: подставляй его, только когда человек прочитал `message` отказа и согласился.

## 6. Ресурсы и подсказки

| Ресурс | Что внутри | Как использовать |
|---|---|---|
| `goamnezia://guide` | этот гайд, `text/markdown` | читать в начале сессии |
| `goamnezia://status` | ответ `server_status` | картина сервера без вызова инструмента |
| `goamnezia://profiles` | ответ `profiles_list` | то же |
| `goamnezia://users` | ответ `users_list` | то же |
| `goamnezia://traffic` | ответ `traffic_report` | то же |
| `goamnezia://diagnose` | ответ `diagnose` | то же |

Ресурсы-действия при чтении вызывают мост; ошибка моста → JSON-RPC `-32603` с ответом моста в `data`; неизвестный URI или отсутствующий файл гайда → `-32002`.

Подсказки (`prompts/get`) — готовые сценарии с порядком шагов на языке сервера: `onboard_user` (`name`*, `profiles`), `diagnose_user` (`name`*), `safe_core_update` (`profile`*). Если задача совпадает — бери шаги оттуда, они согласованы с §4.

## 7. Коды ошибок моста и что делать

Результат с `isError: true` содержит `code`. Сначала — коды MCP-сервера и диспетчера моста, затем модульные.

| `code` | Откуда | Что значит | Что делать |
|---|---|---|---|
| `transport` | MCP-сервер | мост не запустился или не вернул JSON-строку (`exit_code`, `stdout_tail`, `stderr_tail` в ответе) | не повторять вслепую; показать хвосты человеку; проверить `server_status` — если и он падает, сервер сломан, дальше только человек по SSH |
| `timeout` | MCP-сервер | действие не уложилось в лимит (по умолчанию 300 с) и остановлено вместе с дочерними процессами | проверить состояние (`profiles_list`, `backup_list`): установка или обновление могли пройти наполовину — сообщить человеку; повтор только после проверки |
| `lock_timeout` | мост | другой интерфейс держит `config.lock` дольше 30 с (бот, панель, человек в меню, твой же долгий вызов) | подождать 10–30 с и повторить один раз; повторяется — сказать человеку, что что-то долго выполняется |
| `unknown_action` | мост | действия нет в `actions.json` моста — каталоги сервера и MCP разошлись (обновление наполовину) | не повторять; сообщить человеку: обновить goAmnezia на сервере |
| `not_implemented` | мост | действие есть в контракте, но модуля на сервере нет (неполная установка или старый релиз) | не ошибка вызова; сказать человеку, предложить SSH-меню или обновление |
| `module_missing` | мост | функции модуля нет — неполная установка (`lib/*.sh` не скопирован или модуль ещё не доехал) | сообщить человеку: обновить или переустановить goAmnezia; не повторять |
| `missing_arg`, `bad_arg` | мост | вторая линия проверки моста отвергла аргумент (схема MCP пропустила, регексы моста строже) | исправить значение по `message`; не перебирать варианты циклом |
| `invalid_name`, `invalid_port`, `invalid_profile`, `invalid_preset`, `invalid_label`, `invalid_subnet`, `invalid_format`, `invalid_number`, `invalid_argument` | модули | значение прошло схему, но нарушает правила продукта (подсеть пересекается, порт занят системой, пресет не для линейки) | прочитать `message`, предложить человеку другое значение |
| `subnet_legacy` | модуль (`profile_set_subnet`) | профиль подхвачен из старого контейнера `amnezia-awg` на `wg0`: его запуск знает только прежнюю подсеть, и после смены контейнер бы не поднялся | не повторять; сказать человеку, что сменить подсеть можно только новой установкой профиля (ключи перевыпустятся) |
| `params_invalid` | модуль (`profile_set_param`) | значение нарушает правила линейки — или правка сменила бы семейство линейки (например, снятие последнего 3.x-поля превратило бы 3.1 в 2.0); с 1.0.13 — или выходит за пределы (§8.2: коридор таймингов 3.1, всплеск мусора, `Jc` + число `I`, хвосты 3.1) | прочитать `message` — там допустимый диапазон; линейку правкой параметров не меняют — только новой установкой профиля |
| `param_rolled_back` | модуль (`profile_set_param`, с 1.0.13) | значение записалось, но не применилось (контейнер не поднялся, syncconf не прошёл): прежнее значение вернулось в настройки и конфиг сервера, профиль поднят | сказать человеку причину из `message`; ничего не повторять — профиль как до правки |
| `param_apply_failed` | модуль (`profile_set_param`, с 1.0.13) | не применилось, и поднять профиль с прежним значением тоже не вышло: настройки прежние, профиль лежит | `profile_repair` (поднять контейнер заново из копии состояния), затем `profiles_list`; сказать человеку |
| `no_profiles_picked` | мост (`user_add`) | в `profiles` пришла пустая строка. Отсутствующий параметр значит «во все установленные», а пустой — «ни одного», и молча понять его как «во все» значило бы завести ключи в линейках, которых никто не просил | назвать профили явно (`"profiles": "awg2,awg3"`) или **не передавать параметр вовсе**; через MCP пустая строка обычно до моста не доходит — её раньше отвергает схема (`-32602`: шаблон параметра требует хотя бы одно имя) |
| `port_taken`, `port_busy` | мост, модули | UDP/443 уже держит другой профиль (`message` называет его) или порт занят в системе; у `mode_set` в любой режим с сайтом — TCP/80 или 443 держит чужой процесс: в ответе `port`, `proto`, `process`, `pid`, `unit`, `container`, `product` (сосед серии: `gotelegram`, `govless`, `xui`, `amnezia`…), `hint` (`systemctl disable --now <юнит>` или `docker stop <контейнер>`) и `reasons[]` | профиль: предложить `profile_set_port` для того профиля или другой порт; режим: показать человеку `message` и `hint` — «освободите порт или используйте чистый сервер»; чужую службу сам не останавливай |
| `closed_local` | мост (`mode_set`) | TCP/80 или 443 свободен, но закрыт локальным файрволом (ufw, iptables, nftables); поля те же, `hint` — команда открытия (`ufw allow 80,443/tcp` и т. п.) | предложить человеку открыть порт (из SSH-меню мастер спрашивает «Открыть 80,443/tcp?» и делает это сам) и повторить `mode_set`; не режим `lite` |
| `pull_failed`, `rate_limit` | модуль Docker | образ не скачался: Docker Hub недоступен или лимит скачиваний | подождать и повторить позже; при `rate_limit` сказать человеку про `docker login` или зеркало |
| `unsupported_arch`, `preflight_failed` | мост, до действия | сервер не x86_64 (официальные образы только amd64), нет root или каталогов | ничего не повторять; сообщить человеку — это ограничение сервера |
| `deps_missing`, `actions_json_missing` | мост | нет `jq`, зависимостей или каталога действий | сообщить человеку: `goamnezia` из SSH доустановит зависимости |
| `install_failed`, `user_add_failed`, `key_failed`, `port_failed`, `restore_failed` и другие `*_failed` | диспетчер моста | шаг модуля не выполнился; подробности в `message` и в `logs_tail component=<профиль>` | один раз проверить состояние (`profiles_list`, `user_show`), показать `message`; при `install_failed` — `diagnose` |
| `user_not_found`, `user_exists`, `peer_not_found`, `peer_exists`, `profile_not_installed`, `profile_exists`, `no_profiles`, `no_private_key`, `subnet_full` | модули | состояние не такое, как предполагал вызов | обновить картину (`users_list`, `profiles_list`) и пересобрать план; `no_private_key` — §4.6 |

У `confirm_mismatch`, `nothing_selected`, `too_many` в ответе `matched` — сколько выбрано сейчас | `confirm_mismatch` — новый `users_del_bulk_preview`, показать человеку и спросить снова, `matched` в `confirm` сам не подставлять; `too_many` — части по 100 списком `names`; `user_del_failed` — `diagnose`, повтор тем же выбором после починки Docker; ничего из этого не повторять циклом |
| `names_exhausted`, `names_missing`, `invalid_prefix` | `name_suggest`, `users_add_bulk` | свободных случайных имён «прилагательное + столица» не осталось (или их меньше, чем людей); набора имён на сервере нет — неполная установка; префикс не по образцу | до изменений, никто не заведён: предложить человеку префикс (`<prefix>-01…`) или своё имя; `names_missing` — сказать человеку: обновить goAmnezia |

Порт не менялся | показать человеку `message`; сначала предложить привязать их старые ключи (`user_attach_key`); перенос всё равно — повтор с `adopted_confirm` = имя профиля, только по его явному согласию |

| `key_mismatch`, `server_mismatch`, `already_has_key`, `config_unreadable`, `no_config` | `user_attach_key` | ключ не этого человека (в сообщении — чей), не этого сервера, уже есть, не читается или не передан | показать человеку сообщение как есть; ключ другого человека — привязать в его карточке |

У `user_get_key` с `endpoint` три из них — отказ разовой выдачи (§4.9): `address_not_here` — такого адреса или домена у сервера нет (в `message` — какие можно), `addresses_unknown` — спрошен IP, машина своих внешних адресов не видит, а среди известных ей хостов его нет, `invalid_ip` — не IPv4 и не домен или 0.0.0.0 | `address_not_here` — предложить человеку адрес из `message`; `addresses_unknown` — сказать, что на этом сервере свой адрес не задаётся, общий вернуть можно; `address_gone` — `user_set_address` с живым адресом или пустой строкой, затем `user_get_key` (сразу выручает и разовый ключ на живой адрес — `endpoint`, §4.9); отказ по `endpoint` — взять хост из `message`, `edge_status.key_choices` или `server_status.key_hosts`; не перебирать адреса циклом |
| `not_pro`, `needs_site`, `no_domain`, `panel_disabled` | мост (режимы с сайтом) | `not_pro` — нет **домена с доверенным сертификатом**; несмотря на имя, код про сертификат, а не про название режима: `panel_domain_enable` / `panel_domain_rotate` работают в обоих режимах с сайтом и отказывают в `lite` и на запасном самоподписанном. В ответе `mode`, `cert`, `domain` и `reason` (`no_site` \| `no_domain` \| `untrusted_cert`) — та же тройка, что у `panel_status`. `needs_site` — действию нужен режим с сайтом (`site_set_template` в `lite`). `no_domain` — действию нужен домен, а в конфиге его нет (`mode_set` домена не требует: без него сайт поднимается на запасном самоподписанном). `panel_disabled` — панель выключена (`panel_domain_rotate`) | посмотреть `panel_status` (`reason`, `hint`) и предложить ровно тот шаг, которого не хватает: `mode_set` в режим с сайтом, домен и настоящий сертификат — через человека, `panel_domain_enable`; не повторять вызов как есть |
| `invalid_domain`, `cert_failed`, `cert_missing`, `nginx_install_failed`, `nginx_conf_invalid`, `nginx_reload_failed`, `enable_failed`, `disable_failed` | `lib/website.sh` через мост | режим не переключился: домен не валиден, Let's Encrypt отказал (A-запись не на сервер, закрыт 80/tcp, лимиты), `nginx -t` отверг конфиг (прежний файл возвращён; при переходе в `lite` — сайт НЕ снят: без перезагрузки nginx отдавал бы его дальше, ошибка в чужом конфиге того же nginx) | режим остался прежним, домен сохранён; показать `message` — у `cert_failed` в нём уже названа причина: проверка домена (A-запись, порт 80), исходящая сеть самого сервера до Let's Encrypt (повторить через несколько минут) или лимит выдачи (ждать час), а у смены домена живого сайта — что домен возвращён на прежний; не повторять `mode_set` циклом — у Let's Encrypt лимит 5 выпусков в неделю. Примечание: модульные коды (`invalid_*`, `port_busy`, `user_exists`, `pull_failed` …) мост может отдавать внутри `message`, а в `code` ставить код-обёртку `*_failed`. Смотри оба поля.

## 8. Ограничения продукта (обойти нельзя)

### 8.1 Линейки и клиенты

- Линейки AmneziaWG несовместимы между собой. Один профиль = один набор параметров = одна линейка = один контейнер на своём порту. Ключ выдаётся на пару «пользователь, профиль».
- Выбор профиля по клиенту: приложение Amnezia ≥ 5.0.1.5 → `awg3` или `awg2`; 4.8.12.9 – 5.0.1.4 → `awg2`; 4.8.8.1+ → `awg1` (1.5); роутеры Keenetic/MikroTik/OpenWrt, ядерный модуль, wg-easy → `awg1` (1.0, пресет `router`). Всегда называй `min_client` из ответа `user_get_key`.
- Официальное приложение Amnezia, добавив сервер по SSH, видит только `amnezia-awg2` (профиль `awg2`); `amnezia-awg3` и `amnezia-awg1` оно молча пропускает. goWARP PRO видит все `amnezia-awg*`.
- Один пользователь может иметь по одному пиру в каждом профиле (`user_add_profile`).

### 8.2 Параметры маскировки

- Серверные (`S1–S4`, `H1–H4`, `HeaderProtectionKey`, `RandomTrailers`, `DisableCookies`) → после смены обязателен перевыпуск ключей всех пользователей профиля. Клиентские (`Jc`, `Jmin`, `Jmax`, `I1–I5`, `MTU`, `PersistentKeepalive`, `RekeyAfterTime`, `RekeyTimeout`, `RejectAfterTime`, `KeepaliveTimeout`, `MaxHandshakeAttempts`, `ContentPaddingAddition`) → только новые выдачи.
- Правила валидатора: `H1–H4` попарно различны (для 2.0 — непересекающиеся диапазоны `a-b`); `1 ≤ Jc ≤ 128`; `Jmin < Jmax ≤ 1280`; `S1 ≤ 1132`, `S2 ≤ 1188`, `S1 + 56 ≠ S2`; при `HeaderProtectionKey` все `S ≥ 12`; линейка 1.0 не принимает `I*`, `S3`/`S4`, диапазоны и 3.x-поля; 2.0 не принимает 3.x-поля (`HeaderProtectionKey`, `RandomTrailers`, `DisableCookies`, тайминги). Значение не по правилам → `invalid_*` или `param_set_failed`, ничего не меняется.
- `MTU`: 1280 — стандарт и минимум (ниже туннель не поднимется у клиентов с IPv6), на проводном интернете — до 1320; пакет MTU + 80 + S4 больше 1440 на части хостеров и сетей не пройдёт.
- Пределы записи (с 1.0.13, живые проверки): тайминги 3.1 — `RekeyAfterTime` 60–120, `RekeyTimeout` 3–10, `RejectAfterTime` 150–180, `KeepaliveTimeout` 5–15, `MaxHandshakeAttempts` 10–30 (оба конца «a-b»), `ContentPaddingAddition` 0–1400; `Jc × Jmax` ≤ 16384 байт; `Jc` + число заданных `I1–I5` ≤ 127; при `RandomTrailers` суммарная ширина `H1–H3` у тех, чей `S` ≠ `S4`, ≤ 2²⁰. Проверяется только то, что ломает или ухудшает записываемый ключ: у подхваченного профиля с чужими значениями другие параметры меняются. Новые 3.1 получают `ContentPaddingAddition 10-100` и `PersistentKeepalive 25`; выданные профили не трогаются.

### 8.3 Порты и сеть

- UDP/443 — только у одного профиля; в `pro` его по умолчанию занимает `awg2`, в `lite` и `lite_site` профили получают случайный порт 30000–49999. Сайт в обоих режимах с сайтом живёт на TCP/443 и TCP/80 — это другие сокеты, с UDP/443 конфликта нет. Проверяй `profiles_list`, не предполагай.
- Панель на домене (`panel_domain_*`) требует **домена с доверенным сертификатом Let's Encrypt**, а не конкретного режима: она работает и в `pro`, и в `lite_site`, и отказывает (`not_pro`) в `lite` и на запасном самоподписанном сертификате. Пока её нет, человек заходит в панель через SSH-туннель. Доступы агентов по HTTP живут в обоих режимах с сайтом, и адрес зависит от того, чем сайт отдаётся сейчас: домен с Let's Encrypt → `https://<домен>/…`, запасной самоподписанный → `https://<IP>/…`, и клиент доверяет ему по отпечатку из `server_status`.
- Смена порта не меняет ключи, но старые `.conf`/`vpn://` содержат старый порт.
- Ключ на другой адрес сервера (`user_get_key` с `endpoint`) не заводит второго пира: одна пара ключей — один пир, и тот же ключ одновременно с двух адресов или устройств «прыгает» (§4.9). Адрес для него — только хост этого сервера (`edge_status.key_choices`, `server_status.key_hosts`).
- Подсети профилей частные (`10.x`, `172.16–31.x`, `192.168.x`), `/20`–`/24`, не пересекаются между профилями и с `172.29.172.0/24` (`amnezia-dns-net`).
- Сервер только x86_64 (официальные образы Amnezia собраны под amd64); публичный IPv4; Docker, не podman.

### 8.4 Секреты и доступ

- Приватные ключи, `.conf`, `vpn://`, QR — только из `user_get_key`, только по просьбе человека. `users_list` и `user_show` ключей не содержат. В аудит попадают параметры вызова, но не ответ.
- Ты не можешь выдавать, продлевать, усиливать, привязывать к адресу, включать и отзывать доступы агентов и включать HTTP-транспорт MCP: действий `agent-*` и `mcp-http-*` у тебя нет (в каталоге они помечены `mcp: null`). Это делает человек из SSH-меню, бота или панели. Если тебе не хватает уровня — попроси человека выдать другой доступ, не ищи обходных путей.
- Так же закрыты для тебя (в каталоге — `mcp: null`) действия с адресами-секретами и служебные: подписка — создать, показать, перевыпустить и отозвать (`sub-create`, `sub-show`, `sub-rotate`, `sub-revoke`; у тебя только `sub_list` без адресов); короткие ссылки подписки и их подтверждение через Telegram-бота (`short-*`); временные ссылки на файл ключа (`share-*`); Ленивый Pro и выбор линии на UDP 443 в Pro (`lazy-check`, `lazy-setup`, `pro-line`); тики таймеров (`*-tick`). Всё это — у человека в SSH-меню, боте или панели; не ищи их через другие инструменты.
- По HTTP-транспорту у доступа есть уровень (§10): инструменты вне уровня не показываются, вызов по имени → `forbidden`. Адрес подключения (`https://…/a-<секрет>/mcp`) и токен из заголовка `Authorization` — два ключа: не выводи их в ответы, сводки и файлы и не собирай в одну строку.
- Адрес панели на домене (`url` из `panel_domain_enable` / `panel_domain_rotate`) — секрет того же порядка, что ключ: покажи его только человеку, который попросил, не повторяй в сводках и не пиши в другие каналы. `server_status` и `panel_status` его не отдают намеренно.

### 8.5 Чего в продукте нет

goAmnezia — продукт только про AmneziaWG. Протокола VLESS/Reality и ядра Xray в нём нет и
не будет (решение владельца 09.09.2026): для VLESS в серии есть отдельный продукт — goVLESS.
Если человек просит VLESS-ключ, скажи это прямо и не ищи инструмент.

## 10. Уровни доступа по HTTP

При подключении не по SSH, а по HTTP-адресу у доступа есть уровень — он назван в `initialize.instructions`. Форма адреса зависит не от названия режима, а от того, чем сайт отдаётся сейчас: `https://<домен>/a-<секрет>/mcp` — сайт на домене с Let's Encrypt (любой из двух режимов с сайтом); `https://<IP>/a-<секрет>/mcp` — запасной самоподписанный сертификат; `https://<IP>:<порт>/a-<секрет>/mcp` — `lite`, отдельный TLS-слушатель на своём порту.

| Уровень | Что видно в `tools/list` | Чего нет |
|---|---|---|
| `read` (умолчание при выдаче) | инструменты только для чтения (R), **кроме** `user_get_key` | всё изменяющее и выдача приватных ключей клиентов |
| `write` | R + W, включая `user_get_key` — то есть приватный ключ любого клиента | разрушительные (D) |
| `admin` | всё (разрушительные — с `confirm`) | — |

Инструменты вне уровня не показываются (подсказки — только те, все шаги которых доступны); вызов по имени → JSON-RPC `-32003` `forbidden` — это не сбой, а граница доступа: скажи человеку, какого уровня не хватает.

**Доказательств два.** Кроме секретного адреса у доступа есть токен, который клиент шлёт заголовком `Authorization: Bearer <токен>`. Адрес утекает буднично (снимок экрана, пересылка, история браузера, журнал прокси), заголовок — нет, поэтому одного адреса мало. И адрес, и токен — секреты одного порядка: **не выводи их в ответы, сводки, логи и файлы**, не повторяй в чате и не складывай в одну строку «для отправки». Если человек просит показать доступ — отправь его к SSH-меню, боту или панели: у тебя действий `agent-*` нет.

Отзыв мгновенный и без предупреждения. Выключенный, истёкший, перевыпущенный доступ, запрос не с разрешённого IP, не с закреплённого адреса (`pin_ip`) или без верного токена — всё это на любой запрос даёт `404` с телом nginx, **одинаковый и неотличимый**: сервер намеренно не подтверждает, что путь существует (`401` подсказал бы сканеру, что он нашёл живой адрес). Если `404` случился посреди работы, сообщи человеку и остановись: не пытайся подбирать адрес, не перебирай варианты заголовка, не считай это сетевым сбоем. Вероятные причины по порядку: доступ отозвали или он истёк (по умолчанию срок 30 дней), доступ усилили токеном (`agent-harden`) и клиенту нужно добавить заголовок, агент переехал на другой IP при включённой привязке.

**Одноразовый ключ (`mode: rolling`).** У части доступов второй фактор не постоянный: сервер шлёт в каждом ответе заголовок `X-Ga-Next-Key`, и следующий запрос обязан нести именно этот ключ в заголовке `X-Ga-Key` плюс свой одноразовый номер в `X-Ga-Nonce` — **8–64 знака из латинских букв, цифр, дефиса и подчёркивания, свой на каждый новый запрос** (короче или с другими знаками — запрос отвергается тем же неотличимым отказом, что и чужой ключ). Правила для тебя, если твой клиент работает так:

* **Ключ живёт один запрос.** Сохрани выданный ключ до отправки следующего запроса и не используй ключ повторно: сервер держит историю выданных, и повторно пришедший ключ он считает копией доступа на чужой машине — доступ замораживается, владельцу уходит тревога.
* **Повтор — только дословный.** Если ответ не доехал, повтори тот же запрос с тем же `X-Ga-Key` и тем же `X-Ga-Nonce`: сервер вернёт сохранённый ответ и не выполнит действие второй раз.
* **Одновременность разрешена, запоздание — нет.** Запросы, посланные разом (так делают списки инструментов, ресурсов и подсказок сразу после `initialize`), сервер различает: тот, что пришёл раньше, чем ушёл ответ с новым ключом, выполняется и получает **тот же** новый ключ. А вот тот же ключ с другим номером, посланный уже ПОСЛЕ полученного ответа, — второй запрос сожжённым ключом, и это заморозит доступ. Правило простое: получил новый ключ — дальше только им.
* **Один доступ — один клиент.** Не подсовывай один и тот же ключ двум клиентам и не клади файл ключа в синхронизируемую папку: копия неизбежно придёт с сожжённым ключом, и честная настройка будет объявлена кражей.
* **Замороженный доступ отвечает тем же `404`.** Подбирать ничего не нужно: скажи человеку, что доступ заморожен по подозрению на клон, и что решение — «перевыпустить» или «отозвать» в SSH-меню, боте или панели.

**Переходник (`mode: connect`).** Если тебя подключили командой `goamnezia-connect --grant a-…`, всё перечисленное выше — ключ, номер попытки, плавающий путь, сверку времени — делает переходник, а ты работаешь с ним как с обычным stdio-сервером MCP. Ошибка переходника приходит обычной ошибкой JSON-RPC с объяснением для человека: передай её дословно. Не запускай второй экземпляр переходника на том же доступе и не пытайся привязать доступ заново — код привязки одноразовый, и он есть только у владельца.

Запасному самоподписанному сертификату (сайт на IP или отдельный порт в `lite`) клиент доверяет по отпечатку SHA-256, который человек получает из меню или из `server_status` (`NODE_EXTRA_CA_CERTS`, см. README). На домене с Let's Encrypt доверять вручную нечему.

## EN summary

goAmnezia pro manages the server side of AmneziaVPN: official Docker containers, three AmneziaWG lines as separate profiles (`awg2` = 2.0, default, the only one the Amnezia app sees; `awg3` = 3.1; `awg1` = 1.0/1.5 for routers), each on its own UDP port. VLESS/Reality is out of scope by the owner's decision — there is a separate product for it. This MCP server is the fourth interface after the SSH menu, the Telegram bot and the web panel; every tool is one bridge action `install.sh --action=<name> --json`, serialised by one lock (`lock_timeout` after 30 s).

Rules:

1. Start with `server_status` and `profiles_list`; use `users_list` / `user_show` for user tasks, `diagnose` and `traffic_report` for symptoms. Do not change what you have not looked at. Modes: `lite` — AmneziaWG only, no site; `lite_site` — domain, cover site and panel on TCP/443 with a real Let's Encrypt certificate, AmneziaWG on its own UDP port; `pro` — exactly the same, only AmneziaWG sits on UDP/443 next to the site. The two site modes differ **solely in where AmneziaWG is**: site, domain, certificate and panel are shared, and `lite_site ↔ pro` touches neither nginx nor the certificate. A self-signed certificate is **not** a property of a mode but a fallback used by either of them while there is no domain yet (or its A record does not point here): the site is then served over the IP, `site.cert = selfsigned`, the reply carries `cert_fingerprint_sha256`, and the panel on the domain stays off. In both site modes the status carries a `site` block (`url`, `domain` — filled while the site is on the domain with Let's Encrypt, empty on the fallback, template, `cert` = `letsencrypt` / `selfsigned`, `cert_fingerprint_sha256` for the self-signed one, `panel`, `alt_svc`). Judge what is possible by `cert` and `domain`, never by the mode name. `server_status` also carries the alarms `disk` (`level` `low` / `critical`), `docker_stale` (the Docker package was updated but the service is old — `docker_restart`, or wait: the watchdog does it when nobody is connected), `update_rollback` and per profile `packet_risk` (not `null` — the data packet at the standard MTU 1280 is larger than 1400 because of a large S4, downloads stall on mobile internet and PPPoE: tell the human and point to the «Fix S4» button in the SSH menu, panel or bot — there is no tool for it; a manual `S4` above 40 is refused with `params_invalid` (new 2.0 profiles and «Fix S4» pick S4 12–24 themselves, since 1.0.13); each of `I1–I5` written by `profile_set_param` must start with `<b 0x…>` (KeeneticOS 5.1 rejects any other start), otherwise `params_invalid` with advice; MTU 1280 is the standard and the minimum — below it `profile_set_mtu` is refused in words (the tunnel will not come up for clients with IPv6, `AllowedIPs ::/0`), up to 1320 on wired internet, and it answers with `warnings` `path` when the MTU + 80 + S4 packet is larger than 1440); `brief: "on"` gives a short status for frequent polling (no `ports`, `site`, `key_hosts`, `endpoint_effective`, `endpoint_auto`, `mode_port_mismatch`). `profiles_list` → `port_published: false` means the container runs but Docker did not publish its port: `profile_repair`.
2. Before every mutating call tell the human what will change. Destructive tools (`profile_remove`, `profile_regen`, `profile_set_param`, `profile_set_subnet`, `profile_restart`, `profiles_restart` (confirm = `profiles_restart`), `docker_restart` (confirm = `docker_restart`; the VPN drops for everyone for 10–30 s, the watchdog does it by itself when nobody is connected), `user_delete`, `users_del_bulk`, `user_remove_profile`, `user_reissue_key`, `backup_restore`, `upstream_update`, `upstream_rollback`, `core_update`) need explicit consent and `confirm` equal to the first parameter's value; a mismatch is rejected with `-32602` before the bridge runs. The exception is `users_del_bulk`: its own `confirm` is the **number of people** the human saw in `users_del_bulk_preview` and agreed to (a string, `"12"`); the server checks it at the moment of deletion under the lock, and a selection that now covers a different number is refused with `confirm_mismatch` before any change (`matched` in the reply).
3. Keys come only from `user_get_key` (`.conf`, `vpn://`, QR as images, plus `line` and `min_client`). Never forward private keys anywhere but to the human who asked. A connection page (`page_create` → `url`, `page_url`) is a secret of the same order: whoever has the link gets the keys; it needs a domain with a trusted certificate (`pages_need_domain` otherwise), lives for `ttl` (`1h…720h`, `1d…365d`, `forever`) and dies with `page_revoke` / `page_revoke_all` (D). `sub_list` (R) shows per-person subscriptions — permanent links to all of a person's keys (`all.yaml` for Clash Verge Rev, FlClash, Mihomo Party; `all.txt` for incy and AWG Manager; `.conf` and `vpn://` per line for routers and apps) — without addresses (`count`, `domain_ready`, `update_interval`); you never get a subscription address: only a human creates, shows, rotates or revokes one (SSH menu, bot, panel, mini app). Their short links (an 8-character code, a login from a new address is confirmed by an administrator in the Telegram bot) are human-only too: no codes, confirmations or bans for you. `clients_list` is the app catalog per platform and line; `mirror_fetch` / `mirror_list` / `mirror_remove` (D) keep official open-source builds on our server (GitHub release, sha256 verified; `mirror_unverified` means the source gave no checksum — never bypass it).
4. Lines are incompatible: a key belongs to one profile. Pick the profile the client supports (app ≥ 5.0.1.5 → `awg3`/`awg2`; 4.8.12.9+ → `awg2`; routers → `awg1`).
5. Server-side parameters (`S1–S4`, `H1–H4`, `HeaderProtectionKey`, `RandomTrailers`, `DisableCookies`), `profile_regen` and `profile_set_subnet` invalidate every key of the profile: back up, warn, get consent, then reissue with `user_get_key` for each user. `profile_set_port` keeps keys but the old `.conf`/`vpn://` carry the old port — resend them; on a profile adopted from the Amnezia app whose people have no keys on the server it is refused with `adopted_keyless` (they cannot get new configs) until `adopted_confirm` equals the profile name — pass it only after the human read that `message` and agreed. `endpoint_set` needs `host` explicitly: an empty string means the default (the server domain in Pro, otherwise its IP). UDP/443 can be held by one profile only (`port_taken`). `user_set_address` keeps the keys and changes only the address in the Endpoint line: with `resend_required: true` issue the key again (`user_get_key`) and send it; `domain_endpoint: true` means the user's keys carry a manually set domain and the address changes nothing (the default domain in Pro does not override an own address); `address_gone` from `user_get_key` means the user's own address left the machine — move them with `user_set_address` first. Since 1.0.13 `profile_set_param` refuses values outside the limits with `params_invalid` and the allowed range in words (3.1 timings and `ContentPaddingAddition` within a corridor around the app values, `Jc × Jmax` ≤ 16384, `Jc` + number of `I1–I5` ≤ 127, with `RandomTrailers` no wide `H` for `S` that differ from `S4`) — take the range from `message`, do not probe values; a value that did not apply is put back (`param_rolled_back`; `param_apply_failed` — the profile is down, `profile_repair`); `clients_update` and `result.steps` say who needs a new config (subscriptions update by themselves, `vpn://` keys and `.conf` files — `user_get_key` again). `import_adopt` reports such values of an adopted container in `param_warnings` and adopts it anyway.
6. Typical orders: onboard — `profiles_list` → `users_list` (no name given — `name_suggest` gives an unused «adjective + capital» `id` and `label`) → `user_add` (omit `profiles` to get peers in every installed profile; an **empty string is a refusal**, `no_profiles_picked`, not "all" — over MCP the schema rejects it even earlier with `-32602`) → `user_get_key` → `user_show`; several at once — `users_add_bulk` (`count` 1–100, `prefix` gives `<prefix>-01…`, otherwise random «adjective + capital» names; one apply to the containers; `subnet_full` / `names_exhausted` refuse before any change; `partial: true` with `failed` — stopped midway, the people added stay; no keys in the reply); several deleted at once — `users_del_bulk_preview` (exactly one of `names` 1–100 / `prefix` — every `<prefix>-<number>` the way `users_add_bulk` makes them / `state` — `disabled` turned off by hand, `expired`, `quota`) → show the human `selected` and `count` → consent to that number → `users_del_bulk` with `confirm` = `count` (the order of `user_delete` in batches of 10; `confirm_mismatch` — the list changed, preview again; `too_many` — more than 100, split by `names`; `partial: true` — a batch was not accepted by the container and stays in the list turned off (`kept`), or the call was interrupted); cannot connect — `user_show` → `traffic_report` → `profiles_list` → `diagnose` → `logs_tail`; core update — `upstream_check` (first non-draft GitHub release, newest versioned Docker Hub tag, changed scripts, `unsupported[]` placeholders, per-profile `current_tag → available_tag`) → `backup_create` → `upstream_update` (backup, release scripts, image by digest, container recreated from the state copy, verification, and a rollback **attempt** on failure — the two outcomes differ, see 7) → verify → `upstream_rollback` if needed (`no_previous` when nothing to roll back to); `core_update` recreates the container on the pinned image (repair); restore — `backup_list` → `backup_create` → `backup_restore` (it also takes «Delete everything» copies `goamnezia-wipe-*`; the current panel password, bot settings and agent grants stay — `kept_current`, `agents_not_restored`; `server_ip_changed: true` means keys with the old IP are out of date); import — `import_scan` → `import_adopt` (adopted users have no private key: reissue via `user_remove_profile` + `user_add_profile`) → later `import_reconcile` (`apply: "on"`) when the Amnezia app changed peers directly. The prompts `onboard_user`, `diagnose_user`, `safe_core_update` give the same steps.
7. Error codes: `transport`/`timeout` (server) → check state, do not retry blindly; `lock_timeout` → wait and retry once; `unreachable` → GitHub/Docker Hub unreachable from the server, retry later (rollback still works); `already_current`/`tag_not_found`/`no_previous`/`already_managed`/`not_adoptable`/`unsupported_container`/`container_missing` → state conflict, refresh the picture; a failed core update comes back as one of two different codes — `update_failed` means the rollback **was** done, the state is unchanged and nobody has to intervene, while `update_failed_no_rollback` means it was **not**: the container is gone and not running, the profile is down, so stop, tell the human they are needed over SSH, and offer `backup_restore` from the backup the update itself made; `no_profiles_picked` → `user_add` got an empty `profiles` string, name the profiles or omit the parameter; `module_missing`/`unknown_action` → installation incomplete, tell the human; `missing_arg`/`bad_arg`/`invalid_*` → fix the value; `port_taken`/`port_busy` → another port, or (for `mode_set`) TCP/80 or 443 is held by a foreign process named in `process`/`unit`/`container`/`product` — show `message` and `hint` to the human, never stop the neighbour yourself; `closed_local` → the port is free but closed by the local firewall, `hint` carries the opening command (the SSH wizard can open it); `pull_failed`/`rate_limit` → retry later; `unsupported_arch`/`preflight_failed` → server limitation; `not_pro` → despite the name this is about the **certificate, not the mode**: the action needs a domain with a trusted Let's Encrypt certificate, so it works in both site modes and is refused in `lite` and on the self-signed fallback; the reply carries `mode`, `cert`, `domain` and `reason` (`no_site` / `no_domain` / `untrusted_cert`) — read `panel_status` and propose exactly the missing step; `needs_site` → the action needs a site mode (`site_set_template` in `lite`); `no_domain` → the action needs a domain that is not in the config (`mode_set` does not require one — without it the site comes up on the self-signed fallback); `panel_disabled` → enable the panel first; `unknown_template`/`download_failed`/`no_index`/`app_shell`/`broken_assets` → pick another template, the old site is untouched; `cert_failed`/`nginx_conf_invalid` → the site did not come up on the domain, show `message`, do not loop (Let's Encrypt rate limits); for `cert_failed` the `message` already names the cause — the domain check (A record, port 80), the server's own outgoing network to Let's Encrypt (retry in a few minutes) or a rate limit (wait an hour); `selfsigned_failed`/`tls_dir_failed`/`no_server_ip` → the self-signed fallback did not come up, show `message`; `*_failed` → read `message`, check state; `adopted_keyless` → see rule 5; `port_unpublished` → `profile_repair`; `docker_still_stale` → only a reboot helps, the human decides; `docker_restart_failed`/`docker_restart_timeout` → show `message` and the manual `command`, do not retry; `restart_failed` → `profile_repair` for the profiles in `failed`; `docker_unreachable` (`import_scan`) → Docker does not answer, which is not «no containers»; `names_exhausted`/`names_missing` → suggest a prefix or an own name; `forbidden` (`-32003`) → tool outside your HTTP access level (`read` / `write` / `admin`).
8. Modes: `mode_set` switches between `lite`, `lite_site` and `pro` in any direction without touching containers or keys (the reply carries `previous_mode`); `preflight_modes` tells beforehand who holds TCP/80 and 443, which both site modes need free and reachable. It does **not** move the AmneziaWG port: `mode_set pro` alone does not put a profile on UDP/443 and `mode_set lite_site` does not take it off — that is a separate `profile_set_port`. Going from `lite` into either site mode installs nginx, issues the Let's Encrypt certificate once for the domain (from `domain` or from the config) and deploys a random cover-site template if there is no site yet; with no domain at all the site comes up on the self-signed fallback over the IP (browsers warn — expected, the site is for scanners, not people; trust it by `cert_fingerprint_sha256`), which is a legitimate state, not a refusal. `lite_site ↔ pro` **without `domain`** touches neither the site, the domain, the certificate nor the panel — certbot is not called at all; passing `domain` from a site mode is a move to another domain and does issue a new certificate, so send it only when the human asks to change the domain. `site_set_template` changes the template, `site_check` verifies the site from outside (DNS and the Let's Encrypt certificate on the domain, plain reachability over the IP on the fallback; in `lite` the verdict is `not_pro`, meaning "no site at all"), `site_alt_svc` toggles the HTTP/3 announcement (warn about the browser fallback delay). `panel_domain_enable` / `panel_domain_rotate` need a domain with a trusted certificate — they work in **both** site modes and are refused with `not_pro` in `lite` and on the fallback — and return the panel `url` under a secret `app-<86 chars, 512 bits>` path: show it only to the human who asked, never repeat it elsewhere; `panel_domain_disable` takes the panel off the domain in any state. `panel_status` distinguishes `enabled` (the panel really works), `configured` (the path is written down) and `available` (it can be enabled here at all), plus `reason` (`no_site` / `no_domain` / `untrusted_cert`) and `hint` — when `available` is false, never suggest enabling it.
9. You cannot manage agent grants or the HTTP transport (`agent-*`, `mcp-http-*` are `mcp: null` and not published); humans do that from the SSH menu, bot or panel. Not published either: subscription management (`sub-create`, `sub-show`, `sub-rotate`, `sub-revoke`), short links (`short-*`), temporary file links (`share-*`), Lazy Pro and the Pro line on UDP 443 (`lazy-check`, `lazy-setup`, `pro-line`) and timer ticks (`*-tick`). Over HTTP (`https://…/a-<secret>/mcp` plus an `Authorization: Bearer <token>` header — two independent proofs) your grant has a level — `read` (the default: read-only tools, no `user_get_key`), `write` (plus every client's private key), `admin` (everything); tools outside it are hidden, a call by name gets `-32003` `forbidden`. A revoked, expired, rotated, hardened (token added) or address-pinned grant, and any request without the right token, get the same indistinguishable `404` on the next request — stop and tell the human, never probe for the URL or the header. Both the URL and the token are keys: never print them. Every call is audited. Some grants use a one-shot key (`mode: rolling`): every answer carries an `X-Ga-Next-Key` header and the next request must send exactly that key in `X-Ga-Key` plus its own number in `X-Ga-Nonce` (**8–64 characters of Latin letters, digits, hyphen and underscore, a fresh one for every new request** — anything shorter or with other characters is refused by the same indistinguishable answer as a wrong key). Never reuse a key — the server keeps a history of issued keys and treats a returning one as a copy of the grant on a foreign machine: the grant is frozen and the owner is alerted. Repeat a lost request verbatim (same key, same nonce) and you get the saved answer without the action running twice; requests sent at the same time (before the answer with the new key has left) are let through and get that same new key, but the same key with a different nonce sent AFTER you already had the answer freezes the grant — once you have a new key, use only that one. Never share one grant between two clients, and never keep the key file in a synchronised folder. A grant of kind `connect` runs through the `goamnezia-connect` connector: it keeps the key, the nonce, the rotating path and the clock sync for you, so you talk to it as to a plain stdio MCP server; pass its JSON-RPC errors to the human verbatim, never start a second connector on the same grant and never try to enroll again — the enrollment code is single-use and only the owner has it.
10. Key for another server address (one-off, docs/EDGEIPS.md §3.4): `user_get_key` takes an optional `endpoint` — an IPv4 of this server or its configured domain. The key pair and the profile port stay the same, only the server address inside changes, and nothing is saved for the user; empty or absent gives the usual address, the key byte for byte as before. Every `user_get_key` answer now carries `key_host` (the host in this key), `key_endpoint` (`<host>:<profile port>`) and `key_host_override` (`true` for a one-off address). Only hosts of this server are accepted: `address_not_here` (the `message` lists the allowed ones), `addresses_unknown` (an IP was asked, the machine cannot see its external addresses and does not know that IP), `invalid_ip` (not an IPv4 or a domain, or 0.0.0.0). Where the choices come from: `edge_status` → `keys_host` (the usual common address) and `key_choices[]{host, kind, default, verdict, users, in_dns}` — exactly the hosts `endpoint` accepts: the default one first, then domains, then IPs, silent (`dark`) ones last; `verdict`/`users` only with two or more addresses; `server_status` → `key_hosts`; `user_show` → `key_host` (this user's usual address, pinned one included) and `key_host_gone` (the pinned address has left the machine: a normal key is refused with `address_gone`, a one-off one still works). Typical task «an address went `dark`»: `edge_status` → pick a `key_choices` entry with `verdict: ok` (or a domain) → `user_get_key` with `endpoint` → hand the key over under the usual secret rules → if the person should stay there, pin it with `user_set_address` (then `resend_required`), because the watchdog counts people by the address of their usual keys (the pinned one, else the common one; domain users by A records) and never sees one-off keys. One key pair is one peer: the same key used at the same time from two addresses or devices flaps — for simultaneous devices create separate users.

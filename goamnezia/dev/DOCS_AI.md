# goAmnezia pro — техническая документация для ИИ-агента

Для агента, который будет дорабатывать продукт. Здесь: что читать в каком
порядке, инварианты, которые нельзя нарушать, история решений и граблей,
пошаговые рецепты и список мест, куда лезть не надо.

Начат на 0.1.0 (коммит `57579c5`); история решений в §3 дописывалась до 0.5.x, дальше — в документах по
областям и в итогах выпусков. Веток две: `main` — стабильная, её ставит `bootstrap.sh` по умолчанию (сейчас 1.0.11);
`dev` — экспериментальная (`GOAMNEZIA_BRANCH=dev`, сейчас 1.0.13), выпуски сначала идут в неё (§6, «Выкладка»).
Актуальное состояние продукта — [docs/MAP.md](docs/MAP.md); прежний `AUDIT.md` — в
[docs/archive/](docs/archive/README.md). **При расхождении любого документа с кодом верить коду.**

> **Последняя работа (15–17.10.2026, 1.0.13 в `dev`)** — [docs/RELEASE_1.0.13.md](docs/RELEASE_1.0.13.md): исправление
> «нет 2.0», ключи «остальным» от сервера, отзыв страницы с подпиской и ключами, имена файлов, подписки, новые поля
> моста с местами в коде и тестами, быстрый путь и отпечаток, как проверялось, что осталось и с чего начать.
> 29.10 (KEENETIC-I1 + S4-MARGIN): универсальный I1 по умолчанию и правило `<b` первым, миграция прежнего умолчания,
> S4 новых профилей 12–24 — §3 п. 34–35 ниже и тот же RELEASE_1.0.13.md.

## 0. Быстрый старт

**Перед любой правкой — [docs/MAP.md](docs/MAP.md):** где каждая функция живёт в SSH-меню, боте, панели и MCP, чек-лист «что ещё поправить» и правила владельца.

### Что прочитать, в этом порядке

1. **[docs/MAP.md](docs/MAP.md)** — что есть сейчас и где что живёт; открытое — `docs/FINDINGS_TRACKER.md`
   (точка продолжения — вверху); итог последнего выпуска — [docs/RELEASE_1.0.13.md](docs/RELEASE_1.0.13.md).
2. **`docs/CONTRACT.md`** — контракт модулей: раскладка на сервере, схемы
   `config.json` / `users.json`, сигнатуры всех функций, правила диспетчера,
   переменные окружения стендов. Это источник правды по интерфейсам между
   модулями; менять контракт — только правкой этого файла **до** кода.
3. **`lib/actions.json`** — единый каталог действий моста (на 1.0.13 — 121, из них 75 публикуются
   агентам MCP; у остальных `"mcp": null`, а отдельные параметры закрыты `"mcp": false`). Из него строятся
   диспетчер, инструменты MCP, проверки ввода в панели.
4. Дальше по нужде: `docs/MENU.md` (дерево SSH-меню с именами функций и ключами
   словаря), `docs/BOT.md`, `docs/PANEL.md`, `docs/PRO.md` (режимы с сайтом),
   `docs/PREFLIGHT.md` (проверка портов), `goamnezia-mcp/README.md` и
   `AGENT_GUIDE.md`.
5. `NEIGHBOURS.md` — что продукт обещает соседям по серверу. Читать **до**
   любой правки, которая занимает порт, пишет в `/etc` или трогает `/var/log`.
6. `PLAN.md` и `SPRINTS.md` — плановые, местами устарели (см. `docs/archive/AUDIT.md` §15 п. 10).

Шапка каждого модуля `lib/*.sh` — это его собственный отчёт: зачем модуль,
что делает иначе, чем приложение Amnezia, и почему. Начинать правку модуля надо
с его шапки.

### Как гонять проверки

Перед пушем — одна команда, и она должна быть зелёной целиком:

```bash
BASH5=/opt/homebrew/bin/bash bash tests/run_static.sh
```

Внутри: самопроверка отчёта, синтаксис всех скриптов (`bash -n`), `shellcheck`,
`py_compile` и `node --check`, юнит-тесты Python, паритет словарей RU/EN, сверка
`actions.json` с диспетчером и MCP, сверка списка файлов `bootstrap.sh`, сверка быстрого
пути панели с ядром (`check_core_read.py`), `--selftest` и все сквозные прогоны без Docker
(`tests/test_*_dryrun.sh`, список — `E2E` в `run_static.sh`; отдельно запускать не нужно). Задания
идут параллельно, до `GA_TEST_JOBS` сразу (по умолчанию — по числу ядер;
`GA_TEST_JOBS=1` — по одному, как раньше). На macOS bash 5 лежит в
`/opt/homebrew/bin/bash`; без `BASH5` возьмётся `/bin/bash` 3.2 и всё развалится
на ассоциативных массивах.

**Локаль на macOS** (TEST-FLAKE-11): Homebrew bash 5.3 при пустых `LANG`/`LC_ALL` иногда падает SIGSEGV в `$(…)`.
`run_static.sh` сам ставит `LANG=C.UTF-8`, а отдельный набор запускайте так:
`LANG=C.UTF-8 BASH5=/opt/homebrew/bin/bash /opt/homebrew/bin/bash tests/test_<набор>_dryrun.sh`.

**После слияния в `dev`** — `python3 tests/check_core_read.py` (секунда). Отпечаток быстрого пути
(`python3 lib/core_read.py --fingerprint --write`) пишут только после сверки модуля с ядром и подтверждения
проверяльщика, что ответ не изменился (docs/PANEL.md §5b, docs/RELEASE_1.0.13.md §2.4).

Подробности — [tests/README.md](tests/README.md).

## 2. Инварианты, которые нельзя нарушать

Это не стиль. Каждый пункт куплен багом.

1. **Мост печатает JSON последней строкой stdout.** Весь UI, логи, спиннеры —
   в stderr. Бот, панель и MCP берут последний объект со `status`, идя с конца.
   Одна `echo` в stdout из библиотеки — и все три интерфейса получают `transport`.
2. **Subshell-capture.** Функция, вызываемая через `$( )`, печатает в stdout
   **только результат**. Всё остальное — `>&2`. Плюс обратное правило: если вам
   нужен код ошибки, который функция положила в `GA_ERR_CODE`, зовите её через
   `ga_capture var fn args…` (`lib/docker.sh:60`) — `var=$(fn)` выполняет `fn` в
   дочернем процессе, и переменные наружу не доходят. На этом стоит вся передача
   кодов ошибок модулей в ответ моста.
3. **Один замок** `/run/goamnezia/config.lock` на все четыре интерфейса:
   `ga_with_config_lock fn args…`, реентрантный через `GA_CONFIG_LOCK_HELD`,
   пара `fn()` / `_fn_locked()`. Таймаут 30 с → код `lock_timeout`, выход 75.
   Действия с `readonly: true` замок не берут — их дёргают по таймеру.
4. **Атомарная запись конфигов.** `jq … > tmp` рядом с целью + `mv`, с мержем
   поверх старого. Никогда не писать в целевой файл напрямую: битый JSON не
   должен затирать рабочий конфиг (это проверяется тестом).
5. **i18n без хардкода.** Ни одной видимой строки в коде — только `t key` /
   `tf key args…`. Словарь: ядро `lib/lang/<lang>.sh` + фрагмент на модуль
   `lib/lang/<lang>.d/<модуль>.sh`. Разбиение не для красоты: один общий файл
   превращался в постоянный конфликт слияния. Паритет RU/EN проверяется тестом,
   мёртвые ключи — тоже.
6. **Секреты в 0600**, каталоги 0700, `mktemp` вместо предсказуемых путей.
   Приватные ключи отдаёт **только** `export.sh` (действие `user-key`). Секретные
   адреса (панель, агенты) — только в ответах своих действий и никогда в аудит.
7. **Ни одна библиотечная функция не делает `exit`** — только `return`. Модули
   сорсятся в меню; `exit` уронил бы весь интерфейс.
8. **Валидация входа регексами** `[[ $x =~ $re ]]`, не `grep`; белые списки для
   профилей и параметров.
9. **`confirm` читает `/dev/tty`**, а не stdin: при запуске через
   `bash <(curl …)` stdin — это тело скрипта, обычный `read` получает EOF, и
   пустой ответ трактовался бы как согласие на необратимое.
10. **Приложение Amnezia молча пропускает незнакомые имена контейнеров** — на
    этом стоит вся раскладка. Оно разбирает контейнеры с подстрокой `amnezia` в
    имени и видит только `amnezia-awg2`; goWARP PRO по маске
    `^amnezia-awg[0-9]*$` видит все три. **Не переименовывать контейнеры** и не
    заводить новые с подстрокой `amnezia` в других продуктах серии.
11. **`state/` — страховка от `docker rm`.** У официальной схемы Amnezia нет
    томов: ключи живут внутри контейнера. Любое пересоздание обязано идти
    циклом `state_sync → docker rm/run → state_restore → wait_up → state_sync`.
    Сюда же копируются `/opt/warp/` и `/opt/warp-tools/usr/` goWARP PRO (перед сносом —
    из самого контейнера, `ga_amn_container_rm`), блок `WARP-MANAGER` едет в `start.sh`
    и нового релиза. Снос — только через `ga_amn_container_rm` (или `docker_rm`, который
    запоминает ID контейнера с соседями в его сети), подъём — только с `ga_amn_wait_up`:
    он возвращает соседей (`NetworkMode=container:…`, например `warp-socks`) в сеть
    нового контейнера и зовёт сторож goWARP (WRP-01, 29.09.2026). «Удалить всё» уносит
    реестр прежних ID (`state/.netdeps`) в `/var/lib/goamnezia-netdeps`, и новая установка
    возвращает соседей прежней установки тем же путём; о соседях без записи и о goWARP без
    WARP в новых контейнерах говорят конец установки, «Диагностика» и сторож (WRP-06, 03.10.2026).
12. **PSK на клиента, а не общий.** Приложение Amnezia держит один
    `wireguard_psk.key` на всех; у нас свой PSK на каждого пира. Пиры приложения
    с общим PSK при этом спокойно живут в том же конфиге — совместимость не
    страдает.
13. **`users.json` — единственный источник правды по пирам.** Каждая мутация
    **целиком переписывает** серверный конфиг и `clientsTable`, без дописываний
    «в хвост».
14. **Образы только по дайджесту** (`lib/upstream/images.json`), никогда
    `--pull latest`: иначе контейнер 2.0 однажды окажется на другом ядре.
15. **Живой сертификат не перевыпускается** — ни Let's Encrypt (лимиты: 5
    дублей в неделю на домен), ни самоподписанный (его отпечаток — единственное,
    по чему агент MCP отличает наш сервер от подменённого).

## 3. История решений и граблей

Всё уже сделано так, как описано. Список — чтобы не «чинить» починенное и
понимать, почему код выглядит странно.

### Форматы ключей

1. **`qCompress` с 4-байтовым префиксом** (`lib/awgkeys.py:728`). Строка
   `vpn://` — это Qt-шный `qCompress`: **4 байта big-endian длины исходных
   данных**, затем zlib уровня 8, всё в base64url без `=`. Без этого префикса
   `qUncompress` в приложении Amnezia возвращает пустой массив, и ключ не
   импортируется без единого сообщения об ошибке.
2. **Чанковый QR приложения** (`lib/awgkeys.py:116`). Приложение не читает один
   QR со строкой `vpn://`. Сжатые байты режутся по **850**, каждый чанк
   упаковывается как `QDataStream`: `qint16` magic **1984**, `quint8` число
   чанков, `quint8` индекс, `QByteArray` (`quint32` длина + данные), затем
   base64url без `=`. Максимум 255 чанков (`quint8`). Каждый чанк — отдельный
   PNG (`01.png`, `02.png`…), сканируются по порядку.
3. **Уровень коррекции QR — L**, а не выше: у `.conf` около 700 символов, у
   чанка `vpn://` около 1100, и на более высоком уровне картинка перестаёт
   читаться с экрана телефона. Текст в `qrencode` уходит через stdin — аргумент
   такой длины режет шелл.
4. **X25519 написан руками** на чистом Python (RFC 7748, с clamping): панель и
   MCP работают на stdlib без `pip`, тянуть `cryptography` ради одной кривой
   значило бы завести зависимость во все четыре интерфейса. Проверено против
   известного вектора RFC.

### JSON, jq и bash

5. **`jq -e` и булево `false`.** `jq -e` возвращает 1 на значениях `false` и
   `null`, поэтому проверять валидность JSON им нельзя: `reissue_required=@json:false`
   приезжал бы в ответ строкой `"false"`. В `ga_emit_json` (`lib/common.sh:731`)
   валидность проверяется обычным `jq .`. Там же, где `-e` уместен (проверка
   «это объект», «это массив»), он остался осознанно.
6. **Префикс `@json:` в `ga_emit_json`.** Значение с этим префиксом
   вставляется в ответ как готовый JSON без кавычек — так в ответ попадают
   массивы и объекты, не превращаясь в строку с `\"`. Пустое или невалидное
   после `@json:` уходит **строкой**, а не роняет ответ: мост обязан вернуть
   валидный JSON при любом входе. Имя поля проверяется регексом — оно идёт
   прямо в программу `jq`.
7. **`ga_config_set` хранит `true`/`false`/`null` булевыми**, а не строками —
   ровно по той же причине.
8. **`IFS` и `@tsv` с пустыми полями.** `jq … | @tsv` + `IFS=$'\t' read` ломается,
   когда поле пустое: таб для `read` — «пробельный» символ, два таба подряд
   схлопываются, и все последующие поля сдвигаются. В `lib/preflight.sh:807`
   разделителем взят **U+001F**. Если пишете новую разборку многополевой строки
   с возможно пустыми полями — берите тот же приём.
9. **Запасной путь `ga_emit_json` без `jq`** — руками экранированный JSON.
   Лучше так, чем пустой stdout: бот и MCP на пустой строке падают с
   `transport`.

### Docker, порты, файрвол

10. **`docker stop <контейнер>`, а не `systemctl disable docker`**
    (`lib/preflight.sh:833`). Когда порт держит `docker-proxy`, его юнит —
    `docker.service`, и подсказка «остановите юнит» убила бы все контейнеры,
    включая наши. Контейнер важнее юнита.
11. **Юнит определяется по `/proc/<pid>/cgroup`, а не по имени процесса**: у
    `telemt`, `dnsdist` и `xray` процесс называется как угодно (`x-ui` запускает
    `xray-linux-amd64`), а cgroup всегда указывает на юнит, который надо
    остановить.
12. **`userland-proxy=false`**: контейнер держит порт правилом DNAT, и в `ss`
    его не видно. Поэтому список `docker ps` нужен и для порта без слушателя.
13. **Сомнение в разборе файрвола → `unknown`, а не `closed`.** Режим при этом
    доступен, но с предупреждением. Без `ss` честнее сказать «не проверено», чем
    «свободно».
14. **Чистый nftables `preflight_open_local` не трогает**: имена таблиц и
    цепочек произвольны, промахнуться проще, чем помочь. Печатается подсказка.
15. **`start.sh` upstream дублирует правила iptables.** Официальный `start.sh`
    делает `iptables -A` при каждом старте, а контейнер стартует не один раз
    (`--restart always`, перезагрузка хоста, `core-update`) — цепочки распухают
    дублями. **Это единственная наша правка к вендоренному коду**: форма
    `iptables -C … 2>/dev/null || iptables -A …`. Патч накладывается автоматически
    при обновлении (`ga_up_patch_start_sh`, `lib/upstream.sh:298`), а
    `awg/start.sh.upstream` хранится рядом как эталон для сверки.
16. **`podman` отвергается сразу** с кодом `docker_unsupported_runtime`:
    `podman-docker` подсовывает бинарник `docker`, но Amnezia на нём не работает
    (privileged + `/lib/modules` + сеть).
16a. **Клиент docker бывает новее живого демона — и тогда падает ВСЁ.**
    Куплено стендом 10.09.2026. `unattended-upgrades` ночью обновляет пакет
    `docker.io` (24.0.7 → 29.1.3) и демон при этом **не перезапускает**: рестарт
    уронил бы разом все контейнеры, и `postinst` его сознательно не делает. Это
    штатное состояние любого сервера с автообновлениями, живёт оно до
    перезагрузки или до ручного `systemctl restart docker`. Наутро клиент просит
    API 1.52, демон понимает максимум 1.43, и каждая команда отвечает
    `client version 1.52 is too new. Maximum supported API version is 1.43` —
    при том, что контейнеры работают и VPN раздаёт трафик.
    Правила, которые из этого следуют:
    - **версию API спрашиваем у демона, а не у клиента**: клиент в этот момент и
      есть источник ошибки. `curl --unix-socket /var/run/docker.sock
      http://localhost/version` отдаёт `ApiVersion` и `MinAPIVersion` и
      рассогласованию не подвержен. Запасной путь — вычитать число из текста
      отказа. Всё это делает `docker_api_pin` (`lib/docker.sh`) один раз за
      процесс и экспортирует `DOCKER_API_VERSION`; заданную снаружи версию
      уважаем. Каждый вызов CLI внутри модуля идёт через обёртку `ga_docker`,
      которая перед первым вызовом дёргает `docker_api_pin`;
    - **неудача `docker inspect` — это два разных мира.** `no such object` —
      контейнера правда нет; `cannot connect` / `too new` — про контейнер мы не
      знаем **ничего**. Смешивать нельзя: раньше оба звались `missing`, и сторож
      каждые два часа звал восстанавливать из бэкапа три живых профиля. Отсюда
      состояние `docker_unreachable`;
    - **молчаливый «успех» опаснее ложной тревоги.** Тик лимитов ловил отказ
      `awg show` через `|| continue` и отчитывался `status: success, users: 1,
      disabled: []` — лимиты и сроки просто перестали работать, и по логам всё
      было хорошо. Любой тик, который не смог получить данные, обязан вернуть
      ошибку с кодом, а не ноль;
    - **закрепление версии — заплатка, а не лечение.** Она держит управление до
      прихода человека; демон всё равно остаётся старым. Поэтому `quality`
      (`docker_diag_json`) показывает версии клиента и демона, `mismatch` и
      `restart_required` с подсказкой `systemctl restart docker`;
    - **лечит перезапуск службы, и делает его сам продукт** (DK-02, 04.10.2026):
      «старая служба» — это бинарь на диске (`dockerd --version`) другой версии
      или сборки, чем работающий демон, а не только рассогласование API (та же
      версия с исправленной сборкой API не меняет). Сторож перезапускает Docker,
      когда к VPN никто не подключён, apt/dpkg и замок свободны и с прошлой
      попытки прошло 6 ч; человек — «Перезапустить Docker» (мост `docker-restart`).
      После перезапуска всё о демоне — заново (`docker_stale_reset`): Docker 29 не
      принимает API ниже 1.44, и старое закрепление его бы уронило; долгоживущее
      SSH-меню сверяет демон на каждой перерисовке (`docker_pin_refresh`).
    Регрессия — раздел 5 `tests/test_timers_dryrun.sh` на подставном `docker`
    (`tests/fixtures/fake_docker.sh`, режимы `mismatch` / `down` / `ok`).
16b. **Очередь `/run/goamnezia/notify/` может остаться без читателя.** Бота
    может не быть вовсе, он может лежать или потерять токен, а таймеры пишут
    дальше: за одну ночь рассогласования там накопились десятки файлов на tmpfs.
    Предел — `GOAMNEZIA_NOTIFY_MAX` (200) в `ga_notify_trim` (`lib/common.sh`),
    лишними выбрасываются самые старые. Порядковый номер в имени файла дополнен
    нулями (`_0007`), иначе внутри одной секунды лексический порядок расходится
    с хронологическим (`_10` встаёт раньше `_2`) — а по нему идут и обрезка, и
    чтение ботом.

### Обновления из upstream

17. **`releases/latest` пропускает пре-релизы.** По правилам GitHub этот
    эндпоинт отдаёт `5.0.1.5`, хотя самый свежий тег — `5.0.2.1` (помечен
    пре-релизом). Поэтому тег берётся из **списка** релизов
    (`/releases?per_page=…`), первый не-draft.
18. **Образ — новейший версионный тег Docker Hub** (`^[0-9]+(\.[0-9]+){1,3}$`,
    `sort -V`); `latest` — только справка, куда он указывает. У legacy-образа
    `amnezia-wg` версионных тегов нет — там сравнивается дайджест `latest`.
19. **Новый плейсхолдер `$…`** в `template.conf` или `configure_container.sh` —
    это новый параметр протокола. Он попадает в отчёт как «не поддержан» и
    **не подставляется**: молча подставить пусто = сломать совместимость линейки.
20. **Серверный `awg0.conf` собираем сами**, а не официальным
    `configure_container.sh`: у приложения конфиг — одноразовый heredoc с
    генерацией ключей внутри контейнера, повторно его не собрать. Нам нужно
    переписывать конфиг целиком после каждой операции и делать это одинаково на
    сервере и в dry-run. `configure_container.sh` остаётся эталоном **имён
    переменных и путей** — файлы кладём ровно туда же.

### Сертификаты и доступы

21. **Самоподписанный сертификат не перевыпускать.** Его отпечаток SHA-256 —
    то, по чему агенты MCP доверяют серверу. Живой сертификат (≥ 30 дней,
    содержит текущий IP) не трогается; перевыпуск — только при смене IP,
    истечении или явной команде из меню. Тот же порог 30 дней — для Let's
    Encrypt, но там причина другая: 5 дублей в неделю на домен, и стенд уже
    сидел без сертификата.
22. **Самоподписанный создаётся по-настоящему даже в dry-run** — `openssl`
    базовая зависимость, а `GOAMNEZIA_DIR` стенд задаёт всегда. Так тесты
    проверяют CN, SAN, права и отпечаток, а не строку `DRY:`.
23. **`agents.json` перечитывается по mtime при каждом запросе** — поэтому
    отзыв, выключение и перевыпуск действуют на следующий же вызов, без
    рестарта nginx и юнита. Исключение — персональные порты: слушатели
    открываются при старте.
24. **Битый `agents.json` — ошибка, а не пустой список.** Иначе следующая
    запись затёрла бы все доступы.
25. **Одинаковый 404 на «выключен / истёк / чужой IP / неизвестен»** и даже на
    бан (не 429): ответ не должен подтверждать существование пути.

### Прочее

26. **`GOAMNEZIA_SERVER_IP`** — иначе dry-run на macOS и CI без интернета ждал
    бы три таймаута `curl` на каждый `status`.
27. **Dry-run без фикстур = «пусто»**, а не «настоящие команды»: иначе сквозные
    прогоны зависели бы от nginx и ufw машины разработчика.
28. **Единая глубина хранения бэкапов** (30). В goTelegram SSH-меню чистило до 5
    и молча удаляло архивы, накопленные таймером, у которого было 30.
29. **Предохранитель бюджета логов**: в общих каталогах (`/var/log`,
    `/var/log/nginx`) трогаем **только своё по маске**, и маска задаётся
    префиксом, чтобы покрыть и `goamnezia-audit.log.3.gz`. Иначе сторож сжимал
    бы и удалял чужие `syslog.1` и `auth.log.2`.
30. **PATH в юните бота задан явно**: на старых установках юнит наследовал PATH
    без `/usr/sbin`, и мост не находил `ss` и `iptables`.
31. **Токен и ID админов уходят установщику бота через окружение**, не через
    аргументы: argv виден в `/proc` всем.
32. **Линейку профиля спрашивают у его параметров, а не у имени.** Источник
    правды — поле `line` в `config.json`; читать его надо через
    `ga_profile_line <профиль>` (`lib/amnezia.sh`), а не `ga_profile_default`.
    Поле пишут установка (по `detect-line` от сгенерированных параметров) и
    `import-adopt` (по конфигу внутри чужого контейнера); у старых установок
    оно пустое — тогда `ga_profile_line` выводит линейку по `params`, а
    миграция при старте `install.sh` (`ga_migrate_profile_line`) записывает
    выведенное обратно. `ga_profile_default` остался ровно для одного случая —
    **свежей установки**, когда профиля в конфиге ещё нет.
    Проверка и генерация параметров идут не по фактической линейке, а по
    **линейке-основанию** `ga_profile_line_base` — семейству фактической:
    1.0 и 1.5 — одно семейство (поэтому `awg1` свободно ходит между ними,
    добавляя или убирая `I1`), 2.0 и 3.1 — свои. Выше семейства не поднимаемся:
    линейки несовместимы, `S3/S4` в 1.x и 3.x-поля в 2.0 не пройдут.
    **Практическое следствие:** контейнер `amnezia-awg2`, поставленный
    приложением с линейкой 3.1, после `import-adopt` правится в 3.1, а свежий
    `awg2` — в 2.0. То же семейство используют бот (`line_base` в `bot.py`) и
    панель (`LINE_FAMILY` в `admin-web/server.py`) для списка параметров.
33. **Версия продукта — одна константа** `GOAMNEZIA_VERSION` в `lib/common.sh`.
    В goTelegram она была продублирована в четырёх местах и трижды разъезжалась.
34. **I1 по умолчанию — один тег `<b 0x…>`** (KEENETIC-I1, 29.10). Умолчание приложения Amnezia
    `<r 2><b 0x8580…>` KeeneticOS 5.1 не принимает («invalid I1 value»): пакет должен начинаться с `<b>`.
    Поэтому `default_i1()` в `lib/awgkeys.py` — тот же DNS-ответ icloud.com, а 2 байта ID транзакции —
    случайные (`secrets`) при генерации; прежнее значение — `LEGACY_DEFAULT_I1`, только для миграции.
    Правило `write` (генератор, `profile-set-param`) требует `<b` первым в каждом из I1–I5 (код `b_first`),
    `adopt` — только предупреждает. Шаг миграции `_migrate_i1_universal` и подхват меняют ровно прежнее
    умолчание путём `profile-set-param` клиентского параметра: I-пакеты шлёт только клиент, у сервера они
    закомментированы, поэтому без рестарта и перевыпуска. Профиль, в живом конфиге которого есть пир не из
    `users.json` (добавлен приложением), пропускается: перезапись конфига сняла бы этого человека.
    Пресет `quic` не менялся (начинается с `<b`), на Keenetic вживую не проверен.
35. **S4 генератора — 12–24, а предел — 40** (S4-MARGIN, 29.10). `S4_GEN_RANGE` (генератор 2.0 и
    `pick_safe_s4` у «Исправить S4») — 12–24: пакет 1280 + 80 + 24 = 1384, запас 16 байт. `S4_SAFE_MAX` = 40
    остаётся ручным пределом `profile-set-param` и порогом `packet_risk`: не «чинить» их до 24 — выданные
    профили с S4 ≤ 40 не в риске. Свободных значений в 12–24 при любых S1–S3 не меньше 10 (PARAM-06).

## 4. Рецепт: добавить новое действие моста

Шесть шагов, в этом порядке. Пропуск любого ловится тестами.

**1. `lib/actions.json`** — запись в `actions`:

```json
"profile-foo": {
  "mcp": "profile_foo",          // имя инструмента MCP; null — не публиковать агенту
  "readonly": false,             // true → без замка
  "destructive": false,          // true → в MCP и панели потребует confirm
  "params": {"profile": {"type": "profile", "required": true}},
  "description": {"ru": "…", "en": "…"}
}
```

Типы параметров берутся из `param_types` того же файла (их 29) — новый тип
добавляйте туда, а не пишите регекс по месту. Если действие возвращает секрет —
`"secret": true`.

**2. Диспетчер в `install.sh`** — ветка `case` с тем же именем:

```bash
profile-foo)
    _action_run foo_failed amnezia_profile_foo "$ARG_profile" || return $?
    ga_emit_json success "$(t act_foo_ok)" profile="$ARG_profile"
    ;;
```

Аргументы приезжают в `ARG_<имя>` (дефис → подчёркивание) уже проверенными по
`param_types`. Зовите модуль через **`_action_run <код-по-умолчанию> fn args…`**,
иначе код ошибки модуля потеряется и вызывающий получит обобщённое `*_failed`.
Помните: пустой аргумент ≠ отсутствующий.

**3. Функция модуля.** Мутация — пара `fn()` / `_fn_locked()` под
`ga_with_config_lock`. В stdout — только JSON результата, всё остальное `>&2`.
Ошибка — `ga_err <код> "<сообщение>" [rc]`, чтобы код доехал до ответа.

**4. Словари** `lib/lang/ru.d/<модуль>.sh` и `lib/lang/en.d/<модуль>.sh` — оба,
с одинаковым набором ключей и одинаковым числом `%s`. Ключи моста по традиции
начинаются с `act_`.

**5. Тест.** Сквозной шаг в `tests/test_actions_dryrun.sh` (настоящий
`install.sh --action=… --json` процессом) — минимум: ответ ровно одна строка
валидного JSON, ожидаемый код при ошибке, секретов в ответе нет. Функцию модуля
отдельно — в `tests/test_core_dryrun.sh` или в профильный `test_*_dryrun.sh`.

**6. Интерфейсы.** MCP подхватит действие сам (он строится из `actions.json`) —
проверьте `python3 goamnezia-mcp/server.py --check`. Боту и панели нужен экран:
`goamnezia-bot/bot.py` (кнопка + обработчик + ключи в `lang/*.json`) и
`admin-web/static/app.js` + маршрут в `server.py` с картой кода ошибки в
HTTP-статус. Пункт SSH-меню — по `docs/MENU.md`.

Затем: `bash tests/run_static.sh` — `check_actions.py` сверит `actions.json` с
диспетчером в обе стороны, `check_i18n_*` — словари, `check_menu.py` — кнопки
бота.

## 6. Чек-лист правки и выкладки

Перед коммитом:

1. `BASH5=/opt/homebrew/bin/bash bash tests/run_static.sh` — зелёный целиком.
2. Новые `$( )`-вызываемые функции пишут UI через `>&2`; там, где нужен код
   ошибки — `ga_capture`.
3. Новые мутации — под `ga_with_config_lock`, пара `fn` / `_fn_locked`.
4. Ни одной видимой строки в коде: только `t` / `tf`, ключи в **обоих** словарях.
5. Секреты: 0600, `mktemp`, не в аудит, не в argv, не в логи.
6. `GOAMNEZIA_VERSION` в `lib/common.sh` — если поведение изменилось.
7. Новые файлы — в списки `bootstrap.sh` (иначе сервер получит установку без
   модуля; `check_bootstrap_files.py` это ловит).
8. Изменился контракт между модулями — сначала `docs/CONTRACT.md`, потом код.
9. Изменилось поведение — `docs/MAP.md`, changelog в `DOCS_HUMAN.md`.
10. `git diff --check` — хвостовые пробелы.

Выкладка — в две ветки. `main` — стабильная: её ставит `bootstrap.sh` по умолчанию,
в неё — только проверенное. `dev` — экспериментальная (`GOAMNEZIA_BRANCH=dev`):
выпуски сначала идут сюда, и пуш в `dev` — уже выпуск её людям. Ничего
чувствительного в git не выкладываем.

На сервере после обновления: «Обслуживание → Обновить goAmnezia» с выбором ветки или
`bootstrap.sh` с нужной `GOAMNEZIA_BRANCH`; он
перезапишет эталон, а `install.sh` при первом же интерактивном запуске обновит
рабочие копии бота, панели и MCP и переставит таймеры (идемпотентно).

## 7. Где НЕ копаться

- **`lib/upstream/awg/*`** — вендоренные официальные скрипты Amnezia (тег
  `5.0.2.1`, sha256 в `lib/upstream/README.md`, сверяются
  `tests/test_upstream_vendoring.py`). Они обязаны оставаться байт в байт как в
  upstream. Единственное разрешённое исключение — идемпотентные iptables в
  `awg/start.sh`, и то накладывается автоматически патчем. Обновлять их надо
  действием `upstream-update`, а не руками.
- **`lib/upstream/xray/*`** — только справка о провенансе официального клиента.
  Продукт их не использует: `bootstrap.sh` не возит, `lib/upstream.sh` не качает
  и не сверяет. Не «подключать» и не удалять — они зафиксированный снимок.
- **`lib/templates_lib.sh`** и `templates_catalog.json` — библиотека шаблонов из
  навыка `site-templates-library`, взята как есть решением владельца. Изменены
  только пути и имена под наш неймспейс. Логику `_tpl_pick_index_dir`,
  `_tpl_page_ok`, `strip_template_service_files`, `deploy_template_to_nginx`
  **не трогать** — это и есть гарантия качества базы из 33 467 шаблонов. Пять
  сообщений там остались литералами намеренно: перевести их — уже правка чужой
  логики вывода, а `website.sh` дублирует эти ситуации своими ключами. Подписи
  авторов и лицензии в подвалах шаблонов не убирать — это условие использования.
- **Слой входа панели** (`admin-web/server.py`: `guard_request`, `session_state`,
  `_issue_session`, `verify_telegram_init_data`, корзины лимитов) — перенесён из
  goTelegram Pro **без изменений в логике**, там он прошёл внешний аудит и
  несколько итераций правок. Менять — только с пониманием goTelegram `AUDIT.md`
  §7 и с прогоном `tests/test_admin_http.py` целиком.
- **Кодек `vpn://` и чанковый QR** (`lib/awgkeys.py`) — формат чужой, задан
  реализацией приложения Amnezia (`qrCodeUtils.cpp`). «Улучшать» его нельзя:
  любое отклонение приложение просто не примет, причём молча. Правки — только
  вслед за изменением приложения и только с обновлением тестов.
- Старые имена и схемы: контейнер `amnezia-awg` (без цифры) — это legacy
  приложения, мы его только подхватываем на `wg0`, но сами такой не создаём.

## Ключ на другой адрес сервера (0.4.3, 25.09.2026)

`user-key --endpoint=<host>` (и `share-create --endpoint=<host>`) выдаёт тот же ключ пользователя — та же
пара ключей и порт профиля — с другим адресом сервера в `Endpoint` и в `vpn://` (`hostName`, подпись с
адресом). Допустимы только IPv4 этой машины (`ga_edge_list`, `server_ip`) и настроенные домены; отказы —
`address_not_here`, `invalid_ip`, `addresses_unknown`. В ответе — `key_host`, `key_endpoint`,
`key_host_override`. Варианты для интерфейсов — `edge-status.key_choices[{host, kind, default, verdict,
users, in_dns}]` и `keys_host`; `user-show` отдаёт `key_host` / `key_host_gone`, `status` — `key_hosts`.
За пользователем ничего не сохраняется (закрепить адрес — `user-set-address`), сторож адресов разовые
ключи не видит. Один ключ одновременно с двух адресов не работает: у пира на сервере один адрес.

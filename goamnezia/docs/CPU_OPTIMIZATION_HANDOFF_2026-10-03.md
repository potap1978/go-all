## 1. Запрос владельца и рекомендуемое решение

Владелец сообщил о CPU до 100% при работе с админкой на сервере **89.125.74.168**. Разрешил подключиться по SSH, самостоятельно проверять запросы разных страниц и искать источники нагрузки. После диагностики запросил план, обсудил смену технологии и попросил этот файл для другого агента.

## 6. План реализации

### A. Первое ограниченное изменение: управление запросами

1. Следующий автоматический опрос планировать после завершения предыдущего.
2. Ручные повторные клики объединять либо оставлять одно ожидающее обновление.
3. Сохранять защиту от позднего ответа после смены страницы; существующие паузы скрытой вкладки, окна входа, модального окна и мутации.
4. На backend объединять одинаковые выполняющиеся безопасные чтения по action + нормализованные params + lang.
5. Авторизацию проверять на каждом HTTP-запросе до обращения к результату; учитывать контекст доступа, если результат от него зависит.
6. По ошибке, timeout или отмене освобождать всех ожидающих и таблицу выполняющихся запросов. Ограничить её размер.
7. Сохранить возможность чтения во время мутации; не сериализовать всё через глобальный write lock.

Отмена browser fetch сама по себе не убивает уже начатую работу сервера.

### B. Общий снимок и актуальность

Один свежий набор трафика/онлайна обслуживает Обзор, Пользователей и Трафик, а также несколько вкладок. Сбор по потребности; без постоянного дорогостоящего опроса в отсутствие читателей.

Стартовые интервалы для проверки:
- Живой трафик/handshakes: **15–20 с**.
- Runtime-состояние контейнеров: **30 с**.
- Список пользователей/параметры: до **60 с**, с немедленным сбросом после изменений.
- Временные ссылки: до **30 с**, истечение проверять по времени; создание/удаление сбрасывает данные.
- Архивы/последний бэкап: до **60 с**.
- Размеры логов/диск: **5 мин**.
- «Следить» за журналом: **5–10 с** только при включённом режиме.
- Сессии и специальные сценарии ожидания подключения нового клиента сохранить отзывчивыми.

Инвалидизация должна работать и для бота, SSH, таймеров: ревизии или проверка inode + mtime_ns + size соответствующих файлов. Docker-состояние, меняющееся вне продукта, имеет свой ограниченный срок актуальности.

Защитить гонку «чтение началось → мутация → старое чтение завершилось»: старый результат не должен снова заполнить сброшенный кэш. Сравнивать поколение кэша и признаки исходных данных перед публикацией; учитывать частично неуспешные мутации.

Показывать возраст снимка. При ошибке обновления сохранять предыдущую картину с явной пометкой, а не выдавать пустоту как успех. Ручное обновление запрашивает свежий сбор и может присоединиться к уже выполняющемуся свежему сбору.

### C. Главная архитектурная оптимизация: чтение внутри Python

Сделать общий read-only модуль ядра, импортируемый уже запущенной панелью:
- JSON разобрать один раз, строить только разрешённую публичную проекцию.
- Состояние Docker получать пакетно через локальный Engine API с согласованием версии.
- Показания awg/wg получать один раз на профиль за сбор.
- Историческую сводку переиспользовать до изменения stats.json; живые счётчики обновлять отдельно.
- Устранить запуск полного install.sh и десятков утилит для каждого обычного чтения.
- Общие преобразования держать в слое ядра, чтобы панель, бот, SSH и MCP не получили расходящиеся правила.
- Запись, блокировки, аудит и миграции оставить на существующем пути мутаций.

**Уточнение контракта:** docs/PANEL.md:28 прямо запрещает панели читать users.json напрямую; сейчас пользователи идут через user-list/user-show. Поэтому перенос чтения — осознанное изменение архитектуры, требующее согласованного обновления docs/PANEL.md и docs/CONTRACT.md, общего модуля ядра и тестов паритета. Не сводить его к вставке json.load(users.json) в HTTP handler.

Сохранить:
- Публичный набор полей, типы, семантику пустых и повреждённых файлов.
- Отличие Docker недоступен от контейнер отсутствует.
- Ограничение доступа к ключам, разграничение секретных и обычных ответов.
- Поддерживаемые версии Python и переносимость Linux, загрузку нового модуля установщиком.
- Единую семантику счётчиков, квот, отключённых пользователей и сброса счётчиков контейнеров.

**Критичный парсер:** awg/wg dump содержит приватный ключ интерфейса в первой строке. В AWG строка интерфейса бывает длиннее 8 полей, поэтому проверка только количества полей небезопасна. Текущий amnezia_show различает строки по allowed-ips; новый парсер должен воспроизвести корректное отделение интерфейса от пиров. Приватный ключ и PSK не должны попадать в публичный снимок, общий кэш, логи и диагностику.

## 7. Ожидаемый эффект: прогноз, а не результат

| Изменение | Оценка CPU панели |
|---|---:|
| Исходное наблюдение | **32,66% измерено** |
| Только удвоить период опроса 10 → 20 с, стоимость цикла прежняя | примерно **16,3%**, расчёт |
| Только 10 → 30 с | примерно **10,9%**, расчёт |
| Общий быстрый сбор в Python | **целевой сценарий около 3–8%** |
| Аналогичная реализация Go | численно не оценена, нужен прототип |

Модель последней оценки: 0,5–1,5 CPU-секунды на общий сбор раз в 20 с = 2,5–7,5% одного ядра только на эти сборы. Остальная работа панели добавится сверху. Ориентир снижения вклада панели — порядка 75–90%, но он не доказан.

Расчёт 3 × 0,879 = 2,637 CPU-секунды подготовки против 4,227 для пользователей даёт около 62%; это грубое сопоставление разных прогонов, не точное профилирование долей.

Замедление опроса уменьшает частоту пиков, но сохраняет стоимость каждого. Быстрое чтение должно уменьшить и длительность пиков. Краткая отметка 100% сама по себе не критерий провала: оценивать длительность, CPU-секунды, среднее и отзывчивость VPN/панели.

## 8. Почему Python сначала, Go позднее

Для текущего HTTP-сервера выигрыш от смены фреймворка отдельно не измерен. FastAPI может быть полезен для организации API, но оставленные Bash-вызовы сохранят свою цену.

Python уже работает в панели, поэтому общий read-only модуль позволяет исключить основную повторную подготовку с меньшим объёмом миграции. Для возможного нового сервиса на Go достаточно рассмотреть стандартный net/http. Переход на Go оценивать прототипом той же семантики и на тех же данных; не приписывать ему без замеров ещё один кратный выигрыш.

Ни Python-прототип нового сборщика, ни Go-прототип в этой сессии не создавались.

## 9. Проверки и критерии приёмки

Рекомендуемые существующие тесты: tests/test_admin_features.py, tests/test_admin_http.py, tests/test_panel_dom.py, tests/test_core_dryrun.sh, tests/test_actions_dryrun.sh, проверки contracts/actions/bootstrap по затронутому объёму.

Добавить поведенческие проверки:
- Два/три одинаковых одновременных чтения → одна работа; синхронизировать тест барьером, а не случайной задержкой.
- Ошибка, exception и timeout сборщика → все ожидания завершаются, следующий запрос обслуживается.
- Разные языки, права доступа и секретные действия не смешиваются.
- Старый сбор после мутации не перезаписывает свежий кэш.
- Изменения через другой процесс, атомарная замена JSON, обновление stats, удаление пользователя.
- Закрытая/скрытая вкладка, переход раздела, длительный запрос, ручной refresh, выход из сессии.
- Паритет старого и нового read path на временных базах: 5, 100, 1000 пользователей; остановленный/недоступный Docker; повреждённый JSON.
- Публичные данные не содержат private key / PSK / токены / секретные пути ссылок; AWG dump интерфейса с расширенными полями.

Для macOS тесты Bash требуют Bash 5 согласно tests/README.md. Секреты и реальные пользовательские записи в фикстуры не копировать.

Живой сравнительный прогон после локальной проверки:
1. Одна версия кода и одинаковые данные для before/after.
2. Закрытая панель; отдельно 10 мин Пользователи и 10 мин Обзор.
3. Три активных клиента/вкладки, чтобы проверить общий сбор.
4. Отдельно cold/warm отклик, CPU cgroup, CPU daemon, RSS, ошибки, число процессов, I/O wait и steal.
5. Проверка доступности панели и реального VPN-пути, когда есть подходящий клиент.
6. Мутации проверять на тестовых данных/согласованном стенде, не создавать лишних аккаунтов на рабочем сервере.

Цели:

- Новый обычный снимок на исходном объёме данных: p95 ≤3 с.
- Один общий сбор для одинаковых одновременных читателей.
- Изменения видны при следующем чтении без ожидания длинного TTL.
- Нет неограниченной очереди, зависших ожиданий и устойчивого роста памяти.
- Цели 3–8% и ≤1 CPU-секунды на частый сбор — желаемый дальнейший результат, не основание объявлять PASS до замера.

### PERF-04, PERF-05, PNL-05, PNL-06, PNL-02 — после живой проверки PERF-03 (05.10)

### PERF-08, PNL-07, PNL-08 — после живой проверки s168-116 (05.10)

**PERF-08: откуда «холодный» Обзор без мутаций.** На 168 один раз, через ~4 мин после рестарта панели, `/api/overview`
вернул `traffic_total: null`, `pending: [traffic, edge-status]`, без `traffic_total_age`. Пройдены все пути, которые
сбрасывают снимки или делают запас (`_READ_LAST_GOOD`) негодным для запроса:

| путь | когда срабатывает | даёт «холодную» форму? |
|---|---|---|
| `_cache_clear()` | только тесты | нет |
| `_snapshot_invalidate()`, смена поколения | любое не-`readonly` действие панели (в том числе неудачное); `page-url` — `readonly: false`, его зовёт кнопка страницы | нет: чистит `_READ_CACHE`, а запас остаётся, и Обзор отвечает им (`swr`) |
| признаки файлов (`_snapshot_sig`) | запись `config.json`, `users.json`, `stats.json`, файлов сторожа ботом, службой страниц, копиями, таймером | нет: мимо только попадания в кэш, запас тот же |
| секретные чтения (`sub-show`, `user-key` через `/api/action`), карточка | `readonly: true` — снимки не трогают, в аудит пишутся как выдача | нет |
| сбой сбора (таймаут, мост) | запас не обновляется, но живёт 10 мин | нет, пока есть удачный сбор за 10 мин |
| перезапуск панели | всё в памяти | да — по журналу только 5 рестартов самого проверяющего |
| **ключ снимка с языком** | запрос без `X-GoAmnezia-Lang` (curl) жил на своих снимках `действие|`, страница — на `действие|ru` | **да — это и был случай 168** |
| **«Обновить» (`X-GoAmnezia-Fresh`)** у чтений без ожидания | кнопка «Обновить», «Повторить» на пометке о прежней картине | **да** — запас такому запросу не годился, ответ `pending` |
| часы (`_now` — `time.time()`) | шаг системных часов назад: снимки «из будущего» не годятся, а новый сбор не заменяет запас, пока часы не догонят | теоретически; на 168 не наблюдалось |

Доказательство по записи проверяющего: рестарт панели 04:22:02 UTC; запуск страницы 04:25:49–04:26:01 (снимки
`…|ru` тёплые); в 04:26:10 — `curl http://127.0.0.1:18986/api/overview` без заголовка языка: первый запрос без языка
после рестарта, снимки `…|` пусты — `pending: [traffic, edge-status]`. Следующий curl через 6 с — `traffic_total_age: 6`,
то есть сбор, запущенный этим же curl. Дальше 45 проверок шли на тёплых `…|`, и форма не повторилась. Тот же ключ дал и
«сервер отдаёт `users_online: null`» из PNL-08: curl после 75 с простоя читал свои снимки `…|`, которые никто не
обновлял, а страница — `…|ru`, которые держал свежими опрос раздела «Пользователи» (`/api/users` читает `traffic`).

**Исправлено.** `snapshot_lang()`: запрос без языка — на снимках языка установки (`read_language()`, то же правило, что
у ядра), и мосту этот язык уходит явно (`GOAMNEZIA_CALL_LANG`), чтобы ответ совпал с ключом и при смене языка установки

(`wait=False`: Обзор, «Настройки», `/api/traffic?wait=0`) начинает новый сбор и тогда, когда снимок ещё в сроке (кроме

через 1,5 с. Часы оставлены как есть: перевод снимков на `time.monotonic()` трогает и время в `snapshot_at`, и подмену
часов во всех тестах — риск больше пользы; если на сервере заметят шаг часов (`journalctl -u systemd-timesyncd`, «Time
has been changed») рядом с такой формой — это он.

### Риски и что осталось

* **Расхождение с ядром** — главный риск такой архитектуры. Закрыт отпечатком (правка повторённых функций выключает
  быстрый путь до сверки), тестом равенства и сверкой `tests/check_core_read.py` (секунда, без bash, в run_static
  среди сверок): какие места изменились, дифф с ревизии сверки, шаги и команда `python3 lib/core_read.py
  --fingerprint --write`. Первое срабатывание — слияние dev 05.10 (2925fc9): `tf act_failed` → `t act_failed` в
  `_action_run` и `tf short_err_failed` → `t short_err_failed` в `_ga_short_call` — только текст отказа, ответ
  быстрого пути не меняется (отказы он отдаёт мосту); модуль не правился, отпечатки обновлены. Новое поле ответа, добавленное в мост правкой вне повторённых мест
  (новый общий помощник), отпечаток не поймает — автор правки должен знать о модуле: он назван в docs/PANEL.md §5b,
  docs/CONTRACT.md §6 и docs/MAP.md.
* **jq 1.6 на сервере** (Ubuntu 22.04): различия с 1.7 в повторённом коде (`@uri` у `!*'()`, дроби, целые > 2^53)
  модуль отдаёт мосту; тест равенства на Mac зелёный и с jq 1.7.1, и с jq 1.6 (CR-9).
* **Холодный старт** traffic и edge-status — по-прежнему мост (docker exec, awk-аналитика сторожа): фоновое
  обновление прячет их от карточки и списка, Обзор ждёт, как раньше. Python-сбор traffic (Engine API, разбор dump) —
  следующий шаг, если живой замер покажет, что тяжёл Обзор.
* **Мост для остального** не ускорялся: бот, служба страниц (`lib/pages_server.py`: подписка берёт ключ `user-key`
  мостом, кеш 60 с), MCP и фоновые сборы платят прежнюю загрузку (0,6 CPU-с на вызов). Ленивая загрузка модулей
  моста — отдельная задача (D, остаток); службе страниц модуль доступен тем же импортом — это решать её исполнителю.

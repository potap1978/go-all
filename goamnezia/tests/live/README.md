# Живая приёмка одной командой — `tests/live/acceptance.py`

Перед выпуском проверяет установленный goAmnezia на настоящем сервере. Подключения делает настоящий клиент
AmneziaWG с другой машины. Итог — короткая таблица «проверка → OK / FAIL / SKIP → доказательство». Код выхода 1,
если есть FAIL.

Скрипт собран из ручной приёмки 0.4.6 (27.09.2026, `.claude/work/stands/acceptance-046.md`). Две старые проверки
остаются: `e2e_keys.sh` и `live_actions.sh` запускаются на самом сервере (`ssh … 'bash -s' <`).
`acceptance.py` запускается с машины разработчика и ходит на две машины.

## Что нужно

- **Сервер** — `root@…`, goAmnezia установлен. Для страниц и MCP нужен режим с доменом.
- **Клиент** — `root@…` с Docker, лучше другой сервер, чтобы была видна внешняя дорога.
  - Образ клиента выбирается сам: первый найденный из `ga-test-client`, `amnezia-awg3`, `amnezia-awg2`,
    `amnezia-awg1`. Все они собраны из Dockerfile приложения Amnezia и умеют линии 1.0–3.1. Свой образ —
    `--client-image`.
  - Клиент работает в одноразовом `--privileged` контейнере со своей сетевой namespace. Маршруты хоста не
    трогаются, контейнер удаляется.
- **SSH** — только по ключу: `--key`, по умолчанию `~/.ssh/id_ed25519`, BatchMode. Ключ клиента другой —
  `--client-key` (по умолчанию тот же `--key`, KMODB-04): ключи людей идут сервер → клиент трубой через машину
  прогона, каждая сторона — своим ключом, так что ни ssh-agent, ни ключ сервера на клиенте не нужны. Ходит общим каналом
  `ssh_link.py` (TOOL-01): одно рукопожатие на машину за прогон (ControlMaster, сокеты — во временном каталоге
  0700, в конце `ssh -O exit` и каталог удаляется — и при падении прогона). Тестовые серверы под перебором
  паролей рвут свежие рукопожатия («Connection closed by … port 22», `kex_exchange_identification`, код 255) —
  такой обрыв повторяется с растущей паузой (5 попыток: 3, 6, 12, 24 с). Повтор безопасен, пока команда не
  началась: начало видно по метке, которую удалённая оболочка печатает первой. Обрыв посреди команды повторяется
  только у чтения, проверок и заливки файлов; шаг, который меняет сервер (обновление, перезагрузка, изменения через
  мост), вслепую не повторяется — в таблице будет его настоящий итог. В журнал — только хост, попытка и строка ssh
  об обрыве. `GA_LIVE_SSH_TRIES` и `GA_LIVE_SSH_PAUSE` меняют число попыток и первую паузу;
  `GA_LIVE_SSH_DIR=<каталог>` — ехать чужим каналом (так `bot_live.sh` зовёт `acceptance.py`).
- **Секреты — только в локальных файлах 0600 вне git.** Сейчас это один файл: адрес страницы подключения
  (`--page-url-file`). Скрипт откажется работать, если у файла другие права или git может его закоммитить.

## Проверки (`--checks`, через запятую)

| проверка | что делает |
|---|---|
| `conn` | ключ `--user` на каждом его профиле подключается. Доказательство: рукопожатие, ping адреса сервера в туннеле (10.8.x.0), выход в интернет с IP сервера. Вдобавок — каждый `--conn-conf-file` (локальный 0600-конф человека приложения Amnezia, чьего ключа на сервере нет): после подхвата он обязан подключаться как раньше |
| `disabled` | выключенный вручную `--disabled-user` не подключается ни на одном профиле, и его пиров нет в живом конфиге |
| `page` | страница `--page-user` отвечает 200 (UA браузера). Ключи 0.5.0 (SEC50-05) — отдельной строкой: из данных страницы берётся одноразовое значение `reveal`, `GET keys.json` — 405, `POST keys.json` с ним — 200 и `.conf` каждого профиля = мост (плюс `vpn://`), повтор того же значения — 409; у страницы до 0.5.0 значения нет — SKIP. Каждый `key/<профиль>.conf` отдаётся вложением с токеном `?g=` из ответа `POST keys.json` (SEC50-10; у страницы без токена — как раньше, без него), его sha256 совпадает с `user-key` моста, скачанный `.conf` подключается. Отдельной строкой SEC50-10: `key/<профиль>.conf` и `qr/key/<профиль>/{conf,vpn}.png` без токена и с чужим — 404. Ни значение, ни токен, ни ключи не печатаются |
| `newkey` | временный пользователь на всех профилях (или `--newkey-profiles`) подключается, затем удаляется. Подхваченный у приложения профиль помечен в таблице |
| `adopted` | люди подхваченных контейнеров приложения целы: `import-snapshots` = живой контейнер = users.json (pubkey, AllowedIPs, PSK, имя), ключи сервера не менялись. Необязательный базовый файл — `--adopted-baseline <путь на сервере>`. Смену метаданных clientsTable (ACC-1) показывает строкой, но не валит |
| `isolation` | изоляция клиентов одного профиля (SEC-NET-1): два клиента одновременно — `--user` (или `--isolation-conf-file`, локальный 0600-конф человека приложения, чьего ключа нет на сервере) и `--isolation-peer` (или временный новый пользователь). Оба выходят в интернет с IP сервера, но друг до друга ни ping, ни TCP (слушатель `nc` на 18080) не проходит; `status` отдаёт `client_isolation: true`, в контейнере одно правило `FORWARD -i if -o if -j DROP`. С `--isolation-toggle` — `client_isolation=false` в config.json (под замком продукта) + `watch-tick`: связь между клиентами появляется; затем прежнее значение и снова «заблокировано». Профиль — `--isolation-profile` (по умолчанию awg2) |
| `backup` | `backup-create` → временный пользователь и +1 ГБ лимита у `--backup-probe-user` → `backup-restore` этого архива. Снимок до и после: FAIL 0, из WARN допустимы только пересоздание контейнеров (так задумано) и отметка расписания. Службы active, контейнеры подняты, после восстановления ключ подключается |
| `mcp` | MCP по HTTPS: включить (если был выключен), выдать два временных доступа (`read`, `write` + `pin_ip`). Проверить уровни, токен, закрепление адреса, повтор изменений, отзыв. Потом убрать доступы и выключить обратно — vhost снова байт-в-байт прежний. **Токены не покидают сервер**: запросы идут через nginx и настоящий сертификат, но на 127.0.0.1 (`curl --resolve`). Второй адрес для закрепления — внешний IP сервера (`--interface`) |
| `bridge` | только чтение, мост 0.5.0: `name-suggest --lang=ru\|en` дважды — id латиницей, подпись на своём языке, повтор даёт другое имя; `GOAMNEZIA_CALL_LANG=ru\|en` меняет язык `message` (на `user_not_found`); у `backup-last` есть `schedule`; в `status` есть `endpoint_host_gone`, `server_ip_change`, `upstream` |
| `share` | временная ссылка на `.conf` первого профиля `--user` (решение В1, `docs/SHARE.md`): три скачивания подряд — 200, `attachment`, хеш = `user-key` моста; чужой путь на том же порту — 404; `share-list` насчитал 3. Затем `share-revoke`: порт не слушается, ссылки нет в списке, соединение отклонено. С `--share-expiry` вместо снятия ждёт срок: скачивание за 25 с до конца — 200, после срока порт закрыт (около 6 минут). **Адрес не видит даже harness**: он идёт трубой сервер → клиент, тело — во временном каталоге 0700 на клиенте, наружу только хеши |
| `mode` | только с `--mode-switch <профиль>`, и только из `lite_site`: `change-mode pro` + `profile-port <профиль> 443`, проверка сайта и прочих ключей, затем попытка на UDP/443. Возврат: прежний порт + `lite_site`. vhost, сертификат и ключи должны совпасть с исходными |
| `snapshot` | `--snapshot-save ИМЯ` снимает снимок на сервере в `/root/ga-live/snapshots/ИМЯ.json` (0600, только хеши). `--snapshot-compare ИМЯ\|путь` сравнивает сохранённый снимок с текущим (`remote/compare.py`). С `--expect-version X` код должен быть версии X |
| `lazy` | итог Ленивого Pro (0.6.0, `docs/MODES_047.md`), только чтение. Режим и UDP 443: `--lazy-expect pro` (по умолчанию) — `pro`, на сервере обе линии 2.0 и 3.1 (по версии, а не по месту профиля: приложение держит 3.1 и в `amnezia-awg2`, LZ-02), на 443 — 2.0, а если 2.0 уже стоит на своём порту — 3.1; подхваченный профиль на 443 не переезжает, и у каждого подхваченного порт тот же, что в снимке до подхвата и у контейнера (ACC-2); `--lazy-expect semi_pro` — `lite_site`, на 443 никого. Сертификат снаружи: издатель Let's Encrypt, имя домена сходится, сайт — 200. Шаблон — не встроенная заглушка. Панель на домене: её путь — 200, чужой путь — 404 (запросы идут на самом сервере через `curl --resolve`, путь его не покидает). Ключи: ровно `--lazy-keys` (5), у каждого обе линии, подпись и id — пара из `lib/names_capitals.json`. Страницы: по одной на ключ, `ttl 30d`, обе линии, каждая открывается — 200 (адрес страницы тоже не покидает сервер) |

По умолчанию: `conn,disabled,page,newkey,adopted,isolation,backup,mcp,bridge,share,snapshot`. `mode` добавляется флагом, `lazy` — по имени.

## Модуль ядра AmneziaWG (`kmod`, этап Б, `docs/KMOD_PLAN.md`)

Переход с программы `amneziawg-go` в Docker на модуль ядра и обратно — в два плеча, на настоящих клиентах. В набор по
умолчанию не входит, только по имени: ставит на стенд пакеты сборки и модуль и перезапускает профили (люди профиля
переподключаются сами за 15–25 с на каждом шаге). Нужен отдельный `--client` с Docker и **без** модуля `amneziawg` на
нём: клиент работает программой в своём контейнере из образа сервера, как в остальных проверках.

```bash
python3 tests/live/acceptance.py --server root@203.0.113.20 --client root@198.51.100.10 --checks kmod
# ключи у стенда и клиента разные (почасовые серверы бывают с разными ключами) — каждому свой:
python3 tests/live/acceptance.py --server root@203.0.113.20 --key ~/.ssh/stand_key \
    --client root@198.51.100.10 --client-key ~/.ssh/client_key --checks kmod
```

Ход и строки таблицы:

1. `kmod-check` (только чтение): хост годится — ядро, что поставит apt и сколько это места; нельзя (контейнер LXC/OpenVZ,
   Secure Boot, старое ядро, нет заголовков) — одна строка SKIP с причиной, на сервере ничего не меняется.
2. Снимок сервера (`remote/snapshot.py`), временный человек `live-km-*` на профилях `--kmod-profiles` (по умолчанию все
   профили на `awg0`; профиль приложения на `wg0` модуль не переключает) и по постоянному клиенту на профиль
   (`remote/kmod_client.sh`): один ключ на всю проверку, ping раз в 2 с — клиент «на связи», и продукт ждёт его
   возвращения. Отпечаток ключа на клиенте = `users.json`, ключ сервера = `awg show` (`remote/kmod_server.py`).
3. Исходное — программа (профиль уже на модуле — сначала перевод на программу). `kmod-install` — согласие человека
   здесь сам вызов: пакеты, сборка с патчами, самопроверка в netns одноразового контейнера; строка — версия с меткой
   `+kaskad-k31.1`, собран или взят готовый, #218, пакеты, итог самопроверки.
4. Три перевода `kmod-engine`: модуль → программа → модуль. Строка перевода — ответ продукта по каждому профилю:
   откуда → куда, сколько из бывших на связи вернулось и за сколько секунд, был ли откат. Строка клиента на каждом
   профиле: вернулся сам (рукопожатие после начала шага), ping, **ключи те же** (отпечатки клиента и сервера = исходные
   и = `users.json` / `awg show`), движок — по `profiles-status`, по `ip -d link` в контейнере и по файлу `engine`,
   iperf3 10 с в обе стороны (`--kmod-iperf`, 0 — без него; сервер iperf3 — одноразовый контейнер в сетевом
   пространстве профиля, сам контейнер профиля не меняется). Откат перевода — FAIL, дальше шаги не идут.
5. После всех перезапусков: правила TCPMSS в mangle FORWARD ровно по одному на направление (v4 — 2, v6 — 2 или нет
   ip6tables), блок goWARP в `start.sh` тот же, блок движка на месте, `sh -n` проходит.
6. Как было: выбор движка до проверки (модуль — модулем, иначе программа), клиенты вернулись; модуль, которого до
   проверки не было, — `kmod-remove` (`--kmod-keep-module` оставляет; сосед Kaskad им пользуется — продукт оставит
   сам). Пакеты остаются — строка показывает команду `apt remove …`. Клиенты и человек убираются и при сбое.
7. Журнал ядра с начала проверки (`journalctl -k`) без `BUG`, `soft lockup`, `Oops`, `general protection fault`,
   `Call Trace`, `blocked for more than`; сравнение iperf3 программа/модуль — строкой для отчёта; снимок до/после —
   FAIL 0 (ключи людей и сервера, люди, страницы — те же; WARN за изменённый `start.sh` — так задумано).

Долгие шаги (`kmod-install`, `kmod-engine`, `kmod-remove`) идут службой `systemd-run` на сервере: обрыв SSH их не
рвёт, harness опрашивает её и печатает ход из `kmod-status.progress`. Тест #253 (`syncconf` с ключом защиты под
трафиком на стоковом модуле) проверка не делает никогда. Флаги: `--kmod-profiles`, `--kmod-keep-module`,
`--kmod-iperf`, `--kmod-wait` (сколько ждать возвращения клиента, по умолчанию 180 с), `--kmod-install-timeout`,
`--kmod-engine-timeout`. Ход проверки без серверов — `tests/test_live_kmod.py` (подставные сервер и клиент).

## Эксплуатационные проверки (`reboot`, `disk-full`, `logrotate`, `cert-renew`, `update-rollback`) и обновление (`upgrade`, `selfupdate`)

Заменяют критика-сисадмина (`docs/REDESIGN_050.md`, п. 6). В набор по умолчанию не входят, запускаются только по имени
в `--checks`. `disk-full`, `update-rollback` и `upgrade` вдобавок требуют флага `--allow-disk-full` /
`--allow-update-rollback` / `--allow-upgrade`, без флага строка SKIP. Серверная часть — `remote/ops_check.py`; её
режимы можно звать и руками: `python3 /root/ga-live/ops_check.py health`.

| проверка | что делает | что остаётся на сервере |
|---|---|---|
| `upgrade` | Обновление настоящим путём загрузчика. Снимок; `git archive HEAD` дерева `--upgrade-tree` (по умолчанию — этот репозиторий) едет в `/root/ga-live/tree`; `bootstrap.sh` этого дерева с `GOAMNEZIA_LOCAL_TREE` и прежней веткой (`--upgrade-branch`, по умолчанию та, что в `.install-source`) в pty — он сам передаёт управление меню. Строки: новая версия встала, главное меню нарисовано, ветка и `ref` в `.install-source` прежние; `.prev_code` появился до раскладки (meta `from`/`to`, записи манифеста) и исчез после удачной миграции, в журнале действий `update-done`; `config.version` новая, отметка `.migrated_<v>`, «Что нового» показано в первом меню и не показано во втором; службы active (в 0.5.1 — и `goamnezia-isolation`), `.env` бота не менялся. Снимок до/после с `--expect-version` = версия дерева: FAIL 0 | новая версия; дерево удаляется |
| `selfupdate` | «Обслуживание → Обновить goAmnezia» — только просмотр. Меню в pty с заведомо негодным ключом (`GOAMNEZIA_PAT=ga-live-not-a-token`: GitHub отвечает 401, и ни загрузчик, ни файлы не скачиваются). Экран: строки `main`/`dev`, текущая ветка помечена, по Enter — она же. Выбор `1` спрашивает GitHub только про `main`, Enter — только про текущую ветку; оба раза отказ словами, без «Смена ветки», `.install-source` и код прежние. Есть ли ветки на GitHub, harness узнаёт сам через `gh api …/commits/<ветка>` (422 — ветки нет, и с настоящим ключом экран ответит «Ветки main в репозитории нет.»); ключ на сервер не передаётся | ничего |
| `reboot` | Снимок, затем `systemctl reboot` через `systemd-run`. Ждёт SSH с новым `boot_id` (до `--reboot-timeout`, по умолчанию 900 с). Проверяет: службы поднялись сами; Docker поднял контейнеры профилей; правило изоляции `FORWARD -i if -o if -j DROP` есть в каждом контейнере профиля, включая подхваченные, и появилось **до первого тика сторожа** (свои — строкой в `start.sh`, подхваченные — службой `goamnezia-isolation`, OPS-05); видно, через сколько секунд после старта контейнера. Затем проверка здоровья: панель (`127.0.0.1:1985` — `/api/session`, `/api/overview`); страницы (служба отвечает 404 на незнакомую страницу, а с `--page-url-file` настоящая страница отвечает 200); бот; MCP по stdio (`initialize` + `server_status`); таймеры. У бота смотрим: `active`, «bot starting» в журнале, длинный опрос TCP к :443, `.env` не менялся, администратор привязан; сообщений боту проверка не шлёт. У таймеров — есть ли следующий запуск. Снаружи: сайт отвечает 200, ключи `--user` на всех профилях и конфы `--conn-conf-file` подключаются. В конце снимок до/после: FAIL 0 | снимок в `/root/ga-live/snapshots/` |
| `disk-full` | `fallocate` доводит `/` до 98–99 %: людям свободно около 1,3 %, запас root остаётся. При полном диске проверяет: меню открывается (pty: главное меню → «Обслуживание» → «Диагностика» → выход); диагностика SSH, мост `quality` и панель (`/api/quality`, `/api/logs/status`) показывают, что места мало; `status.disk` (уровень `low`/`critical`), строка в шапке главного меню и `disk` в `/api/overview` панели предупреждают о диске (OPS-01); `backup-create` отказывает с `low_disk` и не оставляет ни архива, ни промежуточного каталога; запись `users.json` при 99 % проходит (лимит +1 ГБ и назад). Затем на несколько секунд 100 % и для root: запись обязана сорваться и сказать об этом (`user-quota`, `lang-set` — не success, OPS-04), `config.json` и `users.json` остаются байт-в-байт прежними и корректным JSON, временных файлов нет, `.language` и отметка миграции не обнулены; сайт отвечает, службы не перезапускались. После уборки: место вернулось, `quality` в норме, `backup-create` работает (тестовый архив удаляется), снимок до/после — FAIL 0 | ничего. Заполнители удаляются в `finally` и по сигналу. Если проверка умрёт, временный таймер `ga-live-fill-failsafe` удалит их через 15 минут |

## Бот и мини-апп через подставной Telegram — `bot_live.sh`

Настоящий `bot.py` штатного установщика и настоящая панель на настоящем сервере, а Telegram — подставной: токен
выдуманный (создаётся на сервере, 0600, ни к какому боту не относится и сервер не покидает), `api.telegram.org` в
проверке не участвует вовсе. Так проверяется всё, что видит человек в чате и в мини-аппе, без чужих токенов и без
Telegram владельца.

```bash
bash tests/live/bot_live.sh root@79.137.206.84 --key ~/.ssh/govless_test_key all      # setup → run → conn → cleanup
bash tests/live/bot_live.sh root@… --key … setup          # по частям: setup, run, conn, cleanup
bash tests/live/bot_live.sh root@… --key … run --only=bulk_button,bulk_text,users_pages
ssh root@… 'python3 /root/ga-live/bot/tg_user.py press "Пользователи"'   # руками, после setup: send / press / show / state
```

SSH — тем же общим каналом `ssh_link.py`, что у `acceptance.py` (его командная строка: `open`, `run`, `close`):
обрыв на рукопожатии повторяется у любого шага, обрыв посреди — только у заливки и чтения. setup, run и cleanup
меняют сервер, и после обрыва посреди они не повторяются — шаг падает, и видно, на чём.

## Проверка обновления (0.4.x → 0.5.0)

С 0.5.1 обновление из дерева репозитория целиком делает проверка `upgrade` (выше): снимки до и после, загрузчик, меню,
«Что нового». Ручной путь ниже нужен, когда обновление идёт из GitHub («Обновить goAmnezia» с ключом доступа).

```bash
# до обновления
python3 tests/live/acceptance.py --server root@S --client root@C --user U --checks snapshot --snapshot-save before-050
# обновление: пункт «Обслуживание → Обновить goAmnezia» или bootstrap кандидата, затем один заход в меню
# после обновления
python3 tests/live/acceptance.py --server root@S --client root@C --user U --disabled-user D \
    --page-user U --page-url-file ~/secret/page.txt --snapshot-compare before-050 --expect-version 0.5.0
```

Кандидат обязан уже называть себя новой версией (`GOAMNEZIA_VERSION` в `lib/common.sh`). Иначе меню проводит миграцию
«по отпечатку кода» той же версии: без предупредительного архива `preupgrade_*` и без экрана «Что нового», а
`--expect-version 0.5.0` даёт FAIL `code version`. Так было 27.09 на bad9e2b (версия в коде — 0.4.6).

`compare.py` делит отличия на три уровня:

- **FAIL** — пропало то, что обновление менять не должно: ключи и PSK сервера, люди, их ключи и лимиты, порты,
  подсети, страница, хеш пароля панели. Аварийный ключ панели с 0.6.0 (SEC50-08) — наоборот: прежний постоянный (без
  `token.meta`) обновление на 0.6.0 обязано убрать, остался — FAIL; часовой ключ с `token.meta` сгорает при входе — INFO.
- **WARN** — изменилось то, что новая версия может менять намеренно: vhost, формат `.conf`, образ или
  пересоздание контейнера. Каждое WARN нужно прочитать.
- **INFO** — ожидаемые изменения: версия, код, счётчики.

## Пример (стенды 27.09.2026)

# C2 — обновлённый с 0.4.5 сервер, клиент — C1
python3 tests/live/acceptance.py --server root@203.0.113.20 --client root@198.51.100.10 \

# C1 — чистая установка, подхватившая контейнеры приложения; клиент — C2

## Что это меняет на сервере и что оставляет

- Каталог `/root/ga-live/` (0700) на обеих машинах: вспомогательные скрипты и сохранённые снимки. Снимки хранят
  только хеши, без секретов.
- Временные пользователи `live-nk-*`, `live-bk-*`, `live-mcp-*` и доступы `live-acc-*` удаляются даже при сбое
  проверки.
- `backup` оставляет два архива в `backups/`: свой и снимок, который делает само восстановление. Ещё он
  **пересоздаёт контейнеры** — это нормальное поведение восстановления.
- После `mcp` может остаться пустой `/opt/goamnezia/agents.json`.
- `mode` на время проверки переносит выбранный профиль на UDP/443: его ключи в это время не работают.
  Подхваченный у приложения профиль сюда не передавайте — сломаются ключи людей приложения (ACC-2).
- Эксплуатационные проверки: `reboot` перезагружает сервер (VPN недоступен ~20–40 с). `disk-full` на несколько
  минут забивает диск и на несколько секунд даёт root ENOSPC: тики, пришедшие в это окно, могут упасть, и проверка
  прогоняет их ещё раз. `update-rollback` на несколько минут ставит кандидатов `-rbtest` и `-rbresume` (второй на
  минуту становится рабочей версией, затем прежняя возвращается загрузчиком). Метки `.preupgrade_*`, `.migrated_*`,
  `.migrating_*`, `.update_failed.json`, `.changelog_pending`, которые завели тест и возврат версии, убираются, а
  прежние метки миграций возвращаются как были. Убираются и архивы теста, и кандидаты, и копия прежнего кода
  (`/root/ga-live/ops/rb/`) — как только на месте снова ровно она. В `/root/ga-live/ops/` остаётся `reboot-pre.json`:
  секретов в нём нет, от `.env` бота — только хеш.
- `upgrade` оставляет новую версию (так задумано) и снимок `ops-upgrade-before`; дерево `/root/ga-live/tree`
  удаляется. `selfupdate` ничего не меняет: ключ негодный, GitHub отвечает 401, загрузчик не скачивается.
- `kmod` оставляет пакеты сборки (`dkms`, `gcc`, `make`, заголовки — команда их удаления в строке `kmod-remove`), файл
  `engine` и блок движка в `start.sh` профилей (на программе) и копии состояния `state/.kmod-copies/` (последние 3).
  Модуль, хуки `/etc/kernel/*.d/zz-goamnezia-amneziawg` и `modules-load.d` убираются, если до проверки модуля не было.

## Нагрузка панели — `panel_load.py` (CPU-аудит 03.10.2026)

Сравнительный замер «открытые вкладки панели»: запускается на сервере, повторяет запросы `app.js` (прежнего —
`--client old`, нынешнего — `--client new`, без вкладок — `none`) и каждую секунду снимает CPU cgroup службы панели
вместе с мостом, занятость машины и число порождённых процессов; итог — JSON (средняя, пики, процессов в секунду,
задержки, «тёплые» и «холодные» ответы по заголовку `X-GoAmnezia-Snapshot`). Два кода на одних данных, не трогая
установленный, — вторая панель своей службой на соседнем порту (рецепт `systemd-run` — в начале файла). Замер
03.10.2026 на test1 (две вкладки «Пользователи» + «Обзор», по 5 мин, дважды попеременно): панель 46–47 % ядра →
6 %, машина 55 % → 11 %, процессов 202–208 → 44–46 в секунду.

## Чего проверка не ловит и частые причины FAIL

- **`backup` на сервере с подхваченным legacy-контейнером (`amnezia-awg`, wg0)** — до 0.4.6 падал `profiles=failed` (ACC-4); исправлено в 0ed6fbf: state хранит `awg0.conf`, старые `wg0.conf` переименовываются миграцией.

- **«ключ на UDP/443» FAIL, а остальное OK.** Сравните с `tcpdump -ni <iface> udp port 443` на сервере: если
  пакеты до него не доходят, а на другие порты доходят, UDP/443 режется по дороге. 27.09 так было на пути из
  России (C2 в Петербурге и сеть владельца) к C1 в Германии. Серверная часть при этом рабочая: клиент на самом
  C1 подключался.
- Проверка на скорость, IPv6 и большие скачивания здесь не делается.
- Визуальные сценарии панели и бота здесь не проверяются, только HTTP-коды. Панель и страницу подключения 0.5.0 проверяли руками в браузере (DOM/JS, 27.09): панель — через SSH-туннель, страницу — через локальный прокси, который читает секретный адрес из файла 0600, чтобы адрес не попадал в журнал. Бот и мини-апп как пользователь — `bot_live.sh` (раздел выше).
- `adopted` сравнивает с последним снимком `import-snapshots`. Если сервер подхватывал контейнер дважды, базой
  будет второй снимок.

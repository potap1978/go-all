дизайн — `k3/design/quick-start-design-v1/` (HANDOFF §4, §5, §8), поправки аудита — `AUDIT.md`. Контракт API для

## 1. Сертификат Let's Encrypt на IP

### 1.1 Что умеет Let's Encrypt

- Сертификаты на IPv4 и IPv6 — в общем доступе с 15.01.2026, **только с профилем `shortlived`**:
  160 часов (≈ 6,7 суток). Профиль выбирается полем `profile` в newOrder (ACME profiles).
- Проверка — `http-01` (TCP/80) или `tls-alpn-01` (TCP/443). `dns-01` для IP не бывает.
- В сертификате нет CN, только SAN `iPAddress`. Адрес должен быть публичным.
- Лимиты, которые касаются нас:
  - 5 сертификатов на одинаковый набор имён за 7 дней;
  - 50 на адрес (для IPv6 — на /64) за 7 дней;
  - 5 неудачных проверок на адрес в час;
  - 300 заказов на учётную запись за 3 часа;
  - 10 учётных записей с адреса за 3 часа.

  Продление по ARI (renewalInfo) не тратит лимиты. Обычное продление при 6-дневном сроке — 2 раза в неделю, в пределах
  лимита 5/неделю. Переустановки могут его выбрать — поэтому действующий сертификат не перевыпускается без `--force`,
  а `retry_after` отказа соблюдается.

### 1.3 Решение: свой минимальный ACME-клиент (`lib/kaskad/ipcert`)

Почему так:
- **Пакетный certbot ни на одной поддерживаемой системе IP не умеет.** Ждать certbot 5.4+ в стабильных выпусках — годы.
- **snap, pip, lego, acme.sh** — лишняя зависимость с сети ради одной функции. Это сотни мегабайт (snapd) или
  непроверенный бинарник с GitHub. Не годится установщику, который и так тянет мало.
- **Свой клиент** — это:
  - stdlib Python (HTTP, JSON, base64);
  - команда `openssl` (зависимость `ca-certificates`, есть везде) для ключей и подписей;
  - сборка DER (CSR с `iPAddress`) — в нашем коде, поэтому не зависит от версии openssl и его конфига.

  Около 700 строк, всё проверяется оффлайн на поддельном CA. Сетевая часть — та же схема, что у `ghkey` и `subfetch`.
- Существующий `lib/kaskad/site/acme.py` — обёртка certbot для **домена**; её оставляем как есть. Для IP certbot не
  подходит (см. выше), поэтому IP — отдельный модуль с теми же словами отказов.

Что внутри (`lib/kaskad/ipcert/`):
- `crypto.py`:
  - RSA 2048 — учётная запись, подпись JWS (RS256);
  - EC P-256 — ключ сертификата;
  - `openssl dgst -sha256 -sign … -hex` — текстовый вывод;
  - CSR: пустой subject, одно расширение subjectAltName/iPAddress, ecdsa-with-SHA256.

  Ключи — только в файлах 0600, в argv идёт путь.
- `acme.py` — RFC 8555 на нужном минимуме: directory (проверка `meta.profiles` на `shortlived`), nonce (повтор при
  `badNonce`), newAccount, newOrder `{"identifiers":[{"type":"ip"}], "profile":"shortlived"}`, http-01, finalize,
  загрузка цепочки. Ошибки CA переводятся в причины: `limit` (с `retry_after`), `challenge`, `unsupported`, `profile`,
  `net`, `server`.
- `http01.py` — кто отвечает на :80:
  - **nginx сайта Kaskad** (`site mode site`): файл в `/var/www/kaskad-acme` (webroot). Сервер по умолчанию :80
    (`return 444`) теперь отдаёт `/.well-known/acme-challenge/` — правка в `site/nginx.py::_reject80`;
  - **никто**: свой короткий приём на :80 в потоке, только на минуты проверки, ничего не пишет в журнал. UFW
    открывает 80/tcp на время проверки и закрывает своё правило;
  - **чужая программа** (nginx/Apache другого владельца, проброс TCP/80, Docker) — отказ `port80` с именем
    программы. Чужие службы не останавливаем.
- `store.py`:
  - `/etc/kaskad/tls/ip/<stamp>/{fullchain.pem,privkey.pem}`, ссылка `current` меняется одним `rename` — панель никогда
    не прочтёт новую цепочку со старым ключом;
  - `meta.json` хранит последнюю попытку и её причину;
  - на диске остаются два выпуска.
- `ops.py` — `issue`, `tick`, `status`, `remove`, таймер.

### 1.4 Продление и перечитывание

- Таймер `kaskad-ipcert.timer`: `OnCalendar=*-*-* 00/12:00:00`, `RandomizedDelaySec=1h`, `Persistent=true`. Ставится
  при первом выпуске. Служба — `kaskadctl ipcert tick --quiet`.
- `tick` продлевает, только когда сертификат **нужен**: панель открыта из интернета (с 3.3.0 — и при сертификате
  домена: адрес по IP продолжает открываться, см. выбор по SNI ниже). Порог — **меньше 72 ч** (половина срока). Продление также при смене адреса и когда стоит
  staging. Отказ CA с `retry_after` до этого времени не повторяется — лимит 5 неудач в час не выбирается.
- Панель перечитывает сертификат **без перезапуска**: `Panel.tls()` раз в 5 с сверяет подписи файлов (добавлены
  `current/fullchain.pem` и `meta.json`) и собирает новый `SSLContext` для новых соединений.
- Порядок того, что отдаёт открытый режим (`panel/conf.panel_cert`):
  1. сертификат домена, пока он действует;
  2. сертификат на IP, если он настоящий (не staging), на этот самый адрес и действует ещё больше часа;
  3. самоподписанный сертификат узла с отпечатком — как раньше.
- Выбор по SNI (3.3.0, `panel/server.sni_callback`, `conf.sni_ip_cert`): когда действует сертификат домена, клиент
  без SNI или с IP-адресом в SNI (`https://<IP>:<порт>/` — мастер, открытый до домена, старые ссылки `/p/…`)
  получает сертификат на IP, пока он действует; имя домена (и любое другое имя) — сертификат домена. Нет
  действующего сертификата на IP — всем сертификат домена, как раньше. Продление любого из них подхватывается тем
  же перечитыванием раз в 5 с.

### 1.5 Запасной путь

Если сертификат не вышел, мастер работает на самоподписанном сертификате узла.

- Установщик и `GET /api/setup/ipcert` показывают честную причину и отпечаток SHA-256. Причины: порт 80 закрыт
  хостером или занят, лимит с временем повтора, нет сети, частный адрес.
- Браузер один раз предупредит о сертификате — текст дизайна «Работаем на своём — браузер покажет предупреждение один
  раз».

### 1.6 Проверить на стенде (без этого — не выпускать)

1. `kaskadctl ipcert issue --staging`, затем без `--staging`. Проверить на Aeza и AdminVPS, на Debian 12/13 и Ubuntu
   24.04/26.04: выпуск, `kaskadctl ipcert status`, браузер без предупреждения на `https://<IP>:<порт>/`.
2. Хостер закрыл 80 — причина `challenge` и запасной сертификат. Порт 80 занят чужим nginx — `port80`.
3. После `site mode site` — продление через webroot (`ipcert issue --force`).
4. Связка с goAmnezia Pro на том же сервере (правило владельца): порты 80 и 443, не мешаем друг другу.
5. Продление по таймеру: сдвинуть время или `--force`. Панель меняет сертификат без перезапуска, открытые вкладки
   не рвутся.

## 2. Мастер: устройство бэкенда (`lib/kaskad/setup`)

### 2.1 Где живёт

Внутри нынешнего сервера панели, отдельной группой маршрутов `/api/setup/*`, только под секретным путём
`/setup-<секрет 32>/`. Есть на двух слушателях:
- «public» — открытый режим, случайный порт 30000–60999;
- «local» — SSH-туннель.

Порт **не 443**: на 443 мастер сам ставит то, что выберет человек (SSTP, OpenConnect, сайт домена). Ссылка не должна
ломаться посреди настройки. Сертификат на IP годится для любого порта, поэтому ссылка такая:

```
https://<IP>:<порт панели>/setup-<секрет>/?t=<одноразовый токен>
```

После выпуска сертификата домена `conf.public_host` называет домен, и ссылка становится
`https://<домен>:<порт>/setup-…/`.

Под nginx на домене (слушатель «proxy») мастера нет. Перевод мастера за nginx — на потом.

### 2.2 Вход

Решения: `setup/link.py`, `setup/web.py`, правка `panel/server.py`.

- **Секрет пути.** 32 знака base64url (192 бита). Хранится открыто в `/etc/kaskad/setup.json` (0600, root) — как
  путь панели за nginx. Сравнение — `hmac.compare_digest`. Чужой путь под `/setup-` получает тот же 404, что
  неизвестный путь панели. API `/api/setup/*` вне секретного пути — тоже 404. Под путём отвечают только страница,
  её статика и `/api/setup/*`, ничего из самой панели.
- **Токен.**
  - Одноразовый, в файле — только SHA-256.
  - Первое открытие даёт сессию и 303 на чистый адрес, чтобы токен ушёл из адресной строки.
  - Повторное открытие той же ссылки — `?link=used`, страница советует `kaskadctl setup link`.
  - Неверные токены ограничены отдельным счётчиком на адрес: 10 за 15 минут, как ссылки панели.
- **Срок.**
  - До конца настройки, но не больше 24 ч от последнего `kaskadctl setup link`. Новая ссылка продлевает срок, путь не
    меняется, пока не попросили `--new-path`.
  - После срока путь отвечает страницей, а API — 410 `expired`, чтобы показать экран «Ссылка больше не действует».
  - После «Готово» и `setup off` — 404.
- **Пароль.**
  - Шаг «password» задаёт пароль панели, гасит все неиспользованные токены и сразу выдаёт браузеру новую сессию
    «password». Сессии по ссылке умирают сами: меняется подпись `password.json`.
  - Дальше мастер открывается только паролем: `POST /api/setup/login` с ограничениями входа панели. Новые ссылки
    `setup link` идут без токена.
- **Привязка к IP** (по желанию): `setup link --bind-ip`. Первый открывший запоминается, с другого адреса — 404.
  По умолчанию выключена — решение владельца §10.2 ещё открыто.
- **Сессии.**
  - Тот же класс `auth.Sessions`, отдельное хранилище.
  - Cookie `kaskad_setup`: `HttpOnly; SameSite=Strict; Path=/setup-<секрет>/`, по HTTPS — `Secure`.
  - Изменения — с заголовком `X-Kaskad-Admin: 1`, без чужого Origin (правило панели).
  - «Готово» выдаёт и cookie панели, чтобы «Открыть панель» не спрашивала пароль второй раз.
- **Журналы.**
  - Путь пишется в журнал как `/setup-…`.
  - Токен, секрет и пароль не попадают ни в `kaskad.log`, ни в журнал панели, ни в argv.

### 2.3 Состояние

`/etc/kaskad/setup.json` (0600, своя блокировка `/etc/kaskad/setup.lock`) хранит:
- статус, ссылку и хэши токенов;
- `password_set`, режим (`node` | `classic`), текущий этап, отметки этапов `done` / `skipped`;
- ответы человека и последний итог каждого шага.

Секретов в файле нет: ключей, токенов бота и подписок шаги не сохраняют (флаг `secret`). Рельс считается на сервере
(`model.rail`): «Шаг 2 из 6 · ≈ N минут осталось». У классического режима свой рельс — без «Выходов», с «Пробросом».

### 2.4 Шаги и долгие действия

- Каждый шаг — `kaskadctl setup step <имя> [--stdin] [--json]` и `POST /api/setup/step/<имя>`. Это одна и та же
  функция `setup.steps.run`. Тело шага — объект JSON: в SSH — на stdin, в панели — в теле запроса. Секреты в argv не
  бывают.
- Шаги зовут только то, что в Kaskad уже есть:
  - `migrate scan/plan/apply/rollback`;
  - `gw ops.probe/inbound_plan/enable/inbound_install/exit_preview/exit_add/exit_del/default_route/offers/
    user_add/device_add/issue`;
  - `awgengine.check`, `site ops.set_domain/check_dns/issue/mode/template_set`, `templates.search`;
  - `ghkey.check/save`, `bot.config`, `mcp.keys.add`, `rules.ops`, `gw trace`, `live.json`.

  Подписка выходов и копия настроек — команды другой ветки, их зовёт тонкая прослойка `setup/features.py`. Пока
  команд нет, ответ — `unavailable` «появится в этой версии».
- Долгие шаги (импорт, протоколы, ключ выхода, сертификат, сайт, шаблон) идут **заданием**:
  - тело — в файл 0600 в `/run/kaskad/setup`;
  - под systemd — `systemd-run --unit kaskad-setup-<id> --collect` (вне CPUQuota/MemoryMax панели), иначе отдельный
    процесс; дочерний процесс читает тело и сразу удаляет файл;
  - процесс шага пишет строки живой проверки в `/run/kaskad/setup/job.json`;
  - фронтенд читает их через SSE `GET /api/setup/events` (событие `job`) или опросом `GET /api/setup/job`;
  - задание переживает закрытую вкладку и перезапуск панели;
  - одновременно идёт одно задание; упавший процесс помечается `failed` с причиной.

### 2.5 Установщик и SSH-меню

- Первая установка: после ядра и промо — выбор «1) Квик-старт в браузере … 2) Классически, здесь в SSH. Выбор [1]».
  Это `k3_setup_offer_fresh`, перед прежним предложением мастера шлюза.
  - На 1 — `kaskadctl setup start`: панель открывается из интернета, выпускается сертификат на IP (если можно),
    затем ссылка, QR (`qrencode` через stdin), срок и порт для файрвола хостера. Вопрос про шлюз в SSH снимается.
  - На 2 — всё как раньше.
- `k3_setup_menu` — для пункта главного меню «Быстрая настройка (в браузере)», его добавляет ветка `k3-menu`:
  - ссылка и QR;
  - ссылка только для моего IP;
  - остановить мастер.

  Шаги цифрами в SSH пока не сделаны: SSH-путь — это прежние меню 17–19.
- `gokaskad --bot-start` — запуск бота без вопросов для шага «Бот» (токен и чат уже записаны).

## 3. Что осталось на потом

- SSH-путь «по шагам цифрами» внутри `k3_setup_menu`: сейчас только ссылка и QR.
- Мастер за nginx на домене (слушатель «proxy»).
- ARI (renewalInfo) для продления без лимитов.
- Проверка «порт открыт снаружи» через выход (SPEC §9.3): в подсказке пока только совет открыть порт у хостера.
- Скачивание и показ ключей подписки с галочками, автообновление: ветка `k3-feat`. Импорт копии настроек — она же.
- Вход VLESS Reality: ветка `k3-vless`. Карточка появится сама — список берётся из реестра.
- Видео (этап E) — заглушки `src: null`.

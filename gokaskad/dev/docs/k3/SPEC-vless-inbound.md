# Kaskad 3 · вход VLESS (Reality или TLS со своим доменом)

Версия: 2026-10-09, ветка `k3-vless2` (от `k3-330` 9cc3a17). Основа — волна 2 (`SPEC-wave2-gateway.md`: шлюз, входы,
xray шлюза), волна 3 (`SPEC-wave3.md`: правила, «Обзор», live.json), волна 4 (`SPEC-wave4.md`: домен и сайт).
Доработка по решениям владельца (2026-10-09): маскировка «как в goVLESS Pro», горячее добавление, подписка.

## 0. Итог в шести строках

1. `vless` — вход шлюза: телефоны и компьютеры подключаются к узлу по VLESS + `xtls-rprx-vision` (v2RayTun, Hiddify,
   Streisand, v2rayN, NekoBox, v2rayNG). Выходы VLESS пула остаются как были — это другое.
2. **Два режима маскировки** (§4): по умолчанию — **TLS со своим доменом** на 443 (сертификат домена, всё постороннее
   xray отдаёт сайту узла, nginx за xray, §4.4); **Reality** под чужой сайт по стране сервера (Россия — российские сайты,
   иначе зарубежные, проверка TLS 1.3 с узла) — запасной вариант: нет домена или сертификата, 443 занят, или человек
   сознательно выбрал его после текста рисков (согласие записывается).
3. Режим — выбор человека (`want`): «Маскировка VLESS» в панели, мастере, SSH-меню, `gw vless mode tls|reality`, MCP
   `vless_mode`. Новая установка с доменом и сертификатом включает сайт сама; домен появился позже и ссылок ещё ни у
   кого нет — TLS сам; иначе — рекомендация с ценой. Включение и выключение сайта при устройствах VLESS — с ценой
   «выдать заново» до действия (§4.5).
4. Вход живёт в **том же** xray шлюза (`kaskad-gw-xray.service`), что SOCKS5 и выходы VLESS: маршрут устройства,
   kill switch, правила «Россия напрямую» и блок частных адресов — те же механизмы, что у SOCKS5 (§2).
5. **Устройства без перезапуска xray** (§2.1): новое, включённое снова, сменившее маршрут — через API xray
   (HandlerService, RoutingService на 127.0.0.1:10854). Уход устройства (отзыв, выключение, новый UUID, маршрут
   «блок») — перезапуск: только он рвёт уже открытые соединения. Ещё перезапуск — смена режима, порта, ключей, сайта.
6. Каждому устройству — свой UUID (секрет); трафик и «в сети» — из счётчиков xray (StatsService) в «Обзор»,
   live.json, `gw sessions` (§7); подписка для приложений — `GET /p/<токен подписки>/sub` (§8).

## 1. Что это и чем не является

Сейчас в Kaskad VLESS — только **выход** (ключи пула `upstream.txt`, ноги `gx-<id>` xray шлюза). Этот документ —
про **вход**: узел сам принимает клиентов VLESS Reality. Устройство с входом `vless` получает ссылку `vless://…`,
приложение подключается к узлу, дальше его трафик идёт по маршруту устройства (пул выходов / один выход / напрямую
/ блок) и по правилам узла — как у WireGuard, AmneziaWG, SOCKS5.

Зачем: на мобильных сетях и под DPI VLESS Reality держится лучше UDP-протоколов; приложения есть на всех
платформах, включая iOS без смены Apple ID.

## 2. Один xray или два — решение: один

Вход `vless` — адаптер, который ничего не запускает сам (как `socks5`): он описывает свой вход и правила для xray
шлюза (`xray_inbounds`, `xray_routing`), ядро (`gw/xray.py`) собирает общий конфиг.

Почему один процесс:

- **Маршрут устройства уже есть в этом xray.** Выходы пула — исходящие `gx-<id>`, балансировщики `gw-all`,
  `gw-all-direct`, `b-<id>-direct` с observatory (leastPing, проба раз в 10 с). Пользователь VLESS идёт в них тем же
  `target(route)`, что и пользователь SOCKS5. Второй xray пришлось бы либо поить тем же пулом (вторая observatory —
  двойные пробы и двойные соединения к каждому выходу VLESS), либо цеплять к первому (лишний скачок, и xray выходов
  уже не знает, чей это трафик, — правила по устройству не построить).
- **Правила волны 3** (реклама, торренты, «всегда через выход», «Россия напрямую» по geosite/geoip RoscomVPN)
  уже рендерятся для пользователей xray шлюза (`rules.apply.xray_rules`); VLESS просто попадает в их число.
- **Блок частных адресов** (127/8, 10/8, CGNAT, link-local, адреса самого узла, `localhost`) стоит в xray шлюза
  первым правилом для всех клиентских входов — VLESS получает его без новой строки кода.
- **Безопасность процесса та же**: пользователь `kaskad-xray`, `CAP_NET_BIND_SERVICE` (порт 443 без root),
  `NoNewPrivileges`, конфиг 0600 через `LoadCredential`, gw_out режет его сокеты на loopback, кроме DNS.

Цена и что с ней делать:

- смена учёток VLESS **не** перезапускает xray (§2.1); перезапуск — смена режима (TLS / Reality), порта, ключей узла,
  сайта маскировки, выходов пула, правил волны 3 и учёток SOCKS5 (у SOCKS5 по-прежнему перезапуск). Смена живости
  выхода и маршрута устройства **на ядре** xray по-прежнему не трогает;
- падение xray выключает и вход, и выходы VLESS сразу — это fail-closed (клиенту некуда подключиться), сторож
  поднимает службу (`gw check`, `Restart=always`). В режиме TLS вместе с ним на 443 не отвечает и сайт (§4.4).

### 2.1 Устройства без перезапуска (HandlerService, RoutingService)

- пока вход VLESS включён, он есть в xray **всегда**, даже без устройств (`clients: []`): первое устройство не
  открывает порт заново. API xray: `api.services` = StatsService, HandlerService, RoutingService на вход `stats-in`
  127.0.0.1:10854 (dokodemo-door, первое правило `stats-in → gw-stats`). Снаружи его нет: слушает только loopback;
  клиент VLESS/SOCKS5 к 127.0.0.0/8 не пройдёт (первое правило xray — блок частных адресов; `gw_out` режет сокеты
  `kaskad-xray` на loopback, кроме DNS);
- правила пользователя VLESS — **цепочка на пользователя** в конце правил: «всегда через выход» → «напрямую» (домены
  и сети России) — если профиль `ru_direct`, затем его маршрут; у каждого правила `ruleTag`
  `vl-<логин>-<хэш цепочки>-<n>`. Блок рекламы — одно правило на вход (стоит и без устройств). Закрывающего правила
  «всё прочее с входа → block» у VLESS нет: первый исходящий xray (его «по умолчанию») — `block`, пока есть VLESS;
- балансировщики, которые может назвать маршрут устройства VLESS (`gw-all`, `gw-all-direct`, `b-<выход>-direct`), стоят
  в конфиге заранее — новый маршрут не меняет их набор;
- `xray.apply` пишет новый файл (после `xray -test`), сравнивает его с прежним без клиентов VLESS и без цепочек
  (`hot_plan`): отличаются только они и xray работает — `xray api adrules -append` (новые цепочки), `adu` (новые
  пользователи), `rmrules <теги>` (заменённые цепочки); порядок такой, что у пользователя нет мгновения без цепочки.
  **Уход пользователя** (`rmu` убрал бы его только из новых подключений, открытые жили бы до конца) и переход на
  маршрут «блок» — перезапуск: доступ режется сразу, как раньше. Больше 20 пользователей или 60 правил за раз
  (восстановление копии) — тоже перезапуск. UUID — в файлах 0600 в /etc/kaskad/gw (удаляются сразу), не в argv.
  Любой отказ API (старый xray без команд, xray не отвечает) — обычный перезапуск: файл уже новый, после перезапуска
  живой xray равен файлу. Журнал: «GW xray: без перезапуска — пользователей +1 −0, правил +1 −0».

## 3. Модель

`gateway.inbounds.vless` (публичная запись, секретов нет):

```json
{"enabled": true, "port": 443, "security": "reality", "sni": "www.microsoft.com", "dest": "www.microsoft.com:443",
 "mask": "list", "mask_list": "int", "country": {"code": "DE", "source": "ipinfo"},
 "short_id": "9f3c0a1b2c3d4e5f", "pub": "<публичный ключ base64url>", "fp": "chrome",
 "mask_check": {"ok": true, "tls": "TLSv1.3", "alpn": "h2", "h2": true, "why": "", "at": "2026-10-09T10:00:00Z"}}
```

- `security`: `reality` | `tls` — режим, который выбрал `site.front.sync` (§4.5); xray получает TLS, только пока он
  ещё возможен (сайт включён, сертификат живой, порт 443) — иначе Reality, до следующего `sync`;
- `mask_list` / `country` — список сайтов маскировки и страна сервера, по которой он выбран (§4.2);
- `mask`: `list` (сайт из списка), `own` (свой сайт узла), `custom` (любое имя человека);
- `mask_check` — последняя проверка сайта с узла (§4.3); `null`/нет — не проверялся;
- секреты (`secrets.json`): `vless.server.private` — приватный ключ узла; `dev.<id>.vless.uuid` — UUID устройства
  (одно устройство — один UUID; `revoke`/`reset` стирают его по префиксу `dev.<id>.vless.`);
- устройство: `access` содержит `vless`, адресов (`ips`) нет — вход не выдаёт адресов 10.77 и не попадает в
  `gw_route`, `gw_live`, `gw_rd`; `model.XRAY_KINDS = ("socks5", "vless")` — общий признак «вход xray шлюза»;
- пользователь xray = логин устройства (`email` клиента VLESS; правила маршрута сопоставляют по нему);
- запись удалённого входа хранится (`removed_inbounds`) вместе с ключом в секретах: переустановка возвращает
  порт, сайт, shortId и ключ — выданные ссылки снова работают (как у WireGuard).

## 4. Маскировка: Reality или TLS со своим доменом

Правило (3.3.7.x, `k3/handoff/SPEC-vless-tls-default.md`): **TLS со своим доменом — по умолчанию, Reality — запасной
вариант.** TLS требует сайта на домене (TLS без сайта за спиной на всё постороннее отвечал бы пустотой и выдавал бы
себя), поэтому переход на TLS включает сайт, а выключение сайта уводит VLESS на Reality вынужденно — это не выбор
человека: `want` не меняется, согласие не пишется, причина `no_site` и «Включите сайт на домене». Сайт на этом домене
ещё не включали (`site.template_id` пуст: сертификат пришёл, когда устройства уже были), — причина `ready`: «TLS уже
можно» с ценой, сайт включится вместе с переходом (T-3378 Н-17). Reality при домене и возможном TLS — только по выбору
человека после текста рисков (`reality_consent`); бот согласия не даёт.

### 4.1 Reality: ключи и параметры

- ключ узла — X25519 (RFC 7748), как `xray x25519`: 32 случайных байта с clamping, base64url без `=`; публичный
  считается на чистом Python (`vendor/awgkeys.py`, тот же код, что для ключей WireGuard/AmneziaWG) — xray для этого
  не вызывается, ключ не попадает в argv;
- `shortId` — 8 случайных байт в hex (16 знаков), один на узел;
- `fp` (uTLS-отпечаток клиента) — `chrome`;
- `flow` — `xtls-rprx-vision` (TCP; UDP приложения передают внутри, XUDP);
- `xver` — 0 (PROXY protocol к сайту-маске не шлём);
- sniffing на входе выключен — как у остальных клиентских входов (IPOnDemand проверял бы подсмотренный SNI вместо
  настоящего адреса, поддельный SNI открыл бы частный адрес).

### 4.2 Reality: сайт маскировки по стране сервера

Reality отдаёт «чужие» соединения (активные пробы, сканеры) сайту `dest` и копирует его рукопожатие: снаружи порт
выглядит как этот сайт. Списки — как в goVLESS Pro `lib/reality_domains.sh` (`inbounds/vless_lists.py`):

- **страна сервера** (`vless_lists.detect`): ipinfo.io/<IP>/country, затем ip-api.com, затем диапазоны сетей России,
  которые правила волны 3 уже держат на узле (ru4.txt, без сети); не определилась — зарубежный список. Запоминается в
  записи (`country`), повторно не спрашивается. Запросы несут только публичный адрес узла;
- **Россия** — российские сайты (ya.ru, yandex.ru, vk.com, ozon.ru, … — около 100): узел в России, который весь день
  «ходит» на зарубежный сайт, заметнее; под «белыми списками» мобильных операторов российский сайт проходит;
- **другая страна** — зарубежные (www.microsoft.com, dl.google.com, www.apple.com, … — около 80);
- **автоподбор** (установка, «Подобрать автоматически»): до 8 сайтов списка в случайном порядке (не все узлы за одним
  сайтом) — первый с TLS 1.3 и HTTP/2, иначе первый с TLS 1.3; никто не ответил — первый, с заметкой;
- **свой сайт узла** (`own`) — только пока сайт узла на 443, а VLESS — на другом порту (запасной вариант рядом с
  сайтом, §4.4); **любой другой** — по имени (`custom`; можно вставить ссылку — берётся имя).

`dest` всегда `<sni>:443`. «Проверить все» (`gw vless masks --check`) проверяет по 16 сайтов сразу — до минуты.

### 4.3 Проверка с узла

Перед установкой и при смене сайт проверяется **с узла** (Python `ssl`, минимум TLS 1.3, проверка сертификата
для имени, ALPN h2/http1.1, таймаут 5 с): без TLS 1.3 Reality не работает вовсе. HTTP/2 — подсказка (так советует
XTLS), не условие. Не прошёл — смена отказывает с причиной («сайт ответил TLSv1.2, а нужен TLS 1.3», «сертификат
сайта не прошёл проверку», «недоступен с узла»); человек может настоять (`--no-check`, в меню — «Всё равно взять»,
в панели — `check: false`).

Установка без интернета (ни один сайт не ответил) не падает: берётся первый из списка, карточка показывает
«не прошёл проверку» и советует выбрать сайт.

### 4.4 TLS со своим доменом: xray на 443, сайт за ним

Когда: сайт узла включён (`site mode site`), сертификат Let's Encrypt боевой и живой, вход VLESS и шлюз включены, на
443 нет чужих (сайта соседа в nginx, чужого слушателя, проброса, Docker). Раскладка (`site/front.py`):

```
клиент ──TCP 443──► xray шлюза: VLESS + TLS (сертификат домена, rejectUnknownSni, ALPN http/1.1, flow vision)
                       │ свой UUID → маршрут устройства
                       └ всё прочее (браузер, сканер, панель на домене, /p/, подписка) ─► fallback, xver 1
                                     ─► nginx: listen unix:/run/kaskad-vless/site.sock proxy_protocol
                                        (сайт, панель по секретному пути, страницы людей /p/)
клиент ──TCP 80───► nginx (как было: редирект на https, проверки Let's Encrypt)
```

- xray: `listen 0.0.0.0` (с IPv6 — `::`), `serverName` и SNI ссылок — домен, `certificates` — копия сертификата
  домена для xray `/opt/kaskad/gw/tls/{fullchain,privkey}.pem` (ключ 0640 root:kaskad-xray, каталог 0750: служба
  xray работает не от root и не видит /etc/kaskad); xray перечитывает файлы сам раз в час (без `ocspStapling`: у
  Let's Encrypt больше нет OCSP, xray предупреждал об этом при каждом запуске — T-M6-qs330b №14);
- nginx за xray: тот же vhost, но вместо `listen 443 ssl` — `listen unix:… proxy_protocol`, `set_real_ip_from unix:`,
  `real_ip_header proxy_protocol` (адрес посетителя — настоящий: бан и лимит `/p/` работают как прежде),
  `absolute_redirect off` (nginx не пишет `http://` в редиректы), без строк TLS и без `ssl_reject_handshake`
  (неизвестный SNI отклоняет xray). Каталог сокета `/run/kaskad-vless` 0750 root:kaskad-xray (nginx делает сокеты
  0666 — замок на каталоге), после перезагрузки его создаёт `/etc/tmpfiles.d/kaskad-vless.conf` раньше nginx;
- **правда раскладки — то, что xray запущен с TLS на 443** (`xray_fronts`: /etc/kaskad/gw/xray.json), а не желание в
  state.json: nginx уходит за xray **до** того, как xray займёт 443 (`before_xray`), и возвращается на 443 **после**
  того, как xray его отпустил или остановлен (`after_xray`: `gw disable`, выключение и удаление входа VLESS, `gw
  purge`). xray не принял конфиг — прежний конфиг работает, nginx остаётся как был;
- продление сертификата: deploy-хук (`site cert-installed`) кладёт новую копию для xray — без перезапуска (xray
  перечитывает пару, когда сменились и сертификат, и ключ — certbot по умолчанию делает новый ключ); ключ тот же
  (`--reuse-key`) — один перезапуск xray;
- UFW: 443/tcp открывают и сайт (`kaskad-site`), и VLESS (`kaskad-gw vless`); снятие одного не закрывает порт другому
  надолго — вход VLESS при следующем применении сверяет UFW и возвращает своё правило.

**Конфликт за 443** (что видит человек):

| Было на узле | `site mode site` | Итог |
|---|---|---|
| VLESS Reality на 443, сайта нет | можно (раньше — отказ «443 занят VLESS») | VLESS → TLS на 443, сайт за xray; «VLESS перешёл на TLS со своим доменом… выдайте ссылки заново: …» |
| VLESS Reality на 8443 (узел 3.3.0 с сайтом) | сайт уже включён | ничего само; `gw vless sync` / меню «Режим по сайту узла» переводит на TLS и 443 |
| nginx не принял сайт за сокетом (нет модуля realip, старый nginx) | сайт включается на 443 сам | VLESS уходит на 8443 (Reality), предупреждение «VLESS не перешёл на TLS: …», ссылки — заново |
| на 443 сайт соседа или чужой слушатель | отказ, как раньше | — |
| вход VLESS выключен | сайт на 443, как раньше (VLESS на 443 — отказ «перенесите вход») | — |

### 4.5 Переключение режима

`site.front.sync` (после `site mode site|domain`, снятия и смены домена, установки входа VLESS, `gw vless sync`):
считает, каким должен быть VLESS (`plan`), и, если отличается, меняет запись одной транзакцией шлюза (перезапуск
xray). Ответ: `{"changed", "security", "old", "port", "why", "reissue", "text"}` — `text` — та же строка «выданные
раньше ссылки VLESS не подключатся. Выдайте их заново (меню 17 → 2 → 1 или панель → «Люди и устройства»): …», что и
при смене ключей. Его несут ответы `site mode` (`vless`) и установки входа (`notes`).

| Событие | Режим VLESS | Порт | Маскировка Reality |
|---|---|---|---|
| сайт включили | TLS | 443 | — |
| сайт выключили (режим «домен»), домен сняли | Reality | 443 (nginx его отпустил) | по стране, автоподбор |
| TLS не получился (nginx, xray отказали) | Reality | 8443 (иначе свободный) | прежняя или свой сайт узла |
| копия с узла, где был TLS, на узле без сайта (§12.1) | Reality | 443, если свободен | по стране этого узла |

Таблица — правило 3.3.7 («режим следует за сайтом») для записей без выбора. С 3.3.7.x действуют правила
`k3/handoff/SPEC-vless-tls-default.md` §3: выбор человека `want` (`tls`, `reality`, `reality_nodomain`), согласие на
Reality, цена «выдать заново» в ядре (`site.ops.vless_price`, CONFLICT `vless_change` без `yes`), переход на TLS —
`gw.ops.vless_to_tls` целиком (замок, снимок; TLS не получился — сайт выключается обратно, VLESS как был). Составные
действия (смена домена и её откат, шаг мастера «сайт», установка VLESS) сайт не держат на TLS: отказ TLS — сайт
включается, VLESS на Reality рядом (причина `tls_failed`, «Повторить TLS»); откат смены домена, после которого ссылки
VLESS не прежние, так и говорит и называет, кому выдать заново. Первый сертификат домена (§3.3): ссылок ни у кого
нет — TLS сам; есть — рекомендация с именами устройств и путём; замок перехода занят — «переход отложен, повторите
«Включить TLS» позже». `gw vless sync` остаётся (следует `want`), из меню и панели убран.
**Исключение (З-3, утверждено):** запись без выбора (`legacy`, создана до обновления) в Reality на порту 443 при
включении сайта ведёт себя как 3.3.7 — переходит на TLS (через `vless_to_tls`, с ценой «выдать заново»).

В режиме TLS порт не меняется (`gw inbound port vless N` — отказ: «стоит на 443 перед сайтом»), сайт маскировки и
ключи Reality не нужны (`gw vless mask` — отказ с подсказкой `gw vless mode reality --accept-risks`).

SSH-меню (17 → 1 → VLESS → «Маскировка VLESS», `gwvless.{ru,en}.sh`): «1) Свой сертификат (TLS) — рекомендуем
[домен …]» / «2) Reality — если нет домена или вы сознательно выбираете его», по умолчанию — пункт текущего режима;
TLS нельзя — пункт 1 с причиной, выбор печатает причину и что сделать. Reality при возможном TLS — список сайтов,
текст рисков и «1) Понимаю риски, выбрать Reality  2) Назад» (по умолчанию «Назад»); при вынужденном Reality и без
домена — сразу список. Цена перевыдачи — вопросом до действия. Бот показывает режим, причину и рекомендацию строкой
(«Домен и сайт», сводка шлюза) и путь — панель или SSH-меню; кнопок выбора Reality в боте нет.
## 5. Порт

- новый вход пробует по порядку `port_candidates`: **443**, затем **8443**; занятость — общая проверка ядра
  (пробросы, другие входы, слушатели снаружи, Docker, чужой DNAT); оба заняты — случайный свободный 20000–60000;
  заметка «порт 443/tcp занят (…) — взял 8443» уходит в меню и панель;
- сайт узла в режиме «сайт» держит 443: VLESS встаёт на 443 **перед** ним в режиме TLS (§4.4; сайт и nginx для
  VLESS не конфликт — `port_shared`), если TLS невозможен — кандидат один, 8443 (Reality рядом с сайтом);
- `gw inbound plan vless` показывает тот же выбор (мастер, «Быстрый старт»);
- человек меняет порт как у любого входа (`gw inbound port vless N`, меню, панель); выданные ссылки — заново;
- вход на 443 и сайт: VLESS занял 443, позже включают сайт — VLESS переходит на TLS перед сайтом (§4.4, таблица);
  SSTP и OpenConnect на общем 443 — по-прежнему волна 4.1;
- UFW: только `<порт>/tcp`, комментарий `kaskad-gw vless`, снимается при выключении и удалении.

## 6. Маршрутизация и kill switch

Путь пакета: приложение → TCP к узлу:порт → xray шлюза, вход `gw-vless` (Reality, UUID → email = логин) →
правила xray → исходящий. Ядро nft (метки, `gw_pre`, `gw_route`, dnsmasq) в пути **не участвует**: у клиента нет
адреса 10.77, его трафик рождается в xray. Порядок правил xray для пользователя VLESS:

| # | Правило | Откуда |
|---|---|---|
| 1 | частные, CGNAT, link-local, multicast, адреса узла, `localhost` → `block` | ядро, для всех клиентских входов |
| 2 | реклама/телеметрия (и торренты по переключателю) → `block` | волна 3, для всех пользователей xray |
| 3 | «всегда через выход» → маршрут устройства; «напрямую» (geosite) и сети России (geoip) → `direct` | волна 3, только профиль `ru_direct` и маршрут не «блок» |
| 3–4 | цепочка пользователя (§2.1): «всегда через выход», «напрямую» (если `ru_direct`), затем его маршрут (`target(route)`) | адаптер VLESS + волна 3 (`user_chain`) |
| 5 | всё прочее с входа → `block` — первый исходящий xray (по умолчанию) | ядро |

Маршрут → xray (`target` ядра, с политикой отказа):

| Маршрут | fail=block | fail=direct |
|---|---|---|
| `pool` | балансировщик `gw-all` по всем живым выходам (`gx-`), запасной `block` | `gw-all-direct`, запасной `direct` |
| `exit:<id>` | `gx-<id>`; выхода нет в пуле — `block` | балансировщик `b-<id>-direct`, запасной `direct`; нет выхода — `direct` |
| `direct` | `direct` | `direct` |
| `block` | `block` | `block` |
| пул пуст | `block` | `direct` |

Kill switch по слоям:

- **выходы умерли** — балансировщик с запасным `block` (fail-closed по умолчанию), observatory выбирает только
  живые; AWG-выходы — `freedom` с меткой 256+N: без ноги `gw_out` режет пакет (`meta mark … oifname != "kawg*" drop`),
  в интернет мимо туннеля он не уйдёт;
- **устройство или человек выключены** — UUID нет в конфиге: подключение не проходит Reality, клиент видит сайт-маску;
- **маршрут «блок»** — всё в `block`, и «Россия напрямую» его не открывает (правило 3 не строится);
- **xray не работает** — порт закрыт, подключиться некуда (fail-closed);
- DNS: приложения VLESS спрашивают DNS сами через туннель (их «удалённый DNS») — запросы идут по маршруту
  устройства; dnsmasq узла (10.77.0.1) VLESS не нужен, поэтому `exits.direct_needed` и `rules.apply.kernel_clients`
  VLESS не считают (как SOCKS5). Блок рекламы по домену работает, когда приложение отдаёт имя (sniffing на стороне
  клиента — так по умолчанию в v2RayTun, Hiddify, v2rayNG); соединение по голому IP проверяется только по geoip.

«Куда пойдёт трафик?» (`gw trace`, меню 17 → 9, панель, бот): VLESS, как SOCKS5, — «решает xray», пул — «любой живой
выход пула» (`balancer: any`); у устройства с несколькими входами можно выбрать «через VLESS».

## 7. Трафик и сессии

- пока вход VLESS включён, ядро добавляет в xray `stats`, `api` (`StatsService`, `HandlerService`, `RoutingService`,
  тег `gw-stats`), вход `stats-in` на **127.0.0.1:10854** (первое правило: `stats-in → gw-stats`) и
  `statsUserUplink/Downlink` уровня 0; нет входа VLESS — ничего этого нет, конфиг остальных узлов не меняется;
- `status()` адаптера (сборщик — раз в 10 с; `gw status`, `gw sessions`, сторож) зовёт
  `xray api statsquery --server=127.0.0.1:10854 -pattern user>>>`, берёт счётчики логинов VLESS (логины SOCKS5
  отбрасывает) и сравнивает с прошлыми из `/run/kaskad/gw/vless-traffic.json` (0600): рост за последние 120 с —
  устройство «в сети», `since` — первый рост после паузы; меньшее значение — xray перезапускался, счёт с нуля;
- в live.json: `devices.<id>` — `online`, `inbound: "vless"`, `addr: null`, `rx`/`tx` (rx — что прислал клиент);
  `inbounds.vless` — `sessions`, `rx`/`tx` (сумма по устройствам, держится между быстрыми раундами);
- ограничение: соединение без трафика дольше 2 минут показывается «не в сети» — у VLESS нет рукопожатий, как у
  WireGuard; для «Обзора» этого достаточно;
- API слушает только loopback; HandlerService и RoutingService управляют пользователями и правилами — их зовёт
  только ядро (root, `xray api …`); клиенты VLESS и SOCKS5 до loopback не доходят (§2.1). `gw_out` его не касается —
  это входящее соединение к xray.

**Подписка для приложений** — `GET /p/<токен подписки>/sub` (`kaskad.panel.userpage`, решение владельца §15.3):

- **токен** — свой на человека, не страницы: 43 знака base64url (256 бит), `secrets.json` → `user.<id>.sub` (0600; не
  в state.json, не в журнале, не в argv); включить, показать, сменить (старая ссылка — сразу 404), отозвать. От
  страницы **независим**: подписку можно дать без страницы и наоборот, выключение одной не трогает другую. Удаление
  человека снимает оба токена (`user.<id>.*`); «Удалить шлюз» с сохранением людей оставляет оба;
- **ответ** — `200 text/plain; charset=utf-8`, тело — base64 (стандартный, с паддингом) строк через `\n`: ссылки
  `vless://` и `hysteria2://` (как в выдаче выше) всех **включённых** устройств человека с выданным и включённым
  входом, без повторов; **за ними** (владелец 24.10: «в подписку — все протоколы») — `.conf` его AmneziaWG и WireGuard
  строкой `amneziawg://<base64url .conf без «=»>#<имя>` — формат incy (docs.incy.cc «subscription format»: строки
  `amneziawg://` смешиваются с `vless://` в одном теле, в том числе в base64), байт в байт как `all.txt` goAmnezia Pro;
  `.conf` — тот же, что в окне выдачи, имя — `goKaskad PRO · AmneziaWG 2.0 · <устройство>` (`issue_os.app_label`);
  внутри устройства 3.1 → 2.0 → 1.5 → WireGuard (`model.SUB_CONF_KINDS`). Ссылки VLESS и Hysteria2 от этого не
  меняются — ни текст, ни места. Приложения без `amneziawg://` (v2rayN, Hiddify — у его разборщика только `awg://`,
  `wg://`, `wireguard://`) строку пропускают; incy на компьютере `amneziawg://` не берёт (там только VLESS);
  v2RayTun заявляет AmneziaWG 2.0 (`amneziawg://`), вид ссылки не опубликован — проверка вживую. Забор подписки —
  не «выдали» (`ops.issue(…, mark=False)`, для всех протоколов подписки): пометка «ждут новых настроек»
  (SPEC-awg-engine §6.1) остаётся, «порт закрыт?» (`inlog.closed`) не запускается — приложение само обновляет
  подписку раз в 12 ч со всеми протоколами, а пользуется одним.
  Заголовки: `profile-title: base64:<«goKaskad PRO · <человек>»>` (в incy — имя карточки подписки, до 25 знаков),
  `profile-update-interval: 12`, `Cache-Control: no-store`, `X-Robots-Tag: noindex`; `Content-Disposition` нет;
- **пусто** (устройств с этими входами нет, вход выключен, человек приостановлен) — `200` с пустым телом, без промаха
  бана: приложение честно покажет «пусто», а при следующем обновлении подтянет появившееся;
- **неизвестный, сменённый, отозванный токен**, токен страницы вместо подписки, робот предпросмотра ссылок
  (Telegram, VK…) — тот же `404` пустого сайта и промах **общего** с `/p/` бана (10 промахов за 5 мин — 15 мин тишины);
- **SOCKS5** в подписку не входит: его ссылка — `socks5://логин:пароль@…`, а приложения ждут `socks://` v2rayN; другие
  входы ссылок для этих приложений не дают (`SUB_KINDS`, `SUB_CONF_KINDS`);
- **исключение из правила «страница не отдаёт ключи по GET»** — осознанное: подписка — отдельный секрет, который
  открывает только ключи устройств пользователя (VLESS, Hysteria2, AmneziaWG, WireGuard) и ничего больше; первая страница `/p/<токен страницы>` по-прежнему без ключей;
- **режим «сайт»**: nginx пропускает `location ^~ /p/` к панели как есть (`limit_req` 5 r/s, burst 40, без журнала
  доступа) — `https://<домен>/p/<токен>/sub`; журнал панели пишет путь как `/p/…`;
- **управление**: `kaskadctl page sub on|url|rotate|off <человек>`, `page sub list` (без ссылок); панель — кнопка
  «Подписка» у человека (ссылка, QR, сменить, отозвать), `GET|POST /api/gw/users/<id>/sub`; SSH-меню 17 → 2 → 12 →
  «Подписка для приложений»; **QR у пользователя и у устройства** (владелец 24.10, как вкладки «Статический ключ |
  Подписка» страницы goAmnezia Pro) — сначала окно выбора (`app.js` `qrPick`): «Подписка (обновляется сама)» с меткой
  «Рекомендуем» — первой (окно подписки пользователя), «Статический ключ» — второй (прежнее окно выдачи; у человека с
  несколькими устройствами — выбор устройства); подписке нечего отдать (пользователь выключен, у его включённых
  устройств нет включённых на узле VLESS, Hysteria2, AmneziaWG, WireGuard) — сразу статический ключ, без окна; MCP `page_sub_list`, `page_sub_url`, `page_sub_on`, `page_sub_off`,
  `page_sub_rotate`. Бота у страницы нет — нет и подписки.

## 10. Устройства и ключи

| Действие | Что происходит |
|---|---|
| выдать вход (`grant`) | новый UUID, клиент в xray через API (без перезапуска, §2.1) |
| снять вход (`revoke`), удалить устройство | UUID стёрт, клиента в xray нет (перезапуск — рвёт открытые соединения): ссылка не подключается |
| выключить устройство или человека | клиента в xray нет (перезапуск; UUID хранится): включили — та же ссылка работает, без перезапуска |
| `device reset … --inbound vless` | новый UUID: старая ссылка не подключается, выдать заново |
| сменить маршрут устройства | его цепочка правил xray заменяется через API (без перезапуска); на «блок» — перезапуск |
| сменить сайт (`gw vless mask`) | новые `serverNames`/`dest`: ссылки со старым `sni` не подключатся — перечень устройств «выдать заново» |
| новые ключи (`gw vless rekey --yes`) | новые ключ узла и shortId, UUID те же: все ссылки — заново (перечень) |
| включили / выключили сайт, сняли домен, `gw vless sync` | режим TLS ↔ Reality (§4.5): все ссылки — заново (перечень) |
| выключить вход | вход пропадает из xray, порт закрыт в UFW |
| удалить вход | запись и ключ узла сохраняются для переустановки (тот же порт, сайт, ключ) |
| `gw purge` | всё, кроме паролей устройств и ссылок страниц, как у других входов |

## 11. Что нужно мастеру «Быстрый старт»

Мастер показывает VLESS в сетке протоколов. Данные — без новых команд:

- **карточка в сетке**: `kind: "vless"`, заголовок «VLESS», подпись «телефоны и компьютеры: v2RayTun, Hiddify,
  Streisand — с сайтом узла TLS на 443, без — Reality», значок — как у панели; по умолчанию **не отмечен** — решение
  владельца (мастер панели `setup/product.py` `on: False`, мастер SSH — пункт 9 без отметки);
- **доступность и порт** — `gw inbound plan vless --json` → строка `{kind, title, supported, why, packages: [],
  port: {field: "port", protos: ["tcp"], port, default, conflicts, free}, kept}`: port — 443 или 8443 (что свободно),
  `conflicts` и `free` — если оба заняты; apt не нужен;
- **xray**: `requirements.needs = ["kaskad-gw-xray.service"]` — если на узле ещё нет xray, установка скачает его с
  GitHub (до минуты); мастеру стоит сказать «скачаю xray»;
- **маскировка до установки** (необязательно): `gw vless masks --json` работает и без входа — первым идёт свой сайт
  узла, если он есть; `--check` проверяет все (до 5 с на сайт). Установка выбирает сама (свой сайт, иначе первый
  ответивший), в `notes` — строка «маскировка — …»;
- **установка**: `gw inbound install vless --new-only [--port N] --json` → `record` (port, sni, dest, mask,
  mask_check, pub, short_id, fp), `notes`;
- **после установки**: `gw vless show --json` — для итогового экрана («VLESS: порт 8443, маскировка
  www.microsoft.com ✓»); устройства — `gw device add … --access vless` / `gw device grant <dev> vless`, выдача — как у
  всех (`gw issue`).

## 12. Секреты

- приватный ключ узла и UUID — только в `secrets.json` (0600) и в `xray.json` (0600, служба получает копию через
  `LoadCredential`); в state.json, журнал, `gw status`, `inbound list`, `vless show`, схему, live.json, ответы
  `mask`/`rekey` они не попадают — тесты это проверяют;
- ни один секрет не идёт в argv: ключи считаются в Python, конфиг проверяется `xray -test -c <файл>`; горячее
  добавление передаёт UUID в `xray api adu` файлом 0600 (удаляется сразу), `rmu` получает только логины;
- закрытый ключ сертификата домена для xray — копия 0640 root:kaskad-xray в каталоге 0750 (§4.4);
- выдача — единственное место с UUID (ссылка, QR, поля), предупреждение «ссылку нельзя пересылать».

### 12.1 Копия настроек и перенос

Копия (`backup export`) несёт запись VLESS как есть (режим, порт, маскировку) и ключ узла. На новом сервере вход
ставится с сохранённой записью, затем `site.front.sync` сверяет режим с **этим** узлом: записи «TLS на домене X» без
сайта здесь (домен другой или ещё без сертификата) — Reality на 443 по стране нового узла; «свой сайт узла» чужого
домена — тоже автоподбор. Итог импорта: «сменились настройки протоколов (vless: режим VLESS (Reality / TLS), сайт
маскировки VLESS) — устройствам этих протоколов выдайте настройки заново». Когда здесь выпустят сертификат и включат
сайт — VLESS перейдёт на TLS сам, ссылки — ещё раз.

## 14. Живая проверка на стенде (выход goAmnezia, домен)

1. `gw inbound install vless` на узле без сайта → порт 443, маскировка проверена; с сайтом в режиме «сайт» → 8443,
   маскировка — свой домен; `curl -vk https://<узел>:<порт>` снаружи показывает сайт-маску.
2. Устройство Android (v2RayTun) и iPhone (v2RayTun / Streisand) — по QR; Windows (Hiddify) — по ссылке.
   Открываются сайты; `ifconfig.me` — адрес выхода goAmnezia; `ya.ru` при «Россия напрямую» — адрес узла.
3. «Обзор» панели: устройство «в сети», трафик растёт; `gw sessions` показывает vless.
4. Выход выключить (или уронить ногу) → у устройства с маршрутом «пул, при отказе — блок» сайты не открываются,
   адрес узла наружу не светится; «при отказе — напрямую» → открываются с адреса узла.
5. `gw device revoke`, выключение человека — подключение пропадает; `gw vless mask dl.google.com` и
   `gw vless rekey --yes` — старая ссылка не подключается, новая — да.
6. Меню 17 → «Протоколы» → VLESS: смена сайта цифрами, «проверить все», новые ключи.
7. Горячее добавление: при открытом соединении через выход VLESS и SOCKS5 добавить устройство VLESS — соединения не
   рвутся, `journalctl -u kaskad-gw-xray` без перезапуска, в журнале Kaskad «без перезапуска — пользователей +1».
   Сломать API (старый xray) — перезапуск, устройство работает.
8. TLS: узел с доменом, `site mode site` → `curl -v https://<домен>/` — сайт (через xray, HTTP/1.1), панель по
   секретному пути и `/p/…` открываются, бан `/p/` видит настоящий адрес (журнал панели); `openssl s_client
   -connect <IP>:443 -servername other.example` — отказ рукопожатия; ссылка TLS в v2RayTun/Hiddify подключается;
   `ss -lx | grep kaskad-vless` — сокет nginx; перезагрузка — сайт и VLESS поднимаются (tmpfiles).
9. `site mode domain` → VLESS Reality на 443, ссылки заново; `gw disable` при включённом сайте → сайт на 443 сам.
10. Продление: `certbot renew --force-renewal --cert-name <домен>` → `/opt/kaskad/gw/tls` новый, xray не
    перезапускался, через час (или после `systemctl restart`) клиенты видят новый сертификат.

## 15. Решения владельца (2026-10-09) и кандидаты

1. Порядок выдачи — VLESS после AmneziaWG (так и есть, `ops` матрица `_FIRST`).
2. Сайты маскировки — по стране сервера, как goVLESS Pro (§4.2); с доменом и сайтом — TLS (§4.4).
3. Подписка (§8) — сделана: `GET /p/<свой токен>/sub`, токен на человека, независим от страницы, со сменой и отзывом.
4. Мастер «Быстрый старт» — VLESS по умолчанию не отмечен (так и есть).
5. Горячее добавление — сделано (§2.1). Отзыв, выключение, новый UUID, маршрут «блок» — перезапуск xray (решение
   владельца: отзыв рвёт сразу, операция редкая); человеку честно: «VLESS переподключится у всех на пару секунд»
   (предупреждение результата, «последствия» схемы в панели).
6. Домен без сайта (режим «домен») — Reality; TLS без сайта не нужен (решение владельца).
7. ~~Кандидат 3.4.0~~ **сделано в 3.3.7.x:** ручной выбор «Reality даже при включённом сайте» (белые списки мобильных
   операторов РФ пропускают Reality с SNI из списка, а свой домен узла в такой список не попадёт) — «Маскировка VLESS»
   → Reality после текста рисков; сайт узла при этом остаётся, VLESS уходит с 443 (`SPEC-vless-tls-default.md` §3.5).
8. **3.3.7.x (решение владельца 20.10):** TLS со своим доменом — по умолчанию для новых установок; Reality — запасной
   вариант и сознательный выбор с согласием на риски (`SPEC-vless-tls-default.md`).

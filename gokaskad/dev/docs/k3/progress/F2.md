# F2 — находки критика-сисадмина (разбор 3.1.0)

База: `bc802bc` (голова k3 с волной 3). Порядок: №3 → R-perf → №8 → №5 → №7 → №9.

## Готово

- **№3 DNS шлюза рядом с чужим резолвером на :53.**
  - dnsmasq шлюза слушает `10.77.0.1:5354` (`port=5354`, `bind-interfaces`).
  - Новая цепочка `gw_dns` в `ip kaskad` (nat prerouting, приоритет -102 — раньше `fwd_pre` и iptables nat): DNS клиентов (источник из базы, `10.77.0.1:53`, udp и tcp) → DNAT на `10.77.0.1:5354`. У клиентов DNS прежний — `10.77.0.1`.
  - Юнит `kaskad-dns` — `Type=forking` + `PIDFile`: занятый порт валит сам `systemctl start`, а не «работает» с перезапуском каждые 5 с.
  - `gw enable`/`gw apply` предупреждают «DNS шлюза не запустился: порт 5354 занят: <процесс>» (или строка ошибки dnsmasq из журнала).
  - `gw check` — проблема `gw_dns` с причиной; `gw probe --json` — ключ `dns` (`port`, `busy`, `warning`).
  - Обновление с 3.1.0: `gw apply` (его зовёт install.sh) ставит цепочку и переписывает конфиг и юнит; без него сторож (`net check --repair`) делает то же сам. Таблица без `gw_dns` не считается «пропавшей частью шлюза» — соединения клиентов не сбрасываются.
  - Правила «Россия напрямую» (nftset, address=, max-cache-ttl) не тронуты; golden-файлы обновлены только на 5 строк новой цепочки.

- **R-perf: сборщик и `gw check` без выгрузки всей таблицы.**
  - Новый `gw/peek.py`: `nft -j list chains ip`, `list counters table ip kaskad`, `list map ip kaskad gw_route`, `list set ip kaskad gw_live`, `list set ip kaskad gw_rd`. Результат — в форме `nft.read_live`, но без `gw_ru` и правил.
  - Круг сборщика (`collect.exits_tick`) и `ops.check` читают через него. Полное чтение остаётся там, где нужно сравнение правил: применения (`nft.apply`) и минутный сторож `net check` (код волны 1).
  - Замер на фейке (`gw_ru` — 15 003 диапазона, сцена test_gw_net + «Россия напрямую»):

    | путь | до (bc802bc): вызовов / JSON | после: вызовов / JSON |
    |---|---|---|
    | круг сборщика (каждые 10 с) | 1 / 1 252 150 байт | 5 / 2 473 байта |
    | `gw check` (`ops.check`) | 2 / 1 253 016 байт | 3 / 2 547 байт |

- **№8 обрыв SSH посреди операции меню.**
  - `gw/sys.py`: `hold()` / `@held`. Пока идёт изменение: SIGHUP и SIGINT — SIG_IGN (его наследуют systemctl, nft, ip — их обрыв тоже не рвёт), SIGTERM только запоминается (строка в журнале). Изменение доводится до конца, state.json сохраняется. stdout/stderr не падают на EIO/EPIPE (текст теряется, изменение — нет). Вне главного потока (панель, бот) ничего не меняется.
  - `ops.py`: `hold` на блоке под замком в `_change`, `apply_all`, `enable`, `disable`; `@held` на `inbound_uninstall`, `purge`, `teardown` (у них шаги и после замка). Подготовка до замка (apt, сборка) по-прежнему прерывается — состояние ещё не тронуто.
  - `apt_install`: если HUP уже игнорируется (меню, hold), он остаётся игнорируемым и внутри старого guard — apt-get и dpkg не убивает обрыв SSH.
  - install.sh, `k3_gw`: `$(trap '' HUP; k3ctl gw …)` — ядро из меню запускается с игнорируемым HUP.

- **№5 UFW включили позже или сделали `ufw reset`.**
  - `ufw.json` входа теперь хранит и нужные порты (`want`), и открытые (`open`), и подпись файлов UFW (`/etc/ufw/user.rules`, `user6.rules`, `ufw.conf`: mtime и размер). Старый формат 3.1.0 (список) читается.
  - `sync_ufw` (apply): если файлы UFW менялись с прошлой сверки, «открытые» проверяются по `ufw status`, а не берутся на веру — `gw apply` после `ufw reset` снова открывает порты.
  - Сторож: `ufw_check` из `gw check --repair` (`ops.check`, 2 строки). UFW активен → все `want` должны быть разрешены; недостающие дописываются. Явный DENY/REJECT владельца — только проблема, без борьбы. Дёшево: `ufw status` только при смене файлов UFW или раз в 5 минут; без UFW или при выключенном — ничего.

- **№7 модули PPP только при установке входа.**
  - `accel.py`: `extra_packages` — на Ubuntu ставится `linux-modules-extra-$(uname -r)`, если модуля нет, и метапакет flavor, чтобы extras получали и следующие ядра: generic с `linux-generic`/`linux-image-generic` — ничего (extras и так тянутся); generic с `linux-virtual` — `linux-image-extra-virtual` (`-hwe-24.04` при HWE; тянет `linux-image-generic` и linux-firmware, ~0.8 ГБ — мастер предупреждает); aws/azure/gcp — `linux-modules-extra-<flavor>`; прочие — только extras текущего ядра. На 24.04 flavor `-kvm` нет (`linux-kvm` — переходный пакет на `linux-virtual`). Debian — ничего (модули в образе ядра).
  - Установка входа ставит их до проверки модулей; `requirements` (мастер) не отказывает, если extras принесут модули.
  - `gw check`: `module_problems` — для включённых L2TP/PPTP/SSTP нет модулей работающего ядра → проблема `gw_kernel` с командой (`apt-get install linux-modules-extra-<ядро> <метапакет> && systemctl restart kaskad-gw-accel.service`). Сторож (`--repair`) apt не запускает — пишет строку в журнал (раз в час на вид).

- **№9 свои демоны на удалённом бинаре (часть «работа на удалённом бинаре»).**
  - `gw/sys.py`: `stale_check` — наши юниты (`kaskad-gw-*.service`, `kaskad-dns.service`), у которых `/proc/<MainPID>/exe` = «… (deleted)»: проблема `gw_binary`; с `--repair` — `systemctl try-restart --no-block` и строка в журнале. Не чаще раза на юнит за обновление: запоминается (путь, mtime нового файла) в `/run/kaskad/gw/exe-restarts.json`. MainPID всех юнитов — одним `systemctl show -p MainPID --value …`.
  - `ops.check`: 1 строка. Не во время загрузки (как остальные службы).

Все пункты задания закрыты. Тесты: `tests/test_gw_f2.py` (32), обновлены golden-файлы nft (+5 строк цепочки `gw_dns`), фейки nft/systemctl/ufw/journalctl.

## Не сделано / продолжить (проект на паузе)

- **Минутный сторож `net check` (волна 1, `netcheck.py`) по-прежнему читает всю таблицу** — ~1,25 МБ JSON раз в минуту при 15 тыс. диапазонов `gw_ru`. Ему нужны правила и тип/версия `gw_ru`, но не его элементы. Варианты: `nft -j -t list table ip kaskad` (terse — проверить на стенде, что JSON его учитывает и не печатает `elem`), либо чтение по частям как в `gw/peek.py` (+ `list chain` каждой цепочки, `list set ip kaskad gw_ru_ver`, тип `gw_ru` из `list sets`). Файл не мой — не трогал.
- **Обновление xray и accel-ppp через меню** (№9, вне задачи — идея): xray шлюза — копия из `/opt/kaskad/gw/xray`, обновлять вместе с xray «Прокси для API Telegram» (`--egress-ensure-xray`) и перезапускать `kaskad-gw-xray`; accel-ppp — новая версия = новые `VERSION`/`SHA256`/`SIZE` в `accel.py`, сборка в stage и замена `/opt/kaskad/accel-ppp` (как `copy_stage`), затем перезапуск (рвёт сессии PPP — только по кнопке).
- **Панель и бот** вызывают изменения в рабочих потоках: `hold()` там сигналы не трогает (нельзя вне главного потока). SIGTERM панели/бота посреди изменения по-прежнему может его оборвать (daemon-потоки умирают с процессом). Нужно: по SIGTERM ждать завершения идущего изменения. Не моя зона.
- Не обёрнуты в `hold`: `gw accel on/off` (WP-K, `awgkmod`), `gw rules …` (WP-R), `gw hook` (вызов из ip-up accel-ppp). Сбой `_apply` с ошибкой посередине (не сигнал) по-прежнему оставляет полуприменённое состояние — отдельная тема.
- DNS: порт 5354 фиксирован. Если его займёт чужой процесс, DNAT отдаст ему запросы клиентов — `gw probe`/`gw check` об этом говорят, автоматического выбора порта нет. Экран меню (F2b) может показывать `gw probe --json` → `.dns.warning`.
- Мастер установки PPP на Ubuntu с `linux-virtual`: `requirements().warning` предупреждает о `linux-image-extra-virtual` (~0,8 ГБ с linux-firmware); экран подтверждения — у F2b.

## Риски

- **Откат на 3.1.0** после этой версии: код 3.1.0 не знает цепочку `gw_dns` и не удаляет её, а dnsmasq вернёт на :53 → DNS клиентов сломается. При откате: `nft flush chain ip kaskad gw_dns; nft delete chain ip kaskad gw_dns`, затем `kaskadctl gw apply` (3.1.0 перепишет kaskad.nft без неё).
- `Type=forking` у kaskad-dns: dnsmasq пишет `/run/kaskad-dns.pid` до сброса прав — проверить на стенде, что `systemctl start` ждёт и видит MainPID.
- Формы `nft -j list chains ip`, `list counters table ip kaskad`, `list map|set ip kaskad <имя>` проверены только на фейке — проверить на стенде (команды ниже).
- `hold()` игнорирует SIGINT: Ctrl+C во время изменения шлюза не прерывает его (так и задумано) — меню продолжит после окончания.

## Живая проверка (Debian 12, Ubuntu 24.04)

№3 DNS:
```
apt-get install -y dnsmasq            # пакетный dnsmasq слушает *:53 — «чужой резолвер»
kaskadctl gw apply
nft list chain ip kaskad gw_dns       # два правила dnat to 10.77.0.1:5354
ss -lunpt 'sport = :5354'             # dnsmasq шлюза на 10.77.0.1:5354 (udp и tcp)
systemctl show -p Type,MainPID kaskad-dns    # Type=forking, MainPID != 0
# с клиента (WG, L2TP/PPP, IKEv2): ответы есть, AAAA нет
dig @10.77.0.1 example.com; dig +tcp @10.77.0.1 example.com; dig AAAA google.com @10.77.0.1
conntrack -L -p udp --orig-port-dst 53 | grep 10.77.0.1   # в ответе sport=5354, клиенту уходит 53
journalctl -u dnsmasq --since -5min   # пакетный dnsmasq запросов клиентов не видит
# «Россия напрямую»: у ru_direct-клиента спросить «прямой» домен -> адрес в nft list set ip kaskad gw_ru_dns
# занятый порт:
systemctl stop kaskad-dns; python3 -c 'import socket,time;s=socket.socket(2,2);s.bind(("0.0.0.0",5354));time.sleep(600)' &
kaskadctl gw apply                    # «Внимание: DNS шлюза (kaskad-dns.service) не запустился: порт 5354 … занят: python3»
kaskadctl gw check; kaskadctl gw probe --json | jq .dns
kill %1; kaskadctl gw apply           # откат
# обновление с 3.1.0: на узле 3.1.0 обновиться — gw_dns в таблице, port=5354 в /etc/kaskad/gw/dnsmasq.conf
apt-get remove -y dnsmasq             # откат «чужого резолвера»
```

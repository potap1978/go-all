## Исправление блокера gw_ru (стенд T1, находка 1.1)
Было: диапазоны gw_ru (~15 тыс., concat) входили в каждый `nft.apply` до первой удачной загрузки. Сухой прогон `nft -c`
шёл 100 с, раннер убивал его через 60 с, `gw device route` висел 2–3 мин, а сторож раз в минуту запускал то же самое.
Стало (решение координатора: concat, без `nft -c` по диапазонам):
- `render_update` и `render_full` (загрузочный файл) только объявляют gw_ru и gw_ru_ver, элементов в них нет. Ни один
  `nft -c` (check, check(full), probe кроме пробы с двумя диапазонами) не видит диапазонов.
- `gw/net.py:load_ru` — отдельная транзакция `nft -f -` (flush gw_ru + куски по 5000 + элемент gw_ru_ver), таймаут
  `RU_LOAD_TIMEOUT` = 30 с, без `nft -c`.
- `rules/apply.py:ensure_kernel` решает, когда грузить. Версию в таблице читает отдельно (`nft -j list set ip kaskad
  gw_ru_ver`), всю таблицу не выгружает; при совпадении ничего не делает. После неудачи — пауза 5/15/60/180 мин
  (состояние в /run/kaskad/gw/rules-load.json), в журнал одна строка на серию неудач; новая версия списков — сразу.
- Кто грузит: `kaskadctl rules load [--force] [--quiet]` от нового `kaskad-gw-rules-load.timer` (OnBootSec=20s после
  kaskad-net, затем каждые 5 мин) и `rules update` после новых списков. Устройства, `gw apply`, `net check --repair`
  и сборщик диапазоны не трогают. `gw check`/`gw status` только сообщают «сети России не загружены …».
- Пока загрузки нет, gw_ru пуст: шлюз и пробросы работают, напрямую по сетям никто не идёт (fail-closed).
- gw_ru другого типа (3.1 — plain) удаляется и создаётся заново в update_lines (после flush цепочки), вместе с
  очисткой gw_ru_ver.
- `tools/rules_nft_bench.sh`: ИТОГ учитывает загрузку `nft -f` (лимит 30 с), цену add element (≤ 5 мс) и показывает
  `nft -c` (дольше 2 с — прогонять нельзя).

Цифры стенда (Ubuntu 24.04, ядро 6.8, nft 1.0.9, 1 vCPU, 14 963 диапазона): concat — `nft -c` 99,7 с, `nft -f` 0,67 с,
add element 4,9 мс (как без набора), list -j 246 мс, +33 МБ; plain — `nft -c` 0,16 с, `nft -f` 0,16 с, add element 53 мс.

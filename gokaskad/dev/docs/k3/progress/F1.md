# F1 — исправления находок критика (разбор 3.1.0): ход работы

Основа — `k3` (bc802bc). Порядок: №2 → №6 → №10 → №4 → №11e. Проект на паузе (решение владельца 2026-10-05):
№2, №6, №10 и ip6-часть №4 сделаны; основная часть №4 и №11e — не начаты, план ниже. `bash tools/k3_test.sh` — зелёный,
payload пересобран.

## Готово

- **№2** — правила ip rule одним блоком с закреплёнными pref (`gw/net.py`, раздел «routing»): 4000 ответы (0x10000),
  4001 `to <база> lookup main` (заменил `from база to база`, 31998), 4002 0x200, 4003 0x300/0xff00, 4004 аварийный,
  4004+N правило ноги N (его ставит install.sh, сторож только переносит в слот — ниже `to <база>`).
  Сторож (сборщик каждые 10 с, `net check` каждую минуту) спрашивает ядро: `ip -4 route get 1.1.1.1 from <база+2> iif
  kgw0 mark M` по классам (0x200/0x301 → local table 200, 0 → unreachable, 0x10000 → main, 256+N → table 256+N или
  unreachable при лежащей ноге). Решает чужая таблица → блок встаёт выше самого верхнего чужого правила (сначала новые,
  потом старые — выключатель не пропадает), в журнал: `GW routing: чужое правило «…» стоит выше правил Kaskad: … — правила
  Kaskad переставлены выше (pref A–B)`. Чужое ушло → блок возвращается к 4000 (без «храповика»). Не чинимое (чужое
  правило на pref 0, нет места выше) — только `gw check` (`gw_conflict`), сборщик его не повторяет (он логирует каждую
  починку). Pref 0 для своих правил отвергнут: все поздние правила без pref тоже получили бы 0 и шли бы по порядку
  добавления — у wg-quick `not fwmark` встал бы выше `suppress_prefixlength 0`, LAN/Docker узла ушли бы в туннель.
  Миграция 3.1.0 (31993–31999) — сама, при первом проходе. Точечно в `gw/ops.py` (check): `routing_conflicts`.
- **№6** — строгий rp_filter: `rp_filter=2` только на интерфейсах шлюза (kgw-*, kgw0, kawg*), `all`/`default` не
  трогаются; `/etc/sysctl.d/90-kaskad-gw-rpf.conf` с шаблонами для новых интерфейсов (systemd-sysctl через udev), уходит с
  `gw disable` (значения на оставшихся ногах остаются). `gw check` — `gw_rp_filter` с починкой; строгий kgw0 —
  в `routing_problems` (через kgw0 сторож спрашивает ядро). Проверка источника клиентских пакетов ноги проходит и при
  строгом фильтре без настройки интерфейса: `to <база>` стоит выше правил ног (важно для PPP: accel-ppp переименовывает
  ppp0 → kgw-l2tp0, шаблон udev может не успеть). IKEv2 ядро не проверяет (secpath). Имена интерфейсов входов сверены:
  все `kgw-*` (wg, awg1-3, l2tp/pptp/sstp*, ovpn-u/t, oc*); у IKEv2 и SOCKS5 интерфейсов нет.
- **№10** — таблицы 199/200: свои маршруты только `ip route add` (replace подменял чужой `default via` по префиксу и
  метрике); таблицу с чужими маршрутами, чужими правилами `lookup 199|200` или именем в rt_tables шлюз не трогает (не
  ставит и не убирает), `gw probe`/`gw enable` отказывают (`ops.support`, код `gw_conflict`, «что нашли и что делать»),
  `gw check` — `gw_conflict`. Внутренние порты xray (12345, 12400+N VLESS, DNS, 10852) — `ss -Hltnup`: занят не MainPID
  `kaskad-gw-xray` → отказ probe/enable с именем программы. DNS xray 5353 → **10853** (`xray.DNS_PORT`; в `gw/dns.py`
  одна строка `POOL_SERVER` — зона F2, тест держит их равными); переход сам при `gw apply` после обновления
  (install.sh `--k3-post-update`). Перенос номеров таблиц в state — не делался (необязательно).
- **№4, ip6-часть** — ядро с `ipv6.disable=1`: таблица ip6 kaskad6 не рисуется вовсе (`net.ipv6_off()` по
  `/sys/module/ipv6/parameters/disable`): её `ct direction` без IPv6 не грузится и валила весь kaskad.nft вместе с
  пробросами, а `gw probe` отказывал шлюзу. ip6_problems/apply_ip6/teardown/probe её тоже пропускают.

Тесты: `tests/test_gw_net.py` — RoutingTest (wg-quick после загрузки, Tailscale, миграция 3.1.0, чужое внутри блока,
pref 0, без лишних движений), RpFilterTest, TablesAndPortsTest, Ipv6OffTest. Двойник `ip` (`tests/fakes_gw.py`) знает
порядок правил ядра (pref по умолчанию = второе правило − 1, вставка после равных), `ip route get … iif … mark …`
(обход правил, suppress_prefixlength, проверка источника max(all, iface) с src_valid_mark) и `ip route add` (EEXIST
по префиксу и метрике).

## Не сделано — план для продолжения

### №4 (основное): запасной текст «только пробросы», пауза перед повтором

Учесть от координатора: полная загрузка может падать и по таймауту (gw_ru ~15 тыс. диапазонов, `nft -c` > 60 с — чинит
WP-R), повторы не должны снова и снова гонять тяжёлую проверку; правки в nft.py — компактно (WP-R тоже трогает nft.py).

1. `nft.py`: файл `/etc/kaskad/net/kaskad-forwards.nft` = `_table_text(TABLE_NAME, fwds, counters)` (без секций) —
   пишет `_write_files` рядом с kaskad.nft (атомарно, 0600, только если текст другой).
2. `units.py`, kaskad-net.service: `ExecStart=/bin/sh -c '<nft> -f <kaskad.nft> || <nft> -f <kaskad-forwards.nft>'`
   (shlex.quote путей): юнит не падает, ExecStartPost (`net check --repair`) ставит выключатель. Обновляется
   `net install-units` (post-update).
3. `nft.restore()`: файл → перерисованный полный текст (как сейчас) → иначе «только пробросы» (`nft -f -`), лог
   `NET restore: полная таблица не загрузилась (<ошибка>) — загружены только пробросы, клиенты шлюза закрыты`.
4. `nft.apply()`: если не прошли ни обновление, ни полный текст, секции активны и части шлюза в живой таблице нет:
   пробросы в живой таблице уже как в state → ничего не применять, `KaskadError(«часть шлюза не загружается: … —
   пробросы работают отдельно, шлюз закрыт», data={"stage": "gateway", "degraded": True})` (сторож показывает, не
   пишет файл, не логирует каждую минуту); иначе (fwd add в этом состоянии) — применить `render_update` без секций,
   проверить только пробросы, записать файлы, вернуть `{"degraded": <ошибка>, "warnings": [...]}`. Часть шлюза в живой
   таблице есть → как сейчас (не ронять рабочий шлюз).
5. Пауза: `/run/kaskad/nft-degraded.json` `{"at", "error", "fails", "next"}`, next = now + min(60·2^fails, 3600);
   до `next` apply/restore/сборщик полный текст не проверяют (сразу п.3/п.4 с «следующая попытка в …»); таймаут
   Runner = неудача; успешный полный apply удаляет файл.
6. Видимость: `cli_net.cmd_status` — 2 строки `# F1`: «шлюз: часть шлюза не загружена — <причина>; пробросы
   работают, клиенты шлюза закрыты»; `gw/ops.py` check — точечный вызов (`gw_table`, repaired False). Gate входов и
   выключатель 4004 удерживают шлюз закрытым — уже так.
7. Тесты: FakeNft `fail_apply`/`fail_check` с функцией, отвергающей текст с `tproxy`; restore грузит только пробросы;
   повтор в окне паузы не вызывает `nft -c` полного текста; текст юнита.

### №11e: клиентам шлюза — только 10.77.0.1 (DNS, ping) и адреса интерфейса маршрута по умолчанию

1. `gw/net.py`: `plan()["host"]` = IPv4-адреса интерфейсов маршрутов `default` таблицы main (`ip -4 route show table
   main`, строки default и их `nexthop … dev`; `ip -4 -o addr show dev X`) + `gateway.host`, если это IPv4; без адресов
   базы. Набор `gw_host { type ipv4_addr; }` (SETS/SET_SPECS, `_table_lines`, `update_lines`, verify, teardown).
2. gw_pre: вместо `fib daddr type local meta mark set 0x202 ct mark set ct mark or 0x202 return` —
   `fib daddr type local ip daddr @gw_host meta mark set 0x202 ct mark set ct mark or 0x202 return`,
   `fib daddr type local ip daddr @gw_nets icmp type echo-request meta mark set 0x202 ct mark set ct mark or 0x202
   return`, `fib daddr type local ct direction reply return` (ответы на соединения самого узла),
   `fib daddr type local counter drop`. DNS 10.77.0.1:53 разрешён правилом выше; пробросы волны 1 (DNAT на -101 идёт
   после gw_pre на -150) приходят на публичный адрес — он в gw_host; IKEv2 — так же.
3. `update_map()` (сборщик, 10 с) обновляет и gw_host — смена адреса по DHCP; `probe()` — образец `host`.
4. Тесты: FakeNft — формы `icmp type echo-request`, `ct direction reply return`, `counter drop`; golden-файлы
   `gw_full.nft`, `gw_update_fresh.nft`, `gw_rules_concat.nft`, `gw_rules_plain.nft` перегенерировать

## Не сделано (проект на паузе) — что и как делать дальше

**6. Выходы умерли — красная строка и итог «Состояния».**
- Шапка 17 (`k3_gw_header`, install.sh): красная строка «Интернет у устройств сейчас отключён: сервер выхода не отвечает».
  Дёшево, без ядра — jq по `/run/kaskad/live.json` (пишет kaskad-gw-collect раз в 10 с; путь `${KASKAD_ROOT}/run/kaskad/
  live.json`, формат — gw/live.py: `.exits[id] = {alive, kind, enabled, state}`, `.gateway.enabled`) и state.json
  (`.gateway.routes.default = {via, fail}`). Правило: шлюз включён; маршрут по умолчанию `pool` или `exit:<id>`,
  `fail` ≠ `direct`; среди выходов `kind ∈ {awg, vless}` и `enabled` нет ни одного `alive` (для `exit:<id>` — этот
  выход не alive) → красная строка. `fail = direct` → жёлтая «сервер выхода не отвечает — устройства выходят напрямую,
  с адреса этого сервера». Пул пуст и маршрут `pool` → «интернета у устройств нет: добавьте ключ VPN — 17 → 3 → 3».
  live.json нет или старше 60 с (`.ts`) — строку не писать (сборщик не работает — это видно в «Состоянии»).
  Ту же функцию (например `k3_gw_net_down`, код 0 — «интернета нет») может взять WP-I для красной пометки
  «нет интернета» у пункта 17 главного меню — договориться, чтобы не было двух разных проверок.
- «Состояние» (17 → 5 = `kaskadctl gw status`, gw/cli.py `cmd_status`): первой строкой итог — «Итог: всё работает» или
  «Итог: есть проблемы: …» (шлюз выключен; включённый протокол не работает — «не работает протокол X»; рабочих выходов
  нет при маршруте через VPN — «интернет у устройств отключён: сервер выхода не отвечает»; DNS шлюза не работает;
  `doc["problems"]` из ops.check — их `detail`), второй — «Подключено сейчас: N устройств» (сумма `sessions`
  включённых входов из `doc["inbounds"]`; точнее — число разных `device` в `collect.read_sessions()`). В строке
  выхода убрать id: «  «Вена» (VLESS) — работает». Тесты: tests/test_gw_ops.py (класс со `gw status`), раздел 23
  tools/k3_install_test.sh (`t_gwst` проверяет только `  шлюз: включён` — добавить итог).

**10. Два SSH-окна, правило на один порт.** Сейчас `forwards.add_forward` (lib/kaskad/forwards.py) под
`state.locked()` молча заменяет проброс того же proto:port (так было и в 2.x, бот пишет «Заменён прежний проброс»).
План: параметр `replace=True` (по умолчанию — как сейчас: бот и панель не меняются) и флаг CLI `fwd add --no-replace`
(lib/kaskad/cli_fwd.py) → под замком, если проброс порта уже есть и ведёт в другое место — `ConflictError` (код 3),
`data = {"kind": "forward", "conflicts": [...]}`, текст «Порт tcp 8443 уже занят правилом → 198.51.100.7:8443 (имя).
Правило не создано». В меню (install.sh): `configure_rule`/`configure_custom_rule` до пинга проверяют `get_rules_list`:
порт занят → «Порт 8443 уже занят правилом → X. Заменить его? (y/n)»; «y» — добавление как сейчас (с заменой), иначе
`K3_FWD_KEEP=1` → `k3_fwd_add` передаёт `--no-replace`; код 3 с `kind = forward` — без «Всё равно? (y/n)» и без
`--force`: «[ERROR] Правило не создано: порт уже занят правилом … — его только что добавили, например, из другого окна
SSH». Старый движок (`apply_iptables_rules` уже под `k3_legacy_locked`): при `K3_FWD_KEEP=1` до `remove_rules_for_port`
проверить `iptables -t nat -S PREROUTING | grep kaskad:<port>:<proto>` → отказ тем же текстом. Тесты:
tests/test_forwards.py (два добавления с `replace=False`: второе — код 3, первое правило цело), раздел 4/5
tools/k3_install_test.sh (поддельный kaskadctl: `fwd add … --no-replace` с conflict.json kind forward).

## 0. Итог в восьми строках

1. Политика выходов — **список групп**. У каждой группы своя роль, уровни выходов, способ выбора, блоки условий
   ухудшения и возврата (каждый со своим действием) и **последний шаг**: блок или «с сервера напрямую».
2. Группа **«Основная»** (`main`, зарубежная) = нынешний пул. Обновлённый узел — это одна «Основная» в режиме «Как
   раньше», поведение SE §1.3 не меняется.
3. **Роль группы** — зарубежная или российская, задаётся при создании и не меняется. Выход входит ровно в одну группу (D-045).
   Ключи российских групп лежат в **отдельном файле** `upstream-ru.txt`: в обычный пул, в «Прокси для API
   Telegram», в DNS узла и при откате на 3.3.3 они не попадают никогда.
4. Человек или устройство выбирает **зарубежную группу** маршрутом (`pool` = «Основная», `group:<id>` — другая) и
   отдельно **российскую** — полем `ru_via` для «Россия напрямую». По умолчанию `ru_via` у всех `direct`, как сейчас.
5. **Ядро:** для выбранных людей российские адреса (`gw_ru`, `gw_ru_dns`) получают метку закреплённого российского
   выхода через новую карту `gw_rx`, а не `0x201`. Группа «всегда через выход» (`gw_force`) идёт по зарубежному
   маршруту, как сейчас.
6. **xray:** правила «российские сайты» в цепочке пользователя VLESS или SOCKS5 указывают на `gr-<выход>` вместо
   `direct`. Правка горячая, через `hot_apply`, без перезапуска xray.
7. **Российские выходы проверяет сам Kaskad** по российским целям, без observatory и без HTTP-запросов к Яндексу в
   частых пробах; пробы «ленивые» — часто только при трафике (§6.1). Падение домашнего роутера отличается от падения
   сети узла прямой пробой к российской цели (SE §4.6).
8. **DNS** российских доменов — **как сейчас**, через «Основную» (§5). Обоснование: один dnsmasq на всех; иначе через
   домашний IP пошёл бы DNS чужих людей.

## 1. Решения и умолчания

**Решено владельцем 14.10:** (D-016)
- Российский выход никогда не попадает в обычный пул. Зарубежные сайты через него не идут.
- Ключ — любой поддерживаемый: AmneziaWG и WireGuard (`.conf`, `vpn://`), VLESS, а также новые ключи этапа 1 (`hy2`,
  `ss`, `trojan`, `vmess`, SE §9).
- Резерв — как у выходов: уровни российских ключей, условия ухудшения и возврата, последний шаг на выбор — «с сервера
  напрямую» или блок.
- Проверки российского выхода — по российским целям, не по Cloudflare.
- Область — выбирать людей. По умолчанию выключено у всех, включается у человека или устройства (В4 закрыт).
- Логика условий и резерва — та же, что у выходов. Блоков логики может быть несколько → группы (уточнение
  координатора 14.10).
- Группа «Основная» = нынешний пул (D-015). Умолчание, поведение 3.3.3 и «Как раньше» сохраняются (с отличиями SE §1.3).
- Российских групп может быть несколько. Пример: «Дом» — домашний роутер → дача → с сервера; «Офис» — офисный роутер
  → с сервера.
- Правила этапа 2 будут целиться в «→ группа X». Закрепления — по группе. DNS узла и пробы — от «Основной».

**Решено владельцем 14.10 (ночь):**
- **Смена страны IP у любого выхода, в том числе российского, — только пуш** (D-024), трафик идёт как есть. По желанию в блок
  условий группы добавляется условие «страна ≠ X → ухудшен» (SE §3.3). Умолчания «снят» нет нигде (В2 закрыт).
- **Конкретный выход устройства снят** (D-025) → другие выходы той же группы; нет других → последний шаг группы. Итог —
  блок → устройство **подсвечивается в панели** «нет выхода в интернет» и приходит пуш. Последний шаг «с сервера
  напрямую» → подсветки «нет интернета» нет, пометка «выходы недоступны — идёт с сервера напрямую» (D-026) (решение
  координатора). SE §2.2, §7.3.
- **«Прокси для API Telegram»** (D-028) — по навыку `telegram-api-egress-vless-awg`: свой автоотказ и ручной выбор ключа;
  ключи — **только из выбранной группы**, по умолчанию «Основная» (D-029); HTTP-уведомления этапа 3 — через этот прокси
  (SE §2.9).
- **Новое — в браузере; CLI и MCP — да; SSH-меню из нового — только переименование** (D-050) (решение владельца 15.10, день;
  SE G8). Создание и переименование групп, уровни и условия — только в панели; перенос выхода, удаление группы и
  `flap_standby` — ещё и в CLI и MCP (SE §7.7–7.8, правки 6–8); `ru_via` — в панели, CLI и MCP. Аварийных пунктов в
  SSH-меню нет. Кнопки бота остаются, новое в бот не добавляется (SE G8, §7.6–7.8, §7.10).
- **Пресеты** «Экономно» / «Стандарт» / «Строго» — делаем (D-030); «Стандарт» — новым установкам.
- **Выход — ровно в одной группе** (D-045), одну группу можно назначить многим людям (**подтверждено владельцем 15.10**;
  В7 закрыт).
- **Сервер Aeza в России для стенда** — разрешено (D-031) (В8 закрыт).

**Решения координатора (владелец может поменять):** (D-037)
- последний шаг российской группы по умолчанию — **«с сервера напрямую»**: так в примере владельца «роутер → дача → с
  сервера» (В1 закрыт);
- DNS — как сейчас; окончательно — по замеру S20 (В3 — технический вопрос, не владельцу);
- на весь узел российскую группу в этапе 1 включить нельзя: только у людей и устройств (следует из «выбирать людей»);
- ключи российских групп — в отдельном файле (следствие решения «никогда не попадает в пул», В5 — к сведению);
- роль группы не меняется (D-038); выход переносится между группами **с предупреждением**, в том числе между ролями (В6
  закрыт);
- путь ядра при запасном блоке зарубежной группы ведёт себя как путь xray (D-039): российские сайты идут (SE §2.3, находка Б1).

## 2. Модель данных — группы (часть А)

### 2.1 Политика — список групп (`state.json → gateway.exit_policy`)

Схема внесена в SE §3.1–3.3. Этап 1 ещё не выпущен, поэтому `version: 1` — **сразу с группами** (D-015). Формы «без групп» в
файле не бывает, миграции не нужно. Модуль `gw/policy.py` (T2) — `load`, `save`, `validate`, `ensure_initial`, как в
SE; добавляются `group(doc, gid)`, `group_of(doc, exit_id)` и `place_new(doc, pool, hints)` (§2.4).

```jsonc
"exit_policy": {
  "version": 1,
  "hint_seen": false,                         // SE §7.1, на весь узел
  "probes": {                                 // общее для узла (SE §3.2): пауза «снят», окно потерь, пределы и бюджет
    // правила «упал» в политике нет: одно на узел, константы 3.3.5 (SE §3.2, правка 3, Р1)
    "off_backoff": {...}, "window": 10,
    "speed": {"max_mb": 10, "max_s": 8, "only_quiet": true,
              "budget_day_mb": 200, "budget_month_gb": 3}           // интервала observatory здесь нет — SE §3.2
  },
  "new_exits_group": "main",                  // куда попадает новый зарубежный выход без подсказки (§2.4)
  "tg_proxy_group": "main",                   // группа ключей «Прокси для API Telegram» (SE §2.9), только abroad
  "groups": [
    {"id": "main",                            // фиксированный id; группа есть всегда, не удаляется
     "name": "",                              // "" — имя по умолчанию «Основная» / «Main» (SE §3.1); иначе names.check
     "role": "abroad",                        // abroad | ru — задаётся при создании и не меняется
     "preset": "compat",                      // abroad: compat | standard | strict | economy | custom; ru: ru_home | custom
     "tiers": [{"id": "t1", "name": "", "exits": ["e-1a2b3c4d5e"], "method": "even",   // "" — «Уровень 1» (SE §3.1)
                "weights": {}, "tolerance_ms": 30, "tolerance_pct": 20}],   // как SE §3.1

     "per_connection": false,                 // только у main (§2.6)

       "freq": {"mode": "often", "every_s": null},   // частота проверок группы: lazy | often | normal | rare | custom (SE §3.2)

               "expect": null}},              // null — первая увиденная (SE §3.1 country); ru-группа — "RU"
     "rules": [ ... ]},                       // блоки условий SE §3.3; "exits": "all" = все выходы этой группы

               {"id": "t2", "name": "Дача",   "exits": ["e-dd33ee44ff"]}],

     "checks": {"targets": "ru", "freq": {"mode": "lazy", "every_s": null},
```

- **id группы:** `main` или `g-<6 hex>` (создаётся случайным, как id людей, `model._new_id`). Не меняется никогда.
  Подпись меняется по правилам раздела H плана. Имя `main` и уровней, созданных системой, — пустое, показ по языку
  узла и дубли — по SE §3.1 «Имена по умолчанию» (решение координатора 15.10) (D-111).
- **Пресет** — у каждой группы свой, он задаёт и **частоту проверок группы** (D-044) (`checks.freq`, решено владельцем 15.10,
  SE §3.2). `probes` (счёт неудач, окно) — общее на узел, его задаёт пресет «Основной»; пределы и бюджет теста
  скорости (`probes.speed`) — своя карточка «Тест скорости» (SE §7.1), пресет и сброс их не трогают (SE §7.9

  один на узел (SE §3.2): самая частая из зарубежных групп с выходами. Поэтому xray-выходы неосновной зарубежной
  группы, выбравшей реже, проверяются с общим интервалом — карточка пишет это строкой; реже идут только собственные
  пробы Kaskad (AWG, российские). Пресет «Дом» (`ru_home`) — §6.6, по умолчанию «Лениво — только при трафике» (D-053) (умолчание — решение координатора, З3
  правки 2; у зарубежных групп — частота пресета).
- `geo.action` — только `push` у **любой** группы, включая российскую (D-024) (решено 14.10, ночь; снятия по стране в этапе 1
  нет — SE §4.3, П5 правки 2).
- `ensure_initial` (SE §1.3) пишет одну группу `main`: «Стандарт» при `gen 2`, `compat` при `gen 1`. Российских групп
  по умолчанию нет.
- Политики нет в файле → эффективная политика — одна `main` в `compat` (как SE §1.3).

### 2.2 Роль, файл ключей, теги xray

| | Зарубежная группа (`abroad`) | Российская группа (`ru`) |
|---|---|---|
| Где лежит строка ключа | `/etc/kaskad/egress/upstream.txt` (как сейчас) | **`/etc/kaskad/egress/upstream-ru.txt`** (новый; права `0600`, владелец `root`, как у `upstream.txt`; в журнал — только через маскировку SE §9.7) |
| Номер строки `N` | 1–100 (`MAX_KEYS`, `install.sh:6530`) | **201–232** (`RU_INDEX_BASE = 200`, не больше 32 ключей) |
| Метка AWG / xray | `256+N` / `0x300+N` | те же формулы: `457–488` / `0x3c9–0x3e8` (всё ниже `0x200` и `0x400`) |
| Порты TPROXY / пробы | `12400+N` / `12700+N` | `12601–12632` / `12901–12932` (в границах SE §5.2) |
| Тег исходящего xray | `gx-<id>` | **`gr-<id>`** |
| Observatory, `gw-all`, `gw-vless` | да (селектор `["gx-"]`) | **никогда** — префикс `gr-` не подходит под селектор |
| «Прокси для API Telegram» | строки выбранной группы (`tg_proxy_group`, SE §2.9) | **файл не читается** egress-конфигом бота |
| Откат на 3.3.3 | как SE §1.3 | 3.3.3 этот файл не знает: ключи домашних роутеров **не становятся** выходами пула |

**Почему отдельный файл, а не поле роли.** Потребители `upstream.txt` вне ядра Kaskad 3 роль не знают:
- egress-конфиг бота строил бы `bot-bal` по всем строкам файла (`egress_rebuild`, `install.sh:7709`; группа прокси,
  SE §2.9, ограничивает его зарубежными группами, но при ошибке помощника берёт все строки);
- меню «Прокси для API Telegram», `egress_test`, `egress_active_index`;
- откат на замороженную 3.3.3.

С полем роли каждый из них пришлось бы учить, а откат на 3.3.3 этому не научить вовсе. Тогда трафик бота и
зарубежный трафик всех людей пошёл бы через домашний IP. С отдельным файлом это невозможно по построению.

**Почему свой префикс тега.** Селекторы xray — по префиксу:
- observatory `subjectSelector ["gx-"]` и `gw-all` `["gx-"]` (`xray.py:343-346`, `:410-413`) не подхватят `gr-`;
- новый зарубежный выход, добавленный горячо (SE С0.8), подхватывается этими селекторами без правки.

**Итоговое правило проверки (T-q круг 3, решение координатора 20.10; отменяет «observatory и по `gr-`» круга 2).**
- **Observatory — только зарубежные выходы** (`subjectSelector ["gx-"]`, `xray.observatory_selector`). `gr-` туда не
  попадает никогда. Причины:
  - её цель зарубежная (`cp.cloudflare.com`). Домашний провайдер, который режет Cloudflare, сделал бы рабочий роутер
    «не отвечает»;
  - селектор `gr-` задевал и все российские AWG-ноги (freedom с меткой) — проба каждые 10 с через чужой домашний роутер;
  - первый и последний российский VLESS меняли бы основу конфига, а это перезапуск xray.
- **Российский VLESS (любой xray-выход роли `ru`) проверяет своя проба Kaskad** через свой `probe-<id>`
  (SOCKS5 `127.0.0.1:12700+N` → `gr-<id>`), как в §6.1:
  - CONNECT к `77.88.8.8:53`, затем `77.88.8.1:53` (данные — `probe_targets.json → ru.dns`, `dns_name`), DNS-запрос по TCP
    `A ya.ru`;
  - «работает» — пришёл ответ на этот запрос (любой RCODE). Успех CONNECT ничего не доказывает: xray отвечает
    «успех» до соединения;
  - порт `probe-<id>` закрыт (xray не запущен, выход не нарисован) — «неизвестно»;
  - частота — у группы (`policy.period`), «Лениво» — как у AWG (раз в 5 мин в простое и перепроверка отказа).
- Итог пробы идёт в состояние выхода (правило «упал» SE §3.2) и в выбор резерва группы (`ru_target`).
- xray не перезапускается при появлении и уходе российского VLESS: `probe-<id>`, `tproxy-<id>` и `gr-<id>` приходят
  и уходят горячо (§4.2).

Явный список тегов в селекторе ломал бы эту горячую смену пула. Функция `exits.tag(eid)` (`exits.py:265`) становится
`exits.tag(eid, role="abroad")`. Записи пула получают поля `role` и `tag`; рендер xray (T5) берёт `e["tag"]` и нигде
не собирает `"gx-" + id` сам. Сейчас тег собирает только `exits.tag` (`exits.py:266`); в `xray.py` — 2 вызова
`exits.tag` (`:361-362`) и 5 селекторов по префиксу (`:365`, `:377`, `:378`, `:398`, `:411`), в `dev-mock.js` — 1
место. `exits.pool()` по умолчанию отдаёт только зарубежные выходы, обе роли — по явному `roles=` (SE §3.1, находка
Б7).

**Роль группы не меняется.** Перенести выход между ролями — это перенос строки между файлами (§2.4). У выхода сменятся
номер, метка и тег; **id не меняется**: текст строки тот же, значит, тот же `exit_id`, а id выхода — `exits.pool_id`
(запись карты `subs.json → ids` 3.3.5 или `exit_id`). Карта id одна на узел и чистится по строкам **обоих** файлов
(SE §3.8, находка С2 правки 2): иначе запись выхода, которому 3.3.5 сохранила id, выпала бы при следующем обновлении
подписки, и id «перепрыгнул» бы на `sha1` текста. Перенос проверяет, что `pool_id` строки до и после одинаков. Все
читатели id в Python — только через `exits.pool()`/`pool_id`. Поэтому при смене роли явно
сбрасываются: состояние, причины, окна замеров, `off_until`, `norm_rtt`, ожидаемая страна, закрепления в старой
группе и последнее прочитанное значение счётчика `traffic.json → last` (у выхода новые нога `kawgN` и тег; без сброса
правило дельт дало бы небольшой недосчёт, П3) — иначе «снят» зарубежного прошлого переехал бы в российскую группу. Квота и её счётчики **сохраняются**: это
тариф того же сервера. Перенос — смена тега xray горячо (`rmo`/`ado`, С0.8 пройдена в T0; перезапуск — только для выхода Hysteria2) и пересборка прокси бота
(строка уходит из `upstream.txt` → `egress_rebuild` → перезапуск `kaskad-bot`). Обрыв соединений через этот выход и
перезапуск бота — честные строки в диалоге (решение координатора: перенос разрешён с предупреждением, В6 закрыт) (D-038).

**Один ключ — в одном файле (находка Б8).** Добавление строки, которая уже есть в другом файле, или ключа с тем же
сервером (`peer_key`, SE §3.8) — отказ `gw_ops.err.key_in_other_role` RU/EN: «этот ключ уже в зарубежных (российских)
выходах — перенесите его». Проверка дублей `same_peer_problems` (`summary.py:303`) смотрит оба файла. Подписка — иначе (решение координатора
15.10, Р2) (D-061): свой ключ подписки, перенесённый в другой файл, остаётся там и при обновлении подписки обновляется на
месте; строка подписки с ключом, который уже лежит в другом файле не как её, — в `dups` итога (SE §3.8).

### 2.3 Выход — ровно в одной группе

Обоснование (запрос координатора):
1. **Состояние — у выхода, а условия — у группы.** В двух группах с разными условиями выход был бы «ухудшен» в одной и
   «годен» в другой. Пришлось бы вести состояние, причины, окна замеров, события, пуши и графики по паре «группа +
   выход». Объём SE §3.4–3.6 и §4 удвоился бы, а пуш «выход X ухудшен» стал бы двусмысленным.
2. **Роли несовместимы.** Российский выход в зарубежной группе нарушает решение владельца (D-016). Две зарубежные группы с
   общим выходом — законный случай: например, «Стриминг» из A и B и «Основная» из A, B и C.
3. **Замена для этого случая:** в этапе 2 правило «→ выход A» или «→ группа». В этапе 1 человек выбирает группу или
   конкретный выход маршрутом `exit:E`. Позже можно «участие в нескольких группах с одним состоянием из домашней
   группы» — отдельным решением.

`policy.validate`: выход не более чем в одной группе и одном уровне. id вне пула читаются терпимо (нужно SE §3.8).
Выход файла `upstream-ru.txt` — только в группе `ru`, файла `upstream.txt` — только в `abroad`. Нарушение — код
`ep.err.exit_role` с полем `field`.

### 2.4 Куда попадает новый выход

Новый id без записи в группах не должен ни на один такт оказаться не в той группе. Иначе ключ домашнего роутера
прошёл бы через `main`.
- **Российский ключ** попадает только в `upstream-ru.txt` (D-037), значит, в `main` он не попадёт никогда: проверка §2.3 и
  тег `gr-`. Группу для него задаёт подсказка `exit_pref[<id>].group`. Её пишет добавление ключа **до** записи строки
  в файл, под блокировкой состояния — тот же порядок, что запись настроек до замены пула в шаге 3.3.5 (SE §3.8). Нет подсказки (ручная правка
  файла) → первая российская группа. Российских групп нет → выход вне групп, трафик на него не идёт; в панели плашка
  «российский ключ без группы».
- **Зарубежный ключ:** подсказка `exit_pref.group` → группа подписки (`subs.json → subs[].group`, §2.9) →
  `new_exits_group` (по умолчанию `main`) → уровень по `new_exits_tier` этой группы.
- `policy.place_new(doc, pool, hints)` — чистая функция: размещение одинаково в любом процессе
  (`exits.decision()`, сборщик). Сборщик размещает любую неразмещённую строку при ближайшем такте под блокировкой и
  там же зовёт `rev.note(st)`: размещение — изменение состава группы, `rev` + 1 (SE §3.1, проверка 16, З-1; `note`, а
  не `current` — блокировка уже взята, проверка 18, С-2). Ключ, добавленный через `gw/ops.exit_add`, после возврата
  скрипта размещает и сам `exit_add` (`place_new`, если строка ещё не размещена, и `rev.note`); блокировку на время
  скрипта он не держит (SE §3.1 «Добавление ключа»; проверка 17, З-1).
- Добавление:
  - `kaskadctl gw exit-add … --group <gid>` (по умолчанию `main`);
  - панель — поле «Назначение» (§8.1);
  - подписка — поле `group` (по умолчанию `main`; российская подписка пишет в `upstream-ru.txt`).

### 2.5 Выбор группы у человека и устройства

**Зарубежная группа — это маршрут** (отдельного поля нет):
- `route.via`: `pool` | `group:<gid>` | `exit:<id>` | `direct` | `block` (`model.VIA_SIMPLE`, `parse_route`,
  `model.py:137`, T2);
- `pool` ≡ `group:main`. При записи `group:main` нормализуется в `pool`: маршруты к «Основной» остаются понятны 3.3.3
  при откате;
- `group:<gid>` разрешён только для `role = abroad`; проверка с состоянием — новая `model.check_route(st, route)`, её
  зовут все места записи маршрута (T2). Ошибка — `gw_model.err.route_ru_group`;
- `exit:E` разрешён только для выхода зарубежной группы (`gw_model.err.route_ru_exit`);
- маршрут на несуществующую группу (удалена при импорте, ручная правка) → считается битым и проваливается на следующий
  уровень (`route_of`, `model.py:158`), как битый маршрут в 3.3.3. В панели — предупреждение.

**Последний шаг** зарубежной группы: `direct`, если `group.fail == "direct"` **или** `route.fail == "direct"`, иначе
блок (`fail-block`, SE §2.2). Маршрут с `fail = direct` из 3.3.3 так и работает. В форме маршрута к группе поле «Если
недоступно» не показывается: там строка «как у группы: блок / напрямую», а при `route.fail = direct` — «напрямую
(задано у маршрута)».
- `exit:E`, E «снят» или «в запасе» → устройство идёт через **другие пригодные выходы группы E** (закрепление в
  группе E); нет их → последний шаг группы E по той же формуле (решено 14.10, ночь; SE §2.2) (D-025). Значения `fail = pool`
  нет.
- Итоговый шаг устройства (`exits.target()["step"]`: `last_block` / `last_direct`) — основа подсветки «нет выхода в
  интернет» / «выходы недоступны — идёт с сервера напрямую» (SE §4.4, §7.3).

**Российская группа — отдельное поле `ru_via`** (часть Б, Q1). Хранится в объекте человека и устройства рядом с
`route` и `rules`, а не в `gateway.rules`: `set_rules_conf` пишет туда только три ключа (RF §1).
- значения: `"direct"` | `"<gid>"`; нет поля = наследовать: устройство → человек → узел;
- узел в этапе 1 — всегда `direct` (В4), поле узла не заводится;
- `model.ru_via_of(st, device) -> {"via": "direct"|"<gid>", "from": "device"|"user"|"default"}`;
  `model.parse_ru_via(st, value)` — `inherit` | `direct` | id группы с `role = ru`;
- **действует только вместе с «Россия напрямую»:** нужны профиль `ru_direct` с готовыми списками и согласием ⚠РФ
  (RF §3.5, рубеж 2) и маршрут не «блок по выбору». Иначе `ru_via` хранится, но не действует; в панели — «работает
  только при «Россия напрямую»»;
- согласие ⚠РФ `ru_via` не меняет и не требует. Спрашивает его включение профиля `ru_direct`, как в RF.
  `rfgate.selected` смотрит только профиль;
- ссылка на удалённую группу → `direct` и предупреждение (безопасная сторона: «как сейчас»). Удаление группы, на
  которую ссылаются маршруты или `ru_via`, без явной переброски отклоняется (§8.5).

### 2.6 Ограничения этапа 1
- «По соединениям» (SE §4.5) — только у `main`. У других групп поле не принимается
  (`ep.err.per_connection_main`): балансировщик `gw-vless` и метка `0x200` одни на узел.

### 2.7 Закрепления по группам — `/var/lib/kaskad/gw/pins.json`

Заменяет формат SE §3.4. Этап не выпущен — сразу `version: 1` в этом виде.

```jsonc
{"version": 1, "saved": 1760000000,
 "groups": {
   "main":     {"pins": {"d-1a2b3c4d": {"exit": "e-…", "tier": "t1", "since": 1760000000, "why": "new"}},
                "tier_good_since": {"t1": 1760000000}, "active_tier": "t1", "last_step": null},
   "g-7c1d2e": {"pins": {"d-1a2b3c4d": {"exit": "e-aa11bb22cc", "tier": "t1", "since": 1760000000, "why": "new"}},
                "tier_good_since": {"t1": 1760000000}, "active_tier": "t1",
                "last_step": null}},                 // null | "direct" | "block" — группа на последнем шаге, с какого времени — в событии
 "gw_all": "gx-<id>"}
```
- Устройство может иметь не больше одного закрепления в зарубежной группе (по своему маршруту) и одного в российской
  (по `ru_via`).
- Сменился маршрут или `ru_via` → закрепление в прежней группе снимается в ближайшем такте, в новой выбирается заново
  (`why = "new"`).
- Зажим времени, битый файл, запись «сразу» — как SE §3.4.

`Decision` (SE §2.2, §4.4):
```python
Decision: groups {gid: {pins, active_tier, tier_good_since, last_step}}, states {exit: state}, gw_all, events
assign(devices_by_group, states, policy, pins, metrics, node, now) -> Decision   # цикл по группам
pick_new(device_id, gid, states, policy, metrics) -> exit_id | None
```
- `devices_by_group` строит сборщик:
  - зарубежная группа G — активные устройства, чей маршрут разрешается в G (`pool`/`group:G`, а также `exit:E`,
    когда E из G непригоден);
  - российская группа R — активные устройства, у которых «Россия напрямую» действует (`rules_apply.device_rd`,
    `apply.py:250`), маршрут не «блок по выбору» и `ru_via_of = R`.
- `gw_all` — только по «Основной» (§4.3).
- `node.offline` замораживает все группы. `node.ru_offline` замораживает только российские (§6.4).

### 2.8 `target()` и новая `ru_target()`

- `exits.target(st, device, decision)` (SE §2.2): маршрут → группа → закрепление в ней. Ответ дополняется полем
  `group`. Цель xray — `e["tag"]` выхода (у зарубежного `gx-`).
- Новая `exits.ru_target(st, device, decision) -> dict | None` (Q2) — **одна** точка для ядра, xray, трассировки и
  схемы:

| Условие | Ответ |
|---|---|
| «Россия напрямую» не действует (`device_rd` ложно), маршрут «блок по выбору», устройство или человек на паузе или отозваны | `None` — российских правил у устройства нет; адреса нет ни в `gw_rd`, ни в `gw_rx`, ни (по российской причине) в `gw_live` |
| `ru_via_of = direct` | `{"step": "direct", "mark": 0x201, "xray": {"outboundTag": "direct"}, "group": None}` — как в 3.3.3 |
| группа R, закреплённый выход годен или ухудшен | `{"step": "exit", "mark": <256+N \| 0x300+N>, "xray": {"outboundTag": "gr-<id>"}, "group": R, "exit": id, "tier": t}` |
| группа R, пригодных нет, `R.fail = direct` | `{"step": "last_direct", "mark": 0x201, "xray": {"outboundTag": "direct"}, "group": R}` |
| группа R, пригодных нет, `R.fail = block` | `{"step": "last_block", "mark": 0x2ff, "xray": {"outboundTag": "fail-block"}, "group": R}` |

- «Пригодные» — по порядку SE §2.2 и §4.4: годные → ухудшенные → «в запасе» по уровням. «Снят» — никогда.
- Запасной блок **зарубежной** группы (`fail-block`) на ответ `ru_target` не влияет: российская цель действует и в
  ядре, и в xray (SE §2.3, находка Б1).
- Сравнения со строкой `"ru_direct"` в `ru_target` нет: она зовёт `device_rd`. Тест-страж RF §3.5 не краснеет;
  `device_rd` вносится в его список разрешённых мест (правка RF §3.5, внесена).

### 2.9 Подписки, смена `#имени` (3.3.5, SE §3.8), резервная копия, откат

- **Подписка:** `subs.json → subs[].group` (по умолчанию `main`). Подписка в российскую группу пишет строки в
  `upstream-ru.txt` и только туда.
- **Смена `#имени` ключа** — сделано в 3.3.5: id выхода сохраняется (способ (а), SE §3.8). Политика групп,
  `exit_pref.group` и закрепления `pins.json` ведутся по id — переносить нечего. Для групп SE §3.8 требует (Q4):
  - карта id `subs.json → ids` — по строкам **обоих** файлов (`prune_ids` в `exitsubs._apply`), иначе смена роли
    теряет id при следующем обновлении подписки (С2 правки 2);
  - свои ключи `plan` ищет по `identity` в **обоих** файлах: ключ, перенесённый сменой роли, остаётся в новом файле и
    обновляется там на месте, в файл подписки не дописывается (решение координатора 15.10, Р2) (D-061); новые ключи — в файл
    подписки; строка сама между ролями не перескакивает;
  - подписка, ключи которой стоят в российской группе: её **новые** ключи (и ключ, выданный взамен с другим uuid или
    паролем) встают туда же «в запас» (`manual_why = sub_confirm`) с пушем «подтвердите», в зарубежный пул молча не
    попадают (решение координатора 15.10, вечер; SE §3.8, Н4) (D-068);
  - новая строка — на месте старой в том файле, где лежит. Для российского файла номер `N` = 200 + позиция.
- **`.kbk`:**
  - группы — в `gateway.exit_policy`, `ru_via` — у людей и устройств в `gateway` (переносятся без правки
    `backup.py`, SE §3.5);
  - `upstream-ru.txt` идёт в ту же часть копии, что `upstream.txt` (Q4; правка `backup.py`);
  - при восстановлении на узел без российских ключей группы остаются пустыми, `ru_target` даёт последний шаг —
    плашка в сводке импорта;
  - в справке копии — строка «в копии есть адрес вашего домашнего роутера и ключ к нему — храните её как пароль».
- **Откат на 3.3.3:** `upstream-ru.txt` и поля групп 3.3.3 не читает. Маршруты `group:<gid>` 3.3.3 отвергнет
  (`parse_route`) и возьмёт уровень выше; маршруты к «Основной» записаны как `pool` (§2.5). Ноги `kawg201+` и их
  правила `fwmark` после отката остаются до первой пересборки пула: `egress_awg_sync` 3.3.3 снимает лишние `kawg*`
  (`install.sh:7493-7495`). Строка в заметках к выпуску: «после отката откройте «Прокси для API Telegram» →
  пересобрать».

## 3. Ядро: метки российского выхода (часть Б, Q2)

**Сейчас** (`net.py:45-47`, `ru_rules` `:327`): клиенту из набора `gw_rd` новые соединения к `gw_ru` и `gw_ru_dns`
(кроме `gw_force`) получают метку `0x201` (напрямую), если маршрут не `0x2ff`.

**Будет.** Набор `gw_rd` остаётся для людей с `ru_via = direct`; его правила теряют условие `meta mark != 0x2ff`, а
`gw_live` расширяется российской целью — это часть А, SE §2.3 (находка Б1, T4/T5). Узел без российских групп
отрисовывает таблицу как после части А, без карты `gw_rx` (тест). Добавляется карта:

```
map gw_rx { type ipv4_addr : mark; }      # клиент с российской группой → метка российской цели (§2.8)
...
meta mark set ip saddr map @gw_route
ip saddr @gw_rd ip daddr . meta l4proto @gw_ru ip daddr != @gw_force meta mark set 0x201   # часть А (SE §2.3)
ip saddr @gw_rd ip daddr @gw_ru_dns ip daddr != @gw_force meta mark set 0x201             # часть А (SE §2.3)
ip daddr . meta l4proto @gw_ru ip daddr != @gw_force meta mark set ip saddr map @gw_rx                       # новое
ip daddr @gw_ru_dns ip daddr != @gw_force meta mark set ip saddr map @gw_rx                                  # новое
ct mark set meta mark or 0x4b000000
meta mark 0x3c9 meta l4proto { tcp, udp } tproxy to 127.0.0.1:12601     # TPROXY российского xray-выхода — как у любого
```

- **Промах в карте** оставляет метку маршрута (правило прерывается). На этом поведении уже держится `gw_route`
  (`net.py:84`, `meta mark set 0x2ff` перед поиском). Значит, клиент вне `gw_rx` не затронут. Проверка на стенде —
  С0.15.
- **Наборы не пересекаются:** устройство с российской группой — в `gw_rx`, а не в `gw_rd`. `rules_apply.rd()`
  (`apply.py:132`) сохраняет сигнатуру (список адресов; на нём держится `tests/test_rules_gw.py:287`) и отдаёт только
  `step == "direct"`; новая `rules_apply.rx()` отдаёт `{ip: mark}` для остальных шагов `ru_target` (находка Б12).
- **Условия `meta mark != 0x2ff` в новых правилах нет — и это намеренно** (находка Б1, решение координатора) (D-039).
  Устройства с маршрутом «блок по выбору», на паузе и отозванные в `rx` не попадают совсем (§2.8, `None`). У
  запасного блока зарубежной группы (`fail-block`, в ядре `0x2ff`) российские сайты идут через российскую группу:
  падение зарубежных выходов не отключает «Дом». Чтобы правило вообще дошло до такого пакета, `gw_live` включает
  адреса `gw_rx` с меткой `≠ 0x2ff`, а адрес, живой только по российской причине, попадает в `gw_ruonly` — ему
  закрыты службы узла (SE §2.3). Так ведут себя оба пути: xray (§4.1) и ядро.
- `gw_force` («всегда через выход»: YouTube на российском кэше, Telegram, GitHub, домены Meta ⚠РФ) — **никогда** через
  российскую группу. Эти адреса идут по зарубежному маршруту, как сейчас.
- Последний шаг «блок» → значение `0x2ff` → обратные правила `gw_fwd` (`ct mark … == 0x2ff drop`) отбрасывают. Утечки
  нет.
- Метка российского AWG-выхода `256+N` → правило `fwmark 256+N lookup 256+N` его ноги `kawgN`. Ноги российских ключей
  поднимает та же `egress_awg_sync` (Q4).
- Метка российского xray-выхода `0x300+N` → TPROXY `tproxy-<id>` → `gr-<id>`. Пары (метка, порт) уже даёт
  `net.plan()["vless"]` по всем xray-выходам пула (`net.py:290`); российские входят туда через `exits.pool()` (Q4).
- **Заполнение:**
  - `net.plan()` получает `"rx"`;
  - `map_script`/`update_lines` (`net.py:734`, `:790`) перезаливают `gw_rx` **одной транзакцией** с `gw_route` и
    `gw_rd` (атомарно для пакетов);
  - сборщик — в `net.update_map(…, decision=d)` при смене решения (SE §2.7);
  - `gw_live`/`gw_ruonly` — та же транзакция (SE §2.3), `rx`-адреса с меткой `≠ 0x2ff` входят в них;
  - динамические адреса IKEv2/L2TP/PPTP — `gw/hooks.py` добавляет адрес в `gw_rd` **или** в `gw_rx` по `ru_target`
    устройства, а при `down` **убирает** его из `gw_rx` (и из `gw_route`, `gw_rd`, `gw_live`, `gw_ruonly`, SE §2.3).
    Иначе устаревшая запись осталась бы в `gw_rx`, адрес получил бы другой человек, и его российский трафик пошёл бы
    через чужой домашний IP (находка Б10). Тест: `down` → адреса нет в `gw_rx`.
- **Обрыв при «снят»:** `net.flush_devices(addrs, mark)` (SE §2.3) и для российских меток — соединения устройств,
  уведённых с российского выхода. «Ухудшен» и «в запас» — только при `drop_on_degrade` группы.
- `gw_ru_ver`, `gw_ru` и их загрузка (`load_ru`) не меняются.

## 4. xray (часть А — T5, часть Б — Q2)

### 4.1 Правила пользователей VLESS, SOCKS5 и Hysteria2 — общие правила списков
После T0 правила со списками — **общие на вход с перечнем пользователей** (D-032) (`ls-`, SE §2.4; решение координатора
14.10). Российская цель встраивается туда же:
- правила «напрямую» — домены группы `direct` и `ext:roscomvpn-geoip.dat:direct` — строятся **по цели**
  `ru_target(...)["xray"]`: одно правило на пару (список, цель) с перечнем пользователей — `direct` (как сейчас и у
  людей без российской группы), `gr-<выход>` для каждого закреплённого российского выхода, `fail-block` для российских
  групп на последнем шаге «блок»;
- при `step == "direct"` у всех пользователей правила те же, что после части А: узел без российских групп рисует
  конфиг побайтно как после части А (тест);
- правило `force` по-прежнему указывает на зарубежную цель устройства (`target(route, device)`, SE §2.4);
- условие «маршрут не блок» — только для блока **по выбору** (`block`), не для `fail-block` (так же, как в ядре, §3);
- вход Hysteria2 (`SPEC-stage1-hy2-inbound.md`, префикс `h2-`) попадает в те же общие правила своим `email`
  (`<login>.h2`) и получает российскую цель без своей правки;
- число правил со списками растёт на число закреплённых российских выходов (обычно 1–3), а не на число людей.

### 4.2 Горячие правки
- Смена закрепления в российской группе, переход на последний шаг и возврат меняют **перечень пользователей** в
  правилах `ls-` → замена всех правил одним вызовом (`adrules` без `-append`, весь `routing`) и `bo` заново (SE §2.4,
  §2.6), **без перезапуска**; идущие соединения не рвутся (T0). Цепочки пользователей (`vl-`/`sk-`/`h2-`) при этом не
  меняются: в них только правило маршрута. `gr-`, `direct` и `fail-block` есть в основе всегда.
- Лимит: правил со списками ≤ `HOT_MAX_EXT_RULES` (32, SE §2.5); больше — перезапуск с защитой от шторма (SE Р28).
  Число пользователей на это не влияет.
- **Отпечаток решения** (SE §2.7) включает `ru_target(...)["xray"]` каждого пользователя xray. Правка `collect.py` —
  одна функция отпечатка (Q2).
- Перезапуск xray:
  - добавление или удаление российского ключа — **нет** (смена пула горячая, SE §2.7, С0.8 пройдена), кроме
    выхода Hysteria2 на уже использованном `host:port`;
  - перенос выхода между ролями — смена тега: горячо (`rmo` старого, `ado` нового), кроме Hysteria2 (§2.2).

### 4.3 Сам узел
- `gw-all` (DNS узла, `gw-dns-int`, вход пула `pool-socks`) — переопределение `bo` на лучший выход **активного уровня
  «Основной»** (SE §2.6, `decision.gw_all`). Другие зарубежные группы и российские в `gw-all` не участвуют. Селектор
  `["gx-"]` остаётся запасным путём для leastPing; `gr-` в нём не бывает. **Честно (находка Б9):** до первого `bo`
  после перезапуска xray (≤ 10 с) `leastPing` выбирает среди выходов всех зарубежных групп, в том числе с квотой —
  DNS узла и `pool-socks` в это окно могут пройти через «Стриминг». Строка — в справке группы (SE §2.6).
- `gw-vless` («по соединениям») — список xray-выходов **только «Основной»** (`xray.py:395-400`, T5).
- Observatory — `["gx-"]`, российские выходы в нём не проверяются (§6.1).
- Внутренний SOCKS-вход `probe-<id>` (SE §5.2) рисуется для каждого xray-выхода, включая `gr-`: через него идут
  пробы российских выходов. Порт закрыт nft «только root» (SE §5.2).
- Счётчики трафика `outbound>>>gr-<id>>>>traffic>>>…` — как у `gx-` (SE §5.6). Квота российского выхода работает так
  же: домашний трафик бывает лимитным.

### 4.4 Разрешение имён через российский выход
- **xray-путь, прокси-выход** (VLESS, Trojan, SS, Hysteria2, VMess у роутера): при `domainStrategy: IPOnDemand` имя
  остаётся адресом назначения исходящего. Его разрешает **дальняя сторона**, то есть домашний роутер. CDN выдаст
  «домашние» адреса без отдельной настройки DNS.
- **xray-путь, AWG-выход** (`gr-<id>` = `freedom` с меткой `256+N`, `domainStrategy UseIPv4`): имя разрешает DNS xray
  узла (`gw-dns-int` → `gw-all`, «Основная»), как сейчас.
- **Путь ядра:** имя уже разрешил dnsmasq (§5).

3. В несоразмерно этапу 1.

сервера. Сайт открывается через российский выход, адрес попадает в `gw_ru` или `gw_ru_dns`.

- Иначе — вариант В в этапе 2 (§15, В3).

с прокси-выходом (VLESS, Trojan, SS, Hysteria2, VMess): им имя разрешает роутер (§4.4). При «С сервера напрямую» у
«Основной» DNS идёт напрямую. Строка — в карточке «Основной» и российской группы (RU/EN, `ep.dnsMainBlock`,

## 6. Проверки и состояния российских групп (часть А — T4/T6, часть Б — Q3)

Машина состояний (SE §4.1–4.3), условия (SE §3.3), уровни и возврат на основной (SE §4.4) — **те же**. Меняются
только цели проб и сеть узла.

### 6.1 Пробы российского выхода — сам Kaskad, без observatory
- **Почему без observatory:** у observatory один `probeURL` на всех (Cloudflare/Google `generate_204`), а владельцу
  нужны российские цели. К тому же каждые 10 с это был бы зарубежный запрос через домашний IP.
- **Цели — данными**, не в коде: `lib/kaskad/gw/probe_targets.json` (`{"version", "checked": "YYYY-MM-DD", "ru":
  [...], "abroad": [...]}`):
  - `ru`: TCP `77.88.8.8:443`, `77.88.8.1:443` (Яндекс DNS — адреса для запросов, не сайт); DNS по TCP
    `77.88.8.8:53`, `77.88.8.1:53`;
  - `abroad`: нынешние 1.1.1.1 / 8.8.8.8 / 9.9.9.9 и `cp.cloudflare.com`;
  - какие цели отвечают и как — проверяет T0, С0.14 (SE §2.0); дата проверки — в файле;
  - цели чередуются по кругу. «Упал» — по правилу владельца 15.10 (D-054) (SE §3.2: ≥ 50 % неудач в окне, не меньше 4 проб);
    пробы идут **по разным целям**, поэтому падение одной цели из четырёх даёт ≤ 25 % неудач и выход не снимает.
- **Без HTTP к Яндексу в частых пробах (находка Б3).** Регулярные автоматические запросы `HEAD ya.ru` каждые 10–30 с с
  домашнего IP могут привести к капче у всех в этой домашней сети (не подтверждено, но риск дешевле обойти).
  HTTP-запрос к Яндексу — только в проверке сервиса «Яндекс» (§6.3), раз в 30 мин и по желанию.
- **AWG (ключ WireGuard или AmneziaWG роутера):** «жив / мёртв» — TCP-соединение через метку `256+N` к цели и сразу
  закрытие (`connect_through`, `exits.py:852-918`, со списком целей группы); отклик — время установки соединения.
  Отдельной HTTP-пробы отклика у российского AWG-выхода нет.
- **xray (VLESS и прочие у роутера):** SOCKS5 CONNECT на `probe-<id>` к `77.88.8.8:53` (ATYP=IPv4) и DNS-запрос по
  TCP (`A ya.ru`); удача — ответ DNS за 4 с, отклик — от запроса до ответа. Голого TCP через SOCKS мало: xray отвечает
  «успех» на CONNECT заранее (SE §5.3). Каждая проба — новое соединение VLESS/Reality через роутер: по замеру T0 одна
  проба observatory (соединение + `generate_204`) ≈ 12 КБ на проводе; DNS-ответ чуть меньше HTTP, порядок тот же.
  Поэтому у xray-выхода цену определяет частота.
- **Частота — у группы** (решено владельцем 15.10, В9 закрыт) (D-044), **по умолчанию у российской группы — «Лениво — только
  при трафике»** (умолчание — решение координатора, З3 правки 2; владелец может поменять) (D-053). Варианты и
  период P — SE §3.2: «Лениво», «Часто — 10 с», «Обычно — 30 с», «Редко — 2 мин», «Свой»). Все пробы российского
  выхода — собственные пробы Kaskad (observatory нет), поэтому идут ровно с частотой группы. «Лениво»:
  - **пассивный признак:** входящие байты выхода выросли за такт (AWG — `kawgN` rx, `live.iface_bytes`; xray —
    downlink `gr-<id>` из `/debug/vars`, который сборщик и так читает каждый такт, SE §3.5) → замер «жив»
    засчитывается без активной пробы;
  - **подозрение:** исходящие байты растут, входящие — нет, 2 такта подряд → активная проба сразу;
  - иначе активная проба — только пока через группу был трафик за последние 10 мин, раз в 15 с. В простое **годные**
    выходы не проверяются (SE §3.2); выходы не в «годен» («ухудшен», «в запасе», «снят» не по квоте) проверяются раз в
    15 с всегда, иначе они не вернулись бы;
  - окно правила «упал» у «Лениво» (D-059) — последние 4 пробы, каждая не старше 1 ч (решение координатора 15.10, Р6;
    SE §3.2); пассивный признак — удачная проба не чаще раза в 15 с. Нет трафика — нет проб, состояние годного выхода
    не меняется;
  - в окне — не больше одной пробы за 15 с: перепроверка заменяет результат последней пробы (SE §3.2, Н1 правки 4);
  - отказ замечается: под нагрузкой — за ≈ 1 мин; после простоя до часа — при первом трафике человека (проба «по
    подозрению»), за 15–30 с; после простоя дольше часа окно пусто и нужно 4 пробы — ≈ 45–60 с. Обрыв короче 15 с
    «упал» не даёт. Карточка выхода пишет «последняя проверка: N мин назад (группа
    без трафика)».
- **Выход, снятый по квоте** с `quota.action = remove` (О8, SE §5.6): ленивые и любые другие пробы российского
  выхода на паузе до дня сброса, выход не участвует в правиле «упал» и в «молчат все выходы группы» (§6.4, SE §4.6).
- **Трафик проб через домашний канал** (оценка по размерам пакетов; замер — §13.4; строка «≈ N МБ в сутки» — в
  карточке группы):

| Режим | AWG-выход | xray-выход (VLESS/Reality и др.) |
|---|---|---|
| Постоянно каждые 10 с (черновик: TCP 10 с + `HEAD ya.ru` 30 с) | ≈ 15–20 МБ/сут | ≈ 90–105 МБ/сут |
| Постоянно каждые 30 с | ≈ 5–7 МБ/сут | ≈ 30–35 МБ/сут |
| «Лениво», простой весь день (только пассивный признак) | ≈ 0 | ≈ 0 |
| «Лениво», нагрузка весь день, худший случай (пассивного признака нет, проба каждые 15 с) | ≤ 8–10 МБ/сут | ≤ 60–70 МБ/сут |

  Основа — замер T0 (14.10, 3.3.3, `k3/stand/logs/T0-stage1.md` §8): observatory шлюза на VLESS-выход при 10 с ≈ 105
  МБ/сут (≈ 12 КБ на пробу), TCP-проба сборщика к AWG-выходу при 10 с ≈ 10 МБ/сут на проводе, включая рукопожатия
  AmneziaWG. Прежняя цифра черновика «≈ 4–6 МБ в сутки при 10 с» занижала xray-выход примерно в 20 раз.
- Правило «упал» у российских выходов — то же, что у зарубежных (SE §3.2; прежний `die_after.ru = 3` снят, правка 3,
  Р1); «снова работает» — 2 удачи подряд; пауза «снят» не держит последний годный выход группы (SE §4.3, Р7).

### 6.2 Страна
- Плановая проверка — Cloudflare `cdn-cgi/trace` через выход (SE §5.5), раз в сутки, `geo.expect = "RU"`.
- Защита от ложной смены (SE §4.3 «Страна») — та же. Правило «`loc` выхода = `loc` узла» для российской группы
  проверяется, только если узел сам не в RU: иначе совпадение ожидаемо.
- Другая страна (2 подтверждения) → **только пуш** «у российского выхода «Роутер» сменилась страна: было RU, стало
  FI», трафик идёт как есть, выход не снимается (решено 14.10, ночь; SE §4.3) (D-024). Так у любого выхода.
- По желанию владелец добавляет в блок условий российской группы шаблон «Страна не та» (`country != RU` →
  «ухудшен», вернуть при `== RU`, SE §3.3). Ухудшенный выход остаётся пригодным: трафик не рвётся, при «Уводить с
  ухудшенного» устройства переходят на другой уровень группы («Дача»), если он годен. В пресет «Дом» условие не
  входит; карточка группы подсказывает его строкой «Если роутер может сам ходить через VPN — добавьте условие «Страна
  не та»».
- Запрос к Cloudflare раз в сутки — единственный зарубежный запрос через домашний IP. Выключается `geo.enabled = false`.

### 6.3 Сервисы и скорость
- Проверка сервиса (SE §5.4) — список группы. Шаблон для российской группы — «Яндекс» (`https://ya.ru/`, коды
  200/301/302 — проверить в T0); остальное — своя ссылка. Примеры в справке — `example.com`.
- Тест скорости у российской группы **выключен** (`checks.speed.enabled = false`, как у любой группы — О3): он тратит
  домашний канал. Включается галочкой группы, бюджет — общий узла.

### 6.4 Падение домашнего роутера или сети узла

Проверка — в такте сборщика, **до** `health.evaluate` (SE §2.7). Когда делается прямая проба и что из неё следует —
**таблица SE §4.6** (находка Б4: четыре строки, зарубежная и российская стороны оцениваются независимо, узел без
зарубежных выходов проверяется по российской стороне). Здесь — только российские подробности:
- «Молчат все выходы группы R» — у каждого выхода R последняя активная проба неудачна и пассивного признака (§6.1)
  за это время не было. При «Лениво» в простое годные выходы не проверяются и в «молчат все» не участвуют (SE §4.6):
  без проб группа «молчащей» не считается; прямая проба делается в том же такте, где неудачна последняя активная
  проба.
- **Почему при `node.ru_offline` не переходить на последний шаг «напрямую».** Прямой путь к российским адресам тоже не
  работает: переход ничего не даст, а пуши «роутер упал» были бы ложью.
- Одна российская группа лежит, а другая отвечает → вывод по таблице SE §4.6 почти всегда «роутеры первой группы»
  (прямая проба дешёвая, делается всё равно).
- Выход из `node.ru_offline` — первая удачная прямая российская проба. Окна российских выходов очищаются (SE §4.6).

### 6.5 Повторное разрешение адреса домашнего роутера
- У домашних роутеров адрес часто динамический: ключ указывает домен динамического DNS. Нога AmneziaWG и WireGuard
  разрешает имя **один раз** при старте. После смены IP дома выход мёртв до пересборки пула.
- **Что:** для AWG-выходов **любой роли**, у которых в ключе имя, а не IP, — повторное разрешение. Новый адрес →
  `awg set kawgN peer <pub> endpoint <ip>:<port>` без пересоздания ноги, строка в журнал. xray-выходы разрешают имя
  на каждое соединение — им не нужно.
- **Кто и когда (находка Б5):** решает сборщик (`collect.py`, Q3) — он знает, что выход мёртв: выход мёртв ≥ 60 с и
  в ключе имя → не чаще раза в 5 мин на выход зовёт `install.sh --egress-reresolve <N>` (новый безголовый вход, Q4)
  подпроцессом **после снятия блокировки состояния**, с тайм-аутом 15 с; в `/run/kaskad/reresolve.json` — время
  последней попытки по выходу (переживает перезапуск сборщика до перезагрузки).
- **Через какой резолвер:** системный резолвер узла (`getent ahostsv4`, как при подъёме ноги `egress_awg_leg_up`),
  **не** dnsmasq шлюза (10.77.0.1 ходит через «Основную» и при её блоке не отвечает). Нет ответа за 5 с → прямой
  запрос к `77.88.8.8:53` без метки (тайм-аут 5 с). Ответ — только глобальный IPv4 (проверка как SE §5.4 п. 2).
- **Режим модуля ядра** (`awgkmod`): та же команда `awg set` через `awg_tool_bin` — она одинаково работает с
  интерфейсом `amneziawg-go` и модуля ядра; отдельной ветки нет. Тест — в обоих режимах (подменённый `awg`).
- Ожидание и проверка — с лимитом времени, без бесконечных циклов.

### 6.6 Пресет «Дом» (`ru_home`) для российской группы

У российской группы два набора — «Дом» и «Свой» (решение 11; остальные наборы для РФ — не в этом выпуске, РФ-группы
29.10, Ш3). «Дом» задаёт проверки и поведение при отказе (`policy.PRESET_KEYS` + проверки); **уровни, способ выбора,
«Если все выходы недоступны» и «Новые и перенесённые ключи» в набор не входят** — их правка набор не меняет.

| Поле | Значение |
|---|---|
| Уровни (не поле набора) | куда встаёт новый ключ — `new_exits_tier` (§8.1 «Ещё»): у российской по умолчанию `last` — каждый ключ своим уровнем в конце (1-й роутер, 2-й, 3-й); выбранный уровень — ключи делят устройства в нём |
| Способ выбора (не поле набора) | поровну; «По отклику», «По весам»; «По скорости» — только при замере скорости группы (без замера он как «Поровну»), уже сохранённый остаётся как есть. Смена способа или новый ключ в уровне раскладывает только новые устройства; подключённые остаются на своём ключе, пока он работает, и переходят при ночной перебалансировке, если она включена (REV-plan С-1, вариант а) |
| Частота проверок | «Часто» — раз в 10 с (T-q Н-lazy: домашний роутер, который упал, виден за минуту); группа «Дом», сохранённая с «Лениво» до этого, остаётся «Дом» (`policy.LEGACY_FREQ`); пассивный признак и «подозрение» (§6.1; решено 15.10) (D-044) |
| Ночная перебалансировка | выкл.; видна у российской группы в «Поведении» (С-1); включили — набор становится «Свой» |
| «Упал» / «снова работает» | правило владельца (SE §3.2) (D-054): у «Лениво» — ≥ 50 % неудач из 4 последних проб не старше 1 ч / 2 удачи подряд |
| Правила | потери > 30 % и ≥ 3 неудач за 2 мин → ухудшен; вернуть при < 10 % за 5 мин (обе выдержки в минутах, возврат ≥ ухода — проверка SE §3.3, находка С3) |
| Возврат на основной | вкл., 10 мин |
| Нестабильный ключ (`flap_standby`, SE §4.3) | вкл.: ≥ 3 падений за 15 мин и есть другой годный ключ группы («Дача») — «Роутер» «в запас» на 15 мин, `exit_standby` (`unstable`); ключ один — остаётся в работе с пометкой «нестабилен · до ЧЧ:ММ», без события (правка 5, З2) |
| Страна | ожидается RU, раз в сутки; смена — **только пуш** (решено 14.10, ночь) (D-024); условие «Страна не та» — по желанию (§6.2) |
| Скорость | выкл. |
| Последний шаг (не поле набора) | «с сервера напрямую» при создании группы (решение координатора по примеру владельца) (D-037); дальше — строка «Если все выходы недоступны» |

Отклик по умолчанию в условия не входит: у домашних каналов он скачет, а ложные уходы на дачу хуже, чем лишние 50 мс.
Добавить условие можно, форма та же (SE §7.2).

### 8.1 «Выходы» (T8 — группы, Q6 — российское)
- Вкладка SE §7.1 — **«Группы»**. Это список карточек групп; «Основная» всегда первой. Содержимое

  Добавляется строка **«Если все выходы недоступны: [Блок ▼ | С сервера напрямую]»** (с предупреждением «трафик пойдёт
  с IP сервера»).
- Список выходов делится на два блока:
  - **«Зарубежные выходы»** — по группам, у выхода метка группы;
  - **«Российские выходы»** — отдельный блок ниже, по российским группам, у выхода метка «РФ». Под заголовком строка:

  российской сразу пресет «Дом».
- **«Добавить выход»** — поле «Назначение»:
  - «Зарубежный — в группу [Основная ▼]»;
  - «Российский — в группу [Дом ▼ | + новая]»;
  - поле ключа принимает `.conf`, `vpn://`, `vless://`, `hy2://`, `ss://`, `trojan://`, `vmess://`;
  - подсказка для российского: «Ключ VPN-сервера вашего роутера или сервера в России. Роутеру нужен белый IP или
    домен динамического DNS; за CGNAT провайдера сервер на роутере не работает».

  страна (ожидается RU; сменившаяся — жёлтой строкой, только пуш), «≈ N МБ в сутки на проверки». Кнопки — как SE
  §7.3 и «Перенести в группу…» (между ролями — с предупреждением §2.2: перезапуск бота, сброс состояния).
- **Карточка российской группы** — та же общая карточка, что у зарубежных групп («как у выходов», владелец; РФ-группы

  - в шапке значок «РФ», сводка «N уровней · N ключей · N устройств · выбрали: …», «сейчас: через «Роутер»»,

    ключи недоступны с 12:03»;

### 8.3 Человек и устройство (Q6)
- Поле **«Российские сайты»**: человек — `Напрямую с сервера | Через «Дом» | Через «Офис»`; устройство — `Как у
  человека | Напрямую с сервера | Через «Дом» | …`.
- Поле видно всегда. Когда «Россия напрямую» у этого человека не действует, оно неактивно с подсказкой «работает
  только при профиле «Россия напрямую»».
- Включение российской группы показывает строку: «Российский трафик этого человека пойдёт через ваш роутер — его
  интернет-провайдер увидит эти соединения».
- **Маршрут** (форма SE §7.3, T8): «Куда: [Группа «Основная» ▼ | Группа «Стриминг» | Выход … | Напрямую | Блок]».
  Российские группы и выходы в этом списке не показываются.
- Подсветка устройства — по SE §7.3 («нет выхода в интернет» / «выходы недоступны — идёт с сервера напрямую»); для
  российской группы на последнем шаге «блок» — жёлтая пометка «российские сайты не открываются: ключи «Дом»
  недоступны» (зарубежные сайты работают, поэтому не «нет выхода»; решение координатора) (D-026).

### 8.4 Схема (Q6, минимально)
- Российская группа — отдельный узел схемы с меткой «РФ»; ребро от устройства — только при действующей `ru_via`.
- В инспекторе устройства — поле §8.3 (намерение `{"type": "ru_via", "device"|"user", "via"}` через
  `gw/ops._change`).

### 8.5 Удаление группы
- Нельзя удалить `main`.
- «Удалить группу» — **окно** (D-077) (решение координатора 15.10, «UX ↔ ТЗ»; правка 7; заменяет «подтверждение на месте»
  правки 6), свой запрос `DELETE /api/gw/groups/<gid>` (SE §7.9), не общее сохранение политики:
  - **выходы группы** — радио без номеров «Куда перенести выходы: [группа той же роли ▼]» (`exits_to`); у российской
    группы без другой российской — «сначала перенесите или удалите ключи», кнопка «Удалить» выключена;
  - **ссылки** — на группу ссылаются маршруты или `ru_via`: «На группу «Дом» ссылаются 3 человека. Что им
    поставить:» и радио без номеров «Напрямую с сервера / Другую группу [▼]» (`reassign`; цифры — только SSH-меню);
  - **другие ссылки** (правка 8, З-1) — если это группа прокси бота (`tg_proxy_group`), группа новых ключей
    (`new_exits_group`) или на неё указывают подписки (`subs[].group`), замена выбирается в том же окне: «Прокси бота
    — через группу [▼]» (только зарубежные, `tg_proxy_to`), «Новые ключи — в группу [▼]» (только зарубежные, `new_exits_to`), «Подписки
    «…» — в группу [▼]» (та же роль, `subs_to`); без выбора «Удалить группу» выключена;
  - выходы встают на `new_exits_tier` группы-цели; затронута группа прокси бота — прокси пересобирается (SE §2.9);
  - строка «что изменится» из `DELETE …?dry=1`, при каждой смене выбора — новый прогон с номером запроса; пока
    считает — «Удалить группу» неактивна; не ответил за 20 с — «Не удалось посчитать последствия», удаление только по
    второму подтверждению (с `rev` чтения группы — SE §7 «Откуда `rev`»); кнопки «Отмена · Удалить группу» (`c.cancel`);
  - пока у карточки группы или у группы-цели (`exits_to`) есть несохранённые правки, «Удалить группу» выключена
    («Сначала сохраните или отмените правки»); правки других групп не мешают и не уходят; запрос несёт `rev` своего
    сухого прогона; данные изменились после прогона — 409 `policy_changed`, окно пересчитывает «что изменится» («Данные
    изменились — пересчитал»), удаление — новым нажатием (SE §7 «Версия политики»; проверка 17, З-2).
- Сервер без нужного параметра — отказ 409 с `data.exits`/`data.refs`/`data.uses`; повтор по уже удалённой группе — 404
  `gone` до сверки `rev`, панель считает его успехом (SE §7.9, «Повтор `DELETE`»; проверка 16, З-5). Запись окна
  независима от других записей вкладки; после неё открытые формы с правками перекладываются (SE §7, «Версия
  политики»; проверка 18).
  CLI — `kaskadctl gw group-del` (`--exits-to`, `--reassign`, `--tg-proxy-to`, `--new-exits-to`, `--subs-to`), MCP —
  `group_delete` (SE §7.7–7.8). Российская группа вместе с её ключами (решение 8а, `exits=drop` панели; В1, 3.3.7.12):
  CLI `--with-keys` (не вместе с `--exits-to` и `--subs-to`: подписки группы при этом не переносятся — сначала
  удалить их; сухой прогон и вопрос называют ключи), MCP `with_keys` +
  `confirm_with_keys`; без них последняя российская группа с ключами — по-прежнему 409 `ru_last`, текст подсказывает флаг.

### 8.7 `kaskadctl`

- **Существующие события** (SE §3.6) получают аргументы `group`, `group_name`, `role`. Тексты для `role = ru`

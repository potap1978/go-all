## 3. Модель данных и контракты

Все файлы пишутся атомарно (tmp + `os.replace`), права `0600 root`, JSON в UTF-8. Неизвестные поля читаются терпимо
и сохраняются. Схема — поле `version`.

### 3.1 Политика выходов — `state.json` → `gateway.exit_policy`
Хранится в `st["gateway"]` рядом с `exits` (`model._defaults`, `model.py:80`; `exit_pref` — `model.py:548`), а не
отдельным файлом: попадает в резервную копию без правок `backup.py`. Чтение и запись — новый модуль `gw/policy.py`
(`load(st)` с умолчаниями, `save(st, doc)`, `validate(doc, pool_ids)`, `group(doc, gid)`, `group_of(doc, exit_id)`,
`place_new(doc, pool, hints)` — SPEC-groups §2.1, §2.4).

**Политика — список групп** (D-015) (SPEC-groups §2.1; этап 1 не выпущен, поэтому `version: 1` — сразу с группами, формы «без
групп» и миграции нет). Общее на узел — `version`, `hint_seen`, `probes` (§3.2), `new_exits_group`, `tg_proxy_group`
(§2.9) (D-133); всё остальное — поля **группы**. Рядом с политикой — **`gateway.policy_rev`** (целое, правка 8, С-2) (D-080): растёт
на 1, когда меняется отпечаток (ниже) — запись политики, групп и `exit_pref` (форма, кнопка над объектом, CLI, MCP,
добавление и удаление ключа) и размещение нового выхода сборщиком; сверка — §7.9 (D-079).

**Кто поднимает `rev`** (D-081) (точечная проверка, З-8; проверка 16, З-1…З-3, придирки 1–3; задача **T1**, тест
`tests/gw/test_rev.py`). Одна точка — новый модуль `gw/rev.py`:
- **Отпечаток** — то, что правят формы и кнопки над объектом: id выходов **обоих файлов пула** (`upstream.txt` и
  `upstream-ru.txt`; второго до T15 нет — пустой список; без имён; путь `upstream-ru.txt` T1 берёт рядом с
  `paths.egress_up()` своей константой в `gw/rev.py`, Q4 переводит его на `paths.egress_up_ru`; проверка 17, придирка 1), `exit_policy` без `hint_seen`, без имён групп и
  без `probes.speed` (у общих настроек теста скорости своя версия `ver`, §7.9; путь трафика они не меняют; проверка 19, З-2),
  `tg_proxy_group`, `exit_pref` (`gateway.exits[*]`) — только `enabled`, `manual`, `manual_why`, `speed_skip`,
  `quota` (без `name`, подсказки `group` и всего `country`).
- **Счёт — два входа** (проверка 18, С-2) (D-097). Блокировка состояния повторно не входит: `state.locked()` на каждый вызов
  открывает новый дескриптор и ждёт `flock` до 15 с, а второй `flock` в том же процессе не проходит (`state.py:178–199`).
  Поэтому:
  - **`note(st)`** — для вызова **внутри уже взятой блокировки** (`state.transaction()`): сравнивает отпечаток `st` с
    его `gateway.policy_sig`; не совпал — пишет в тот же `st` `policy_rev` + 1 и новый `policy_sig` (сохраняет
    транзакция вызывающего); отдаёт `policy_rev`. Блокировку не берёт.
  - **`current(st)`** — для чтения **вне блокировки**: сравнивает отпечаток с сохранённым без блокировки; совпал —
    отдаёт `policy_rev`, ничего не пишет; не совпал — открывает свою `state.transaction()` и зовёт в ней `note` по
    свежему состоянию (чтения не спорят со сборщиком за блокировку, `gw/collect.py:328`; придирка 2). Звать `current`
    под взятой блокировкой нельзя. **Отдаёт пару `(rev, st)`** (проверка 19, З-3): совпал — тот же `st`, не совпал —
    свежий `st` своей транзакции. Ответ чтения (`GET /api/gw/policy`, `GET /api/gw/exits`, чтения CLI и MCP) строится
    из этого `st`, а пул читается после `current`: данные и версия — из одного чтения; строка пула, дописанная между
    ними, только сделает `rev` ответа старше данных — запись с ней получит 409, а не пройдёт поверх невиденного.
  - **`bump(st)`** (восстановление `.kbk`, ниже) — как `note`: внутри блокировки вызывающего, своей не берёт.
  - **Защита от вложенной блокировки** (T1): `state.locked()` помечает поток (`threading.local`, панель —
    `ThreadingHTTPServer`); повторный вход в том же потоке — сразу `NestedLockError` с текстом о вложенной блокировке,
    без 15 с ожидания. Это подкласс `LockedError`: прежние обработчики занятости ловят его как раньше, но **сборщик**
    ловит его отдельно, до `LockedError`, и пишет в журнал ошибкой с местом вызова — не тихим «пропуском такта»
    (`collect.tick`: `except LockedError: return {"skipped": True}`, `collect.py:333–334`; T4; проверка 19, придирка
    4). `hooks._maybe_state_lock` (`hooks.py:133–145`) поведение не меняет: при вложении блокировку уже держит тот же
    поток. **Вложение — ошибка кода, а не «занято»** (проверка 20, З-2) (D-100): у `NestedLockError` код `ERROR` (1), не
    `LOCKED` (6); `routes.core_error` (T7) проверяет его до `LockedError` и отдаёт 500 со строкой в журнал (место
    вызова), а не 409 «занято» с «Повторить», который повторял бы ту же ошибку; CLI — код выхода 1. В тестах «занято»
    блокировку держит **другой процесс** (не тот же поток), иначе тест прошёл бы и на вложении (§11.1, T7).
  Полей нет (узел с 3.3.x) — `policy_rev` = 0, отпечаток пуст: первый подсчёт даёт 1 (придирка 3).
- **Кто зовёт.** `current` — только чтения вне блокировки: `GET /api/gw/policy`, `GET /api/gw/exits`, чтения CLI и
  MCP. `note` — внутри уже взятой блокировки: записи, которые пишут состояние сами, в своей `state.transaction()`
  (`gw/ops` через `_change`, `policy_ops`, бот через них), — до записи для сверки `rev` (§7.9, `--rev`) и после неё
  для подсчёта, в той же транзакции; сухой прогон (§7.9); сборщик после размещения (SPEC-groups §2.4);
  `ensure_initial` в `ops.enable`. **Записи через скрипт пула** — иначе, в три шага (ниже). `bump` — `backup.apply`.
  Запись мимо Python (пул пишет bash: `install.sh`, SSH-меню, ручная правка) поднимает версию при следующем подсчёте
  (`current` или `note`), без своего кода.
- **Записи через скрипт пула** (проверка 19, С-1; T7) (D-098): добавление ключа (`exit_add`, `gokaskad --egress-add`), удаление
  ключа (`exit_del`, `--egress-del`, `ops.py:1868–1897`), подписки (`exitsubs.replace_pool`, `--egress-replace`,
  `exitsubs.py:574–580`). Скрипт берёт блокировку состояния сам, в своём `gw apply` (`ops.py:1520–1524`), поэтому
  держать её вокруг скрипта нельзя: `gw apply` 15 с ждал бы `flock` и падал. Три шага:
  1. **до скрипта** — короткая `state.transaction()`: то, что нужно до запуска, и, где запись её требует, сверка `rev`
     (`rev.note(st)`; не совпала — 409 `policy_changed`, скрипт не идёт). У удаления ключа — 404 `gone` и сверка в
     порядке §7.9 («Объекта нет») и `moves` для ответа; у `exit_add` — подсказка `exit_pref.group` (`rev` не сверяется,
     §7.9). Транзакция закрывается до запуска скрипта;
  2. **скрипт** — без блокировки состояния. Подмену пула между шагами 1 и 2 ловит сам скрипт: удаление — по номеру
     строки и hex ключа (`RC_POOL_CHANGED` → 409 `conflict`, `ops.py:1880`), замена пула подписки — по хэшу прежнего
     пула (`--egress-replace <hash>`, `RC_POOL_CHANGED`); другое окно меняет пул — `RC_POOL_BUSY` → 409 «занято» (код 6,
     §7 «Ошибки»);
  3. **после скрипта** — `state.transaction()` с `rev.note(st)` (у `exit_add` перед ним — `place_new`, ниже); эта `rev`
     — в ответе записи. Изменение, сделанное кем-то между шагами 1 и 3, не теряется: шаг 3 его тоже сосчитает, а
     открытые формы переложатся (§7 «Версия политики»). **Шаг 3 — по возможности** (проверка 20, З-1) (D-100): пул уже
     изменён, поэтому `LockedError` шага 3 (блокировку дольше 15 с держит чужое применение) запись в отказ не
     превращает — ответ успешный, `rev: null`, строка в журнал (`util.log_action`: что не досчитано). Панель после
     записи и так перечитывает страницу и берёт версию оттуда (§7 «После каждой своей записи»); `rev` догонит
     ближайший `current` или `note` — id строк пула входят в отпечаток. Неразмещённую строку `exit_add` разместит
     сборщик (SG §2.4). `NestedLockError` в шаге 3 — ошибка, как везде (выше).
  **Подписки** (обновление по таймеру, из панели, CLI, бота) `rev` не сверяют — пишут не формы, а фон, — шаг 1 у них
  только свой (замок подписок `exitsubs._locked`, `exitsubs.py:206`, — не блокировка состояния), а `note` после
  скрипта (шаг 3) — одна транзакция **после `_record` и `save(doc)`**, вне цикла по подпискам, тоже «по возможности»
  (проверка 20, З-1): иначе `LockedError` вышел бы из `_apply` раньше учёта ключей подписки (`exitsubs.py:689–692`,
  `:758–760`), и ключи, уже попавшие в пул, остались бы в нём навсегда. Ответ записи подписки в панели несёт эту `rev`
  (или `null`).
- **Сборщик** меняет `rev` только размещением нового выхода в `tiers[].exits` (SPEC-groups §2.4): это изменение
  состава группы, и открытая форма этой группы должна получить 409. Первая увиденная страна (`country.expected`,
  `accepted_at`) и `country.notified` вне отпечатка: их не правит ни одна форма, `country` меняют только сборщик и
  «Принять новую страну» (её ответ отдаёт текущую `rev`). Подсказку `exit_pref.group` сборщик не снимает. Сборщик
  размещает **любую** неразмещённую строку пула; отличать строки `exit_add` ему не нужно.
- **Добавление ключа через `gw/ops.exit_add`** (панель, CLI, MCP, бот; проверка 17, З-1; T7) — запись через скрипт
  пула в три шага (выше), подробности шагов 1 и 3. Подсказку
  `exit_pref.group` `exit_add` пишет до запуска скрипта. Пул пишет скрипт (`gokaskad --egress-add`, `ops.py:1520–1526`),
  и **блокировку состояния на время скрипта `exit_add` не держит**: скрипт берёт её сам в своём `gw apply`, а скрипт
  идёт секунды, первый ключ AWG — минуты (`EXIT_ADD_TIMEOUT` = 23 мин). Пока скрипт идёт, сборщик может разместить
  строку на своём такте — это обычное размещение (+ 1). После возврата скрипта `exit_add` в своей
  `state.transaction()` зовёт `policy.place_new` (строка ещё не размещена — размещает; уже размещена — ничего не
  меняет) и `rev.note(st)` (не `current`: блокировка уже взята; проверка 18, С-2); ответ добавления несёт эту `rev`.
  Следующий такт сборщика её не меняет: строка уже размещена. Формы вкладки с правками перекладываются по §7 «Версия
  политики»; панель на время добавления ничего не держит (проверка 18).
- **Сколько прибавляется.** Каждая запись, изменившая отпечаток, — + 1: две записи подряд (квоту задали, затем
  сняли) — + 2. `rev` не меняют запись без изменений и правка «туда и обратно» мимо Python между двумя подсчётами
  (содержимое то же — затирать нечего). Имена (выходов, групп, людей, устройств) (D-081), маршруты людей, устройств и узла
  по умолчанию, `hint_seen`, `probes.speed` — вне отпечатка (у маршрутов и `probes.speed` своя `ver`, §7.9).
- **Восстановление `.kbk`** берёт `rev` не из копии: `rev.bump(st)` ставит `policy_rev` = max(текущая, из копии) + 1
  (вызов в `backup.apply` под его блокировкой — T1). **`ensure_initial`** меняет политику — отпечаток поднимет `rev`
  сам (текущая + 1).
- **После `gw purge` с людьми** (и точного восстановления копии без шлюза — оно зовёт тот же `purge`) `gateway` пуст, но
  счёт идёт **не с 0**, а со случайного 31-битного числа (`rev.seed`, база `policy_rev_base` в корне `state.json`, вне
  `gateway` и вне `.kbk`; первый подсчёт — база + 1, затем база удаляется): вкладка, открытая до сброса, сверку не
  пройдёт (решение координатора 15.10, REV-s1-t1 З-6) (D-109). Узел 3.3.x без сброса по-прежнему начинает с 1.

Поля политики:

```jsonc
"exit_policy": {
  "version": 1,
  "hint_seen": false,              // плашка §7.1, на весь узел
  "probes": { ... },               // §3.2 — общее на узел (без services/geo/speed.enabled)
  "new_exits_group": "main",       // куда попадает новый зарубежный выход без подсказки (SPEC-groups §2.4)
  "tg_proxy_group": "main",        // группа ключей «Прокси для API Telegram» (§2.9); только role = abroad
  "groups": [
    {"id": "main",                 // main | g-<6 hex>, неизменный; main есть всегда и не удаляется
     "name": "",                   // "" — имя по умолчанию («Основная» / «Main», ниже); иначе names.check, 1–40 знаков
     "role": "abroad",             // abroad | ru — задаётся при создании и не меняется (ru — T15)
     "preset": "compat",           // abroad: compat («Как раньше») | standard | strict | economy | custom; ru: ru_home | custom; кто пишет — §1.3
     "tiers": [                    // порядок = приоритет; пусто → один уровень из всех выходов группы
       {"id": "t1",                // [a-z0-9-]{1,16}, неизменный
        "name": "",                // "" — имя по умолчанию («Уровень 1» / «Level 1», ниже); иначе names.check
        "exits": ["e-1a2b3c4d5e", "e-9f8e7d6c5b"],   // id выходов (e["id"] из exits.pool(), §3.8); выход ровно в одном уровне одной группы
        "method": "even",          // even | best_rtt | weights | capacity
        "weights": {"e-9f8e7d6c5b": 3},                     // 1–100, по умолчанию 1; только method=weights
        "tolerance_ms": 30, "tolerance_pct": 20}           // только best_rtt: «равны», если хуже лучшего не больше max(ms, %)
     ],
     "new_exits_tier": "last",     // last | first | <tier id> — куда попадает новый выход группы
     "per_connection": false,      // режим «по соединениям» (§4.5), только у main
     "evict_degraded": true,       // уводить закреплённых с «ухудшен» (§9 в. 4, решено) (D-010)
     "flap_standby": true,         // нестабильный выход — «в запас» на 15 мин (§4.3, правка 5, З2) (D-071); compat — false
     "return_to_primary": {"enabled": true, "hold_min": 10},   // 1–120 мин (§9 в. 7, решено) (D-012)
     "night_rebalance": {"enabled": false, "at": "04:00"},     // по поясу узла (§3.7)
     "drop_on_degrade": false,     // обрывать открытые соединения при «ухудшен»/«в запас» (ядро: conntrack -D)
     "fail": "block",              // последний шаг группы: block | direct (§2.2)
     "checks": {                   // проверки группы (§3.2)
       "targets": "abroad",        // abroad | ru (T15, SPEC-groups §6.1)
       "freq": {"mode": "often", "every_s": null},   // lazy | often | normal | rare | custom (§3.2, решено 15.10) (D-044)
       "speed": {"enabled": false, "every_h": 6, "url": "default"},   // тест скорости группы (§3.2, §5.3; О3 решён 15.10)
       "services": [],             // §3.2
       "geo": {"enabled": true, "every_h": 24, "confirm": 2, "action": "push", "expect": null}},
     "rules": [ ... ]}             // §3.3; "exits": "all" = все выходы этой группы
  ]
}
```

- **Выход — ровно в одной группе и одном уровне** (**подтверждено владельцем 15.10** (D-045), план «Решено 15.10 (ночь)»;
  SPEC-groups §2.3):
  состояние — у выхода, условия — у группы. Одну группу можно назначить многим людям и устройствам (маршрут
  `pool`/`group:<gid>`). Не больше 8 групп на узел.
- **Роль выхода** — по файлу ключа: строки `upstream.txt` — `abroad`, строки `upstream-ru.txt` — `ru` (T15,
  SPEC-groups §2.2). `exits.pool(st=None, roles=("abroad",))` **по умолчанию отдаёт только зарубежные выходы**: так
  нынешние потребители пула (`gw/ops.py:182, 789, 1483, 1844, 2174`; `gw/xray.py:462, 726`; `panel/api.py:235`;
  `panel/scheme.py:134`; `rules/ops.py:280`; `summary.py:303`; `awgkmod.py`, `awgengine.py`) российский выход не
  увидят, даже если их забыли поправить. Обе роли берут явно (`roles=("abroad", "ru")`) только места, которым они
  нужны: `xray.render` (исходящие `gr-`, `tproxy-`, `probe-`), `net.plan` (пары метка–порт), сборщик (пробы,
  счётчики, `health`), `awgkmod`/`awgengine` (проверка ядер ног), список выходов панели и схема (T15). Записи пула
  получают поля `role` и `tag` (`exits.tag(eid, role)`, T1). Тест-страж (T1, дополняется T15): российский выход ни
  при каких данных не попадает в `gw_route`, `gw-all`, `gw-vless`, observatory, `bot-bal`, кандидаты `assign`
  зарубежной группы, списки выбора маршрута (панель, бот, SSH, CLI, MCP), подписи схемы и сводку.
- Политики нет в файле → эффективная политика — одна группа `main` в `compat` (§1.3).
- **Имена по умолчанию не хранятся текстом** (D-111) (решение координатора 15.10; проверка 16, «вне правки»; единственное
  место правила — здесь). Имя, которое пишет сама система, — пустое поле `name: ""`: у группы `main` и у уровней,
  созданных системой (`ensure_initial`, «+ уровень», «Разложить по протоколу»). Показ — по языку узла
  (`KASKAD_LANG`) одной функцией T2 `policy.label(group, lang)` / `policy.tier_label(group, i, lang)`: пустое имя
  `main` — «Основная» / «Main», пустое имя уровня — «Уровень N» / «Level N» (N — место уровня в группе, с 1);
  непустое — как есть; ключи `ep.name.main`, `ep.name.tier` (RU+EN). Так показывают все: API (`label` рядом с
  `name` у групп и уровней в `GET /api/gw/policy`; остальные ответы отдают id группы), панель (несохранённый уровень
  в форме — та же формула по `i18n-*.js`, тест сверяет тексты с Python), бот (§7.10), CLI и MCP (`gw groups`,
  `gw policy`, `exit_groups_list` — поля `name` и `label`), SSH-меню (таблица §7.6, маршрут `group:<gid>` в меню

  (проверка — `policy.validate_exit`). Владелец правки `model.py` — T2:
  ```jsonc
  {"enabled": true, "name": "…",
   "group": "main",                // подсказка группы для нового выхода (SPEC-groups §2.4); пишет добавление ключа
                                   // до записи строки в файл; после размещения сборщиком не используется
   "manual": null,                 // null | "standby" | "maintenance" — ручные состояния
   "manual_why": null,             // null | "sub_confirm" — новый ключ подписки ждёт подтверждения (§3.8, Н4);
                                   // снимается вместе с manual («Вернуть»)
   "speed_skip": false,            // true — тест скорости группы этот выход пропускает (§5.3; лимитный канал) (D-117)
   "country": {"expected": "DE", "accepted_at": 1760000000,
               "notified": ["FI"]},  // о каких новых странах уже был пуш (§4.3): та же страна повторно не пушится;
                                     // чистится при «Принять новую страну» и при возврате ожидаемой страны
   "quota": {"period": "month",    // month | day
             "limit_gb": 500,      // > 0, шаг 0,1
             "reset_day": 1,       // 1–28 (month); для day — полночь по поясу узла
             "warn_pct": 80,       // 50–99
             "action": "remove"}}  // remove — «снят» (по умолчанию, решено) (D-011) | standby | push
  ```
  Значение действия «снят» во всех полях (`quota.action`, `rules[].then`) — `remove`, а не `off`:
  `off` читается как «выключено». Состояние выхода «снят» в API и файлах по-прежнему `off` (§4.2).

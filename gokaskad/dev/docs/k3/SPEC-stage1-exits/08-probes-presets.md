## 5. Пробы

### 5.1 Отклик, потери, джиттер (в такте сборщика)
- Цели проб — данными, `lib/kaskad/gw/probe_targets.json`, по `checks.targets` группы выхода; `connect_through` и
  HTTP-проба принимают список целей. Выходы российских групп проверяет сам Kaskad без observatory (T15,
  SPEC-groups §6.1).
- **AWG:** новая HTTP-проба `GET http://cp.cloudflare.com/generate_204` сокетом с `SO_MARK = 256+N`
  (≈ 2 RTT: SYN и запрос), неблокирующе в `probe_round` (`collect.py:108`) рядом с `connect_through`
  (`exits.py:852-918`; сейчас только True/False, время не меряет). Время — от `connect()` до первой
  строки ответа. Период — от частоты группы (§3.2): `max(3P, 30)` с; если за 60 с через выход не было трафика —
  `max(12P, 120)` с (при «Часто» — 30 / 120 с). Проба «жив/мёртв» (TCP к 1.1.1.1 / 8.8.8.8 / 9.9.9.9) — как сейчас,
  но раз в P группы (при «Часто» — 10 с, как в 3.3.3); каждая — одна проба в окне правила «упал» (§3.2); «Лениво» —
  §3.2.
- Выход, снятый по квоте с `quota.action = remove`, сборщик не проверяет ни пробой «жив», ни пробой отклика, а из
  observatory он выпал вместе с `gx-` (§2.7, §5.6).
- **xray-выходы:** поле `delay` observatory (`/debug/vars`, `exits.observatory()` `exits.py:921-934`; сейчас
  берёт только `alive`, мёртвый приходит без ключа) вместо одного `alive`. **Отсев повторов:**
  замер новый, только если `last_try_time` выхода изменилось с прошлого чтения; `delay = 99999999` — неудача
  (поправка С4). Интервал общий для всех (`observatory_s` — самая частая зарубежная группа, §3.2), «ленивым» по
  выходу его не сделать. Из `/debug/vars`
  берутся **только теги текущего пула**, и замер старше `2 × observatory_s` — «нет ответа» (T0: после `rmo` запись
  остаётся «живой» с замороженным временем).
- Окно: `deque` в памяти сборщика на выход; `loss` = доля неудач в окне; `jitter` = стандартное отклонение отклика
  удачных замеров окна; `rtt_med`/`rtt_p90` для графиков.
- Сравнение отклика AWG и xray — только внутри вида или по `x_norm` (С2).
- Замер трафика проб AWG — на стенде (§11.4).

### 5.2 Внутренние SOCKS-входы и вход пула
- `probe-<id>` рисуется для каждого xray-выхода любой группы, включая `gr-` (через него идут пробы российских
  xray-выходов, T15). `pool-socks` → `gw-all` → «Основная».
- По одному входу xray на **каждый xray-выход**: `127.0.0.1:12700+N`, `tag: probe-<id>`, правило
  `inboundTag [probe-<id>] → gx-<id>`. Рендер — в `xray.render()` рядом с `tproxy-<id>` (`xray.py:321-322`, правило `:383-384`).
- Вход пула: `127.0.0.1:12699`, `tag: pool-socks` → балансировщик `gw-all`.
- Оба вида входов — в списке входов правила `blocked_ips(node_addrs) → block` (SSRF на стороне xray). У обоих
  `"udp": false` (UDP через них не нужен, лишний порт не открываем).
- nft «только root» (поправка С3): в таблице `ip kaskad` новая цепочка `gw_out` (`type filter hook output priority 0`):
  `ip daddr 127.0.0.1 tcp dport { <только отрисованные порты> } meta skuid != 0 reject`. Набор — ровно те порты,
  которые есть в текущем конфиге xray: API 10854 (без пароля: сейчас его может звать любой процесс узла), метрики
  10852, вход пула 12699, `12700+N` по каждому xray-выходу. **Не весь диапазон** 12700–12955: порты, которые Kaskad
  не слушает, соседним продуктам не закрываем. dnsmasq ходит в 10853 — этого порта в наборе нет. Список даёт
  `xray.internal_ports(st, sec)`; `net.rules()` (`net.py:515`) рисует цепочку, применяется вместе с остальной
  таблицей. Тест: от `nobody` подключение к отрисованному порту отклоняется, к неотрисованному из диапазона — нет; от
  root — проходит.
- Порты: `12700+N` при `N ≤ 255` → `12701–12955`, не пересекаются с `12401–12655` (TPROXY). Добавить в
  `internal_ports()` (`xray.py:714-731`) и `port_conflicts()` (`xray.py:742-766`), чтобы проброс портов и входы их не заняли.
  Порт API 10854 `internal_ports` сейчас добавляет только при VLESS-входе (`xray.py:724-725`); раз API рисуется всегда,
  когда в пуле есть выходы (§2.6), — и в `internal_ports` он всегда в этом случае.
- Для AWG-выходов SOCKS-вход не нужен: всё через `SO_MARK`.
- Кто ходит в эти порты: сборщик, юнит проб, панель, `xray api` — все под root. Если в этапе 3 HTTP-уведомления
  «через пул» будет слать процесс не под root — его uid добавляется в правило явно.

### 5.3 Тест скорости
- **Решено владельцем 15.10 (О3):** (D-034) выключен по умолчанию; частота на выбор 1 / 3 / 6 / 12 / 24 ч; ссылка — своя или
  стандартная.
- **Где галочка — у группы, исключение — у выхода** (решение координатора, находка З10) (D-117): включение, частота и
  ссылка — `checks.speed` группы; пределы одного теста и бюджет — общие на узел (`probes.speed`, своя форма — §7.1,
  проверка 19, З-2); у выхода —
  переключатель «Не проверять скорость этого выхода» (`exit_pref.speed_skip`). Почему так: условия по скорости
  («скорость < N → ухудшен») живут в группе, и тест должен идти у тех же выходов, что и правило, — иначе правило
  «неизвестно»; одна галочка держит их вместе и не требует щёлкать каждый выход. Исключение у выхода — для
  лимитного канала (квота, мобильный интернет) без отдельной группы. Выход с квотой: форма теста пишет «тест расходует
  квоту: ≈ N МБ в сутки» (подсказка включить исключение). Кнопка «Проверить скорость сейчас» в карточке выхода
  работает при любом положении галочек (ручной запуск, тот же бюджет).
- Включение теста у группы переводит её пресет в «Свой»; переключатель у выхода пресет не меняет (это поле выхода, а
  не политики).
- Исполнитель — юнит проб (§5.7). Цель по умолчанию `https://speed.cloudflare.com/__down?bytes=<max>` (до 50 МБ — 200).
- Путь: AWG — сокет с `SO_MARK 256+N`, имя цели резолвится через выход (DNS-over-TCP к 1.1.1.1:53 той же меткой);
  xray — SOCKS5 CONNECT на `12700+N` с ATYP=domain (резолвит выход).
- Клиент stdlib: `ssl.create_default_context()` (проверка сертификата всегда), ручной `GET`, `Accept-Encoding:
  identity`, `User-Agent: Kaskad-speedtest`, буфер `recv_into(bytearray(256 КБ))`.
- Метрики: `ttfb`, `tls`, скорость = байты после 1 с разгона / время окна; остановка по `max_mb` или `max_s` с RST.
  Время подключения через SOCKS не меряем (xray отвечает «успех» заранее).
- Расписание: `every_h` ± 20 %; «только когда тихо» (трафик выхода за 60 с < 1 Мбит/с); не было тишины 2 интервала —
  тест всё равно, вдвое меньшим объёмом; не больше одного теста на узле (`flock /run/kaskad/speedtest.lock`,
  `LOCK_NB` — пропустить); выходы разнесены ≥ 60 с.
- Ручной запуск («Проверить скорость сейчас») — тот же lock и бюджет; сверх суточного лимита — с явным подтверждением.

### 5.4 Своя ссылка (SSRF-защита) и проверка сервиса
Сервисы — список группы (`checks.services`).
Одна функция `probe/fetch.py: safe_get(url, via, limits)` для теста скорости, проверки сервиса и «Проверить ссылку»:
1. Только `https://`, без `user:pass@`, порт 443 или явный, кроме 25, 53 и портов узла (`internal_ports()`).
2. Имя резолвится **через тот же выход** DoH к `https://1.1.1.1/dns-query` (AWG — сокет с меткой; xray — через
   `probe-<id>` к IP 1.1.1.1). Отказ, если хоть один адрес: `not ipaddress.ip_address(a).is_global`, или в
   `0.0.0.0/8`, `100.64.0.0/10`, `198.18.0.0/15`, `224.0.0.0/4`, `240.0.0.0/4`, адресах узла и `gw_nets`.
3. Подключение — к **проверенному IP** (xray: SOCKS ATYP=IPv4), SNI и `Host` = имя (защита от DNS rebinding, З1).
4. Редиректы ≤ 3, каждый проходит 1–3 заново; https → http — отказ.
5. Лимиты: байты (`max_mb`, потолок 50 МБ), время (`max_s`, потолок 30 с), подключение 5 с, TTFB 10 с, заголовки ≤ 16 КБ.
6. В журнал, панель и `probe-results.json` пишется только `хост/путь`, без query и фрагмента.
7. «Проверить ссылку» — 1 МБ через первый годный выход; не чаще раза в 30 с на сессию и 20 раз в час на узел.

Проверка сервиса: `safe_get` с `max_mb = 0,25`, ожидаемые коды `expect`, время ≤ `max_ms`; раз в `every_min` ± 20 %.
Готовые: YouTube и Google `generate_204` (204), Cloudflare `cp.cloudflare.com/generate_204` (204); Telegram
`api.telegram.org` — коды проверить на стенде.

### 5.5 Страна IP выхода
Ожидаемая страна — `checks.geo.expect` группы, иначе первая увиденная (`exit_pref.country`). Действие по умолчанию —
только пуш (§4.3). Оговорка «`loc` выхода = `loc` узла» для российской группы — T15 (SPEC-groups §6.2).
`GET https://www.cloudflare.com/cdn-cgi/trace` через выход → `ip`, `loc`. Раз в `geo.every_h` (24 ч) ± 20 % и после
каждого возврата из `off(dead)`; при первой смене — внеочередной проход по всем выходам и прямая проверка узла, затем
подтверждение через 5 мин (§4.3 «Страна»). `geo.enabled = false` — проверки нет совсем (ни плановой, ни
внеочередной), запросов к `cloudflare.com` через выходы нет; условие `country_changed` тогда «неизвестно».

### 5.6 Трафик и квоты
- Квоты — у выхода любой группы, включая российский (счётчики `gr-<id>`, T15).
- Счётчики: `kawgN` (`/sys/class/net/kawgN/statistics`, уже читает `live.iface_bytes`) и статистика xray по `gx-<id>`
  (`outbound>>>gx-<id>>>>traffic>>>uplink|downlink`). Для этого в конфиг xray — `policy.system.statsOutboundUplink/
  Downlink = true` и `stats {}` **всегда** (сейчас — только при VLESS-входе: `stats_wanted`, `xray.py:232`, `:414-417`).
  **`statsInboundUplink/Downlink` не включать:** с ними пропадают счётчики пользователей и `email` у входа Hysteria2
  (T0, С0.13).
- Правило дельт (§3.5). Счётчики периода — `traffic.json` (§3.5), день — по поясу узла; месяц — от `reset_day`.
- Пробы считаются в квоту; отдельно ведётся `probe` (байты проб, оценка по длинам ответов) — для замера цены.
- **Выход, снятый по квоте, не проверяется до дня сброса** (D-035) (О8 — решение координатора, владелец может поменять;
  находка С2). Иначе observatory тратила бы трафик исчерпанной квоты: ≈ 105 МБ/сутки у VLESS при 10 с (замер T0,
  §6). Правило:
  - только при `quota.action = remove` («снят»). При `standby` и `push` выход остаётся в работе или в запасе — пробы
    идут как обычно (иначе запасной выход нельзя было бы взять);
  - на 100 %: горячий `rmo gx-<id>` (и `gr-<id>`), `rmi`/`rmrules` его `tproxy-<id>` и `probe-<id>` (§2.7; С0.8
    пройдена). Пока исходящего нет, трафик на эти входы закрывается (fail-closed: несуществующий тег закрывает
    соединения, T0); собственные пробы AWG и российских выходов — на паузе; нога `kawgN` остаётся (её снимает только
    пересборка пула);
  - такой выход не участвует в правиле «упал» (причина `dead` не ставится) и в «все не ответили» (§4.6) — сборщик не
    считает его мёртвым и не решает, что у узла пропала сеть;
  - тест скорости, проверка сервисов и проверка страны для него не запускаются (§5.7);
  - **возврат** — в день сброса (`reset_day` по поясу узла), при смене квоты (лимит выше набранного, другое действие)
    или её снятии, по ручному «Вернуть» в карточке (`POST /api/gw/exits/<id>/manual` `restore`, `kaskadctl gw exit <id>
    --restore`): `ado`/`adi`/`adrules -append`, состояние `unknown` до первого замера (§4.2), затем обычная машина;
  - счётчики `gx-<id>` после `rmo`/`ado` начинаются с нуля — правило дельт (§3.5) это учитывает (`cur < last` →
    `d = cur`);
  - карточка выхода: «Квота исчерпана — проверки остановлены до <дата сброса>» (RU/EN);
  - открытые соединения через xray после `rmo`, скорее всего, закрываются (как при несуществующем теге) — проверить в
    S9 и по итогу поправить первую честную строку ниже.
- 80 % (`warn_pct`) — пуш один раз за период; 100 % — `action` (по умолчанию «снят») (D-011). «Уже пушили» хранится в
  `traffic.json` (`warned`, §3.5) — перезапуск сборщика повторного пуша не даёт.
- **Честные строки в карточке квоты** (RU и EN):
  - «Открытые соединения через xray после снятия не обрываются: длинная загрузка докачается и потратит трафик» —
    путь xray при «снят» соединения не рвёт (§2.2, §2.4); путь ядра (WG/AWG, L2TP и др.) при «снят» их сбрасывает (§2.3);
  - «Kaskad считает полезную нагрузку; хостер считает с накладными расходами — обычно на 5–10 % больше. Ставьте
    лимит с запасом».
- Перезапуска xray для квоты нет — **решено 14.10** (D-022) (план §9 «Решено 14.10 (вечер)»: решение координатора, владелец
  может поменять; О9 в §12.1).

### 5.7 Юнит проб
- Читает `groups[].checks` (сервисы, страна, скорость — по группе выхода) и `exit_pref.speed_skip`.
- **Пропускает** выход, снятый по квоте с `quota.action = remove` (§5.6): ни скорости, ни сервисов, ни страны до
  возврата. Внеочередной проход страны (§4.3) такие выходы тоже не трогает.
- `kaskad-gw-probe.service` (`Type=oneshot`, `Nice=10`, `IOSchedulingClass=idle`, `MemoryMax=96M`,
  `TimeoutStartSec=120`, **без `CPUQuota`** — поправка З7) + `kaskad-gw-probe.timer` (`OnBootSec=2min`,
  `OnUnitActiveSec=60`, `RandomizedDelaySec=10`). Без `OnBootSec` таймер с одним `OnUnitActiveSec` после перезагрузки не
  сработает, пока службу ни разу не запускали; в проекте так и принято (`units.py:91-92`). Ручной запуск:
  `systemctl start kaskad-gw-probe@<exit id>.service` (шаблон, тот же код).
- **Снятие юнитов** (владелец — T6): `kaskad-gw-probe.timer`, `kaskad-gw-probe.service`, `kaskad-gw-probe@.service`
  останавливаются и удаляются при `gw disable` (`gw/ops.py:420`, рядом с остановкой сборщика `:397`), `gw purge` и
  при удалении Kaskad (`remove` в `install.sh`: если он снимает юниты шлюза через `kaskadctl gw purge` — правки bash
  не нужно; если списком — одна строка в этом списке, сверить `git grep -n kaskad-gw-collect install.sh`). Тест: после
  `disable` `systemctl list-unit-files 'kaskad-gw-probe*'` пуст.
- Сам решает по расписанию и бюджетам, что пора (скорость, сервисы, страна); политику, снимок `exits.json`
  (состояния) и `traffic.json` (тишина выхода) только читает.
- Пишет `/var/lib/kaskad/gw/probe-results.json` атомарно: `{"seq", "results": [{"exit", "kind": "speed|svc|geo",
  "ts", …}]}`; сборщик забирает новые `seq` в базу и в `Obs`.
- Бюджеты: суточный и месячный на выход (§3.2); остаток считается по `speed.bytes`; не влезает — тест не запускается,
  событие `speedtest_budget` (раз за период). Прогноз «≈ N ГБ/мес» в форме группы = `max_mb × 24/every_h × 30 × число выходов группы без speed_skip`.

## 6. Пресеты

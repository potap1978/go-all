### 3.6 События — `live.json`

  покажет иначе, хвост старше 24 ч держать только в `metrics.db.events`, а в `live.json` — 100 последних.

- Новые ключи и аргументы:

| `key` | `args` | Когда |
|---|---|---|
| `exit_degraded` | `id, name, rule, metric, value, threshold` | переход в «ухудшен» |
| `exit_recovered` | `id, name, from, after_s` | возврат в «годен» из «ухудшен»/«в запас»/«снят» (кроме «мёртв» — там `exit_alive`) |
| `exit_standby` | `id, name, why` (`rule:<id>`, `manual`, `sub_confirm` или `unstable`; при `sub_confirm` ещё `sub`, `sub_name`; при `unstable` — `flaps`, `until`) | переход в «в запас»; `unstable` — нестабильный выход на 15 мин (§4.3, правка 5, З2); `sub_confirm` — новый ключ подписки встал в российскую группу и ждёт подтверждения (§3.8, Н4), выпускается и для нового выхода (из `unknown`) |

| `exit_rule_push` | `id, name, rule, metric, value, threshold` | сработало правило `then=push` — выход годен, состояние не меняется (не путать с «ухудшен») |
| `exit_quota` | `id, name, used_gb, limit_gb, pct, reset` (дата) | 80 % (`warn_pct`) и 100 % |
| `exit_country_changed` | `id, name, old, new, all_exits` | подтверждённая смена: по умолчанию **только пуш**, трафик идёт как есть (решено 14.10, ночь) (D-024); `all_exits=true` — подозрение на сбой замера |
| `group_last_step` | `group, name, role, step` (`direct`/`block`), `devices` | в группе не осталось пригодных выходов: «нет выхода в интернет у N устройств» или «… идут с сервера напрямую» (§4.4, SPEC-groups §10) |
| `group_restored` | `group, name, exit, after_s` | группа вышла с последнего шага |
| `xray_rejected` | `error` (первая строка, без секретов) | `xray -test` отверг конфиг сборщика (§2.7); только лента панели и журнал, пуша нет |
| `xray_ru_open` | `n` (число путей) | B7: после отказа нового конфига xray не удалось остановить (disable, stop, kill; «остановлен» — только inactive/failed), а прежний пускает Россию напрямую тем, кому это уже не разрешено; повтор при смене числа, без часового подавления; пуш всегда (переключателя нет) |
| `xray_ru_closed` | `n`, `why` | B7: закрыто — сборщик остановил xray (`stopped`), метка открытого ушла (`restarted`: xray перезапущен с текущими настройками, остановлен вручную, перезагрузка) или вернули выбор либо согласие ⚠РФ (`allowed`: xray не трогали; следующее открытие снова даёт `xray_ru_open`); пуш всегда |
| `node_offline` | `since` | узел без сети (§4.6) |
| `node_online` | `since, until, minutes`, `restart` | сеть вернулась — сводка «сервер был без связи с 12:03 до 12:10». `restart: true` — сборщик Kaskad перезапустили во время пропажи и он застал сеть: `until` — его последний такт до перезапуска, связь вернулась тогда или позже («связь проверили после перезапуска сборщика Kaskad», REV-s1-t4 З1). Открытая пропажа берётся из live.json один раз на процесс; закрытая (`node_online` уже был) после перезапуска событий не даёт |
| `speedtest_budget` | `id, name, period` (`day`/`month`) | лимит тестов исчерпан (раз за период) |

- `exit_dead` / `exit_alive` — **как в 3.3.5** (решение координатора 15.10, Р1; BACKLOG-3.3.5 п. 3) (D-058): правило «упал»
  (§3.2), в журнале причина (`delay` и `last_error_reason` observatory, до 200 знаков). Выпускает их **тот же слой,
  что в 3.3.5** (`gw/live.py`, по смене состояния выхода). Этап 1 меняет только источник: смена `state` из `health`
  (§4.2–4.3) вместо `alive` из `exits.merge`. Второго места выпуска нет. `exit_alive` приходит, когда выход реально
  снова годен (2 удачи подряд и пауза §4.3).
- **Антиспам — как в коде 3.3.5** (D-067, D-088, D-094) (решение координатора 15.10, правка 5, С1; `dev-335` `8433a5f`: `gw/live.py`
  `_exit_event`/`_publish`/`_window_end`, около `:575–641`; тест `tests/test_335_flap.py`, `EventsQuietTest`). Одно
  правило для ленты панели и бота:
  - **окно — по виду события.** Повтор того же вида по выходу, если этот вид публиковался меньше 15 мин назад
    (`EVENT_QUIET`, словарь `told[(выход, вид)]`), глушится и считается. **Первое событие другого вида уходит
    сразу**: «упал 12:00 → ожил 12:01» — оба сразу;
  - **конец окна** — 15 мин от последнего опубликованного события выхода (`window[выход]`), если были заглушенные.
    Текущее состояние не совпадает с последним опубликованным (`said[выход]`) — публикуется **текущее** со
    счётчиком падений окна («не работает (обрывов за 15 мин: 3)»); совпадает — ничего, счётчики обнуляются, окно
    заново. Последнее опубликованное верно не позже чем через 15 мин;
  - **сводка «нестабилен»** (этап 1, только при `gateway.notify.flap_summary = true`, §8.2): в конце окна, если у
    выхода ≥ 3 падений за последние 15 мин — **по `falls` из `health`, тот же счёт, что у пометки §4.3** (правка 6,
    З1-5), — публикуется «нестабилен» и тогда, когда состояние совпадает с опубликованным. **Не публикуется**, если
    выход ушёл «в запас» как нестабильный: одно сообщение — `exit_standby` (`unstable`), правка 6, С1-5. Счётчик
    «обрывов за 15 мин» в тексте 3.3.5 остаётся по `drops`;
  - **ручные действия владельца** («В запас», «Вернуть», «Обслуживание», «Принять новую страну», вкл/выкл,
    подтверждение `sub_confirm`; `why = manual`) антиспам не придерживает: публикуются сразу, мимо проверки повтора, и
    записываются в `told`/`said`/`window`, как любая публикация (правка 6). Как всякая публикация (`_publish` 3.3.5),
    ручная очищает заглушённое этого выхода — ожидаемая сводка «нестабилен» в конце окна тогда не выходит: так и
    задумано, ручное действие — последнее слово владельца (правка 8) (D-067);
  - после перезапуска сборщика первое событие — сразу (окна живут только в памяти, как в 3.3.5);
  - **часы окна — монотонные** (решение координатора 15.10, правка 6) (D-067): длительности окна и повтора считаются по
    `live._mono` (`time.monotonic`), время события в ленте (`ts`) — по `live._now` (`time.time`), как в 3.3.5.
    Скачок системных часов окна не сдвигает ни в одну сторону (П-7-5 снимается). В 3.3.5 окно считалось по `_now`:
    T4 добавляет `_mono`, тесты 3.3.5 подменяют и его (одна строка в `setUp`, §11.1);
  - этап 1 распространяет то же правило на новые виды состояния выхода — `exit_degraded`, `exit_recovered`,
    `exit_standby`, `exit_removed` — с теми же словарями и ключом `(выход, вид)`. В конце окна состояние сравнивается
    по смыслу вида (мёртв — `exit_dead`; годен — `exit_alive`/`exit_recovered`; ухудшен, в запасе, снят — свои) и
    публикуется вид текущего состояния: «годен» — `exit_alive`, если последним опубликовано «мёртв», иначе
    `exit_recovered`. `group_last_step`/`group_restored` — то же правило с ключом `(группа, вид)`: `group_restored`
    после `group_last_step` уходит сразу. «Вернуть» после `exit_standby` (`sub_confirm`) — `exit_recovered` сразу.
    Тот же слой `gw/live.py`, без второй склейки;
  - события в `live.json` (лента) — это опубликованные события, после антиспама. Бот отправляет те же события;
    переключатели `gateway.notify.push` (§8.1) гасят только отправку в бот, в ленте событие остаётся;
  - **состояние выхода** в панели, `gw exits`, `kaskadctl`, MCP — из `health`, всегда честное и без задержки,
    антиспам его не касается; метки «отвечает снова» и «нестабилен» — из полей снимка (`recovering`, `unstable`,
    §7.9), а не из событий;
  - **полная история переходов** — в карточке выхода (§7.3): каждая смена состояния пишется в `metrics.db.events`
    (§3.5) до антиспама строкой `key = "transition"` (`args`: `from`, `to`, `why`); опубликованные события — там же
    своими ключами. Лента после перезагрузки подгружает только опубликованные, карточка выхода — переходы
    (`GET /api/gw/exits/<id>/transitions`, §7.9).
- Время в тексте — по поясу узла (§3.7).
- Все события выходов получают аргументы `group`, `group_name`, `role` (тексты для `role = ru` — T15,
  SPEC-groups §10). Ключи `node_ru_offline`/`node_ru_online` — T15.

### 3.7 Часовой пояс узла
- Хранится в `/etc/kaskad/config` рядом с `KASKAD_LANG` ключом `KASKAD_TZ` (запись по образцу
  `i18n.set_lang`, `i18n/__init__.py:135`; bash — `save_config_val`), значение — имя IANA (`Europe/Moscow` по
  умолчанию) (D-009). **Системный пояс ОС не меняем**: на сервере могут жить другие продукты и журналы. `KASKAD_TZ`
  попадает в резервную копию (часть `gateway`, §3.5).
- **`zoneinfo` нельзя** (код обязан работать на Python 3.8, `tools/k3_py_compat.py` запрещает). Новый модуль
  `kaskad/tz.py`: разбор TZif из `/usr/share/zoneinfo/<имя>` (v2+, 64-битные переходы) **и строки POSIX-TZ хвоста**
  после последнего перехода. Хвост обязателен: файлы, собранные `zic -b slim`, после последней смены правил переходов
  не содержат (например, `Europe/Berlin`: летнее время после 1996 г. — только в хвосте), и «последнее смещение»
  ошибалось бы на час полгода. Разбираются формы `std offset [dst [offset] [,start[/time],end[/time]]]` с правилами
  `Mm.w.d`, `Jn`, `n` и временем перехода со знаком (до ±167 ч, RFC 8536 §3.3.1). Толстые ли tzdata в Debian 12/13 и
  Ubuntu 24.04 — не подтверждено, поэтому хвост разбирается всегда. API: `name()`, `offset(ts)`, `local(ts) -> struct_time`, `day(ts) -> 'YYYY-MM-DD'`,
  `next_at('04:00', now)`. Имя проверяется по `^[A-Za-z_+-]+(/[A-Za-z0-9_+-]+){0,2}$` и наличию файла. Нет файла
  или ошибка разбора → фиксированный `UTC+03:00` и предупреждение в «Настройки → Время».
- Пользователи: день сброса квоты, «трафик за день», ночная перебалансировка, время в пушах и на графиках; позже —
  расписания сценариев.
- Видно в настройках: текущее время сервера в поясе Kaskad, пояс ОС, синхронизация часов
  (`timedatectl show -p NTPSynchronized --value`, нет `timedatectl` → «неизвестно»).
- **Часы не синхронизированы** (REV-s1-t4 З3): счётчики в `traffic.json` не пишутся (квоты не считаются). Строка
  журнала `gw_collect.log.clock_unsynced` — сразу и раз в сутки, `clock_synced` — когда синхронизировались. Через час
  без синхронизации, если у выхода пула есть квота, — проблема шлюза `gw_clock` в live.json (панель, бот, меню
  `summary`): в тексте проблемы — «включите службу времени: `timedatectl set-ntp true` (chrony или
  systemd-timesyncd)», совет — только «квоты снова начнут считаться сами» (без повтора), пункта меню нет (`item` 0:
  часы чинит служба времени, не Kaskad); сторож часы не чинит (REV-s1-b2 З2, REV-s1-b4 П-2).
- Смена пояса не трогает уже записанные `ts` (UTC); меняется только разбиение `traffic.day` с ближайшей полуночи.

### 3.8 Смена `#имени` ключа в подписке — сделано в 3.3.5 (id сохраняется), что добавляет этап 1
**Предпосылка — 3.3.5, способ (а): id выхода сохраняется** (решение координатора 15.10; правка 2, находка С1) (D-065). Код —
ветка `dev-335`, коммит `8dba0b0` «смена имени ключа в подписке не меняет id выхода»; сверено 15.10 через
`git show dev-335:<файл>`. Исполнитель 3.3.5 ещё работает, поэтому ниже — имена функций и смысл, номера строк —
«около». Этап 1 этот механизм **не повторяет** и второго рядом не пишет. Переноса «старый id → новый» в этапе 1 **нет**:
ни файла переноса, ни пути к нему в `paths.py`, ни номера переноса в `pins.json`, ни приёма переноса сборщиком, ни
своей соли и HMAC для удалённых ключей. Если код 3.3.5 к слиянию разойдётся с контрактом ниже — вопрос координатору.

**Контракт 3.3.5, на который опирается этап 1:**
1. **Кто ключ** — `exits.identity(line)` (около `exits.py:369` в `dev-335`), а не текст строки:
   - VLESS — `peer_key`: `vless|<uuid>|<host:port>`;
   - AmneziaWG — `peer_key` (`awg|<открытый ключ сервера>|<endpoint>`) **плюс** `sha1` своего приватного ключа: два
     клиента одного сервера — два выхода;
   - остальные строки — `exit_id(line)`: тот же ключ — только тот же текст.

   `exits.identity_hash(line)` — 16 hex от `identity` (около `:388`).
2. **Тот же выход.** `exitsubs.plan` (около `exitsubs.py:557-680`): свой ключ подписки пришёл другой строкой с тем же
   `identity_hash` (другое `#имя` или параметры) — это тот же выход. Новая строка встаёт **на место старой** в пуле,
   id выхода сохраняется (`renamed` в итоге `plan`). Два кандидата на одно место — не сопоставляются. Другой uuid,
   пароль или сервер — новый выход.
3. **Карта id** — `subs.json → "ids"`: `{id текста строки: id выхода}`.
   - `exits.pool_id(line)` (около `exits.py:323`) = запись карты, иначе `exit_id(line)`; карту читает `kept_ids()`.
   - Записи `exits.pool()`, `line_ids()`, `preview()`, `pool_fallback()` несут `pool_id`.
   - Карта пишется **до** замены пула (`exitsubs._apply`) и уходит в копию `.kbk` (`backup.py`).
   - install.sh знает строку только по тексту: `ops.exit_del` передаёт `--egress-del` id текста; `fold_pending`
     переводит id текста из `subs-excluded.pending` в id выхода через карту.
4. **Чистка карты** — `exitsubs.prune_ids(doc, ids, lines)` (около `exitsubs.py:712-721`): запись живёт, пока её
   строка есть в `lines` или её выход ещё числится ключом подписки.
5. **Удалённый вручную не возвращается под другим именем:** `subs[].idents` (`{id: identity_hash}`) и
   `subs[].excluded_idents` (`_exclude`, `plan`).
6. `PARSER_VERSION` в 3.3.5 остаётся **18**, heredoc разборщика не менялся (§9.2).

**Что из этого следует для этапа 1:**
- **id выхода — только `e["id"]` записей `exits.pool()` или `exits.pool_id(line)`.** `exits.exit_id(line)` — id
  текста: он нужен только для вызова install.sh и для карты. Ни один читатель этапа 1 в Python не считает id выхода
  из строки сам.
- Все хранилища этапа 1 ведутся по id выхода, поэтому переносить нечего:
  - политика и `exit_pref`;
  - `pins.json`, `traffic.json`, `metrics.db`;
  - снимок `exits.json`.
- Теги `gx-`/`gr-`/`tproxy-`/`probe-` прежние: xray не перезапускается, обрывов нет, сборщику нечего «принимать».
- Маршруты `exit:<id>`, подпись и `enabled` сохраняются тем, что id не меняется (О10) (D-023).

**Что добавляет этап 1:**
- **`peer_key` новых схем — в самом `exits.peer_key`, на stdlib, без разборщика** (находка З2). 3.3.5 зовёт
  `peer_key`, `identity` и `identity_hash` в `exitsubs.plan` **без** `parser`. Если считать новые схемы только через
  разборщик, смена `#имени` у них молча давала бы новый выход. Поэтому — как `vless_peer` (`urllib.parse`,
  `base64`, `json`):
  - `hy2|<auth>|<host:port>` (`hy2://`, `hysteria2://`; `auth` — userinfo; у диапазона портов — первый порт);
  - `ss|<method>:<password>|<host:port>` (SIP002 `ss://base64(method:password)@host:port`, SIP002 без base64 у
    2022-методов и старый вид `ss://base64(method:password@host:port)` дают одно и то же; оба алфавита base64, без
    `=`);
  - `trojan|<password>|<host:port>`;
  - `vmess|<id>|<host:port>` (`vmess://` + base64 JSON: поля `id`, `add`, `port`; поле `ps` — имя — в ключ не входит).

  Как у `vless_peer`: хост в нижнем регистре, IPv6 в скобках, порт по умолчанию 443; фрагмент `#…` и параметры
  (`sni`, `obfs`, `fp`, `alpn`) в ключ не входят. Не разобралось → `exit_id(line)`, как сейчас. `identity` новых
  схем = их `peer_key` (своего приватного ключа, как у AWG, у них нет). Так смена `#имени` даёт тот же выход через
  механизм 3.3.5 без правки `plan`. `peer_key` в heredoc разборщика и его подкоманда `peers`
  расширяются на эти схемы и дают **ту же строку** для bash (решение координатора 15.10, Р3; §9.2) (D-062).
  Владелец — T11.
- **Карта id — по обоим файлам ключей** (находка С2). У российских групп свой файл `upstream-ru.txt` (SPEC-groups
  §2.2). Смена роли выхода переносит строку между `upstream.txt` и `upstream-ru.txt` как есть, текст не меняется.
  Но `prune_ids` 3.3.5 видит только строки `upstream.txt`: запись карты выхода, перенесённого в `upstream-ru.txt`,
  выпала бы при следующем обновлении любой подписки. Тогда id стал бы `sha1` текста, и политика, закрепления, маршруты
  `exit:<id>`, квота и подпись потеряли бы выход. Поэтому:
  - карта `ids` одна на узел (`subs.json`), `exits.pool_id` применяется к строкам **обоих** файлов (`exits.pool(roles=…)`,
    `line_ids`, `pool_fallback`, `preview`);
  - во всех вызовах `prune_ids` из `exitsubs._apply` в `lines` входят и строки **другого** файла (подписка роли
    `abroad` — плюс строки `upstream-ru.txt`, подписка роли `ru` — плюс строки `upstream.txt`);
  - смена роли (SPEC-groups §2.2) запись карты не трогает: текст тот же → `exit_id` тот же → id выхода тот же. Перенос
    проверяет, что `exits.pool_id` строки до и после одинаков; иначе — откат переноса и ошибка, а не тихая смена id;
  - удаление вручную из `upstream-ru.txt` пишет id текста в тот же `subs-excluded.pending`, что `egress_pool_drop` для
    `upstream.txt`.

  Владелец — Q4 (T15): места вызова `prune_ids` в `exitsubs._apply`, смена роли (вместе с T7), чтение российского
  файла.
- **Свой ключ подписки — там, где лежит** (решение координатора 15.10, Р2) (D-061). Новые ключи подписка пишет в свой файл
  (`subs[].group`, SPEC-groups §2.9). Свои ключи (`subs[].idents`) `exitsubs.plan` ищет по `identity_hash` в **обоих**
  файлах: ключ, перенесённый сменой роли в другой файл, считается уже размещённым — в файл подписки не дописывается,
  а обновляется **на месте** в том файле, где лежит (новая строка — на место старой, id сохраняется, как в 3.3.5).
  Ключ ушёл из подписки — строка снимается из того файла, где лежит. Строка подписки, чьи `exit_id` или `identity`
  уже есть в другом файле не как её ключ (добавлен вручную), — в `dups` итога: не дописывается, и не молча. Сама
  строка между `upstream.txt` и `upstream-ru.txt` не перескакивает — переносит только смена роли. Это правка
  `plan`/`_apply` поверх 3.3.5, владелец — Q4.
- **Новые ключи подписки, чьи ключи стоят в российской группе** (решение координатора 15.10, вечер; Н4) (D-068). Подписка
  зарубежной группы, хотя бы один свой ключ которой (`subs[].idents`) лежит в `upstream-ru.txt` (перенесён сменой
  роли). Её новый ключ — не `renamed` и не найденный в обоих файлах, в том числе ключ, который провайдер выдал взамен
  ушедшего с другим uuid или паролем (другая `identity`), — пишется **туда же**: в `upstream-ru.txt`, в ту российскую
  группу (`exit_pref.group`), где стоит больше её ключей (поровну — первая по порядку групп), и сразу **«в запас»**: `exit_pref.manual =
  standby`, `manual_why = sub_confirm` (`set_exit`, T2). В зарубежный пул молча не попадает. Событие `exit_standby` с `why =
  sub_confirm` (§3.6) и строка итога обновления подписки, RU+EN: «Подписка «…»: новый ключ «…» поставлен в запас в
  группе «Дом» — подтвердите в карточке выхода» (EN: «Subscription «…»: new key «…» was put on standby in group
  «Home» — confirm it on the exit card»). Подтверждение — «Вернуть» в карточке (снимает `manual` и `manual_why`);
  «Перенести в группу…» `manual`/`manual_why` **не снимает** — выход остаётся «в запасе» в новой группе до «Вернуть».
  Все новые ключи такой подписки идут в российскую группу, даже если там лишь один её ключ из многих (решение
  координатора; вред мал — каждый ждёт подтверждения, П-9 правки 5). Остальные ключи подписки (ни один не в российской группе) — как раньше, в файл подписки.
  Владелец — Q4.
- Для российского файла номер `N = 200 + позиция`. Новая строка встаёт на место старой (как в 3.3.5), поэтому метки
  `256+N`/`0x300+N` других выходов не меняются. Сброс соединений по сменившимся меткам (`_forget_renumbered`,
  `exits.renumbered`/`line_marks`) считается по каждому файлу отдельно (Q4).
- **`dup_endpoint`** для Hysteria2 не считает дублем строку, которую новая заменяет в `plan` 3.3.5 (`renamed`), §9.1.
- **Отпечатки TOFU** (`tofu-pins.json` 3.3.4, §9.1) хранятся по серверу `host:port|sni` — переносить нечего.
- **Хеши в файлах — как в 3.3.5** (П6). `subs[].idents` и `excluded_idents` — несолёный `sha1(identity)[:16]` в
  `subs.json` и в `.kbk`. Для новых схем туда попадут хеши строк вида `trojan|<пароль>|host:port`. Сами ключи и так
  лежат открыто в `upstream.txt`/`upstream-ru.txt` (`0600`) и в той же копии, поэтому новой утечки нет. Сам
  `peer_key`/`identity` в файлы и журнал не пишется — только хеш. Второй схемы (соль, HMAC) не делать.
- **Сделано в 3.3.5 — не повторять:** новая строка на месте старой; удалённый вручную ключ не возвращается под другим
  именем (`excluded_idents`); карта пишется до замены пула; итог `renamed` в отчёте обновления.

**Тесты этапа 1** (`tests/gw/test_s1_idcarry.py`, `tests/test_gw_exitsubs.py`; базовые тесты механизма — у 3.3.5,
`tests/test_335_rename.py`):
- **по тесту на каждый протокол** — `hy2`/`hysteria2`, `ss` (SIP002 ↔ старый вид, и смена `#имени`), `trojan`,
  `vmess` (смена `ps`): `plan` без `parser` даёт `renamed`, id выхода прежний, строка на прежнем месте; другой
  пароль, uuid или сервер — новый выход;
- `exits.peer_key` (stdlib) совпадает с `peer_key` разборщика (и выводом `peers`) на фикстурах всех схем; bash
  `egress_add_key`: второй ключ `hy2`/`ss`/`trojan`/`vmess` на тот же сервер — повтор узнан (Р3);
- тест-страж: у выхода есть политика (группа, уровень, вес, правило), закрепление, квота с паузой, ручное «в запас»,
  маршрут `exit:<id>` и подпись. После смены `#имени` ни одно хранилище этапа 1 не изменилось, xray не
  перезапускался, `exit_failover` нет;
- **смена роли с сохранённым id** (С2): выход с записью в карте `ids` переносится в российскую группу (строка — в
  `upstream-ru.txt`), затем обновляется любая подписка → id прежний, запись карты на месте; то же в обратную сторону;
- **ключ подписки в другом файле** (Р2): ключ подписки «Основной» перенесён в российскую группу → обновление этой
  подписки → ключ ровно в одном файле (`upstream-ru.txt`), в `upstream.txt` его нет, id прежний; провайдер сменил
  `#имя` перенесённого ключа → строка обновлена в `upstream-ru.txt`, id прежний; ключ ушёл из подписки → строка
  снята из `upstream-ru.txt`; ручной ключ того же сервера в другом файле → `dups` итога, строка не дописана;
- **новый ключ подписки с ключами в российской группе** (Н4): ключ подписки «Основной» перенесён в группу «Дом» →
  провайдер сменил у него uuid (другая `identity`) → обновление: старая строка снята из `upstream-ru.txt`, новая
  встала в `upstream-ru.txt` в «Дом» «в запас» (`why = sub_confirm`), в `upstream.txt` её нет, устройства «Основной»
  её не получили; событие `exit_standby` (`sub_confirm`) одно, строка итога RU и EN; «Вернуть» — выход годен в
  «Дом»; подписка без ключей в российской группе — новые ключи в `upstream.txt`, как раньше;
- российский файл: пара только внутри него, метки зарубежных выходов не сменились;
- `peer_key`/`identity` новых схем не попадают в файлы и журнал (в `subs.json` — только 16 hex).

**Владельцы:** T11 — `peer_key` новых схем в `exits.py` и в разборщике (`peer_key`/`peers`, Р3), сверка Python ↔
разборщик, тесты на протокол; Q4 (T15) — карта id по обоим файлам, `prune_ids`, смена роли, `plan` по обоим файлам
(Р2). T3 и T4 по §3.8 ничего не делают.

На этот раздел ссылаются `SPEC-stage1-rename.md` §3.3 (N3) и SPEC-groups §2.2, §2.9.

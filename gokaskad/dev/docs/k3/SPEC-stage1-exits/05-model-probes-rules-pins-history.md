### 3.2 Пробы — `exit_policy.probes` (общее) и `groups[].checks` (у группы)
`probes` — **общее на узел**: пауза «снят», окно замеров потерь, пределы и бюджет теста скорости. Всё, что различается по
группам, — в `groups[].checks` (§3.1): **частота проверок**, цели проб, тест скорости (включение, частота, ссылка),
сервисы, страна. Интервал observatory **не хранится** — он выводится из частоты групп (ниже).
```jsonc
"probes": {
  // правила «упал» здесь нет: оно одно на узел и у всех пресетов — константы 3.3.5 (ниже, Р1);
  // die_after/live_after прежних редакций не пишутся, при чтении не действуют
  "off_backoff": {"base_s": 30, "max_s": 600, "reset_after_s": 3600},
  "window": 10,                    // замеров в окне потерь и джиттера
  "speed": {"max_mb": 10, "max_s": 8,            // пределы одного теста — общие на узел
            "only_quiet": true,
            "budget_day_mb": 200, "budget_month_gb": 3}   // бюджет — общий на узел; своя форма и ver (§7.1, §7.9)
}
// groups[].checks:
"checks": {
  "targets": "abroad",             // abroad — цели §5.1; ru — российские цели (T15)
  "freq": {"mode": "often",        // lazy | often | normal | rare | custom — ниже
           "every_s": null},       // только custom: 10–600 с
  "speed": {"enabled": false,      // тест скорости выходов группы (О3, решено 15.10: выкл. по умолчанию) (D-034)
            "every_h": 6,          // 1 | 3 | 6 | 12 | 24, ± 20 %
            "url": "default"},     // default (Cloudflare __down) | https://… (своя ссылка, §5.4)
  "services": [                    // пусто по умолчанию; id уникальны внутри группы
    {"id": "yt", "name": "YouTube", "url": "https://www.youtube.com/generate_204",
     "expect": [204], "max_ms": 3000, "every_min": 30}],
  "geo": {"enabled": true,         // false — страна не проверяется, запросов к cloudflare.com через выходы нет (план F)
          "every_h": 24, "confirm": 2,
          "action": "push",        // только push в этапе 1 (решение владельца 14.10, ночь; П5) (D-024); реакция — условие «Страна не та» (§3.3)
          "expect": null}          // null — первая увиденная (exit_pref.country); у российской группы — "RU"
}
```
Ограничения: `max_mb` ≤ 50, `max_s` ≤ 30, `every_min` 5–1440, не больше 5 сервисов.

**Частота проверок — у группы** (решено владельцем 15.10; вопрос В9 SPEC-groups закрыт) (D-044). Варианты предложил
координатор. **Умолчания — решение координатора** (D-053) (правка 2, З3; владельцу сообщено, может поменять): «Лениво» — только
у российских групп; у зарубежных — частота пресета (у «Лениво» xray-выходы шли бы под общей observatory раз в 2 мин, а
уход с упавшего выхода занимал бы ≈ 2–4 мин). Выбор радио в карточке группы (в панели — без номеров, цифры — только SSH-меню; правка 5, UX):

| `freq.mode` | Подпись | Базовый период P | По умолчанию у |
|---|---|---|---|
| `lazy` | «Лениво — только при трафике» | при трафике через группу за последние 10 мин — 15 с; в простое годные выходы **не проверяются** | российских групп («Дом», `ru_home`) — решение координатора (З3) (D-053) |
| `often` | «Часто — 10 с» | 10 с | «Как раньше», «Стандарт», «Строго» |
| `normal` | «Обычно — 30 с» | 30 с | «Экономно» |
| `rare` | «Редко — 2 мин» | 120 с | — |
| `custom` | «Свой: [N] с» | `every_s`, 10–600 | — |

Как частота группы действует на разные пробы:
- **Собственные пробы Kaskad — ровно по группе.** Это проба «жив/мёртв» AWG-выходов (TCP через метку), проба
  отклика AWG (HTTP через метку, §5.1) и все пробы выходов российских групп (SPEC-groups §6.1, там же через
  `probe-<id>` для их xray-выходов). «Жив» — раз в P; отклик AWG — раз в `max(3P, 30)` с при трафике через выход за
  60 с и раз в `max(12P, 120)` с без трафика (при P = 10 с это прежние 30 / 120 с).
- **«Лениво»:** активные пробы — только пока через группу был трафик за последние 10 мин (раз в 15 с); пассивный
  признак и «подозрение» — как SPEC-groups §6.1. В простое **годные** выходы не проверяются; выходы **не в «годен»**
  («ухудшен», «в запасе», «снят» не по квоте) проверяются раз в 15 с всегда — иначе они не вернулись бы: устройства с
  них уведены, трафика нет. Карточка выхода пишет «последняя проверка: N мин назад (группа без трафика)».
- **Observatory xray — одна на узел** (T0: одна вместо двух; все зарубежные выходы `gx-`, и AWG, и xray). Интервал
  observatory per-exit задать нельзя, поэтому `policy.observatory_s(doc)` = **самый частый** P среди зарубежных групп,
  в которых есть выходы; «Лениво» для observatory считается как «Редко — 2 мин» (по трафику она не умеет); нет
  зарубежных выходов — observatory нет. Значит, xray-выходы группы, выбравшей реже, всё равно проверяются с общим
  интервалом узла — **экономит выбор реже только собственные пробы Kaskad** (AWG, российские). Карточка такой
  группы пишет честно: «xray-выходы (VLESS и др.) проверяются общей проверкой сервера раз в N с — её задаёт самая
  частая группа («Основная»: часто)». Health xray-выхода берёт все свежие замеры observatory (прореживания нет).
- Смена частоты, которая меняет `observatory_s`, — **перезапуск xray шлюза** (интервал — в конфиге; как смена
  `observatory_s` раньше). Форма сохранения пишет это строкой, известной заранее (панель считает её без запроса, §7), «xray перезапустится: общая проверка станет раз в N с».
- Время ухода с упавшего выхода — по правилу «упал» (ниже): форма рядом с выбором частоты пишет «реакция на отказ
  ≈ …» (решение координатора 15.10, Р6) (D-059).
- Трафик проб на выход в сутки (расчёт от замера T0, §6) — в карточке группы рядом с выбором.
- Выход, снятый по квоте с `quota.action = remove`, не проверяется **никак** до дня сброса (§5.6, О8).

**Правило «упал» — решение владельца 15.10** (D-054) (план «Решено 15.10 (вечер)»; в 3.3.5 — `k3/handoff/BACKLOG-3.3.5.md`
п. 3). Одно для VLESS, AWG, новых схем и российских выходов, у всех пресетов: **пресеты меняют частоту проверок, но
не правило 50 %** (Р1). Окно при редких проверках и у «Лениво» — **решение координатора 15.10** (Р6) (D-059).
- **Проба** — одна разная попытка: AWG — проба «жив» этого раунда; xray — замер observatory с новым
  `last_try_time` (повторное чтение той же пробы не считается, §5.1); российский выход — своя проба по очередной цели (SPEC-groups §6.1); пассивный признак «Лениво» — удачная проба не
  чаще раза в 15 с.
- **Не больше одной пробы за период P** (D-070) (решение координатора 15.10, вечер; Н1; в 3.3.5 — BACKLOG-3.3.5 п. 3). Проба
  учитывается как новая, если с последней учтённой пробы выхода прошло не меньше `P − 2 с` (допуск такта); иначе она
  **заменяет результат** последней учтённой и новой пробы не добавляет. Так работает перепроверка AWG через 5 с после
  провала (`collect.py` 3.3.5: `RECHECK = 5`, при провале — раз в 5 с): ответила — провал последней пробы заменён
  удачей; не ответила — остаётся один провал, а не два. Обрыв короче P оставляет в окне не больше одного провала
  (короче P − 5 с — ни одного). У xray P —
  `observatory_s`, новый `last_try_time` и так не чаще раза в P; у «Лениво» P = 15 с (и пассивный признак, и активная
  проба). P — фактический период выхода сейчас (частота группы, у xray — `observatory_s`), смена частоты действует со
  следующей пробы.
- **Окно** — пробы выхода после последней смены его состояния, моложе 2 мин; если их меньше 4 — последние 4 пробы
  после смены состояния. При частоте реже 30 с окно растягивается до 4 проб: «Редко — 2 мин» → 8 мин, «Свой 600 с» →
  40 мин. «Лениво» — последние 4 пробы, каждая не старше 1 ч; нет трафика — нет проб, состояние годного выхода не
  меняется (негодные проверяются раз в 15 с, выше).
- **«Упал»** решается на неудачной пробе: в окне не меньше 4 проб, и не меньше 50 % из них неудачны.
- **«Снова работает»** — 2 удачные пробы подряд. При каждой смене состояния окно начинается заново — кроме смен между `ok`, `degraded` и `standby`: выход всё это время проверялся, его пробы в силе (Н12, стенд КТ1: после возврата из «в запасе» 15-секундный обрыв давал «упал» за 16 с — 2 неудачи из 4 проб после возврата). Пауза «снят»
  (`off_until`, §4.3) — поверх этого, только в группах с пресетами этапа 1 и не для последнего годного выхода группы
  (Р7). В «Как раньше» (`compat`) паузы нет: 2 удачи подряд — и выход сразу снова работает, как 3.3.5 (§1.3 отличие 3,
  D-134).
- **Молчание xray самого узла** (нет ответа `/debug/vars`, observatory не обновляет замеры) и нога AWG, которая не
  поднимается, — «упал» от начала молчания, без окна (как в 3.3.5). Пропажа сети узла — §4.6: заморозка, а не «упал».
- **Где живёт.** Константы и окно — те же, что в 3.3.5 (рабочее дерево `dev-335`, `gw/exits.py`: `WINDOW = 120`,
  `DEAD_SHARE = 0.5`, `MIN_TRIES = 4`, `RISE = 2`, `CHECK_PERIOD = 10` — «одна проба за период», сравнение `< CHECK_PERIOD`
  без допуска, коммит `116bc6d`; окно — в `/run` (`exits-window.json`), на диск — только
  состояние). После слияния 3.3.5 `health` берёт их оттуда и второго набора не заводит; имена сверить. В политике
  правило не хранится и в формах не настраивается. Нижний предел «4 последние пробы», окно «Лениво» и P группы в
  правиле «одна проба за период» (в 3.3.5 — общий интервал сборщика) — дополнение этапа 1 к 3.3.5: этап 1 заменяет `CHECK_PERIOD` на `P − 2 с` группы (второго набора констант нет); на частоте 10 с
  (умолчание «Как раньше») поведение то же, что в 3.3.5.
- **Реакция на полный отказ** (от начала отказа, с учётом «одна проба за P»; плюс такт сборщика до 10 с):
  - P ≤ 30 с — ≈ 1 мин (окно 2 мин, нужно столько же провалов, сколько удач в нём): «Часто — 10 с», «Обычно — 30 с»,
    «Свой» до 30 с;
  - P > 30 с — от ≈ P (не раньше `P − 2 с`) до 2P (окно — 4 последние пробы, «упал» на 2-м учтённом провале): «Редко — 2 мин» — 2–4 мин,
    «Свой 600 с» — 10–20 мин; в форме — «≈ P–2P»;
  - «Лениво» (P = 15 с): под трафиком — ≈ 1 мин; после простоя до часа (в окне 4 старые удачи) — 15–30 с от первого
    трафика; после простоя дольше часа (окно пусто, нужно 4 пробы) — ≈ 45–60 с. В форме — «≈ 15 с – 1 мин»;
  - **холодный старт** (перезагрузка узла, новый выход): окно пусто, нужно 4 пробы — ≈ 3P–4P (при 10 с — 30–40 с,
    «Обычно» — 1,5–2 мин, «Редко» — 6–8 мин);
  - обрыв короче P «упал» не даёт ни при какой частоте.

  У xray-выходов P — общий интервал observatory (`observatory_s`), у AWG и российских — P группы. **Строка формы** —
  по этим правилам отдельно для AWG и для xray; совпадают — одна строка («реакция на отказ ≈ 1 мин»), различаются —
  две: «реакция на отказ: AWG ≈ 2–4 мин, VLESS и др. ≈ 1 мин».

### 3.3 Условия — `groups[].rules[]`
Блоки условий — **у группы**; блоков может быть несколько, у каждого своё действие. `exits: "all"` = все выходы
этой группы; список id — только выходы этой группы; сервисы в условии — из `checks.services` своей группы.
```jsonc
{"id": "r-high-rtt",               // [a-z0-9-]{1,24}
 "name": "Высокий отклик",
 "enabled": true,
 "exits": "all",                   // all (выходы группы) | ["<exit id>", …] | {"kind": "awg"|"xray"}
 "when": {"match": "all",          // all («все из») | any («любое из»)
          "conds": [
            {"metric": "rtt", "op": ">", "value": 300, "unit": "ms"},
            {"metric": "rtt", "op": ">", "value": 2, "unit": "x_norm"},
            {"metric": "loss", "op": ">", "value": 5, "unit": "pct", "min_fails": 2}],
          "hold": {"samples": 3}}, // или {"minutes": 2}
 "then": "degraded",               // degraded | standby | remove («снят») | push
 "back": {"match": "all",
          "conds": [{"metric": "rtt", "op": "<", "value": 200, "unit": "ms"}],
          "hold": {"samples": 5},
          "manual": false},        // true → вернуть только вручную
 "push": true}
```

| `metric` | Единицы | Операторы | Откуда |
|---|---|---|---|
| `rtt` | `ms` (абсолютно, для своего вида выхода) или `x_norm` (× медиана выхода за сутки) | `>` `<` | §5.1 |
| `loss` | `pct` (доля неудачных проб в окне `window` или за `minutes`); для `>` — и не меньше `min_fails` неудач (1–10, по умолчанию 2) | `>` `<` | §5.1 |
| `jitter` | `ms` (стандартное отклонение отклика в окне) | `>` `<` | §5.1 |
| `speed` | `mbps` (последний тест) | `>` `<` | §5.3 |
| `service` | `ok` с параметром `service: "<id>"` | `==` `!=` (`true`/`false`) | §5.4 |
| `country_changed` | `bool` (после `confirm` подтверждений) | `==` | §5.5 |
| `country` | код страны ISO (`RU`, `DE`; подтверждённая страна выхода) | `==` `!=` | §5.5 |
| `traffic` | `gb_day` / `gb_month` | `>` `<` | §5.6 |

Проверки при сохранении:
- `back` на «хорошей» стороне порога (для `>` — `back.value < when.value`), выдержка возврата ≥ выдержки ухода.
  **Как сравнивать** (находка С3): обе выдержки переводятся в секунды — `minutes × 60`, `samples × P_ном`. `P_ном`
  одно на правило (обе стороны меряют одни и те же выходы): наибольший номинальный период замера среди видов выходов
  правила — xray: `observatory_s` узла (§3.2); AWG: период пробы отклика при трафике `max(3P, 30)`; выход российской
  группы и «Лениво» — 15 с. Разные единицы у ухода и возврата допустимы, форма показывает пересчёт «≈ N мин». Пресеты
  пишут обе выдержки в минутах (§6);
- абсолютный `rtt` при `exits` из разных видов → предупреждение «отклик AWG и xray меряется по-разному, используйте ×K»
  (поправка С2); в уровне со смешанными видами форма по умолчанию ставит `x_norm`;
- не больше 20 правил, не больше 5 условий в группе;
- `then: remove` только при `back` с явной выдержкой или `manual: true`;
- у условия `loss` — ещё и минимум неудач в окне `min_fails` (по умолчанию 2): одна потерянная проба при 8–12
  замерах окна не даёт «потери > 10 %».

Порядок правил не важен: итоговое состояние — самое строгое из сработавших (`remove` → `off` > `standby` > `degraded`).

**Страна — только по желанию владельца** (решено 14.10, ночь) (D-024). Смена страны у любого выхода, в том числе российского, по
умолчанию — только пуш (§4.3). Кто хочет, добавляет в блок условий группы шаблон «Страна не та»: `country != "RU"`
(или `!= <код>`) → `degraded`, вернуть при `== <код>` 2 подтверждения. Ухудшенный выход остаётся пригодным (§4.4),
трафик не рвётся; при «Уводить с ухудшенного» устройства переходят на годные выходы группы, если они есть. В пресетах
этого условия нет.

### 3.4 Закрепления — `/var/lib/kaskad/gw/pins.json`; состояния — снимок `/etc/kaskad/gw/exits.json`
Закрепления — **по группам** (SPEC-groups §2.7; этап не выпущен — сразу `version: 1` в этом виде):
```jsonc
{"version": 1, "saved": 1760000000,
 "groups": {
   "main": {"pins": {"<device id>": {"exit": "<exit id>", "tier": "t1", "since": 1760000000,
                                     "why": "new"}},   // new | failover | evict | return | rebalance
            "tier_good_since": {"t1": 1760000000},    // для возврата на основной
            "active_tier": "t1",
            "last_step": null}},                       // null | "direct" | "block" — группа на последнем шаге
 "gw_all": "gx-<exit id>"}                             // только из «Основной» (§2.6)
```
- У устройства не больше одного закрепления в зарубежной группе (по маршруту) и одного в российской (T15). Сменился
  маршрут → закрепление в прежней группе снимается в ближайшем такте, в новой выбирается заново (`why = "new"`).
- Состояния выходов **не дублируются** в `pins.json`: существующий снимок `exits.json` (`exits.snapshot_path`,
  `exits.py:1048`; формат `{"at","pool","exits":{id:{alive,since,fails,…}}}`) получает поля `state`, `reasons`,
  `state_since`, `off_until`, `falls`, `unstable_until` (правка 6, З2-5: срок «нестабилен» переживает перезапуск
  сборщика), `norm_rtt` (24 часовые медианы), `geo {loc, ip, pending}`; окно правила «упал» — в `/run`, как в 3.3.5 (§3.2), не в снимке. Пишется, как сейчас,
  при изменении (`save_snapshot`, `exits.py:1064`); `norm_rtt` — не чаще раза в час.
- `pins.json` пишет только сборщик — **сразу**, в том же такте, где сменились закрепления, до снятия блокировки
  состояния (не чаще раза за такт). Отложенной записи нет: все процессы (`ops._apply` → `nft.apply` → `net.plan` →
  `exits.marks`, `net.py:289`; `xray.apply`; `hooks`; `trace`) читают решение из файла, и устаревший файл откатил бы
  переезды. Только поле `saved` и `tier_good_since` без смены закреплений пишутся не чаще раза в 60 с. При остановке
  юнита (SIGTERM) — сразу.
- **Скачки часов.** На VPS без RTC часы после загрузки прыгают при синхронизации NTP (план D1). Длительности внутри
  сборщика (выдержки `minutes`, `hold_min`, окна 60 с защиты от шторма, окна антиспама и склейки событий, §3.6, §8.2)
  считаются по `time.monotonic()`; в файлах — `time.time()` только для показа. При чтении `pins.json` и снимка состояний значения
  зажимаются: `off_until ≤ now + off_backoff.max_s`, `unstable_until ≤ now + 15 мин`, `tier_good_since ≤ now`, `since ≤ now`, `state_since ≤ now`.
  Прыжок назад не держит выход «снятым» часами и не мешает возврату на основной.
- Удаление устройства (`model.del_device`, `model.py:430`) → запись удаляется в ближайшем такте (сборщик сверяет с моделью); удаление
  выхода из пула → его закрепления становятся «переезд».
- Старт сборщика (и после перезагрузки): читает `pins.json`, состояния, `off_until`; окна замеров пусты → мягкие
  правила не срабатывают, пока окно не наберёт `max(hold, window)` замеров; «упал» — как только в окне 4 пробы (после перезагрузки окно в `/run` пусто, как в 3.3.5) (хвост BACKLOG
  «стартуем с выходов из таблицы закреплений»).
- Битый файл → `pins.json.bad-<ts>`, старт с пустой таблицы, событие в журнал (не пуш).

### 3.5 История — `/var/lib/kaskad/metrics.db`
- `sqlite3` из stdlib; `PRAGMA journal_mode=WAL; synchronous=NORMAL; busy_timeout=2000`.
- **Писатель один — сборщик** (`kaskad-gw-collect`). Юнит проб и панель в базу не пишут: юнит проб — файлом
  `/var/lib/kaskad/gw/probe-results.json` (§5.7), панель только читает (`file:…?mode=ro`, отдельное соединение на запрос).
- Нет модуля `sqlite3` или база не открывается → графики выключены (`"charts": false` в API), остальное работает.

```sql
CREATE TABLE meta (k TEXT PRIMARY KEY, v TEXT);              -- schema=1, created, tz
CREATE TABLE m1  (exit TEXT, ts INTEGER, rtt_med REAL, rtt_p90 REAL, loss REAL, jitter REAL,
                  ok INTEGER, n INTEGER, rx INTEGER, tx INTEGER, devices INTEGER, state TEXT,
                  PRIMARY KEY (exit, ts)) WITHOUT ROWID;     -- ts кратно 60

CREATE TABLE h1  (...те же поля...) WITHOUT ROWID;           -- ts кратно 3600
CREATE TABLE speed (exit TEXT, ts INTEGER, mbps REAL, ttfb_ms REAL, tls_ms REAL, bytes INTEGER,
                    host TEXT, ok INTEGER, why TEXT, PRIMARY KEY (exit, ts)) WITHOUT ROWID;

                    PRIMARY KEY (exit, svc, ts)) WITHOUT ROWID;

CREATE TABLE traffic (exit TEXT, day TEXT, rx INTEGER, tx INTEGER, probe INTEGER,
                      PRIMARY KEY (exit, day)) WITHOUT ROWID;  -- day = YYYY-MM-DD по поясу узла
```

- `rx`/`tx` — дельты за точку по **правилу дельт**: `d = cur − last`, если `cur ≥ last`, иначе `cur` (обнуление при
  перезапуске xray и пересоздании `kawgN`).
- **Квоты от sqlite не зависят:** счётчики периода — в `/var/lib/kaskad/gw/traffic.json` (сборщик, атомарно, раз в
  60 с): `{"version": 1, "exits": {"<exit id>": {"day": "YYYY-MM-DD", "day_bytes", "period_start", "period_bytes",
  "last": {"rx", "tx"}, "warned": {"<period_start>": [80, 100]}}}}`. `warned` — какие пороги за этот период уже
  пушились: перезапуск сборщика не даёт повторного пуша 80 % и 100 %. `last` переживает перезапуск сборщика; после
  перезагрузки `cur < last` → `d = cur` (верно). Таблица `traffic` в базе — только история для графиков.

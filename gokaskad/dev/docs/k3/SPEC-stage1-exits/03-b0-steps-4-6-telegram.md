### 2.5 Шаг 4. Массовый переезд — пачками через API
- `hot_plan` больше не отказывает при `> HOT_MAX_RULES`: `hot_apply` делит `add_rules`/`rm_rules` на пачки по
  `HOT_MAX_RULES = 200` (T0, С0.9: 200 простых правил — 18 мс за вызов) и `add_users` по `HOT_MAX_USERS`.
- **Правила со списками** (`ls-`, §2.4) — отдельный предел **`HOT_MAX_EXT_RULES = 32`** (≈ 100 КБ на правило, предел
  gRPC 4 МБ): замена всех правил идёт одним вызовом, только если правил со списками в новом конфиге ≤ 32; иначе —
  перезапуск xray (Р28).
- Общий потолок операций за один `apply` — `HOT_MAX_TICK` (ориентир 1000 простых правил). Сверх него — перезапуск
  (единственный «массовый» случай, честно в B2). Цепочка пользователя после §2.4 — одно правило маршрута, поэтому
  массовый переезд (смена закрепления в любой группе, переход группы на последний шаг, сбой российской группы T15) —
  ≈ 1000 пользователей xray за такт плюс одна замена всех правил; на стенде перезапусков нет.
- Ошибка любой пачки → как сейчас: `restart = True` (`xray.py:503`) — конфиг на диске уже новый, после перезапуска
  xray состояние совпадает.
- Защита от «шторма»: не больше одного перезапуска xray по решению сборщика за 60 с (кроме «нет конфига» и
  «сменилась страна»). **Отложенный перезапуск не теряется:** `xray.apply(..., defer_restart=True)` при нужном, но
  отложенном перезапуске **не заменяет** `/etc/kaskad/gw/xray.json` (временный `xray.new.json` удаляется) и
  возвращает `{"deferred": true}`. Правило: файл на диске = то, что работает в xray. На следующем такте `render`
  снова отличается от диска, и перезапуск выполняется, как только окно 60 с прошло. Ручные правки (`ops._apply`)
  ограничению не подлежат. (Сейчас `xray.apply` пишет файл до решения о перезапуске, `xray.py:479-497`, — без этой
  правки следующий такт увидел бы «нет отличий», и xray разошёлся бы с файлом навсегда.)
- **Чисто горячая правка без `xray -test`:** если `_strip(old) == _strip(new)` (отличаются только пользователи горячих
  входов и цепочки), основа уже проверена — `xray -test` (`xray.py:483`, второй процесс xray с geo-файлами, до 30 с)
  не зовётся. `xray -test` — только при смене основы.
- **Не держать блокировку состояния на вызовах API:** сборщик под `state.locked` только считает решение и `render`
  (текст конфига в памяти). После снятия блокировки — под отдельным замком `/run/kaskad/xray-apply.lock` (`flock`):
  сравнение с диском, `xray -test` при смене основы, запись файла, вызовы `xray api` (пачки) или перезапуск. Тот же
  замок берёт `ops._apply` вокруг тех же шагов — правки xray из двух процессов не перемешиваются. Порядок замков один:
  сначала состояние, потом xray; под xray-замком блокировка состояния не берётся (нет взаимной блокировки). Панель
  ждёт блокировку состояния 5 с (`panel/api.py:943`) — такт её не задерживает.
- **Устаревший рендер не применяется (номер рендера).** Иначе такт, нарисованный по старому состоянию, мог бы
  применить его **после** ручной правки (`flock` не справедлив): отозванное устройство снова в xray, а отпечаток в
  `xray.decision` совпал бы, и перерисовки не было бы часами.
  - Счётчик `/var/lib/kaskad/gw/xray-seq` (целое, атомарно, `0600`, переживает перезагрузку). Номер берётся **под
    блокировкой состояния** прямо перед `render`: сборщиком в такте и `ops._apply` (он держит блокировку состояния всё
    своё время). Блокировка упорядочивает номера: больший номер нарисован по более свежему состоянию. Пока `ops._apply`
    держит блокировку, сборщик номер взять не может — у ручной правки номер всегда наибольший на момент её применения.
  - `xray.decision` хранит `{"fp": <отпечаток решения>, "seq": <номер>}` последнего **применённого** рендера (§2.7).
  - Под xray-замком, до сравнения с диском: номер своего рендера **меньше** `seq` в `xray.decision` → рендер
    выбрасывается (в xray уже более свежее), сборщик рисует заново на следующем такте по свежему состоянию.
  - Сборщик рисует заново и без смены отпечатка, если счётчик `xray-seq` больше `seq` в `xray.decision`: номер взят, а
    до xray не дошёл (тайм-аут замка, отложенный перезапуск, сбой). При старте сборщика — один рендер и сверка с
    диском всегда (на случай гибели процесса между применением и `state.save`).
  - Ожидание замка: сборщик — ≤ 5 с, иначе пропуск до следующего такта; `ops._apply` — ≤ 60 с.
  - **Тайм-аут замка у `ops._apply`** — не отказ операции: таблица nft и маршруты уже применены, состояние
    сохраняется. В ответе — предупреждение RU/EN «Настройки сохранены, xray применит их в течение 20 с»
    (`gw_ops.warn.xray_deferred`), в журнал — строка. Номер остаётся взятым, и сборщик применяет изменение по правилу
    «счётчик больше `seq`» на ближайшем такте.
  - **Время под замком у сборщика ограничено:** `xray -test` (только при смене основы, ≤ 30 с) плюс вызовы API не
    дольше `HOT_LOCK_S = 20` с суммарно (каждый вызов `xray api` — `-timeout 8`, как в 3.3.3: 40 правил со списками —
    1,45 с, запас под нагрузкой; пачка — `HOT_MAX_RULES` правил, `HOT_MAX_USERS` пользователей или одна замена всех
    правил). 20 с держатся для ≤ 4 пачек со списками (T0). Если план не укладывается в 20 с — вместо API перезапуск
    (с защитой от шторма). Значит, `ops._apply` ждёт замок не дольше ≈ 50 с; лимит 60 с — с запасом.
  - Тесты (§11.1, `xray.py`, `collect.py`): порядок «такт нарисовал → правка применила → такт применяет» — рендер такта
    выброшен, отозванный пользователь не вернулся; тайм-аут замка у `ops._apply` — состояние сохранено, сборщик
    применил на следующем такте; гибель после применения — сверка при старте.

### 2.6 Шаг 5. Сам узел: переопределение `gw-all`
- `gw-all` (`xray.py:343-346`, selector `["gx-"]`, `leastPing`, fallback `block`) остаётся: на нём `dns-in`,
  `gw-dns-int` (`xray.py:376-378`) и вход пула. Observatory не убираем (поправка С1).
- **API — всегда:** блок `api` (`HandlerService`, `RoutingService`, `StatsService`) и вход `stats-in` 10854
  рисуются, когда в пуле есть выходы, а не только при VLESS-входе (`xray.py:328`, `:414-417`). Порт закрыт nft «только
  root» (§5.2).
- Сборщик ставит `RoutingService.OverrideBalancerTarget(gw-all, gx-<best>)` (`xray api bo`), где `best` = `decision.
  gw_all`: лучший годный выход активного уровня **группы «Основная»** (способом уровня; при «поровну» — меньший
  отклик в своём виде с допуском §4.4). Другие зарубежные группы и российские в `gw-all` не участвуют; `gr-` не
  подходит под селектор `["gx-"]`.
- Это **основной путь** (T0: С0.1–С0.5 пройдены). Выбранный перестал быть годным → **в том же такте** следующий;
  годных нет → ухудшенный по порядку B2 → «в запасе» → последний шаг «Основной» (ниже; С0.2: цель вне `selector`
  принимается, несуществующий тег тоже закрывает соединения, но цель всегда пишется явно).
- **`gw_all`, когда у «Основной» нет пригодных выходов** (находка С4; решение координатора, владелец может поменять) (D-116).
  DNS узла (`dns-in`, `gw-dns-int`) нужен **всем** устройствам ядра, в том числе людям других групп. Поэтому:
  1. `main.fail = direct` → `bo gw-all direct`: DNS узла идёт с IP сервера, как и трафик «Основной» на этом шаге;
  2. иначе — лучший пригодный выход **другой зарубежной группы** (по порядку списка групп, способом её активного
     уровня), кроме выходов с квотой (`exit_pref.quota` задана): через него идут только запросы DNS узла и «Проверить
     ссылку» (`pool-socks`) — килобайты; устройства других групп не теряют DNS, когда «Основная» лежит;
  3. нет и таких → `block` (как в 3.3.3: DNS узла молчит). У людей «Основной» на запасном блоке зарубежные сайты
     закрыты в любом случае — DNS через другую группу их не открывает. Российские сайты **по имени** при этом не
     открываются и у людей с «Россия напрямую» — на пути ядра (dnsmasq: только пул) и xray (`gw-dns-int` → `gw-all`)
     одинаково; по адресу и из кэша dnsmasq — открываются. **3.3.7.2 (SEC-3371 Б-2, Д-1 закрыт):** оговорки «если на
     узле есть устройство ядра «напрямую»» больше нет. У `kaskad-dns` (порт 5354) верхний сервер — только пул или
     ничего, всегда. Прямой верхний DNS живёт во втором dnsmasq `kaskad-gw-dnsdirect` (порт 5364): пул первым
     (`strict-order`), затем системные резолверы узла (`/run/systemd/resolve/resolv.conf`, затем `/etc/resolv.conf`,
     без петли 127.0.0.53; КТ3-2 — узлу в России 1.1.1.1 бывает недоступен), 1.1.1.1/1.0.0.1 — запасом. Его служба
     стоит, только пока `exits.direct_needed()`. Какой dnsmasq спросит клиент, решает цепочка `gw_dns` по метке
     клиента в `gw_route` в момент запроса: 0x201 («сейчас напрямую») → 5364, любая другая → 5354. Порты 5354/5364
     напрямую клиентам закрыты в `gw_pre` (SEC-3372 З-1). Поэтому у WG-устройства «всё через выход» имя не уходит
     мимо выхода, даже когда на узле есть кто-то «напрямую». Принято как Р-Г9 (SPEC-groups §5): строка в карточке
     группы, вариант В (свой резолвер по людям) — этап 2. Прямой DNS для имён прямой группы (КТ1 Н6, круг 1) отменён:
     dnsmasq и xray выбирают сервер по имени, а не по человеку — имена людей без «Россия напрямую» ушли бы мимо
     выхода (REV-s1-kt1a-sec С-1).
  Событие `group_last_step` «Основной» получает аргумент `dns_via` (`direct` / имя группы по `policy.label`, §3.1 / `none`) — строка в пуше и
  в карточке группы: «DNS сервера сейчас идёт через «Стриминг»». Владелец — T2 (`assign`, поле `gw_all`), тест §11.1.
- **Прямой DNS dnsmasq и группы** (находка С4). `exits.direct_needed(st)` (`exits.py:1345-1355`; зовут
  `collect.py:165`, `ops.py:227`, `rules/ops.py:291`) сейчас смотрит только `route.fail`. После групп устройство ядра
  выходит «напрямую» и при `group.fail = direct`, а dnsmasq без прямого upstream отправил бы его DNS в `dns-in → gw-all`
  — при лежащей группе имена не разрешались бы, а панель писала бы «идёт с сервера напрямую». Новое правило:
  `direct_needed(st, policy)` истинно, если у активного устройства входа ядра маршрут `direct` **или** (маршрут не
  `block`) `route.fail = direct` **или** у группы, в которую разрешается его маршрут (`pool` → `main`, `group:G` → G,
  `exit:E` → группа E), `fail = direct`. Признак статический (по настройкам, не по текущему состоянию) — конфиг
  dnsmasq не дёргается при падениях выходов; порядок `strict-order` прежний: сначала пул, потом прямой. Владелец —
  T4 (`exits.direct_needed` и три места вызова), тест §11.1. Российские группы на это не влияют (SPEC-groups §7).
- Переопределение живёт в памяти xray и **теряется** после перезапуска xray и после замены всех правил (`adrules` без
  `-append`, §2.4) — T0, С0.5. Сборщик хранит `applied_gw_all` и время старта xray (`exits.xray_age()`,
  `exits.py:937`, `ActiveEnterTimestampMonotonic`); старт сменился → поставить заново. `xray.apply` после замены всех
  правил сам ставит `bo` (`gw-all` и балансировщик бота не трогает — он в другом xray) в том же вызове, под тем же
  замком. Раз в 5 мин — сверка через `xray api bi` (печатает `Selecting Override: <tag>`, T0).
- Цель ставится в любом пресете, включая `compat` и «по соединениям» (здоровье видит только Kaskad);
  `bo -r` — только при удалении шлюза или пустом пуле.
- Запасной путь с пересборкой `selector` и перезапуском **не пишется**: С0.1–С0.2 пройдены (T0).
- **Окно после перезапуска xray (честно, находка Б9).** Переопределение `bo` живёт в памяти xray и сбрасывается при
  перезапуске. До первого `bo` после перезапуска (сборщик ставит его в ближайшем такте, ≤ 10 с) `gw-all` выбирает
  `leastPing` по селектору `["gx-"]` — то есть по выходам **всех зарубежных групп**, в том числе с квотой. В это окно
  DNS узла и `pool-socks` могут пройти через выход группы «Стриминг»; объём — запросы DNS за ≤ 10 с. Исключить
  такие выходы из селектора без перезапуска нельзя (селектор — по префиксу), поэтому окно оставлено, строка — в
  справке группы.
- **Вход пула** `127.0.0.1:12699` (`tag: pool-socks`, SOCKS без пароля) → `gw-all` («Основная»): для «Проверить
  ссылку» через пул. Закрыт nft «только root». HTTP-уведомления этапа 3 «через пул» ходят **через «Прокси для API
  Telegram»** (§2.9, решено 14.10, ночь) (D-028, D-029), а не через `pool-socks`.

### 2.7 Шаг 6. Сборщик сравнивает и применяет только горячие правки
- Механизм сравнения уже есть: отрисованный конфиг против `/etc/kaskad/gw/xray.json` → `hot_plan` → `hot_apply`
  (`xray.py:458-515`). Сборщик начинает вызывать `xray.apply(st, sec, runner, pool_exits, decision)` **не только при
  смене пула**, а когда изменился отпечаток решения: `sha1(pins пользователей xray + цели exit:E + состояния
  выходов, влияющие на правила)`; с T15 — и российские цели пользователей xray (`ru_target(...)["xray"]`,
  SPEC-groups §4.2). Без изменений — `render` не вызывается (экономия CPU на 200 устройствах).
- **Отпечаток хранится рядом с конфигом, а не в памяти сборщика:** `xray.apply` после удачной записи и применения
  пишет `/etc/kaskad/gw/xray.decision` (`{"fp", "seq"}`: отпечаток решения и номер рендера, по которым отрисован файл
  на диске; атомарно, `0600`; номер — §2.5). Сборщик сравнивает свой отпечаток с этим файлом. Если `ops._apply`
  (другой процесс) отрисовал конфиг по другому решению, сборщик это увидит и применит своё на ближайшем такте.
  Отложенный перезапуск (§2.5) файл отпечатка не меняет.
- **Отказ `xray -test` не повторяется каждый такт.** Отпечаток пишется только после удачного применения; без защиты
  отвергнутый конфиг (`xray.py:484-491`, `KaskadError`) звал бы `render` и `xray -test` (второй процесс xray с
  geo-файлами, до 30 с) каждые 10 с. Сборщик запоминает `sha1` текста отвергнутого конфига в
  `/run/kaskad/xray.rejected` (`{"hash", "at", "error"}`) и тот же текст повторно не проверяет; другой текст
  проверяется сразу, тот же — не чаще раза в 5 мин (на случай временной причины: geo-файлы ещё качаются). Первый отказ
  — строка в журнал и событие `xray_rejected` в `live.json` (лента панели; пуша нет), повторы — не чаще раза в час.
- Порядок такта (`collect.tick`, `collect.py:318`): `probe_round` (без блокировки) → проверка сети узла (§4.6) → под
  блокировкой `exits_tick`: `merge` + `health.evaluate` (все выходы, условия и проверки —
  группы выхода) → `assign.assign` (циклом по группам; `devices_by_group` — SPEC-groups §2.7)
  → `pins.save` **сразу**, если закрепления изменились, и снимок состояний `exits.json` — **там же**, до снятия
  блокировки (иначе `exits.decision()` другого процесса склеит свежие закрепления со старыми состояниями) → номер
  рендера и `render` при смене отпечатка или «счётчик больше `seq`» (§2.5) → `net.update_map(runner, st,
  live=live, decision=d)` (план меток из решения в памяти, а не из файла; сейчас без `elems` план строится из файла,
  `collect.py:192-193`) → события в `LIVE.full`. После снятия блокировки: применение xray под xray-замком (§2.5),
  `gw_all` (`bo`), запись `metrics.db` и счётчики квот из `/debug/vars` — раз в 60 с.
- Это касается: смены закреплений, состояний, `gw-all`, а в этапе 3 — истечения аренды слоёв сценариев (упал движок
  сценариев → слой гаснет ≤ 5 мин).
- **Смена состава пула — горячо** (T0, С0.8 пройдена): новый выход — `ado gx-<id>` + `adi tproxy-<id>`/`probe-<id>` +
  `adrules -append` его правил; удалённый — `rmrules`, `rmi`, `rmo`. Observatory подхватывает новый `gx-` ≤ 25 с.
  Исключение — выход Hysteria2 на уже использованном в этом запуске xray `host:port` и смена ключа такого выхода: xray
  запоминает клиента по адресу (T0) → перезапуск. Владелец — T5 (`hot_plan`/`hot_apply`: операции `add_outbounds`,
  `rm_outbounds`, `add_inbounds`, `rm_inbounds`).
- **Выход, снятый по квоте с `quota.action = remove`, выпадает из конфига xray** (О8, §5.6): `render` не рисует его
  `gx-`/`gr-` исходящий, `tproxy-<id>`, `probe-<id>` и их правила — горячо `rmrules`/`rmi`/`rmo`, как удалённый
  выход (С0.8), но строка пула, закрепления в истории, квота и счётчики остаются. Возврат — `ado`/`adi`/`adrules
  -append`. Hysteria2 исключением не является: возвращается **тот же** ключ на тот же `host:port`, кэш клиента xray
  ему не мешает (исключение §2.7 — только для **другого** ключа на занятом `host:port`). Правило «файл на диске = то,
  что работает» (§2.5) соблюдается: снятие и возврат — обычная разница `render`.
- Перезапуск xray допустим только в случаях B2/B4: выход Hysteria2 по исключению выше, переезд сверх
  `HOT_MAX_TICK`, правил со списками больше `HOT_MAX_EXT_RULES` (§2.5), новый или удалённый аккаунт SOCKS5 (T0, С0.7), блок **по выбору человека** (маршрут `block`, пауза,
  отзыв — как в 3.3.3), режим «по соединениям» при смене годных. Смена страны — только пуш, без
  перезапуска (§4.3). Смерть выхода, «в запасе», «снят» по правилу или квоте (в том числе
  выпадение из конфига при `quota.action = remove`, выше), «нет годных» и переход группы на последний шаг — **без
  перезапуска** (запасной блок `fail-block`, §2.2). Смена частоты проверок, меняющая общий интервал observatory
  (§3.2), — перезапуск, как смена `observatory_s` раньше.
- `ops._apply` (ручные правки) передаёт в `xray.apply` решение `exits.decision(st)`, чтобы не откатить закрепления
  сборщика (`pins.json` уже свежий, §3.4), и берёт номер рендера (§2.5). Владелец строк в `ops._apply` — T4 (§10.1).

### 2.8 Что не меняется

  `gw-vless` никто не ходит.
- fail-closed (`unreachable` в таблице 199), `blocked_ips → block` (`xray.py:379-380`), `ct mark`.

### 2.9 «Прокси для API Telegram»: ключи выбранной группы (решено 14.10, ночь)
Решение владельца (D-028): прокси бота работает **по навыку `telegram-api-egress-vless-awg`** (вырос из Kaskad 2.13.1): свой
балансировщик `bot-bal` с автоотказом и ручной выбор ключа, как в 3.3.3. Общая политика групп (уровни, условия) на
него не распространяется. Ключи прокси — **только из выбранной группы**, по умолчанию «Основная» (предложение
координатора) (D-029). HTTP-уведомления этапа 3 «через пул» ходят через этот же прокси.
- **Поле** `exit_policy.tg_proxy_group` (D-133) (в `state.json`, часть `gateway` — переносится `.kbk` без правки `backup.py`):
  id зарубежной группы (`role = abroad`), по умолчанию `main`. Нет поля, группа удалена или не зарубежная → `main`
  (проверка — `policy.validate`, код `ep.err.tg_proxy_group`). Смена группы — в панели (G8); при удалении группы прокси бота замена выбирается в том же окне (`tg_proxy_to`,
  §7.9; CLI `gw group-del --tg-proxy-to`), перенос выхода в группу прокси или из неё и удаление группы пересобирают
  прокси бота (правка 8).
- **«Напрямую» и откат на прямой путь (3.3.7.10, D-139; `k3/handoff/SPEC-tg-proxy.md`).** Кроме id группы поле
  принимает `"direct"`: прокси бота не собирается (`tg-proxy-indexes` печатает `direct`, `egress_bot_config` → код 4 →
  `egress_bot_off direct`), бот ходит с адреса узла. По умолчанию по-прежнему `main` (D-029). При группе демон бота сам
  уходит на прямой путь, если выходы группы не отвечают (≥ 3 опросов и ≥ 90 с, `getMe` напрямую проходит), и раз в
  5 мин пробует группу снова. Выбор — в панели «Настройки → Бот и ИИ-агент» (`POST /api/bot/proxy`); SSH, CLI
  (`kaskadctl bot proxy`) и MCP (`bot_proxy`) показывают состояние словами, не меняют.
- **Какие строки:** `kaskadctl gw tg-proxy-indexes` (скрыт в MCP, `hidden`) печатает через пробел номера строк
  `upstream.txt`, чьи выходы входят в группу (включённые, в любом состоянии: автоотказ — у `bot-bal`). Политики нет
  (шлюз не включали) → все строки, как в 3.3.3. Пусто (группа без ключей) → строки «Основной» (D-042); и она пуста
  (или в группе только AWG без ядра) → прокси бота **не собирается**: служба xray бота снимается, бот ходит напрямую,
  метка `egress_warn:tg_group_empty` и запись в журнал; пул, ноги AWG и шлюз (`gw apply`) работают дальше — добавление
  ключа и обновление подписки не откатываются (REV-s1-t11 С5). Ключ появился в группе — пересборка включает прокси снова.
  Шапка меню с именем группы — только при политике выходов; ключи других групп в списке меню серым, ручной выбор —
  только ключей группы (REV-s1-t11 З3). Конфиг бота 3.3.x после обновления пересобирается по группе один раз
  (`--k3-post-update`, метка `.bot-config-ver`, REV-s1-t11 З4). Токен бота пересборки читают из настроек бота, не из
  переменной (REV-s1-t11 С1).
- **Сборка:** `egress_rebuild` (`install.sh:7709`) передаёт номера разборщику: `egress_parse.py config --only
  "<N N …>"` — строки вне списка пропускаются, **номера остальных сохраняются** (нога `kawgN`, метка `256+N` у бота
  те же, что у шлюза; ноги не дублируются). Ошибка помощника (`kaskadctl` недоступен, тайм-аут 15 с) → все строки (D-042), как
  в 3.3.3, и строка в журнал: связь бота важнее границы группы. Ручной выбор ключа в меню «Прокси для API Telegram»
  (`egress_active_index`, `bo` балансировщика бота) показывает только ключи группы. Ноги AWG по-прежнему поднимает
  `egress_awg_sync` по **всем** строкам: они нужны шлюзу.
- **Одна observatory вместо двух (T0; находки Б1 и С1).** В 3.3.3 каждый выход проверяют две observatory по 10 с —
  шлюза и xray прокси бота (`kaskad-egress`, своя observatory `out_*`); у бота это ⅓ всего трафика проб, и она
  работает **даже без настроенного бота**.
  - **Что умеет xray 26.3.27 без observatory** (прогон 15.10, настоящий `xray run -test` и живой трафик на петле;
    конфиги и итог — `k3/stand/logs/botbal-15.10/RESULT.txt`): `leastPing`, `random` и `roundRobin` **с
    `fallbackTag`** не стартуют (`core: not all dependencies are resolved`); `leastPing` без `fallbackTag` — тоже;
    `random`/`roundRobin` без `fallbackTag`, но с `ObservatoryService` в `api.services` — тоже. Стартуют:
    `roundRobin` или `random` **без `fallbackTag`**, `api.services` = `RoutingService` + `StatsService`. С таким
    конфигом `xray api bo -b bot-bal out_2` ведёт **все** новые соединения в `out_2` (10 из 10), `bo` на мёртвый
    (`blackhole`) — 0 из 10, `bo -r` — снова по кругу. Один ключ в группе — тот же вид (`bot-bal` из одного
    `out_1`) тоже стартует.
  - **Конфиг бота «без проб»** (`egress_parse.py config --no-observatory`, T11): `bot-bal` всегда, даже при одном
    ключе; `strategy roundRobin` (по кругу: N подряд новых соединений проходят все N ключей — нужно для настройки
    бота, ниже); **без `fallbackTag`**; `api.services = ["RoutingService", "StatsService"]`; блока `observatory` нет (D-033).
    Тест T11: `xray run -test` на настоящем бинаре (`tools/fetch_test_bins.sh`) для группы из 1 и из 3 ключей.
  - **шлюз включён** (с ботом и без) — конфиг «без проб». Цель `bot-bal` ставит сборщик через API xray бота
    (`xray api bo --server=127.0.0.1:${EGRESS_API_PORT} -b bot-bal out_<N>`) — лучший пригодный выход группы
    `tg_proxy_group` по тому же здоровью, что и у шлюза (свой автоотказ прокси, без уровней и условий групп). Нет
    пригодных → `bo -r` (по кругу: бот хоть как-то пробует). Ручной выбор ключа (`.override`) главнее: при нём
    сборщик цель не трогает. После перезапуска `kaskad-egress` цель теряется — сборщик ставит её заново по времени
    старта службы (как `gw-all`, §2.6); до этого (≤ 10 с) `bot-bal` идёт по кругу среди строк группы. **Честно:**
    автоотказ бота теперь зависит от живого сборщика (в навыке и 3.3.3 он был свой) — Р30;
  - **шлюз выключен, бот настроен** — как в 3.3.3: своя observatory бота (`leastPing` + `fallbackTag`, при одном
    ключе — без балансировщика), но `probeInterval` 60 с вместо 10 с;
  - **шлюз выключен, бот не настроен** (нет токена) — конфиг «без проб»: проб нет, сборщика нет, балансировщик идёт
    по кругу.
  - **Служба `kaskad-egress` работает всегда, когда в группе есть ключи** (как в 3.3.3), с токеном и без: проверка
    токена при подключении бота идёт **через прокси** (`bot/onboard.py:83-86` `check_token` → `connect`,
    `detect_chat`, `bot test`; `BOT_PROXY` = `127.0.0.1:10808`, `install.sh:7745`), и на российском узле без неё бота
    не подключить (находка С1). Лишних проб это не даёт: без бота и без шлюза конфиг «без проб».
  - **Подключение бота при переборе по кругу** (T11, `bot/onboard.py`): `connect` при сетевой ошибке через прокси
    (`net_proxy`) повторяет попытку **новым соединением** до `min(число ключей группы, 5)` раз с тем же тайм-аутом
    попытки — по кругу каждая попытка идёт через следующий ключ, мёртвый ключ не ломает настройку. Общее время —
    с лимитом (≤ 5 попыток × тайм-аут клиента). При шлюзе цель уже стоит, и первая попытка идёт через лучший ключ.
  `egress_rebuild` выбирает вариант по `k3_gw_enabled` и наличию токена; включение и выключение шлюза и сохранение
  токена зовут `--egress-tg-rebuild`. Теги `out_<N>` бота — по номеру строки (стабильны при пересборке; сверить в
  `egress_parse.py`, иначе T11 делает их такими). Порт API xray бота (`EGRESS_API_PORT`, 10851) — в цепочку `gw_out`
  «только root» (§5.2; П5): теперь в него ставит цель сборщик. Владельцы: T11 — конфиг, `--no-observatory`,
  `egress_rebuild`, повтор в `bot/onboard.py`; T4 — `bo` бота в сборщике; T5 — порт 10851 в `gw_out`.
- **Пересборка при смене состава.** Номера группы меняются от правки политики (перенос выхода между группами, смена
  `tg_proxy_group`) — это Python (`policy_ops`, T7). После сохранения T7 сравнивает новые номера с
  `/etc/kaskad/egress/.tg_indexes` и при отличии зовёт новый безголовый вход `install.sh --egress-tg-rebuild`
  (только конфиг бота: `config --only`, `xray -test`, перезапуск egress-xray и `kaskad-bot`; без `k3_gw_pool_changed`)
  — после снятия блокировки состояния, в фоне (`systemd-run --no-block`), тайм-аут 120 с, не чаще раза в 60 с
  (отложенный запуск не теряется: запоминается в файле `.tg_indexes.want`). Смена пула (добавление, удаление ключа,
  подписка) и так идёт через `egress_rebuild`.
- **Тексты.** Шапка меню «Прокси для API Telegram» в SSH: «Ключи группы «<имя>» (N из M) — группа меняется в панели»
  (<имя> — `policy.label` группы прокси, §3.1: у `main` с `name: ""` — «Основная»/«Main»; bash берёт его из
  `kaskadctl gw tg-proxy-indexes --label` — T11 и так владеет командой, а `gw groups` T10 сливается позже, §10.2);
  в панели — строка выбора группы в карточке «Бот/агент» (§7.5). RU и EN.
- **Владельцы:** T11 — `config --only` и `--no-observatory` в heredoc разборщика, `egress_rebuild`,
  `--egress-tg-rebuild`, шапка меню и **`kaskadctl gw tg-proxy-indexes`** (перенесена из T10: её зовёт
  `egress_rebuild` T11, и КТ1 должна проверить «только строки группы» — находка З8); T7 — поле, `validate`,
  пересборка из `policy_ops`, API (§7.9); T8 — строка выбора в панели. Тесты: bash-тест «конфиг бота — только строки
  группы, номера сохранены»; `tests/gw/test_tg_proxy.py` (умолчание `main`, удалённая группа → `main`, пересборка
  только при смене номеров).
- Российские ключи (`upstream-ru.txt`, T15) в прокси не попадают никогда: другой файл (SPEC-groups §7).
- Перенос последнего выхода из группы прокси или удаление этой группы — в панели предупреждение «бот останется без
  прокси для API Telegram: выберите другую группу»; сохранить можно, прокси тогда берёт «Основную» (выше).
